# 源码与项目认知维护

将代码变更、注释和类图作为同一个交付。先读仓库根目录 `AGENTS.md`；其注释和类图要求只适用于 `src/`，不要扩大到 tests、scripts、docs 或本 Skill。

本流程同时维护代码资料的准确性和开发者对系统的理解。职责调整、分层解耦与共性提炼由 [architecture-evolution](../architecture-evolution/SKILL.md) 提供方案和证据，本流程据此同步资料、解释变化和维护入口，不重复扫描或扩大重构范围。

只要求理解工程时，默认只读核实并解释；要求维护说明时更新相关文档；已授权源码修改时完成代码、注释、类图、验证与认知交接。产出材料不等于维护者已经理解或接受。

## 必须遵守的规范与治理衔接

本 Skill **必须读取并遵守 [文档 1：通用项目架构设计规范与原则](../../../design/project-architecture-standard.md)**，并将相关要求落实到源码说明和维护者交付。参与架构治理时，同时读取 [文档 2：架构治理规范与治理流程](../../../design/architecture-governance-process.md)，按其 S6–S7、认知分级及验收标准交付；治理决策与迁移流程仍由 `architecture-evolution` 负责。已核实且未变化的上下文可复用，普通注释维护不因此重新启动全套治理。

## 1. 确认真实结构与阅读范围

- 先运行 `git status --short`、查看相关 diff，保留已有未提交工作。
- 阅读 `src/ARCHITECTURE.md`、涉及目录的 `ARCHITECTURE.md` 与 `CONTRACT.md`，再读实际源码、调用方与测试。当前实现说明随源码维护；`docs/` 只保留 01–04 四份概念设计，代码优先于文档。
- 批量重构或生成全部类图前，完整分析 src 的入口、数据流、职责边界及依赖，再决定目录结构；禁止先按旧目录机械生成文档。
- 根据 diff 判断依赖是否变化；导入、文件路径或分层变更按第 5 节检查，不为每次源码修改重复建立全仓检查基线。把每个文件作为模块，类型引用也算依赖；只读理解或纯说明修改不运行无关产品检查。
- 从维护者要理解的问题和当前版本出发，核实主要能力、外部系统、数据与状态所有者、运行入口和生命周期；沿相关真实场景读到副作用与结果返回，并解释必要的失败、取消或重启路径。
- 记录实际阅读范围，将静态阅读、实际执行和推断分开。不能仅按目录名、旧文档或测试数量推断能力已实现；证据链接到实际文件和关键符号，按需要补行号。

## 2. 保持单向依赖

单向依赖是系统后续可渐进治理的硬约束。按实际职责边界同时审视层、模块和文件，类型依赖也计算在内；易变业务与实现依赖稳定契约，稳定核心不反向依赖具体消费者。运行返回／回调与静态依赖方向分开说明；文件无环后仍检查模块边界、依赖过密和共享状态耦合，不能用目录挪动或间接调用伪造解耦。

当前允许方向以 `scripts/check-dependencies.mjs` 的 layers 和源码为准：

新四层以 [四层设计](../../../design/four-layer-architecture.md) 为目标：Core 不依赖业务，Logic 依赖适用 Core，Bridge 服务端依赖 Logic 公开入口，View 只使用 Bridge 客户端/契约与便携 Core。当前 src/core 已建立，旧 backend/frontend 和 Bridge 的旧领域契约重导出仍按现有规则受限；不得把目标画成全部已迁移。

- 共享 Core → 自身获准入口与第三方库；utility 不依赖平台，platform/node、platform/electron 与前端/Bridge 客户端隔离。文件与网页基础能力已迁入共享 Core，便携协议、Node I/O 和 Electron 实现使用独立入口。
- 旧 backend/core → 自身、Core 文件/Web/utility 等获准入口，以及 Logic models/web 的精确纯入口；不反向认识应用装配或具体引擎。
- backend/engines → 自身、backend/core、core/utility 通用公开入口与 Logic models 精确纯入口；不借此访问其他基础方案、Node 入口或私有实现，具体 SDK 与 HTTP 传输不得被 Core 反向引用。
- backend/scheduler-engine → 自身、backend/core、core/utility 通用公开入口与 Logic models/web 精确纯入口；assembly 中的引擎装配可以依赖 backend/engines。
- backend/bootstrap → 自身、backend/updater、backend/main；固定加载器的计算式入口仍纳入真实源码依赖检查，不作为外部加载豁免。
- backend/main → 自身、backend/scheduler-engine、旧 backend/core、backend/updater、bridge/contracts、Core 获准入口及 Logic models/web 的纯入口和 service/index.ts；Electron Web 读取器仅允许 main.ts 装配入口直接导入。
- backend/updater → 自身、bridge/contracts、core/utility 通用公开入口；更新程序不得反向依赖 Main、调度或业务运行时，不能跨入 utility Node 入口或其他基础方案。
- bridge/contracts → 自身、backend/core 的公开契约和纯函数；models.ts/web.ts 仅具名重导出已登记的 Logic 纯契约，不开放凭据、服务或任意重导出。
- frontend → 自身、bridge/contracts、共享 core/utility 公开入口；具体模块的窄依赖规则仍生效。
- 前端适配库 frontend/foundations → 自身与共享 Core 的便携公开入口；不引用 React、页面或通信契约。equalJson 已组合共享排序，其余能力按真实语义逐项评估；不能为共享引入 Node 或后端业务。Bridge 不转发工具。
- bridge/preload → 自身、bridge/contracts。
- frontend 是视图层，backend 是本机后端逻辑层；bridge 是通信边界。禁止前端直接导入后端实现，也禁止后端导入前端。

遇到循环时，先确认职责归属；把双方需要的协议抽到独立契约模块，或用端口注入实现。不要仅改成 `import type`、动态加载或 re-export 隐藏循环。契约不得再引用实现类，否则循环仍然存在。不要为了消环把不相关职责堆到公共文件。

变更路径时同步导入、构建入口、测试引用和文档导航。不要引入空目录、占位实现，或把计划能力描述为已交付。

## 3. 同步注释与类图

系统、模块和类的封装均按单一职责与开闭原则审阅：职责以变化原因判断，已识别的业务变化通过稳定契约扩展。相关注释与架构说明应指出稳定部分、可变部分及装配位置，让维护者能理解为什么新增业务无需侵入公共核心；真实契约调整则说明影响和兼容代价。

受影响的模块与类必须按业务变化点划界，变化频率不同的代码分别封装。在相关契约或架构说明中记录变化点、频率依据和连接两侧的稳定接口；频率未知时如实注明，不虚构统计。类图和职责说明需反映稳定机制与可变策略的实际分离，不能仅换文件位置而保留同一封装及共享可变状态。

- src 脚本顶部说明作用定位、设计原因及必要的边界；关键接口补充生命周期、权限、事务、并发、失败或释放语义。关键字段说明身份、单位、所有权和空值含义。
- 每个受影响目录维护 `ARCHITECTURE.md`。叶子目录展示全部代码类图；非叶子目录展示本层代码与直接子目录的真实关系。不要将目录画成实际类，也不要虚构继承。
- 若新增目录，先人工确定其职责并维护 `scripts/source-architecture.mjs` 中的目录定位，再执行 `node scripts/source-architecture.mjs`。
- 检查生成后的 diff、代码清单、关键成员、连线方向和链接。生成器不能替代架构分析；只改行为而未改依赖时，同步相关职责说明，不制造无意义关系。

## 4. 面向维护者交付项目认知

围绕维护决策组织解释，复用已有说明，只补缺失的解释、失效事实和本次变化，不按文件逐个翻译：

- **职责与关键路径：** 主要模块解决什么、不负责什么，依赖和数据怎样经过边界。用真实场景解释操作如何完成，谁拥有状态、何时发生副作用、失败后留下什么。
- **稳定与变化地图：** 哪些契约和实现已有稳定证据，哪些仍是候选。说明重要模块／类的业务变化点、频率及依据、隔离方式和稳定接口；未知或需求推断明确标注。用一次高频业务变更说明修改位置和应保持稳定的低频核心。
- **设计理由与变化影响：** 解释约束、选择和代价，以及本次前后规则、契约、消费者和入口的变化。机制可以从代码核实，历史动机不能编造；当前实现与未来方案分开。
- **阅读与修改导航：** 先读哪些契约、再读哪些实现；针对一项真实需求指出扩展位置、稳定边界和应运行的验证，不列出整棵代码树充当解释。

图有帮助时用可读的小图分别表达职责、数据流或状态机，并明确图间连接。区分运行调用、代码依赖、数据流与继承，不靠缩小巨图容纳复杂系统。

重要职责、公共抽象、状态归属或生命周期改变后，更新项目已有的概念／架构说明和必要决策记录，给出原因、被替代做法与适用边界。当前事实只维护一处；历史记录保留当时结论并链接现状，不无故新建百科式文档。

交接应让维护者能定位三类答案：业务规则由谁负责及其理由；新增同类需求怎样扩展、哪些契约与核心实现应保持稳定；修改后如何验证、哪里仍缺证据。可以用具体场景帮助核对理解，不强制答题或逐步骤审批，不把沉默当作认可。只对影响后续工作的真实业务歧义或取舍分歧集中提问，区分材料交付与人的明确确认。

## 5. 验证后再报告

utility 的类图按实际类别文件表达 JSON、字符串、字节、异步协调等工具模块，展示各具名算法、独立实例数据结构与通用/Node 公开入口；不按函数数量机械拆文件，也不因合并文件而虚构算法间依赖或共享状态。当前 SerialQueue 归 `src/core/utility`，旧 concurrency 目录已退役；同步消费者导入、测试归属和依赖规则，不能残留两份队列实现。Core 的 hash/json 兼容出口仍保留，注明算法只在 utility 实现。

前端 utility 单独维护类图与契约，当前 `json.ts` 提供 equalJson。迁移同类比较须保留 localeCompare、对象 undefined、数组次序及错误语义；类图展示控制器到前端公开入口的依赖，不画成后端算法复用。单元归属前端基础模块，业务回执与恢复用原消费者测试验证。

前端 `events.ts` 的 SubscriptionSet 展示 subscribe、notify、size、clear 及实例监听集合；消费者组合关系和通知行为同步维护。控制器仍拥有状态、轮询、代次与销毁，类图不将清空监听器画成请求取消或资源退出；同步实时遍历与异常中断的兼容边界写入契约，并分别验证集合机制及消费者生命周期。

前端 async.ts 的 AsyncGeneration 类图展示 capture、advance、isCurrent 和实例标记。消费者拥有何时推进、成功/失败/finally 的判断点及资源清理；标记失效不等于请求取消。同步保留业务身份、版本和冻结命令回执边界，模块单元与消费者迟到结果回归分别维护。

严格解析归 JSON 类别、字节流消费归字节类别，标明 Core 的错误适配和 Main/Updater 的业务策略。reader 释放与网络/进程退出不能画成同一个完成保证；取消、不完整输入和大小限制的回归随实际消费者同步。

键排序、在途集合、LF 分帧分别归 JSON、异步协调、字符串类别，测试仍按各自行为职责独立维护；类图展示消费者组合及本地策略归属。排序策略不画成统一历史指纹，Promise 快照等待不画成物理退出，文本帧不画成已验证协议。同步各引擎实际字符/字节限额与业务排空顺序，保留独立生命周期状态。

测试也按职责维护：所有单元套件归属一个模块，数据/纯断言/临时目录与 Application 集成夹具分离；不导入其他测试套件，不依赖执行顺序。测试归属在 `tests/modules.json`，不是实时待办。涉及测试增删、导入或夹具变化时运行 `pnpm check:test-modules`；模块单元与跨模块契约/集成分别记录，禁止仅改变分类绕过解耦。该检查可证明登记和静态依赖边界，断言责任及共享状态仍需代码 review。

按 [AGENTS.md 的验证范围](../../../AGENTS.md#日常验证范围) 选择与实际变化相关的检查，不设置每次源码修改必跑的固定套餐：

| 本次变化 | 日常验证 |
| --- | --- |
| 业务逻辑、状态或交互行为 | 受影响单元及直接相关契约的测试文件／用例，覆盖实际受影响消费者 |
| 类型或公共接口，需要编译验证 | `pnpm typecheck`；不把它连带扩大为全量行为测试 |
| 导入、文件路径、模块边界 | `pnpm check:dependencies`；同时更新类图时用已包含它的 `pnpm check:architecture`，不重复运行 |
| 架构资料或生成器 | `pnpm check:architecture` 核对结构；纯说明文字变更只人工核对事实与引用 |
| 依赖检测器或分层规则 | 对应的 `tests/dependencies.test.ts` 或 `tests/layer-boundaries.test.ts`，按实际修改选择 |
| 纯文档或 Skill | 事实、格式、引用和入口一致性，不运行产品测试、类型检查或构建 |

先说明单元测试的选取依据，通过后收尾；只有新变化、失败或新增影响证据才补跑相关范围。广泛重构按实际迁移的单元及受影响消费者验证，不默认运行 `pnpm test`。打包入口、原生模块变更在本步验证受影响逻辑，并记录后续集成／发布阶段需要的真实制品验收；日常不自动打包或启动全套桌面／升级测试。用户明确要求专项验收时按其范围执行。全量回归由后续自动化阶段承担，未运行的检查不能标为通过。

循环检测范围为 src、tests、scripts、design、docs、.claude、.codex 的 JS/TS 文件及仓库根 JS/TS 配置，包含声明文件、类型 import/export、import type 表达式、动态字面量 import、require 与 createRequire 常见本地别名。根目录新增其他代码树时，必须扩展检测器 roots，避免漏检。

构建产物、依赖、缓存不属于维护代码。无法解析的本地引用、指向扫描范围外的源码、未审核的计算式加载和层级越界均失败。第三方非字面量加载只能在核实目标后按“文件 + 精确表达式 + 理由”登记；禁止为项目内部循环加豁免。静态分析不保证任意运行时元编程或反射的实际依赖，此类代码必须人工审查。

修改检测器时，用系统临时目录创建测试样例，至少验证类型环、长环、自引用和正常无环图；不要把有意成环的样例放入仓库被检测目录。

源码修改的最终说明列出依赖边界、实际验证、同步维护的注释与架构文档、维护者需要更新的认知及剩余限制；没有完成同步维护，不得报告完成。只读解释或纯文档任务按实际交付报告，不冒充完成了重构或运行验证。

## 多宿主同步

本流程同时存放在 .agents/skills/architecture-maintenance/SKILL.md、.claude/skills/architecture-maintenance/SKILL.md 和 .codex/skills/architecture-maintenance/SKILL.md。修改任一份时同步其余入口，保持内容一致。

前端图布局通过 utility/graphs.ts 的 rankDirectedGraph 组合；只沉淀 ID/边与层级，业务边筛选、错误文案、坐标和路径保留原适配。分层与无环判断是不同契约，暂保留各自实现；共享须核实语义，不开放业务互引；拓扑单元与任务布局消费者分别验证。

前端本地记录存储已有 utility/storage.ts 的 JsonRecordStorage；仅复用注入式有界 JSON 读写。迁移核对空串/缺失规则、UTF-8 上限、序列化字节、写失败前后的内存状态；schema、条数、坏数据禁写、回执及原请求恢复保留业务控制器，不能扩成统一命令状态机。

后端 JSON 补齐优先复用 orderJsonValue，迁移显式固定比较器与 undefined 策略，业务身份与哈希字段留在原模块。调度器仅可导入 core/utility 的通用公开入口，禁止私有实现及 Node/files/web；手工拼接字符串、排序后读取属性的协议须单独核对，不直接统一。

后端字符串精确脱敏统一组合 strings.ts 的 redactLiteral；凭据来源、认证模式、事件序列化和错误屏障留在引擎。保留空凭据、大小写、非重叠及编码语义，不以字符串函数宣称覆盖所有泄露途径；独立算法与真实引擎适配分别测试。

Pi/Codex 的请求关联使用 utility/async.ts 的 PendingRequests；register/take/rejectAll 仅管理 ID、回调与计时器。协议决定超时处置：Pi 单项未知、Codex 整体失败及杀进程必须保留；发送异常、重试与物理退出不下沉，分别验证乱序/重复回包、超时及关闭。

后端无环判断组合 utility/graphs.ts 的 isDirectedAcyclic，前端分层独立实现；领域入口先核验节点/端点，再选择启用依赖与等待边并保留原错误码。公共图算法不认识任务或授权；独立拓扑测试与领域防环/重放契约分别验证，新增私有类别同步依赖清单。
