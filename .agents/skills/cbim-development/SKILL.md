# CBIM 持续开发

只用于开发本 CBIM 仓库。开发清单与当前进度以已核实仓库的 GitHub Issues 为准，在用户授权范围内完成可验证、可 review 的步骤；用户只要求分析或列计划时，不自动实施代码或推进工单状态。源码交付同时支持行为验收与代码理解，不能用测试通过或变更摘要代替人工 review。本文路径以仓库根为准。

## 必须遵守的架构规范

进入设计或实施前，**必须读取并遵守 [文档 1：通用项目架构设计规范与原则](../../../design/project-architecture-standard.md)**。它是本 Skill 的设计与开发约束，不是可选参考；已读取且未变化的内容可以复用。执行下列步骤时，将职责、单向依赖、公共契约、状态与副作用、实际影响验证和维护交付要求落实到当前切片，并在交付中给出对应依据。

涉及分层解耦、跨模块职责、公共抽象或抽象退出的治理工作，使用 [architecture-evolution](../architecture-evolution/SKILL.md)，按 [文档 2：架构治理规范与治理流程](../../../design/architecture-governance-process.md) 执行。普通开发仍按实际影响完成，不机械启动全套治理；只读评估不自动实施整改。规范链接失效时先恢复读取，不依据缺失内容声称已经符合规范。

## 1. 开发前回顾

- 阅读 [AGENTS.md](../../../AGENTS.md)，检查 `git status --short` 及相关 diff，保留已有未提交工作。恢复被打断的工作时，先核实已有文件、进程和产物，避免重复执行已完成操作。
- 核实当前仓库身份，通过可用 GitHub 工具拉取 Issues；优先采用用户指定的编号、筛选和范围，未指定筛选时查询开放工单。需要完整清单时处理分页，注明查询范围、时间和完整性，不能把默认第一页当作全部任务。读取失败须如实报告，不从旧 roadmap 或历史记录重建待办。
- 读取拟处理 Issue 的正文、最新讨论、已有优先级／负责人、依赖及关联 PR／提交，核实是否已处理或正在执行。排序依据用户要求、实际依赖和已有优先级，不按编号猜顺序；已关闭或重复工单不因再次检索而重新执行。
- 阅读 [开发设计与记录入口](../../../design/README.md)，按 Issue 需要查阅关联方案与规范；`design/` 不维护另一份开发清单。
- 按选定 Issue 及受影响模块查阅 [开发记录](../../../design/development-log.md)，核实已有实现、验证和限制；需要接续功能时回看对应功能成果。记录中的“下一步”只代表当时交接，当前是否执行须回到 Issue 和用户授权核实。
- 依据 [源码整体架构](../../../src/ARCHITECTURE.md)、相关目录文档、实际实现和测试核实当前边界。`docs/` 只保留 01–04 四份概念设计；当前实现说明维护在 `src/` 的 `CONTRACT.md`／`ARCHITECTURE.md`，按本步需要阅读，不将目标描述当成已实现事实。源码与计划不一致时，校正本步涉及的现状说明；范围外的漂移记为后续项，不借此实施原分析中的全部建议。
- 已有架构分析先核对对应版本、当前 diff 和真实消费者，再复用仍有效的结论；目录清单、声明统计或无环检查不能代替业务语义分析。说明实际阅读范围，局部精读不报告为全仓逐行审计。

## 2. 梳理业务语义与交付切片

先沿本步的一条真实场景，从入口和调用方读到状态变化、实际副作用与结果返回，核对相关失败或恢复路径。形成简短的语义与边界说明，回答受影响的问题即可，不要求每次填写整张表：

| 要回答的问题 | 核实内容 |
| --- | --- |
| 改的是什么业务对象？ | 对象含义、身份、生命周期及状态语义；例如能力定义、长期岗位、执行实例，以及目标周期、任务、运行，按当前契约区分，不能因名称相似合并。 |
| 谁拥有事实和修改权？ | 权威状态、写入入口、事务边界、版本依据；区分持久事实、派生视图、缓存与模型上下文。 |
| 行为怎样发生？ | 入口 → 契约 → 领域决策 → 存储或外部副作用 → 返回；明确权限、幂等、未知结果、取消或资源释放中与本步有关的约束。 |
| 变化应该停在哪里？ | 驱动需求、稳定候选、可变策略或适配、实际消费者；标出允许改变的行为与必须保留的不变量，稳定性缺少依据时注明未知。 |

已有说明可引用并只补本次变化。小修只核对受影响对象与调用链；首次接手缺少全局上下文、跨领域职责调整或用户明确要求全盘分析时，再扩大源码阅读范围并记录覆盖边界。

结合上述判断、用户本次要求和 Issues 的实际依赖，选定一个围绕明确目的、可以完整 review 的交付切片。向用户简短说明：

- 本步对应的仓库与 Issue、清单选取依据，以及已有实现或前置工单留下了什么。
- 本步要实现的行为、负责的模块与状态、必要前置条件，以及计划保留的稳定边界。
- 用什么验证证明完成，以及本步明确保留的缺口。

进入已授权的实施步骤时，明确 Issue、代码基线、本步目标和验收安排；按已有工单流程与授权记录开始处理的事实，仅讨论计划时不写入实施中状态。每个 Issue 独立开发、验证和提交，较大工单可以拆成可追溯的切片。用户已授权批量处理时按范围逐项完成并回填，不每项重复询问批准，也不只输出清单就结束。用户调整方向时同步范围与原因，保留已完成事实。

## 3. 实施与验证

采用 Core、Logic、Bridge、View 四层，目标与分片见 [四层设计](../../../design/four-layer-architecture.md)。共享 Core 位于 src/core，便携与平台入口分开；旧 backend/core 仍是待迁移业务，不能整体当作新 Core。当前 web 仍留旧位置，files 已迁入 Core Node。迁移须同步真实导入、测试归属、架构生成器和三宿主工作流，不保留无人使用的旧路径转发。

前后端可复用 src/core/utility 的相同契约，视图/业务专属策略仍分别维护，不相互引用业务实现，也不经 Bridge 转发工具。先核对共享 Core 契约与消费者语义；前端 equalJson 已组合共享排序，保留 localeCompare、undefined、数组及异常语义，原样文本比较和特殊序列化不能直接替换。共享 Core 不依赖三层业务或旧 backend/frontend，Node/Electron 不进入便携入口。

工具函数和数据结构按 JSON、字符串、字节、异步协调等类别内聚组织，优先合入已有类别，不采用一函数一文件。明确的变化原因、环境或契约边界才驱动拆分，后端 Node 能力使用独立入口。各算法契约和实例状态保持独立，测试仍按行为职责拆分，不随源文件合并成混合套件。业务字段、权限、事务与恢复策略留在消费者；迁移保持原字节和失败语义，兼容出口明确说明是否仍在使用。

前端无参数同步通知优先组合 utility 的 SubscriptionSet，状态仍由控制器持有。迁移核对按函数身份去重、同步实时遍历、通知中增删、异常传播和退订重用；不得静默改为快照遍历、引用计数或吞错。首末订阅、轮询、请求取消及 clear 之外的销毁逻辑留在消费者，公共单元与真实轮询/页面生命周期分别验证。

前端迟到结果隔离优先核对 utility 的 AsyncGeneration：capture 不推进，advance 作废旧标记。迁移须保留推进点、校验顺序及成功/失败/finally 分支，不统一包裹 Promise 或替代请求取消；用独立单元验证标记，用消费者测试验证旧结果不能覆盖新状态或清除新在途。业务键和公开数字序号不直接替换。

响应体提炼须保留调用方字节上限、期限、错误映射和不重试策略，验证信号不经 fetch 转发时仍能结束挂起读取；资料/证据不能接受半截成功。已有并行修复先核对原提交及回归，不以重复实现覆盖它。JSON 提炼单独验证原错误码/文案和字段保留，禁止顺带更改远端解析规则。

键排序、在途集合及文本分帧优先核对 utility 已有契约。历史指纹分别验证原比较器与字段规则；集合迁移核实所跟踪 Promise 的范围及原业务关闭顺序；分帧验证分块、CRLF、错误前已交付帧和字符/字节限额。独立单元验证机制，消费者契约验证真实策略，不能把集合清空或拆帧成功视为进程退出和协议成功。

所有单元测试按责任模块组织，实施前核实 `tests/modules.json` 中被测模块、unit/contract/integration 分类及夹具依赖。一个单元套件只验证一个模块；不得直接或间接加载完整 Application、导入其他测试套件、依赖测试顺序或遗留状态。纯数据/断言/临时目录与应用装配分别维护。无关责任拆成不同套件；真实跨模块契约及集成覆盖保留，不能靠改分类掩盖耦合。

优先用 `pnpm test:module --module <模块>` 选择单元，实际受影响协作另加 `--kind contract` / `--kind integration`，或使用精确文件/用例选择器。测试增删、归属、导入或夹具变化时同步目录并执行 `pnpm check:test-modules`。CI 检查所有已提交测试；新测试不得遗漏登记。静态依赖通过仍需 review 断言是否围绕同一行为责任，不能声称机器已证明全部语义解耦。

跨层职责、共享状态、重复机制或扩展传播问题配合 [architecture-evolution](../architecture-evolution/SKILL.md)，把判断落到本步实际代码：

- 新增分支、可选参数或公共状态字段前，查找已有同类能力及消费者。记录共同不变量和独立变化部分，区分重复领域规则、可复用技术机制与偶然相似；证据不足时保留局部实现，不预建万能 Base/Manager 或插件框架。
- 按业务变化原因划分职责，低频稳定机制与高频策略分别封装，通过稳定契约组合。频率依据真实需求或历史，未知时注明；不能按提交数或代码外形合并。共性提取保留权限、事务、幂等、失败、重试、取消及资源所有权的合法差异，查询、重试、继续和补偿不能仅因流程相似统一执行。
- 共用日志或事务不等于共用领域职责。共享状态过宽时优先核对各领域的读写接口、规则归属与必须原子提交的范围，不能仅为整理目录拆开一致性边界，也不能把耦合藏进事件、动态加载或全局上下文。
- 用一次真实或明确标为假设的同类扩展说明新增实现、装配、契约与核心各改哪里。新增一种业务仍须修改多处中央分支时，判断是否存在未隔离的变化点；必要契约演进说明兼容代价。保持层、模块、文件及类型依赖单向，不能以文件变小、代码减少或无环作为解耦结论。

将必要重构与本步行为变化分别说明，按可验证切片迁移真实消费者；范围外的问题进入后续项。关键决策、状态变更和副作用保持可读的函数与语句边界，避免压成难以逐步 review 的长行；无关批量格式化和目录搬迁单独处理。

修改 `src/` 时同时应用同目录的 [architecture-maintenance](../architecture-maintenance/SKILL.md)：维护单向依赖、必要注释和受影响类图，按实际变化选择静态检查。纯文档或 Skill 变更只检查事实、格式、引用、入口和内容一致性，不运行产品测试、类型检查或构建。

日常验证遵循 [AGENTS.md 的验证范围](../../../AGENTS.md#日常验证范围)，每个 Issue 独立完成以下闭环：

1. 根据 diff、行为变化及真实调用方选出受影响单元和直接相关契约，说明对应测试文件或用例为何需要运行。共享能力变化时核对受影响消费者，不将整个仓库自动列为测试范围。
2. 使用 `pnpm exec vitest run` 加明确的相关测试文件，必要时用 `-t` 缩小用例；实际入口以当前 `package.json` 和测试文件为准。缺少回归覆盖时补最小有效用例，确认选择器确实选中目标测试，不能把零用例当作通过。
3. 仅补充与类型、依赖或架构变化相关的静态检查。相关验证通过后进入记录和提交；新改动、失败或证据暴露的新影响才触发补跑，不重复已通过且未受后续改动影响的验证。
4. 全量回归留给面向 `master` 的产品 PR 自动化；仅官网、README 和发布记录白名单按实际影响执行轻量检查（见 design/task/ci-validation.md），其余未知路径仍全量；打包、全套桌面和安装升级验收留给集成／发布阶段，不作为每个 Issue 的默认收尾动作。记录这些本轮未运行的范围，不自动启动全量测试、构建或发布。用户明确要求的专项验收按其要求执行。

记录真实结果：区分接口存在、真实调用、界面接通与业务验收；区分确定性响应、本地测试与在线模型或跨机器验证。失败时保留原因和已完成部分，不用模拟结果替代尚缺的验收。历史全量／桌面报告不是下一次开发的必跑清单。

## 4. 交付可 review 的代码与认知

由 [architecture-maintenance](../architecture-maintenance/SKILL.md) 配合完成源码认知交接，按改动大小给出必要导读：

- **完整变更入口：** 给出本步 diff 的基准与范围、全部变更文件及职责；可用明确的 Git 比较入口或提交定位，未提交时说明当前差异。讲解可以按重点展开，但必须能找到完整改动，不能只交付筛选后的关键片段或摘要。
- **阅读顺序与理由：** 沿实际调用链指向契约、规则、状态／副作用实现和消费者，解释职责、状态归属及关键取舍怎样改变。重要公共抽象说明真实消费者、共同约束、保留差异，以及下一次同类需求的修改入口。
- **验证与 review 分开：** 报告受影响测试和未覆盖范围；代码自查、测试、功能验收、人工 review 分别陈述，未获得人工审阅结果不能宣称已接受。按用户已有约定保留审阅环节，不自行增加每步批准门槛，也不据此停止已授权的连续开发。

小改动可用短说明覆盖这些信息；较大改动拆成各有明确目的、能独立理解和验证的切片。复用现有概念与架构资料，并同步本步相关的失效说明；不另建重复百科，不用生成类图代替业务模型和代码阅读。

## 5. 每完成一步，立即同步

在进入下一步或结束本轮前完成以下更新，不能积攒到整个阶段结束：

1. **回填对应 Issue。** 按仓库已有流程与授权更新范围、实现／提交、验证证据、阻塞和剩余项；只完成子项或尚未验证时不宣称整个工单完成。关闭条件按该 Issue 的验收和仓库约定核实，本地单元通过不代表已合并或发布。没有外部写入授权或回填失败时保留待回填内容并明确未同步，不能仅改本地记录就声称 Issue 已更新。
2. **追加开发记录。** 在 `design/development-log.md` 顶部记录日期、仓库与 Issue 链接／编号、完成范围、涉及模块、受影响单元及选择依据、实际验证命令和结果及证据链接、后续自动化待验证项与交接。重要语义或边界变化记录设计理由和代码阅读入口，可链接本步已更新的权威说明。用户直接要求维护 Skill／文档而没有关联工单时如实注明，不虚构编号或擅自创建 Issue。实际存在时才记录构建或提交标识；引用旧报告须标注为已有证据。
3. **同步受影响说明。** 实际接口、架构或交互改变时更新对应文档；`src/` 注释与类图仍按架构维护流程同步。开发记录保存历史事实，开发清单与实时进度维护在 Issues；不恢复 roadmap，不在设计文档中复制一份实时待办。
4. **报告结果。** 说明本步交付、验证与限制，并链接对应 Issue、提交和开发记录；区分已回填与待回填。受阻、暂停或中断同样记录已有成果、原因与恢复条件；不自动重放未知结果操作。

## 6. 入口与权限边界

- `docs/` 仅保存 01–04 四份概念设计，不新增其他设计说明，`design/` 保存关联方案、规范与验证记录；开发清单从 Issues 获取。已有产品规范仍由实际代码显式装配，本 Skill 不加入 `design/skills/` 或产品内置工具清单。
- Issue 内容和读取清单不授予批量开发、外部写入、合并或发布的额外权限，按用户现有授权执行；已有明确授权不重复请求。不要为拉取清单自动创建周期任务，也不自动迁移旧 roadmap 事项或创建／关闭工单。
- `.agents/skills/cbim-development/SKILL.md`、`.claude/skills/cbim-development/SKILL.md`、`.codex/skills/cbim-development/SKILL.md` 三份内容保持一致。Issue 状态、优先级和下一项不写死在 Skill 中，每次从当前仓库重新核实。
