# 证据与完成条件

从冻结前建立本次记录。原始本机文件保存在唯一候选／`test-results/` 子目录，云端产物按 run ID／attempt 下载到不同目录；这些目录通常被 Git 忽略，关键事实、链接与限制还须进入受版本控制的 `design/verification/`、开发记录和 PR，不能只留本机路径。

## 记录字段

下面是记录模板的字段，不是已完成事实。每项使用“未开始／进行中／通过／失败／未知／不适用”，不适用必须说明原因；时间写绝对日期，提交和摘要使用完整值。

| 记录项 | 必须能追溯的事实 |
| --- | --- |
| 范围与授权 | 版本、纳入／排除 Issue、各自提交／验证、签名或未签名选择依据；允许的仓库／账号／公开／合并／官网操作 |
| 仓库基线 | repo、actor、defaultBranch、本地与远端 master/develop SHA、旧 Python latest ID／tag、现有 PR／Release／tag |
| 源码与验证 | sourceCommit、完整 CI head／base、mergeCommit；不同提交之间产品及构建输入差异依据；锁文件、版本说明和模式 |
| 构建 | 候选绝对目录、build-receipt 路径、buildStamp、packagedDirectory、EXE 摘要、资源／payload 摘要、构建锁处理（如有） |
| 签名 | mode；实际 NotSigned 或签名者／证书公开指纹／时间戳与验签结果；升级发布者配置。不要保存凭据／私钥／PIN |
| 四附件 | 每个 name、字节数、SHA-256、远端 asset ID／state／digest；latest.yml 中安装包 SHA-512，SHA256SUMS 对应关系 |
| Actions | workflow、ref、实际 head SHA、输入、scope、run ID／attempt、各 job 结果及 artifact 链接；受理与实际完成分开 |
| 全仓检查 | 类型、架构／依赖、品牌、官网、完整四片；文件／测试通过、失败、跳过数；每个跳过前置条件和是否新增 |
| 打包隔离 | 本候选 EXE 路径／摘要、六项隔离场景、页面／进程错误、自有资源回收报告 |
| 候选安装 | 干净隔离 runner、无原安装检查、fresh install；真实旧版来源／摘要、版本跨度、对应签名模式、isPackaged、截图 |
| 升级保留 | 原工作区、模型、同一 completed task/run、localStorage、文件标记、无重放；确定性模型请求次数和验证边界 |
| 发布 | 唯一 Release ID、tag 及 peeled SHA、published_at、公开／稳定状态、日志、四附件复核、旧 latest 保持、匿名更新读取 |
| 在线升级 | 旧版身份/交互模式；自动发现；用户下载和缓存摘要；两步或下载后自动重启的实际链；独立普通退出取消场景；实际新进程、原用户目录、新版及最后状态 |
| 官网 | 公开回执对应的 release.json、文案／签名状态、14 场景结果；master 部署 head／run／URL、六个匿名文件摘要对照 |
| 分支与交付 | PR head／base／merge 回执，本地／远端 SHA、仅 master/develop、默认 develop、工作树；关联 Issue／PR、报告与日志链接及回填结果 |
| 失败与恢复 | 每次原失败 ID／现场、发生在哪一阶段、已完成副作用、根因已证实或未知、修正及独立新证据、未完成项／恢复条件 |

## 阶段交接检查

- **公开之前**：候选对应模式重新核验通过；真实候选安装通过；完整 CI 与 PR 合并匹配；四附件及标签未变；没有未知并发变更。源码修正已产生新候选时，不复用旧制品报告。
- **公开之后**：读回同一 ID 和附件；匿名更新通道可用；真实线上升级完成。若后两项未完成，明确“已公开，升级验证待完成”，不隐去已发生的发布。
- **最终收尾**：官网来自公开回执且 master 部署可读；分支保持约定；当前进度／版本报告／PR 内容没有过时的“待发布／待部署”。不为填写最终提交 SHA 制造无休止的记录提交；可以用 PR、部署 run 和已冻结源码关联。

## 报告时区分这些结论

| 可以说的结论 | 所需证据／不能代替它的东西 |
| --- | --- |
| 已生成候选 | 构建回执与实际产物；不代表公开 |
| 制品核验通过 | 字节、清单及适用签名检查；单元替身不证明真实签名 |
| 已公开 | Release 读回、四附件、标签；publish 命令受理不够 |
| 更新通道可用 | 匿名元数据＋旧版实际发现；官网链接或管理员带 token 访问不够 |
| 线上升级通过 | 真旧版 UI 下载并按该版本实际交互安装、最终新版和原数据；直接运行候选 NSIS 不够 |
| 检查通过但存在跳过 | 如实列出通过、失败、跳过及原因；不要写“全部测试通过”掩盖缺口 |
| 用户能够检查并升级 | 已发布及验证过的产品检查行为；不等于关闭／离线用户已收到，更不等于所有用户已安装 |
| 已切换签名版本 | 更高版本真实签名及迁移；签名代码已接入或证书已购买不够 |

## 维护 Skill 本身时的验证

仅改 Skill／文档：校验 YAML frontmatter、命名、引用、Markdown 代码块及三目录逐文件一致；核对命令／workflow 输入仍存在、限制说明与源码相符。通过只读场景走查检查缺证书、草稿部分上传、公开回包丢失、旧 CI head、部分安装和后续签名等分支，记录走查结果。

这类走查不是新版本端到端验收；不要运行历史发布 helper、创建测试 Release／Issue、安装真实客户端或派发生产发布来“测试 Skill”。只有新增可执行 helper 时才为其做隔离行为验证；继续复用现有工具，不为文档另写第二套发布器。
