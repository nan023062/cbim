# 故障与恢复

只读取与当前现象相关的部分。依据实际回执确定已完成到哪一步；历史原因是诊断线索，不是遇到同一错误就直接打补丁的依据。原失败 run／报告和新的修正结果分别保留。

## 构建、签名和终端环境

| 现象 | 先核实 | 下一步及停止条件 |
| --- | --- | --- |
| `SIGNING_NOT_CONFIGURED` | 用户是否已选择未签名；公开证书元数据、构建账号、签名配置是否实际存在 | 已授权未签名则三个入口显式 `--unsigned`；否则只澄清缺失选择／签名环境。不自动降级，不把安装 SignTool 当作已有证书 |
| 有证书但验签／时间戳不通过 | 证书链、有效期、公开发布者、私钥访问、签名顺序和真实最终文件 | 修正构建环境并生成新候选；不删除签名断言、不把自签名当公众可信、不在旧清单生成后补签 |
| `RELEASE_SOURCE_DIRTY`／`RELEASE_SOURCE_CHANGED` | 实际 diff、HEAD、构建期间外部编辑，是否有用户未提交工作 | 保留用户改动和失败候选；整理本次范围并重新冻结，不 stash／丢弃未知工作后强行通过 |
| 已有 `build/desktop-signing.lock` | 锁中的 PID、命令行、source SHA、输出目录；PID 可能复用 | 仍在运行就观察原进程；确认没有原构建进程才处理该精确锁文件。不并发构建，不递归清空 build |
| 中文说明变成 `???`／参数被截断 | PowerShell 版本、输入与输出编码、生成文件真实字节 | 读取用 UTF-8；向 Node 管道传中文时同时设 `$OutputEncoding` 与 `[Console]::OutputEncoding` 为 UTF-8。多行正文写文件，PR 用 `--body-file`，API 用 `--input`；JSON.stringify 不是 shell 转义 |
| PS 参数包含 `$()`、反引号、花括号 | 参数是否被 shell 二次解析，Git ref／JSON 是否仍为原值 | 使用工具结构化参数或安全脚本文件；PowerShell 中引用 `'HEAD^{tree}'` 等表达式。不要把正文拼成命令；`gh --jq` 引号易失真时读取 JSON 再解析，不输出秘密验证转义 |
| `Get-AuthenticodeSignature` 模块读取失败 | runner 的 PowerShell 7 与 Windows PowerShell 5、继承的 PSModulePath | 在实际 runner 使用一致的 pwsh；先修正环境，再读真实签名状态。模块错误不是 NotSigned，更不是签名通过 |

## Windows CI

| 现象 | 可区分原因的证据 | 合理处置 |
| --- | --- | --- |
| 干净检出时许多 ARCHITECTURE／品牌摘要不同 | 文本内容与原始换行、git attributes、Windows/Linux 差异 | 核实 `.gitattributes` 固定相关文件 LF；用干净检出复验。不要删除架构检查或用无意义重新生成掩盖 CRLF；不要泛化为所有文档都要重写 |
| 工作流还没启动 job 就失败 | Actions 工作流预检错误、上下文所在层级 | 历史问题是 `${{ runner.temp }}` 放在不支持它的 job env；按现有入口放在 step env。预检失败不计为执行了行为测试 |
| 路径／工作区身份拒绝 `RUNNER~1` | TEMP/TMP、realpath 和 8.3 别名比较 | 使用步骤级规范 runner.temp，保留真实路径断言；不放宽产品路径保护 |
| 依赖安装 Electron 下载 HTTP 504 | 下载错误与测试是否真正开始 | 锁定依赖安装最多三次有界重试，持续失败停止；不更新依赖碰运气，不将网络重试扩大成测试／发布自动重放 |
| `ISOLATION_RUNTIME`／`RUNTIME`，本机通过而缓存 runner 失败 | 拒绝发生于启动前还是执行后；Electron 与数据文件的 isFile、realpath、nlink、size 和来源 | 历史缓存用硬链接导致 nlink=2；现有 CI 使用 `pnpm install --frozen-lockfile --package-import-method=copy` 并要求 nlink=1。核对同缓存修正和完整 CI，不删除硬链接保护或误当退出清理问题 |
| Electron 在 LPAC 内以 `2147483651` 退出 | 实际宿主是否同一 Electron，原始 stdio、NUL 初始化和打包版本 | 当前产品已仅对同宿主 Electron 使用 `--no-stdio-init` 及明确继承的标准流。先验证本次实际包含该修复；不能给普通 Node 乱加参数，不能放开 ACL／网络／Job 限制来过测试 |
| 终端到十秒仍 running | 原时点状态、实际进程、最终输出／退出、是否有产品时限要求 | 没有时限要求且仅等待不足时可用有界等待并保存耗时；历史用例采用 30 秒等待、45 秒测试上限。仍检查真实退出码、输出和会话隔离，不盲目延长所有超时、不自动重试命令。未定位的 Windows 内部原因保持未知 |
| 暂停／检查点查询偶发 `unverifiable` | 是否只等 HTTP 到达而没等真实 `message.delta` 持久化，查询期间是否发生并发修改 | 修正测试的同步前提，保留产品对并发／未知结果的拒绝；不改成永远给成功回执 |
| UI／工具参数旧断言失败 | 当前需求、可信参数、真实组件与原测试意图 | 只有需求已改变才更新失效断言，并保留等价业务保证；不按失败文本机械改预期。隐藏错误、改标记成功或加 skip 都不能代替修复 |
| 两项历史 EXE 用例跳过 | 每个跳过名称、所需真实旧包、当前运行是否新增跳过 | 有真实旧包才补验；如实记录范围，不用现代包／替身冒充迁移，不把旧版 2470/2472 固定成验收标准 |
| 定向诊断绿色，或已有绿色是旧 head | run head、PR head／base、scope、四片 job 名与报告 | 重新核实本次完整检查；独立诊断只能说明其覆盖场景，不伪造同名合并检查 |
| 重跑受理但尚未 queued；取消／强制取消返回 409 | run ID、run_attempt、jobs 和服务端状态 | 不宣称已取消，不循环发 rerun／cancel。保留状态；必要的新检查独立关联提交，实际启动后才计入结果 |
| `gh run view --log --job` 等整个 workflow 完成 | 目标 job 是否已经 completed | 已完成 job 可从 REST jobs 日志接口读取；仍运行 job 等待可用日志。保持有界观察，不把拿不到日志当作 job 通过或无限忙轮询 |

## GitHub 草稿、附件与公开

恢复时先取本次候选 `build-receipt.json`、`publish-journal.jsonl` 或分阶段日志，再按记录的仓库／Release ID／tag 查实际状态。日志缺少“完成”不证明操作没发生；网络回包丢失也不证明失败。日志含意图但无 ID 时，用有权限的身份分页查询唯一匹配 tag；没有足够证据就停在核实，不猜一个新 ID。

| 实态／症状 | 恢复动作 | 不允许据此推断 |
| --- | --- | --- |
| 草稿列表为空，read-only token | 核实身份和该 token 是否有草稿所需的 push／contents:write 权限；已有候选验收 job 用此权限只读附件 | 空列表不等于 Release 不存在；不创建第二个草稿、不公开草稿只是为了让测试读到 |
| 创建回包异常或列表短时看不到新草稿 | 保存意图，按回包 ID 直读并有限等待列表一致；同 tag 出现多个匹配就停止调查 | 不重复 create，不删除旧日志后再运行一体发布器 |
| 同一草稿有部分附件 | 比对四个预期附件的 ID／name／state／size／digest；已一致的跳过，确认缺失的补一次并回读 | 上传超时不等于缺失；同名错误摘要不能直接 `--clobber`；未完成状态不能视为可公开 |
| 附件全齐且已验收，但尚未公开 | 重新 verify、核对完整 CI／合并／标签和无并发变化，再只执行公开 PATCH | 不重新打包、建草稿或上传正确附件；`--replace` 不是 resume |
| PATCH 404 | 先按 ID 查是否仍草稿、账号／仓库／tag／source 是否正确，再查安全权限元数据 | 404 不必然是不存在。0.1.2 中 CLI 缺 workflow scope，目标工作流与默认分支不同；补标签并未解决。先验证原因，不套用每次 404 都缺同一权限 |
| 当前凭据不足但另有既有授权连接 | 明确核实同一账号、目标及所需权限后，按用户授权使用该连接；敏感凭据仅留在安全工具／进程内 | 不打印／写入 token，不悄悄换账号或扩大授权；没有合适授权则说明缺口，不通过反复尝试绕过权限 |
| tag 已存在但 SHA 看起来不同 | 区分 annotated tag 对象和 peeled commit，核对真实指向 | 不强推标签“修正”到新 HEAD；源码不一致则停止并查版本占用 |
| 发布回包丢失，但 Release 已公开 | 只读核验同 ID、公开状态、附件、标签、旧 latest 和匿名更新入口；一致后继续在线验收 | 不再次公开／替换，不将已发生操作记成失败并回滚 |
| 远端在核实过程中变了／旧 latest 被改变 | 保留前后回执并停止，明确哪项事实不一致，再提出具体修复 | 不盲目覆盖他人变更、删除 Release 或自动修改旧 Python 通道 |
| `RELEASE_EXISTS`／`RELEASE_INCOMPLETE`／已有 journal | 进入上述逐步恢复，确认现有公开或草稿状态 | 不删日志消除保护，不将新版本当同版本替换 |

同版本替换仅在另行明确授权、完整下载核对旧四附件和元数据、确认非 immutable 后按签名指南执行。GitHub 不提供四附件原子替换，草稿期间会短暂失去下载；已安装同版本通常不会发现更新。当前正常发行与签名迁移均用更高版本。遇 immutable 或已公开错误版本不移动旧 tag，先给出具体更高版本修复／撤回方案并按授权执行。

## 安装、线上升级与官网

| 现象 | 先查什么、怎样继续 |
| --- | --- |
| 想在本机用 `/D=临时目录` 试安装 | 检查 CBIM 进程及卸载注册信息；只要有真实安装就使用隔离 runner。不要伪造 `GITHUB_ACTIONS` 环境绕过脚本门禁或停掉用户客户端 |
| 新版本测试输入已换，但仍测试旧路径 | 核对 previous_version 是否为实际上一公开版；当前支持 0.1.1／0.1.2 两步界面、0.1.3／0.1.4 自动安装界面、0.x 未签名目标及 NotSigned。其他旧版交互或签名模式需先适配验证，不能把 candidate/online 当签名选项，不能跳过旧版身份断言 |
| 已安装或已升级，末尾一步超时／报错 | 先读实际安装元数据、签名、运行进程、版本、用户目录和现有报告；在原安装状态继续剩余核验。仅当确需独立重测时使用新 runner；不自动再次安装或卸载 |
| 更新弹窗找不到“软件更新”region | 对照实际旧包 DOM／无障碍名称。0.1.1 起“版本与更新”是 dialog，“软件更新”仅是内部标题；使用实际下载按钮，保存截图，不以 IPC 模拟点击通过 |
| NSIS 后重启丢失测试配置／数据 | 核对更新进程 `--updated` 与 `--cbim-user-data-root`、真实目录与 task/run ID，等待窗口就绪；不只相信父进程环境，不用新建相似数据假装保留 |
| 线上发现成功但未下载／未安装 | 分别记录阶段；需要真实 UI 下载、缓存摘要、普通退出保持旧版和显式重启后新版。Release 成功或直接 NSIS 候选升级都不能证明这条链 |
| 官网仍旧版本或下载跳到 Python | 先核对公开 Release 与 release.json；再查 master 部署 head、目标 URL、匿名六文件摘要和 CDN 状态。不能改用 releases/latest、重新发布包或部署到另一平台解决 |
| 改 signed 后官网构建拒绝 | 阅读 `build-website.mjs` 的签名提示检查，依据真实签名同步可见文案；不能删该检查或沿用未签名警告的相反承诺 |
| 官网测试报告已存在／字节摘要跨机不同 | 保留固定输出目录内的历史报告后在隔离检出测试；核对已有 LF 属性和同一个构建输入。不覆盖旧证据，不将换行不同伪称线上一致 |
| master／develop 不一致或多出分支 | fetch 后查看差异、远端 HEAD、合并回执与用户授权；可快进才快进。发现未知工作先保留，不重置／强推／批量删除；不为满足“两条分支”误删未合并成果 |

发生公开后缺陷时，明确当前用户可下载的状态与影响，保留已发制品和证据。修复应使用新候选／更高版本；任何撤回或同版本替换都按具体授权执行，不将故障处理默认升级为删除或强制用户重装。
