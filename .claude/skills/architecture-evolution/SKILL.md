# 架构演进与共性沉淀

帮助维护者判断工程该怎样随需求成长。以真实代码、调用链和变更原因解释边界，交付能逐步验证的调整；不以增加层数、目录或设计模式作为进步。只要求评估时不修改业务代码；明确要求实施时在既有授权范围内完成，不增加逐步骤批准。

## 必须遵守的规范与标准流程

本 Skill 是项目架构治理入口。开始工作前，**必须读取并遵守 [文档 1：通用项目架构设计规范与原则](../../../design/project-architecture-standard.md)，并按 [文档 2：架构治理规范与治理流程](../../../design/architecture-governance-process.md) 执行**。已读取且未变化的内容可复用；链接失效时先恢复读取，不能用通用经验替代缺失规范并声称合规。

执行顺序为：S1 目标、基线与授权 → S2 事实与问题证据 → S3 影响、分级与排序 → S4 方案与切片 → S5 范围内迁移 → S6 验证与资料同步 → S7 review、归档与反馈。以下章节提供各阶段的具体分析方法，不另立一套可跳过的流程。

按文档 2 记录变更原因与影响证据、C1–C3 检查分档、L0–L3 认知等级、四问及第五问候选；涉及抽象替换时执行退出与消费者核实要求。小改动可合并说明，但不能省略适用判断。仅评估时执行到方案与报告归档，不进入代码迁移；失败或新证据回到相关阶段。既有授权内持续推进，不逐步骤重复审批，不自动晋升候选规则。

## 以稳定系统为演进目标

分层和抽象应保护已经稳定的规则与机制，让常规业务变化局限在扩展点和边界适配中。对系统、模块和类都应用单一职责与开闭原则：说明它因什么原因变化，以及新增一种已预期业务时能否主要添加实现、调整装配，而不连带修改稳定核心。

用真实变更原因、接口改动和影响范围辨别稳定程度，分别评价契约与实现。长期无人使用或没有提交不能证明成熟；缺乏历史证据时标为稳定候选。合理的缺陷修复和契约演进仍然允许，但要解释为何必须改变核心及其兼容代价。

## 先建立全局位置，再判断局部变化

- 阅读项目协作规则、入口、当前架构说明和本次目标，核对实际源码及工作区差异。区分文档目标、代码现状和已经验证的行为。
- 画清理解本次问题所需的系统边界：用户入口、业务编排、领域规则、平台适配、外部系统。列出各自的职责、输入输出、状态所有者及允许依赖；沿至少一条相关真实调用链读到最终副作用和结果返回。
- 对照全仓维护代码清单寻找同类职责和受影响消费者，再深入相关模块。报告实际阅读范围和未覆盖项；只读了局部不能称完成全仓评估。生成目录、第三方依赖和运行数据不作为自有架构扫描对象。
- 用搜索定位相似职责、业务规则和调用方式，阅读真实消费者及相关测试；必要时核对变更历史，区分重复业务知识、重复技术机制和偶然相似的代码外形。为复用候选记录共同不变量、变化部分，以及权限、幂等、错误、重试、取消、并发和资源所有权差异。
- 检查调用方和被调用方，以及接口、类型、事件、注入和持久化形成的间接耦合。目录聚合图中的双向边不直接等于文件循环；用实际依赖核实。
- 按实际职责边界检查层、模块和文件的单向依赖，包含类型引用；易变业务与实现指向稳定契约。稳定核心不能反向导入业务细节。区分运行时返回／回调与代码依赖方向，不能用事件总线、回调约定或共享状态掩盖真实耦合。

## 判断值得调整的边界

模块和类按业务变化点划分边界，变化频率不同的代码不得混在同一封装中。对正在评估的职责列出“变化点、触发它的业务需求、变化频率及依据、所属模块／类、对外契约”，核对哪些代码一起变化、哪些应独立变化；不能仅按功能名称或代码外形划分。

低频稳定机制与高频业务策略分别封装，由稳定契约连接，并在装配处组合。检查一次高频业务调整是否仍会迫使低频核心修改内部字段、分支或状态；仅移动文件而保留这种连带变化，不算形成有效边界。变化频率缺乏依据时标明未知或需求推断，排除格式化、批量重命名等非业务提交；频率相同也不代表属于同一职责。

关注能够指出代码证据或真实迭代成本的问题：

- 一项业务规则分散在多层，需要同时修改多个地方；或一个模块因互不相关的原因频繁变化。
- 领域决策依赖具体 UI、存储或网络实现；上层装配细节进入底层，类型引用也产生反向依赖。
- 状态、事务、资源释放或失败恢复由多个模块共同隐式拥有，调用方必须了解内部执行顺序。
- 共享模块知道过多调用方细节，新增消费者需要不断增加例外参数、分支或回调约定。

区分职责问题、接口问题和纯文件组织问题。移动目录不能替代解耦；增加接口也不能单独证明可替换。新的边界需要说明由谁拥有决策、数据和生命周期，以及它允许哪些变化独立发生。

单向无环是持续治理的硬约束，也要检查无环图中的过密依赖、跨层直达和共享状态。一个节点依赖几乎所有模块时，仍需解释其必要性并缩小职责；不能仅凭“没有循环”判定架构健康。

## 选择可沉淀的抽象

技术解决方案可放入独立 `src/foundations/<能力>`：只依赖自身、标准库和必要第三方库，不依赖 Core 或任何业务模块，类型引用也不能反向。每项能力有自己的公开入口、契约、状态与资源所有者；不建立统一万能容器。领域状态、权限、事务与业务失败策略保留在所属模块。优先核对 utility、files、web 等已实现能力能否满足真实契约；不是只要存在重复代码就继续抽取。

通用算法、数据结构与实例级串行执行归 `foundations/utility`，每项能力单独实现、具名导出；通用入口与 Node 入口分离，不把 I/O、领域身份或日志失败屏障混入工具库。迁入序列化/摘要算法时固定现有字节与错误语义；不同 canonical 排序不能直接统一。数据结构须有真实用途，不为凑目录添加未使用的容器。

传入流的消费机制与建立连接分开：utility 可持有 reader 的字节上限、取消和释放，URL、凭据、时长与物理退出屏障留在消费者。不得把不合作的底层 cancel 当作必须无限等待的清理。严格 JSON 只报告语法/重复键事实，业务错误、危险字段与资源限制由适配层解释；不能把普通协议自动升级为更严格解析。

已有机制入口包括 `orderJsonValue`、`InFlightOperations`、`LineFramer`。排序迁移先固定比较器、undefined/数字键/数组规则与历史字节，不能用“确定性”掩盖 locale 差异；在途集合只等待调用时快照，不能取代停止接单、动态排空或物理退出；分帧保留字符/字节、CR、空白及 EOF 差异，协议和限额通过原适配组合，不预建通用 RPC 框架。

抽象必须能以模块单元验证自身，消费者用契约/集成验证组合后的真实行为。测试沿同一职责边界拆分：模块单元不加载 Application，不依赖其他套件；通用测试支持不反向导入业务装配。迁移时同步 `tests/modules.json` 及依赖规则，用 `pnpm check:test-modules` 检查测试边界。不能仅登记类型或换目录就宣布所有测试已在语义上单一职责。

以真实复用点或已明确的稳定边界为依据，不机械要求出现三次，也不凭设想的未来消费者提取。变化频率不同的代码不能合并到同一模块或类：抽取低频稳定的共同机制，高频策略、规则和适配分别封装，通过稳定契约组合。暂不抽象时说明原因和重新评估的触发条件。

| 证据与变化方式 | 优先考虑的形式 | 需要核对的边界 |
| --- | --- | --- |
| 无状态的转换、计算或校验，共同语义稳定 | 具名纯函数或内聚工具模块 | 不混入调用方业务、全局状态或隐式副作用；不只为有“类”而包装静态类 |
| 相同领域规则、状态约束或事务需要统一维护 | 领域对象、值对象或内聚领域服务 | 归属明确的业务边界，不把不同业务概念放进万能工具目录 |
| 同一能力存在多种实现，消费者只依赖共同契约 | 接口与策略、多态适配 | 实现在契约下可替换，由装配选择；公共层不反向认识具体消费者 |
| 多个能力独立变化，或只是需要借用一种能力 | 组合、委托、依赖注入 | 职责和生命周期明确，避免继承带来无关状态与方法 |
| 稳定的“是一种”关系，或同一算法骨架只有受控步骤变化 | 浅层继承、抽象基类或模板方法 | 子类满足基类不变量、前置与后置条件，不削弱错误、取消及资源释放契约 |

继承和多态是可以充分利用的工具，不是必须使用的目标。子类需要禁用基类方法、反复判断具体类型、依赖父类内部字段或扩大权限时，重新考虑契约或组合。接口多态不要求共享实现或共同基类。

比较保留局部重复与拟议抽象：一个消费者独立变化会影响谁，新增真实实现要改哪里，调用是否更易理解。用一次真实扩展核对开闭原则；每增加一种业务都要修改公共分支、字段或接口，说明变化点尚未隔离。不要用不断增加的布尔开关、宽泛回调或万能 Base/Manager 类吞并差异，也不为了“零修改”预建未知扩展框架。

## 选择最小有效的演进并验证

对关键候选比较保留现状与有依据的调整，写清收益、代价和暂不解决的事项，不凑满方案数量。

- 以业务语义、变化原因和状态归属划分模块；稳定契约由有权定义它的边界拥有，具体实现通过装配或明确端口接入。
- 策略选择与执行机制可以分开，但契约必须保留错误、取消、重试、事务和资源所有权的真实语义。不要靠全局服务定位器或万能上下文把依赖藏起来。
- 公共能力放在职责所属模块，跨层复用先核实允许依赖；不要为了复用把领域实现降到基础层或破坏独立子系统边界。没有真实变化需求时，不预建插件框架、通用基类或分布式边界。
- 将方案拆成能保持系统工作的切片：建立行为基线、引入边界、迁移一个真实消费者、验证其余受影响入口、清除不再使用的旧路径。每片写明可观察结果和回退条件；避免边改边重写全项目。
- 固定消费者可观察的输入输出与副作用，保留合法差异；覆盖实际相关的失败、取消、并发和替换场景。基类或接口的各实现需满足共同契约，不能只断言抽出了函数或减少了行数。
- 分别说明重构与新增业务行为。旧调用、注册和动态入口均核实迁移后再删除旧实现，同步导入和构建入口；不把行为变化藏进抽象整理。

## 实施与维护者交接

实施源码调整时遵循 [architecture-maintenance](../architecture-maintenance/SKILL.md)，同步注释、依赖规则、架构文档和受影响测试。日常只运行当前切片及实际受影响消费者的单元／契约测试，静态检查按边界变化选择；不因抽取公共能力或广泛重构自动跑全量回归、打包及全套桌面验证，全量留给后续自动化阶段。通过后收尾，仅在新变化或失败暴露相关影响时扩展验证；静态无环不等于运行时已解耦。

交付以维护者能判断的内容为主：

1. 当前问题、源码或调用证据，以及继续维持现状的成本。
2. 调整前后的职责、依赖和状态归属；哪部分成为受保护的稳定能力，业务变化被限制到哪里，如何符合单一职责与开闭原则；明确保持不变的外部行为和已授权改变的行为。
3. 本次最小切片、实际验证结果、未覆盖边界及后续重新评估的具体触发条件。
4. 一个真实需求例子：调整后该改哪里、为什么只需要改这些位置，以及维护者应先读哪些入口。

在现有模块契约或架构文档中记录公共能力的职责、范围、真实消费者、变化点、状态与失败语义，以及添加一个实现的最小路径，不另建脱离源码的工具名录。契约调整要核对全部实际消费者，区分兼容扩展与破坏性变化；按后续真实使用、缺陷和独立变化继续修正，必要时收缩或拆回。分别说明契约与实现的稳定程度、业务变化传播范围和新增耦合，不能仅凭一次提取、提交数或代码行数判断成熟。

重要取舍写入项目现有的架构或决策文档，并链接源码；没有现成位置时按需要建立简短记录。由 [architecture-maintenance](../architecture-maintenance/SKILL.md) 同步代码资料并完成认知交接，复用已经核实的材料，不重复生成平行说明。对真实业务歧义集中提问，不把例行技术选择变成审批门槛，也不声称维护者已经理解或接受。
