# CBIM 持续开发

只用于开发本 CBIM 仓库。以用户当前目标为范围，沿开发计划完成可验证、可 review 的步骤；用户只要求分析或列计划时，不自动实施代码或推进未完成状态。源码交付同时支持行为验收与代码理解，不能用测试通过或变更摘要代替人工 review。本文路径以仓库根为准。

## 1. 开发前回顾

- 阅读 [AGENTS.md](../../../AGENTS.md)，检查 `git status --short` 及相关 diff，保留已有未提交工作。恢复被打断的工作时，先核实已有文件、进程和产物，避免重复执行已完成操作。
- 阅读 [开发计划入口](../../../design/README.md) 与 [roadmap](../../../design/tool-architecture-roadmap.md)：回顾整体目标、阶段状态、剩余顺序和“开发接续”。
- 阅读 [开发记录](../../../design/development-log.md) 的最近步骤，找到上一步实际完成的功能、验证与遗留项；如果最近只是文档维护，继续回看上一条功能成果。
- 依据 [源码整体架构](../../../src/ARCHITECTURE.md)、相关目录文档、实际实现和测试核实当前边界。`docs/` 是概念设计与配套说明，按本步需要阅读，不将目标描述当成已实现事实。源码与计划不一致时，校正本步涉及的现状说明；范围外的漂移记为后续项，不借此实施原分析中的全部建议。
- 已有架构分析先核对对应版本、当前 diff 和真实消费者，再复用仍有效的结论；目录清单、声明统计或无环检查不能代替业务语义分析。说明实际阅读范围，局部精读不报告为全仓逐行审计。

## 2. 梳理业务语义与交付切片

先沿本步的一条真实场景，从入口和调用方读到状态变化、实际副作用与结果返回，核对相关失败或恢复路径。形成简短的语义与边界说明，回答受影响的问题即可，不要求每次填写整张表：

| 要回答的问题 | 核实内容 |
| --- | --- |
| 改的是什么业务对象？ | 对象含义、身份、生命周期及状态语义；例如能力定义、长期岗位、执行实例，以及目标周期、任务、运行，按当前契约区分，不能因名称相似合并。 |
| 谁拥有事实和修改权？ | 权威状态、写入入口、事务边界、版本依据；区分持久事实、派生视图、缓存与模型上下文。 |
| 行为怎样发生？ | 入口 → 契约 → 领域决策 → 存储或外部副作用 → 返回；明确权限、幂等、未知结果、取消或资源释放中与本步有关的约束。 |
| 变化应该停在哪里？ | 驱动需求、稳定候选、可变策略或适配、实际消费者；标出允许改变的行为与必须保留的不变量，稳定性缺少依据时注明未知。 |

已有说明可引用并只补本次变化。小修只核对受影响对象与调用链；首次接手缺少全局上下文、跨领域职责调整或用户明确要求全盘分析时，再扩大源码阅读范围并记录覆盖边界。

结合上述判断、用户本次要求和 roadmap 的依赖顺序，选定一个围绕明确目的、可以完整 review 的交付切片。向用户简短说明：

- 全局处于什么位置，上一步留下了什么。
- 本步要实现的行为、负责的模块与状态、必要前置条件，以及计划保留的稳定边界。
- 用什么验证证明完成，以及本步明确保留的缺口。

进入已授权的实施步骤时，将 roadmap 的“开发接续”更新为本步目标、状态与验收安排，再开始实施；仅讨论计划时不写入“开发中”状态。通常选择一个可验证的小闭环；用户已授权多步开发时，逐步执行并逐步更新，不每步重复询问批准，也不只输出计划就结束。用户调整方向时同步范围与原因，保留已完成事实。

## 3. 实施与验证

跨层职责、共享状态、重复机制或扩展传播问题配合 [architecture-evolution](../architecture-evolution/SKILL.md)，把判断落到本步实际代码：

- 新增分支、可选参数或公共状态字段前，查找已有同类能力及消费者。记录共同不变量和独立变化部分，区分重复领域规则、可复用技术机制与偶然相似；证据不足时保留局部实现，不预建万能 Base/Manager 或插件框架。
- 按业务变化原因划分职责，低频稳定机制与高频策略分别封装，通过稳定契约组合。频率依据真实需求或历史，未知时注明；不能按提交数或代码外形合并。共性提取保留权限、事务、幂等、失败、重试、取消及资源所有权的合法差异，查询、重试、继续和补偿不能仅因流程相似统一执行。
- 共用日志或事务不等于共用领域职责。共享状态过宽时优先核对各领域的读写接口、规则归属与必须原子提交的范围，不能仅为整理目录拆开一致性边界，也不能把耦合藏进事件、动态加载或全局上下文。
- 用一次真实或明确标为假设的同类扩展说明新增实现、装配、契约与核心各改哪里。新增一种业务仍须修改多处中央分支时，判断是否存在未隔离的变化点；必要契约演进说明兼容代价。保持层、模块、文件及类型依赖单向，不能以文件变小、代码减少或无环作为解耦结论。

将必要重构与本步行为变化分别说明，按可验证切片迁移真实消费者；范围外的问题进入后续项。关键决策、状态变更和副作用保持可读的函数与语句边界，避免压成难以逐步 review 的长行；无关批量格式化和目录搬迁单独处理。

修改 `src/` 时同时应用同目录的 [architecture-maintenance](../architecture-maintenance/SKILL.md)：维护单向依赖、必要注释和受影响类图，按实际变化选择静态检查。纯文档或 Skill 变更只检查事实、格式、引用、入口和内容一致性，不运行产品测试、类型检查或构建。

日常验证遵循 [AGENTS.md 的验证范围](../../../AGENTS.md#日常验证范围)，每个 Issue 独立完成以下闭环：

1. 根据 diff、行为变化及真实调用方选出受影响单元和直接相关契约，说明对应测试文件或用例为何需要运行。共享能力变化时核对受影响消费者，不将整个仓库自动列为测试范围。
2. 使用 `pnpm exec vitest run` 加明确的相关测试文件，必要时用 `-t` 缩小用例；实际入口以当前 `package.json` 和测试文件为准。缺少回归覆盖时补最小有效用例，确认选择器确实选中目标测试，不能把零用例当作通过。
3. 仅补充与类型、依赖或架构变化相关的静态检查。相关验证通过后进入记录和提交；新改动、失败或证据暴露的新影响才触发补跑，不重复已通过且未受后续改动影响的验证。
4. 全量回归留给面向 `master` 的 PR 自动化；打包、全套桌面和安装升级验收留给集成／发布阶段，不作为每个 Issue 的默认收尾动作。记录这些本轮未运行的范围，不自动启动全量测试、构建或发布。用户明确要求的专项验收按其要求执行。

记录真实结果：区分接口存在、真实调用、界面接通与业务验收；区分确定性响应、本地测试与在线模型或跨机器验证。失败时保留原因和已完成部分，不用模拟结果替代尚缺的验收。历史全量／桌面报告不是下一次开发的必跑清单。

## 4. 交付可 review 的代码与认知

由 [architecture-maintenance](../architecture-maintenance/SKILL.md) 配合完成源码认知交接，按改动大小给出必要导读：

- **完整变更入口：** 给出本步 diff 的基准与范围、全部变更文件及职责；可用明确的 Git 比较入口或提交定位，未提交时说明当前差异。讲解可以按重点展开，但必须能找到完整改动，不能只交付筛选后的关键片段或摘要。
- **阅读顺序与理由：** 沿实际调用链指向契约、规则、状态／副作用实现和消费者，解释职责、状态归属及关键取舍怎样改变。重要公共抽象说明真实消费者、共同约束、保留差异，以及下一次同类需求的修改入口。
- **验证与 review 分开：** 报告受影响测试和未覆盖范围；代码自查、测试、功能验收、人工 review 分别陈述，未获得人工审阅结果不能宣称已接受。按用户已有约定保留审阅环节，不自行增加每步批准门槛，也不据此停止已授权的连续开发。

小改动可用短说明覆盖这些信息；较大改动拆成各有明确目的、能独立理解和验证的切片。复用现有概念与架构资料，并同步本步相关的失效说明；不另建重复百科，不用生成类图代替业务模型和代码阅读。

## 5. 每完成一步，立即同步

在进入下一步或结束本轮前完成以下更新，不能积攒到整个阶段结束：

1. **更新 roadmap。** 同步受影响的阶段状态、能力/缺口和剩余项，以及“上一步成果、当前开发、下一步、限制”。只完成子项时标明部分完成，未验证时保留待验证；未满足整体验收不把阶段标为完成。
2. **追加开发记录。** 在 `design/development-log.md` 顶部记录日期、对应阶段/步骤、完成范围、涉及模块、受影响单元及选择依据、实际验证命令和结果及证据链接、后续自动化待验证项与交接。重要语义或边界变化记录设计理由和代码阅读入口，可链接本步已更新的权威说明。实际存在时才记录构建或提交标识；引用旧报告须标注为已有证据。
3. **同步受影响说明。** 实际接口、架构或交互改变时更新对应文档；`src/` 注释与类图仍按架构维护流程同步。开发记录保存历史事实，实时进度只维护在 roadmap，避免两份待办互相矛盾。
4. **报告结果。** 说明本步交付、验证与限制，并链接更新后的计划/记录。受阻、暂停或中断同样记录已有成果、原因与恢复条件；不自动重放未知结果操作。

## 6. 入口与权限边界

- `docs/` 解释概念和设计，`design/` 管理开发计划；已有产品规范仍由实际代码显式装配。本 Skill 不加入 `design/skills/` 或产品内置工具清单。
- 路线图不授予提交、推送、发布、操作真实工作区或外部账号的额外权限；按用户现有授权执行。不要为记录进度自动创建周期任务。
- `.agents/skills/cbim-development/SKILL.md`、`.claude/skills/cbim-development/SKILL.md`、`.codex/skills/cbim-development/SKILL.md` 三份内容保持一致。状态和下一步不写死在 Skill 中，始终从 roadmap 读取。
