# CBIM 持续开发

只用于开发本 CBIM 仓库。以用户当前目标为范围，沿开发计划完成可验证的步骤；用户只要求分析或列计划时，不自动实施代码或推进未完成状态。本文路径以仓库根为准。

## 1. 开发前回顾

- 阅读 [AGENTS.md](../../../AGENTS.md)，检查 `git status --short` 及相关 diff，保留已有未提交工作。恢复被打断的工作时，先核实已有文件、进程和产物，避免重复执行已完成操作。
- 阅读 [开发计划入口](../../../design/README.md) 与 [roadmap](../../../design/tool-architecture-roadmap.md)：回顾整体目标、阶段状态、剩余顺序和“开发接续”。
- 阅读 [开发记录](../../../design/development-log.md) 的最近步骤，找到上一步实际完成的功能、验证与遗留项；如果最近只是文档维护，继续回看上一条功能成果。
- 依据 [源码整体架构](../../../src/ARCHITECTURE.md)、相关目录文档、实际实现和测试核实当前边界。`docs/` 是概念设计与配套说明，按本步需要阅读，不将目标描述当成已实现事实。源码与计划不一致时，先校正有依据的进度，不猜测完成度。

## 2. 梳理下一步

结合用户本次要求和 roadmap 的依赖顺序，选定下一步可交付结果。向用户简短说明：

- 全局处于什么位置，上一步留下了什么。
- 本步要实现的行为、涉及模块及必要前置条件。
- 用什么验证证明完成，以及本步明确保留的缺口。

进入已授权的实施步骤时，将 roadmap 的“开发接续”更新为本步目标、状态与验收安排，再开始实施；仅讨论计划时不写入“开发中”状态。通常选择一个可验证的小闭环；用户已授权多步开发时，逐步执行并逐步更新，不每步重复询问批准，也不只输出计划就结束。用户调整方向时同步范围与原因，保留已完成事实。

## 3. 实施与验证

每次实现先说明改动所属层、调用方和状态归属，按全局边界判断局部方案。跨层职责、耦合、重复机制、共性业务以及封装／继承／多态问题统一配合 [architecture-evolution](../architecture-evolution/SKILL.md)。按实际证据选择，不为小改动机械执行完整巡检；只要求分析不自动重构，已授权实施继续完成必要工作。

分层与抽象以沉淀低变化频率的稳定能力为目标。对系统、模块和类按变化原因核对单一职责，用真实扩展示例核对开闭原则，并保持层、模块、文件及类型引用的单向依赖。方案与交付应说明稳定核心、业务变化点和影响传播范围；不能仅以代码减少、类增多或无循环作为架构优化结论。

模块和类的边界按业务变化点划分，变化频率不同的代码分别封装。对受影响边界核对变化原因、频率依据和稳定契约，以一项真实或明确标注的业务变更场景验证高频策略不会牵动低频核心；不要将表面相似或提交数相近当作合并依据。

修改 `src/` 时同时应用同目录的 [architecture-maintenance](../architecture-maintenance/SKILL.md)：维护单向依赖、必要注释和受影响类图，按实际变化选择静态检查。纯文档或 Skill 变更只检查事实、格式、引用、入口和内容一致性，不运行产品测试、类型检查或构建。

重要职责、公共抽象、状态或生命周期改变后，继续由 `architecture-maintenance` 完成认知交接：解释调整前后、设计原因、验证证据及下次需求的修改入口。复用已有架构与分析材料，不另建重复事实；不能代替维护者宣称已经理解或接受。

日常验证遵循 [AGENTS.md 的验证范围](../../../AGENTS.md#日常验证范围)，每个 Issue 独立完成以下闭环：

1. 根据 diff、行为变化及真实调用方选出受影响单元和直接相关契约，说明对应测试文件或用例为何需要运行。共享能力变化时核对受影响消费者，不将整个仓库自动列为测试范围。
2. 使用 `pnpm exec vitest run` 加明确的相关测试文件，必要时用 `-t` 缩小用例；实际入口以当前 `package.json` 和测试文件为准。缺少回归覆盖时补最小有效用例，确认选择器确实选中目标测试，不能把零用例当作通过。
3. 仅补充与类型、依赖或架构变化相关的静态检查。相关验证通过后进入记录和提交；新改动、失败或证据暴露的新影响才触发补跑，不重复已通过且未受后续改动影响的验证。
4. 全量回归留给面向 `master` 的 PR 自动化；打包、全套桌面和安装升级验收留给集成／发布阶段，不作为每个 Issue 的默认收尾动作。记录这些本轮未运行的范围，不自动启动全量测试、构建或发布。用户明确要求的专项验收按其要求执行。

记录真实结果：区分接口存在、真实调用、界面接通与业务验收；区分确定性响应、本地测试与在线模型或跨机器验证。失败时保留原因和已完成部分，不用模拟结果替代尚缺的验收。历史全量／桌面报告不是下一次开发的必跑清单。

## 4. 每完成一步，立即同步

在进入下一步或结束本轮前完成以下更新，不能积攒到整个阶段结束：

1. **更新 roadmap。** 同步受影响的阶段状态、能力/缺口和剩余项，以及“上一步成果、当前开发、下一步、限制”。只完成子项时标明部分完成，未验证时保留待验证；未满足整体验收不把阶段标为完成。
2. **追加开发记录。** 在 `design/development-log.md` 顶部记录日期、对应阶段/步骤、完成范围、涉及模块、受影响单元及选择依据、实际验证命令和结果及证据链接、后续自动化待验证项与交接。实际存在时才记录构建或提交标识；引用旧报告须标注为已有证据。
3. **同步受影响说明。** 实际接口、架构或交互改变时更新对应文档；`src/` 注释与类图仍按架构维护流程同步。开发记录保存历史事实，实时进度只维护在 roadmap，避免两份待办互相矛盾。
4. **报告结果。** 说明本步交付、验证与限制，并链接更新后的计划/记录。受阻、暂停或中断同样记录已有成果、原因与恢复条件；不自动重放未知结果操作。

## 5. 入口与权限边界

- `docs/` 解释概念和设计，`design/` 管理开发计划；已有产品规范仍由实际代码显式装配。本 Skill 不加入 `design/skills/` 或产品内置工具清单。
- 路线图不授予提交、推送、发布、操作真实工作区或外部账号的额外权限；按用户现有授权执行。不要为记录进度自动创建周期任务。
- `.agents/skills/cbim-development/SKILL.md`、`.claude/skills/cbim-development/SKILL.md`、`.codex/skills/cbim-development/SKILL.md` 三份内容保持一致。状态和下一步不写死在 Skill 中，始终从 roadmap 读取。
