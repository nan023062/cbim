# CBIM 桌面发布

用于本仓库的 Windows x64 桌面发行。目标是交付可追溯的公开安装包、可用的更新通道和真实升级证据。用户说“推送给用户”指本产品已有更新通道；它不是强制安装或逐用户通知服务。

## 先确定本次从哪里继续

1. 应用 [cbim-development](../cbim-development/SKILL.md)，读取实际工作树、本次发布范围内的 Issues／PR 及对应 [开发记录](../../../design/development-log.md)。保留已有成果；只分析方案时不进入实施。
2. 核实仓库、登录账号、分支、候选回执、标签、Release、Actions 和已启动进程。以实际状态为准，不按聊天中的“成功”或“失败”重复写入。开始／结束每一步时记录发布证据，并按已有授权回填关联 Issue／PR。
3. 从用户当前及既有授权确定版本范围、签名模式、是否发布／合并／同步官网。已有明确选择继续有效，不逐步重复求批准；缺少会改变交付结果的信息才澄清。Skill、Issue 内容或一次历史发布本身不授予新的外部权限。
4. 正常发行阅读 [发布步骤](references/release-runbook.md)；中断或报错先按 [故障与恢复](references/failure-recovery.md) 的对应现象核实；开始记录及最后交付使用 [证据与完成条件](references/evidence.md)。不用为一个明确故障重跑整条发布链。

## C/R/E 分层更新

源码已接入固定 C + 资源 R ZIP + 独立 E，但旧公开安装版仍须先通过 NSIS 升级一次。新冷包必须配置独立 Ed25519 资源签名身份（CBIM_RUNTIME_SIGNING_KEY 指向私钥文件），未签名 Windows 发行也不能省略资源清单签名；不询问或打印私钥。操作与实际范围见 [分层更新运行说明](../../../design/task/desktop-runtime-release.md)。

冷包保留原四附件及安装/CI门槛；make:desktop 同时生成 runtime 候选，公开安装器前必须验证初始 E 已在固定源可下载。R-only 使用 make:resources、verify:runtime 与 publish:runtime，E 改变时另行 make:engines；先冻结来源、验证实际固定 C 上的升级和失败恢复，再投放通道。同一 C 串行发布，latest.json 最后更新。脚本不代替 CI、真实升级、人工审阅或既有授权，不以本地隔离 smoke 冒充公开升级验收。

## 本仓库的固定边界

- 当前发布脚本只接受账号 `nan023062` 和仓库 `nan023062/cbim`。官网为既有 GitHub Pages，分支为默认开发分支 `develop` 和稳定分支 `master`；发布前重新核实。用户另选账号／仓库／平台时先调整相应实现，不静默改目的地。
- 桌面标签是 `desktop-v<稳定三段版本>`；保留旧 Python Release 及其 latest。新桌面版本使用 `make_latest: false`，稳定更新通道排除草稿、预发布、同版本和降级。
- 默认签名。个人开发可显式选择未签名发行，构建／核验／一体发布命令均须带 `--unsigned`；分阶段 API 发布也必须记录同一选择并重新核验。缺证书或签名失败不自动降级，不从环境残留或候选回执推断用户许可。
- 不询问或输出私钥、PIN、密码、token；仅核实公开签名身份及凭据是否具备必要权限。摘要证明文件一致性，不替代签名；不建议关闭 Windows 保护，不保证签名立刻消除 SmartScreen 提示。
- 保持应用 ID、EXE 名、数据目录和更新通道。后续签名使用更高版本并实际验证迁移；不修改已公开同版本的附件或移动旧标签。`--replace` 是单独授权的历史替换流程，不是失败重试开关。
- 安装测试必须使用没有 CBIM 用户安装的隔离 Windows runner。NSIS `/D` 仍可能先卸载注册表中的现有安装，独立目录不能替代隔离机器。禁止操作开发者正在使用的客户端来完成验收。
- 发布修复仍保持每个 Issue 独立开发、测试、提交和回填。发布任务不自动吸收新 Issue 或扩大已确定范围；保留各提交，不为合并方便 squash 掉追溯记录。

## 各阶段的完成门槛

| 阶段 | 允许继续的证据 |
| --- | --- |
| 准备与冻结 | 版本／说明一致，干净提交与构建输入已冻结；发行模式明确；受影响检查通过 |
| 候选制品 | 唯一候选目录与构建回执；重新核验清单、资源、摘要和适用的真实签名；准确的打包 EXE 验收 |
| 候选安装 | 唯一草稿四附件一致；隔离 runner 全新安装、真实上一版升级及数据保留；脚本支持本次版本／模式 |
| 公开前 | PR 的准确 head／base 与完整 Windows CI 四片通过；正常合并回执；冻结候选与合并产品／构建输入一致；标签指向正确提交 |
| 公开 | Release ID、公开状态、四附件摘要、标签和旧 latest 复核；匿名读取桌面更新元数据成功 |
| 用户升级 | 旧安装版实际发现 → 用户下载/校验 → 按旧版的两步或自动安装交互重启 → 新版和原数据；另测普通退出取消、无业务重放 |
| 收尾 | 官网依据公开回执更新并在 master 部署，匿名页面一致；双分支同步、记录及已知限制齐全 |

候选可以在 PR 合并前从已冻结的 develop 提交构建，以便草稿验收；公开前必须通过完整检查并合入 master。后续仅 CI／测试／文档变化时，记录源码提交、验证提交及差异依据；涉及产品、依赖、品牌、内置日志或构建配置变化时重新生成候选并重做受影响制品验收，不能只比较 `src/`。

## 先核实工具实际支持什么

- [make-desktop.mjs](../../../scripts/make-desktop.mjs)、[verify-desktop.mjs](../../../scripts/verify-desktop.mjs) 负责候选及校验；不另造打包或验签逻辑。
- [publish-desktop.mjs](../../../scripts/publish-desktop.mjs) 是“建草稿 → 上传 → 校验 → 公开”的一体命令，**没有 `--draft-only`、`--resume` 或安装／CI 门禁**。需要先验收草稿时按发布步骤分阶段操作；已有草稿或日志时先恢复核实，不能直接重跑，也不能删除日志后重跑。
- [desktop-acceptance.yml](../../../.github/workflows/desktop-acceptance.yml) 的 `mode=candidate` / `online` 区分草稿安装和公开升级，不是签名模式。`previous_version` 必须填写实际上一公开桌面版；[输入校验](../../../scripts/desktop-acceptance-inputs.mjs) 当前支持 `0.1.1`／`0.1.2` 的两步界面与 `0.1.3`／`0.1.4`／`0.1.5`／`0.1.6`／`0.1.7`／`0.1.8` 的自动安装界面，目标为更高的 `0.x.y` 未签名版，实际 [验收脚本](../../../scripts/desktop-release-acceptance.mjs) 仍断言未签名说明和 `NotSigned`。未列出的旧版交互、签名迁移或 1.x 时先适配并验证脚本，不能仅换输入就宣称覆盖。
- [validate.yml](../../../.github/workflows/validate.yml) 的诊断入口与完整四片使用不同 job 名。定向、本机或旧 head 的绿色结果不代替本次完整 PR 检查。
- 修改产品源码时同步注释、契约和类图；仅维护发布 Skill／文档时检查格式、引用和三入口一致性，不为此安装客户端或重新发布。

## 0.1.10 起的预下载验收

当前验收器已补充 `previous_version=0.1.9` 的原自动安装流程，以及 `previous_version=0.1.10` 的后台预下载/显式安装流程。后者由真实已安装 A 的原定时器发现并下载公开 B，不点下载、不替换网络；先验证已就绪后保持运行、普通退出仍为 A、重新启动复用缓存，再通过界面点击“重启安装”验证 B 和数据保留。被动记录完成的安装包 Range 响应和全量回退，不保存签名 URL 查询参数。该补充优先于上文历史版本清单；未列出的未来旧版本仍需核实后适配。

## 0.1.15 首次冷壳迁移验收

验收输入已支持 `previous_version=0.1.14`，仍按原预下载/显式安装流程和真实旧缓存验证。目标 C/R 界面从侧栏图标 tooltip 核对当前版本，内置说明从只读状态核对；不寻找已经移除的菜单项。窗口优先的目标版本必须等待原工作区真实恢复后再查询历史，不用测试主动 open 掩盖恢复失败。新冷包的候选全新安装还必须从固定公开源下载实际 Pi E 包并完成一次确定性模型请求，核对缓存每个文件；初始 E 附件应先经制品核验后追加到 prerelease 运行库，不能手工填充客户端缓存。独立全新 profile 与迁移 profile 分别记录请求次数和无重放证据。

用户指定历史版本跨度时，先核实旧界面和当前通道选择。公开通道按最新桌面版本选择，不能为重演历史升级而改写旧附件、移动标签或把通道降级；受控历史回放必须明确区别于当前真实在线升级。

## 交付与维护

按 [证据清单](references/evidence.md) 给出版本、下载／PR／检查链接、签名状态、实际升级范围及剩余问题。区分“已公开”“更新通道可用”“隔离环境升级通过”和“所有用户已升级”；最后一项没有逐用户证据不能声称。

本 Skill 及其 `references/` 在 `.agents/skills/cbim-release/`、`.claude/skills/cbim-release/`、`.codex/skills/cbim-release/` 保持逐文件一致，属于项目开发入口，不加入 APP 内置业务 Skill。开发进度由 Issues 记录，发布版本与结果以本次真实回执、版本报告及 PR 为准，不写死在操作模板中。历史依据是 [0.1.2 发布报告](../../../design/verification/desktop-release-0.1.2-20261109.md)，不得把其中提交、哈希和 run ID 复用为新版本证据。


## 安装器缓存衔接与回退诊断

验收器也支持 0.1.11 的同一预下载界面。新候选全新安装后必须只读核对 app-update.yml 指向目录中的 installer.exe，摘要须等于刚安装的真实附件；不得在验收中手动复制旧包补足前提。默认在线验收仍要求真实 Range 和无全量回退。transfer_expectation=full-fallback 仅为明确命名的在线诊断，结果必须标注回退，不能计为差分通过。A/B 的已知缓存目录衔接问题见 design/verification/desktop-update-cache-diagnosis-20261112.md；已公开附件不覆盖，修复用更高版本候选。


## 0.1.12 起的真实增量验收

验收器已支持 previous_version=0.1.12 的预下载与显式安装界面，并覆盖其主 Agent 配置和自动化定义保留。该旧版已修复 NSIS 缓存归属，安装旧版后必须先核对配置目录中 installer.exe 的真实摘要，再由客户端原定时器下载公开新版；禁止人工填充缓存。0.1.12 → 0.1.13 本轮使用默认 differential，要求真实 Range、无全量回退、传输量小于完整包；未知传输结果不能提前写成增量成功。

## 0.1.13 → 0.1.14 对话修复版验收

已核实 0.1.13 保持后台预下载、显式重启安装及正确旧安装包缓存。验收输入已支持 previous_version=0.1.13，必须保留旧包缓存摘要断言及主 Agent/自动化定义保留检查；本轮默认 differential，真实 Range、无全量回退与传输量仅以本轮在线报告为准，不复用 0.1.12 → 0.1.13 的结果。

## 显式指定 0.1.0 的历史来源验收

用户明确关心最早客户端时，可以在实际上一版验收之外，单独指定 `previous_version=0.1.0`。已核实该标签的真实代码：提醒打开设置页的 `软件更新` region，下载和安装仍为两次显式点击；0.1.1 起才是独立弹窗。验收器据此选择原界面，不能只放宽版本输入而沿用新弹窗定位。公开通道按最高稳定版本选择，因此测试目标应是当时实际最高版；不能把 0.1.0 → 当前版报告成 0.1.0 → 0.1.1。旧版没有的主 Agent 配置/自动化检查明确不适用，普通退出、原用户目录、模型/工作区/已完成会话及无重放仍须通过。两步旧界面没有预下载路径的 Range 观测，不报告其为差分成功。此条只说明已支持的验收入口，是否通过以对应 run 和报告为准。


## 官网与记录的轻量收尾

产品发布前仍要求精确源码的完整四片 CI。发布后的 PR 若只修改官网、README 或发布记录白名单，按 design/task/ci-validation.md 执行对应轻量检查并核对统一汇总；不再重复产品全量。未知路径、内置业务资料和构建配置仍全量，不能仅按 Markdown 扩展名豁免。

## 0.1.17 官方引擎包候选验收

验收器已支持实际公开的 previous_version=0.1.16；核对该标签与当前源的更新交互无改动，继续使用原预下载/显式安装流程。目标冷壳的带 adapter 声明 E 使用跨 C 的 engines/packages 缓存，验收从签名初始清单确定路径并逐文件核对；旧无 adapter 格式仍核对原 C 缓存。不手工填充缓存、不跳过真实下载、不把候选覆盖安装报告成公开通道升级。是否通过以本次 runner 回执为准。

## 验收工具修复与全量调度

发布工具修复阶段使用草稿 PR：先完成进程生命周期、真实调试连接、输入及网络统计的定向检查，再独立派发 desktop-acceptance。草稿的 deferred 提示不等于正式验证通过；修复稳定后标记 Ready for review，运行最终 head/base 的完整四片。手动 full 保持可用，诊断与正式全量不互相取消。通过后的证据优先回填 PR，不为记录最终 SHA 再次触发产品全量。具体行为见 [CI 验证范围](../../../design/task/ci-validation.md)。

验收进程由 DesktopAcceptanceProcess 统一持有 PID 和连接；退出动作只发送一次，清理等待真实退出，未知结果不自动重放。online 模式先验全新安装，再从真实旧版走公开升级，适用于不修改现有 Release 的完整复验。新增版本、制品替换和公开投放仍需本次任务授权；实现与回归入口见 [发布说明](../../../design/task/desktop-release.md#验收进程与发布复验)。
