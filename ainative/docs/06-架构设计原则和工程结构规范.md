# 架构设计原则和工程结构规范

文档编号：1｜版本：1.3｜日期：2026-11-17｜性质：设计与开发必须遵守的规范

## 1. 目标与适用范围

**控制变化传播，让稳定能力可以长期复用，让工程结构和模块边界可理解、可持续演进。**

本文规定架构设计原则和工程结构规范，覆盖职责划分、依赖方向、公共契约、状态与资源归属、分形结构及架构模型。具体技术栈、业务分层名称和实现目录由项目按这些原则组织。

[05《代码阅读设计及编码规范》](05-代码阅读设计及编码规范.md) 负责源码声明、排版、命名和注释；本文负责架构与工程结构。开发流程、测试执行、交付验收和发布操作由各自的项目流程维护。

分形结构与目录架构模型适用于维护中的产品源码。验证设施、工程脚本、设计资料、标准文档、第三方依赖、构建产物和运行数据不作为产品业务模块，不要求逐目录生成架构类图。

“必须／不得”为约束，“应”为默认做法，“可”为按实际情况选择。目录重命名、接口包装或图形简化不能代替真实的职责与依赖边界。

## 2. 十二条架构原则

### P01：按业务语义和变化原因划分职责

一个封装围绕同一类业务决策组织。判断职责时说明业务对象、变化原因、权威状态和消费者；互不相关的变化不应反复迫使同一封装修改。单一职责不以文件小、方法少或类名统一为依据。

### P02：稳定机制与易变策略分离，遵守开闭原则

通用机制负责可靠执行，业务策略负责条件与选择。变化频率不同的代码应分别封装，通过稳定契约组合；频率依据真实需求和变更原因，不能只数提交次数。

对已经识别的变化，主要通过新实现、策略、适配和装配扩展，减少对稳定核心的连带修改。真实契约变化和核心缺陷修复仍可修改核心，但必须解释原因、兼容代价和影响。不预建未知扩展框架，也不用大量开关假装实现开闭原则。

契约与实现的稳定性分别判断。长期无人使用或长期未改不能证明成熟；缺少证据时标为稳定候选。

### P03：分层明确，依赖单向且无环

先定义职责与允许依赖，再组织目录。层、实际逻辑模块和文件的依赖必须形成有向无环结构，类型引用、重导出及可识别的动态引用同样受约束。

运行返回、回调和数据流应与源码依赖方向分开说明。目录聚合中的双向边不直接证明文件循环，但需要核实是否混合了不同逻辑边界；文件无环也不代表模块已经解耦。

### P04：核心规则不依赖外部实现细节

核心通过自身需要的稳定端口使用存储、模型引擎、网络、文件和平台能力，由外部适配实现并在装配入口连接。UI、数据库、SDK 和供应商差异应尽量停留在对应实现。

端口及其类型不得反向引用具体实现。不得通过全局状态、服务定位器、动态加载或事件转发隐藏依赖；事件也必须明确协议、所有者和生命周期。

### P05：通过小而明确的公共契约协作

调用方只取得完成职责所需的能力，不直接读写其他模块内部状态或依赖其私有执行顺序。契约必须明确参数、返回、身份、权限、空值、错误和兼容边界中容易误解的部分。

公共类型与可序列化数据不得泄露服务实例、存储对象或平台句柄。编译期类型约束与运行时边界校验各有职责，不能互相替代。

### P06：共性抽象必须有业务语义依据

抽象前必须核对真实消费者、共同不变量、变化方向和合法差异，区分重复领域规则、重复技术机制与偶然相似。共用日志或存储不等于属于同一业务职责。

优先使用内聚纯函数、领域封装、组合与接口多态；使用继承时，子类型必须满足基类不变量、前后置条件及错误、取消和资源契约。子类需要禁用父类能力或扩大权限时，应重新评估设计。

允许暂时重复，说明暂不抽象的原因和再评估触发条件。不以重复次数、行数减少或假想消费者自动决定提取，也不强迫不同语义共用万能 Base／Manager。

### P07：状态、事务与资源必须有明确所有者

每份权威状态必须明确维护者、写入入口、生效时点和一致性要求；持久事实、派生视图、缓存与临时上下文分别说明。

事务边界由原子性要求决定，不为拆模块破坏事务内读取或原子提交。共享存储可以保留，暴露给业务的读写能力仍应收窄。进程、锁、连接、队列及临时资源必须有明确创建、取消、释放和恢复责任。

### P08：副作用与失败语义必须进入契约

必须说明操作修改的状态及外部副作用，区分未执行、部分完成、已提交和结果未知。失败、超时、取消、重试、幂等及补偿不能依赖调用方猜测。

调用报错不等于没有执行；未知结果不得未经核实重放。结构调整应保持相关权限、并发、日志／提交顺序、取消和资源释放语义；契约变化必须明确兼容边界及消费者影响。

### P09：模块边界必须支持独立验证

模块应通过自身公开契约独立验证规则、状态和失败语义，所需外部能力可以经明确端口替换。验证一个局部模块不应被迫启动完整应用、读取其他模块私有状态或依赖其他测试的执行顺序。

子模块验证自身功能，父模块验证本层组合。跨模块的联合契约和真实应用协作保持独立的验证边界；不能只因测试文件被移入某个目录，就认定模块已经解耦。

### P10：架构约束必须明确且可核对

允许依赖、公共入口、循环和契约边界必须明确，并能对应到实际代码。职责混杂、接口过宽、依赖过密及共享状态耦合仍需语义判断，不能仅用无环或目录整齐证明架构合理。

无法解析的依赖不能被当作不存在；动态引用必须具有明确的来源、目标和适用边界，不能用运行时装配隐藏反向依赖。

### P11：渐进演进保护稳定边界

架构随真实业务变化逐步收敛，通过稳定契约替换实现，并明确兼容边界。结构重组应保留既有行为与状态语义，避免为了统一形式而扩大对稳定能力的影响。

目录移动、增加接口或建立事件总线本身不算解耦。必须能够说明独立变化被限制在何处、保留了什么稳定能力。抽象失配时允许收缩、拆分或退役，不因既有投入继续扩大错误抽象。

### P12：架构模型必须准确且可理解

源码、注释、契约和架构图必须描述同一实际系统。模型说明设计意图、关键协作、状态归属和重要取舍，帮助维护者定位规则、故障及变化入口。

同一封装的当前说明集中维护，通过链接逐层展开。当前实现、目标设计与未知项明确区分，不能用未来 API、推测的历史动机或无依据的保证补齐模型。

## 3. 工程结构设计

### 3.1 工程结构标准：分形结构与虚拟类

工程按分形结构逐层组织。分形表示各层重复采用“设计意图、组成、边界、协作、下钻入口”的建模方式，不要求各层具有相同数量的目录、类或固定深度。必须遵守以下六项规则：

1. **模块具有独立的设计意图。** 每个模块解决明确的问题，说明自身职责、边界及划分理由，不能只用目录名代替设计。
2. **父模块负责整体组合。** 父层只说明本层有哪些组成、各自承担什么职责以及如何协作；每个直接子模块作为完整的虚拟类参与本层设计，不展开其内部成员。
3. **子模块负责内部设计。** 子模块自己的架构文档解释内部类、关系和实现取舍。父层通过公共契约使用它，不能依赖其内部执行顺序或穿透读写私有状态。
4. **目录嵌套表达组合关系。** 目录层级表达系统如何分解和组合；虚拟类是架构建模抽象，不代表源码嵌套类或继承。目录位置也不能替代真实依赖、状态及生命周期分析。
5. **架构文档即本层设计模型。** 每个维护中的产品源码目录保留一份 `ARCHITECTURE.md`，集中说明设计意图、组成定位和关系，并与实际代码同步。验证设施及项目映射中的排除范围不作为产品业务模块。
6. **阅读按需逐层展开。** 从工程到系统、模块再到源码，当前层应能独立解释本层组合；需要内部细节时沿链接下钻，不能依赖一张展开全工程的巨图才能理解父层。

### 3.2 纯粹容器与实现目录

工程结构区分**组合型父目录**与**实现目录**。组合型父目录采用纯粹容器模式：产品实现下沉到有明确职责的子模块，父目录以子模块目录和 `ARCHITECTURE.md` 表达整体组合。实现目录承载内聚的类、函数、组件或契约；需要继续分解时，沿同一规则形成下一层封装。

父目录中散落的工具、业务逻辑和运行时装配代码，按真实职责归入已有子模块或建立必要的新子模块。例如装配代码可以归入 `assembly`，对外协调可以归入 `facade`；通用工具只有在语义独立且内聚时才归入相应工具模块。不得把所有散落文件机械装进一个 `utils`，也不为达到目录数量或层数要求预建空模块。

运行时组合本身也是实现职责，由明确的装配模块承担；父层的架构模型负责描述这一组合。框架、构建或兼容协议确实要求保留在父目录的固定入口，应在当前架构说明中列明路径、原因和转交对象，保持最小转接，不在入口中继续累积业务实现。测试设施、资源和必要许可证按各自用途保留，不为了目录形式删除。

文件迁移必须保持并核实实际依赖方向。例如父目录的一段代码原本使用 `core`，下沉到 `assembly` 后应如实表达 `assembly → core`；不能因两者变成兄弟目录就反转调用关系或宣称已经解耦。兄弟模块也只能通过允许的公共入口协作，遵守单向依赖及状态归属。

存量混合目录按下文记录当前实现与目标结构的偏差，不能为满足形式要求隐藏现有代码或虚构已经完成的封装。

### 3.3 参考职责与依赖模型

以下是可映射的职责角色，不要求逐项建目录，也不规定所有项目采用相同层数。具体模块及其允许依赖由项目按业务边界明确，最终形成有向无环结构。

| 职责角色 | 负责内容 | 依赖边界 |
| --- | --- | --- |
| 表现层 | 展示、交互、页面本地状态 | 通信契约、公共展示能力；不依赖后端服务或存储实现 |
| 通信边界 | 操作定义、请求／响应、序列化与边界校验 | 独立公开契约及必要纯类型／纯函数；不承载业务编排 |
| 应用编排 | 组织用例、组合领域与跨域能力 | 领域／执行公共契约和所需端口；实现由装配注入 |
| 领域规则 | 业务对象、不变量、领域状态转移 | 本域规则及明确公共契约；跨域依赖必须显式允许且无环 |
| 执行机制 | 授权执行、日志、取消、结算和生命周期 | 必要执行契约及端口；不认识具体业务策略和供应商 SDK |
| 技术适配 | 存储、文件、SDK、网络与平台实现 | 被实现的端口、纯契约与外部库；不反向决定领域规则 |
| 装配入口 | 创建实例、选择实现、注入与应用生命周期 | 可认识要组合的能力；其他模块不得反向导入装配入口 |

规则和机制声明所需能力，适配器实现端口，装配连接二者。公共契约由有权定义语义的边界拥有，不能为消环将不相关职责堆入万能公共层。

### 3.4 测试设施与运行资产的归属

全部测试集中在工程根目录 `tests/`，其中的模块目录镜像源码的仓库相对路径：`src/<模块>/` 对应 `tests/src/<模块>/`，工程工具同理。模块的单元、契约、集成测试及领域夹具归相应镜像目录，父模块组合测试归父层；工程整体的端到端、全局装配和跨工作区生命周期测试直接放在根 `tests/`。测试类型与责任归属分开，集中存放不代表共享状态或合并模块边界。源码模块内不再建立 `unittest/`。 验证设施不参与产品运行时组合，不得编入 Release。

领域夹具随责任模块，通用纯断言和临时目录能力归工程测试支持。验证设施不参与产品运行时组合，产品源码不得依赖测试入口或测试运行器，生产产物不包含测试。

运行资源按真实消费者和使用范围归属，源码、样式、配置与资源保持各自文件；资源目录不虚构代码类。构建产物、缓存和运行数据不作为维护中的源码模块。

## 4. 模块设计标准

本节是模块设计标准。系统、模块、虚拟类和实际类沿相同的封装原则设计：每个封装有独立设计意图，父层负责整体组合，子层负责内部设计；内部实现变化应尽量保持对外契约稳定。

模块的现有契约或架构资料必须能够回答以下问题；小模块可简写，不要求每项独立成文。

| 项目 | 必须明确的内容 |
| --- | --- |
| 设计意图与职责 | 解决什么问题、负责和不负责什么，按哪类业务决策划界及其理由 |
| 本层组成与协作 | 各组成的定位与合作方式；直接子模块作为虚拟类参与组合，内部细节沿子层展开 |
| 入口与依赖 | 公共入口、允许依赖、实际消费者及不得穿透的内部实现 |
| 状态与资源 | 权威数据、写入者、事务、生命周期和释放责任 |
| 行为契约 | 输入输出、权限、副作用、失败、取消、恢复和兼容语义 |
| 稳定与变化 | 稳定能力与证据、策略／适配／装配位置、真实扩展路径 |
| 可验证性与阅读入口 | 自身行为和本层组合的验证边界，内部设计、源码和变化入口 |

职责按业务语义和变化原因划分。逻辑上属于同一功能，不自动意味着必须放进同一个物理模块：表现、领域规则和平台适配仍需遵守各自边界。只有共同职责、契约及状态归属成立时，才将散落实现认定为同一待聚合模块。

原则存在取舍时，必须描述实际不变量与影响，例如模块拆分不能破坏原子性；不能用“更符合分层”笼统覆盖业务正确性。

### 4.1 架构说明的事实要求

架构说明面向维护者，解释当前模块的设计意图、本层类或无类模块的定位及协作关系。需要解释设计的状态与资源责任须核实；不要求列全文件、字段、方法和调用参数，不为文档创建基类或空接口。

本层各个类的定位与关系应清楚；每个直接子模块视为一个虚拟类封装，图中明确标注，父层只表达它的整体职责和协作。内部实现由子模块自己的文档解释，逐层形成工程模型。目录组合不表示代码继承，引用关系不自动证明资源所有权；不按语法声明数量扩张类图。

关系与导航可以辅助生成，设计意图和关键协作仍需对照代码核实。自动更新须保护人工正文，报告无法解析的来源和覆盖限制；生成一致、无环或链接可达均不能单独证明语义正确。架构说明在人工区域维护“设计意图”和“主要组成”，组成表说明本层实际类或必要无类模块的定位并链接源码；纯粹容器说明本层无直接实现，不为填表虚构类。生成区域只维护关系图和子模块导航，不能覆盖人工正文。非标状态和跨目录映射放在独立人工章节，不混入当前组成表或生成图。

### 4.2 非标模块的黑盒封装

对于内部职责混乱、循环依赖严重或暂时无法安全拆分的遗留实现，可以先在上层将其整体建模为一个非标虚拟封装，例如“遗留子系统（非标）”，而不是在文档中虚构已经清晰的内部结构。父层说明它的整体责任、允许入口、外部依赖和已知影响；问题证据及内部细节由该模块自己的架构说明承载。

黑盒化必须具有实际边界：限制新增消费者使用的入口，明确状态和副作用的出口，记录仍然存在的穿透调用及其影响。若隔离尚未完成，应标为“隔离中”或“待隔离”，不能仅靠改名或合并图节点宣称影响已经受控。

非标标记用于暴露和隔离问题，不表示架构达标。内部循环与穿透调用仍属于真实架构事实，不得通过缩小模型或扫描范围将其隐藏。

### 4.3 应然与实然的映射

当一个已明确的逻辑模块实现散落在多个目录时，应建立“逻辑封装—物理实现”的映射，使目标边界和当前差距可被 review：

| 映射内容 | 记录要求 |
| --- | --- |
| 逻辑封装与目标（To-Be） | 名称、设计意图、预期边界；未形成的封装明确标为拟议或待聚合，不能当作现有实际模块 |
| 当前实现（As-Is） | 与该职责相关的真实物理路径、关键符号、当前公共入口及实际归属；无法确认的部分标为未知 |
| 差距与影响 | 实现分散、跨边界调用、状态归属或循环等已有证据，以及对消费者的实际影响 |
| 设计依据 | 指向相关契约和边界取舍，说明尚未形成的封装及预期归属 |

当前 `ARCHITECTURE.md` 在人工说明区域记录必要的非标状态、现状映射与目标边界标记，作为后续重构的依据。映射明细放在负责该逻辑封装的说明中，父层只保留摘要和下钻入口；当前组成表与生成关系图仍描述真实代码，不能将目标模块、未来 API 或不存在的目录伪装成现有组成。

完整目标方案与当前模型分别表达，通过映射说明实际差距。结构变化后同步映射、组成和关系，使读者始终能区分真实边界与预期边界。

### 4.4 渐进式阅读与上下文边界

各层 `ARCHITECTURE.md` 是人和 AI 共用的设计模型。当前层应能解释自身意图、组成和协作，需要内部细节时沿子模块入口下钻；不在父层复制所有内部类和实现。

目录边界帮助限定阅读范围，公共契约与状态责任用于判断哪些协作者必须一并理解。分形导航应保留必要的跨模块关系，不能因简化上下文而隐藏影响设计判断的依赖。
