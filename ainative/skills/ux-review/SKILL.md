# UX 规范检查与整改

用户只要求“检查/评审”时输出带证据的清单；要求“规范化/整改/重构”时，在当前范围内完成修复与复验。用户给出的范围和截止时间优先。此工作流用于仓库开发，不创建项目内的 Agent 技能或后台定时任务。

## 1. 建立可重复的检查场景

从[桌面 UX 规范](../../../design/desktop-ux-spec.md)读取本次涉及的规则和验收场景，再从[模块 UX 索引](../../../design-ux/README.md)查对应 CONFIG 与原型。[框架控件手册](../../../docs/ui-framework.md)用于选择实现。不要把历史截图或当前 CSS 的值当作标准；当原型、规范与用户已确认的行为冲突时，指出具体冲突，保留已确认的业务行为，标记需要同步的文档。

列出页面入口、任务路径、控件角色和关键状态。全局检查从当前路由和弹窗入口建立清单，包括独立窗口；局部检查覆盖改动及共享控件的其他消费者。记录提交、工作区差异、浏览器或 Electron 版本、真实或模拟数据、主题、视口和缩放。按规范组合宽窄窗口、深浅主题、长名称与窄分栏；记录实测组合和跳过原因。

## 2. 比较同角色的实际表现

| 维度 | 怎么验 |
| --- | --- |
| 排版与颜色 | 读取计算样式中的字体栈、字号、字重、行高、前景及实际合成背景；分别比较页标题、正文、辅助文字、代码和指标。计算正文及焦点对比度，对照规范阈值；状态须能通过图形、文字或可访问描述区分。 |
| 尺寸与布局 | 用 DOM 边界测点击区域、图标本体、间距、圆角及两侧留白。同角色横向比较，保留标准、紧凑与触控规格差别。检查内部滚动、浮层裁切和缩放后主要操作可达性；页面没有横向滚动不能单独判为通过。 |
| 工具栏与输入 | 图标按钮复用框架控件，有操作名和 tooltip；用鼠标悬停及键盘聚焦分别打开提示、Esc 关闭。禁用时仍能了解原因；尝试激活并断言业务回调次数为零。区分“按住”“已选中”和业务运行状态。 |
| 交互与可访问性 | 对适用控件验证默认、悬停、按下、焦点、选中、禁用；检查 Enter/Space、页签方向键及 Home/End、弹窗初始焦点和关闭后的焦点返回。验证减弱动效、加载、空、失败与重试路径。无此状态记为“不适用”。 |

优先用正式页面和可重复数据。比如检查“刷新”：在商城、组织树和业务树分别测按钮可点击宽高；依次截图悬停、记录按压后的计算样式，等待过渡结束再对比；同时测试禁用实例。原生窗口、触屏或读屏器未测时单列，不能用模拟环境替代其通过结论。

## 2.1 设计师评审：同一个产品能否只学一次

选两个承担同类任务的页面，在相同数据密度、主题、视口下并排比较。先隐藏鼠标，不读源码，指出页面主题、当前对象/范围、下一步和主要反馈。再核对实现。若必须靠 tooltip 才知道当前项目、价格、危险后果或失败原因，记录为信息缺口。专业感看信息是否可信、操作是否可预测，不以是否模仿某种系统外观评分。

- **层级与秩序**：在常用任务中标出第一眼最醒目的元素。若次要工具、徽标或多个主按钮争抢注意力，说明它们遮蔽了哪个决定。比较标题基线、成组留白、阅读宽度、图标光学重量与数字对齐；允许编辑器、工具栏和阅读区有不同密度。
- **一致与例外**：按“同一意图 → 名称 → 图标 → 位置 → 操作结果 → 返回位置”逐项比对。关注同名动作是否影响不同范围（本机、项目或会话），以及同一状态在首页、详情、对话里是否一致。合理的平台或风险差异要写明理由。
- **持续阅读的舒适度**：用一屏真实长文、密集列表和进度更新做“读一段 → 切详情 → 返回原行 → 继续读”。记录反复找行、滚动跳位、持续闪动、大片高亮、细字低对比或被刷新抢走焦点的具体位置。在深浅、放大字体、减弱动效下重做；降低正文对比度不是减轻疲劳的办法。短时专家观察只能指出负担风险，不能证明长时间使用不会疲劳。

## 2.2 体验走查：第一次会用，第二次省力

把任务写成用户目标，不透露按钮名或正确路径。先以首次使用者身份无提示完成，再以熟悉用户身份连续处理第二个对象。每条关键路径至少插入一次取消、失败或中断后返回；危险动作使用测试数据。记录“当时看到什么 → 预计会发生什么 → 实际发生什么 → 怎样继续”。标出依赖记忆、绕路、重复输入、误触、重复确认和丢失上下文的那一步。步骤增加若用于预防不可逆错误，不作为低效扣分。

| 使用环境 | 实际要做的事 |
| --- | --- |
| Mac 式桌面工作 | 分别用指针和纯键盘完成同一任务。验证菜单锚点、焦点顺序、默认操作、取消与返回；切窗口或调整分栏再回来，仍能找到原对象和草稿。快捷键提示与实际系统一致。 |
| iPhone 式触屏使用 | 不靠悬停或精细指针，单手找到主要操作；验证点击热区及相邻误触、返回、滚动与手势的可见替代入口。打开软键盘、放大文字，检查当前字段、错误和提交按钮是否仍可到达，内容是否避让安全区。没有触屏产品入口时写“不适用”；只有窄屏模拟时注明真机未测。 |

跨端追求相同的对象、术语、结果和恢复能力；允许桌面用锚定菜单、手机用适合触摸的选择面板。不要把平台示例当作新的品牌、字号或配色规范。

**示例任务**：“为当前项目采用一个资源，确认它在用哪个版本，然后回到刚才的位置。”设计师比较卡片与详情对“本机已安装”和“项目正在用”的表达；体验走查者在确认前预判影响、取消一次、模拟一次失败后重试。复验时看能否在操作前说明影响范围、失败后保留选择、返回后找回同一商品，而非只比较两张截图。

## 3. 定级、限时与修复

从复现时起计算以下**建议目标**，不是已承诺的交付日期。按用户期限或项目里程碑调整，写出实际日期、时间和时区；有阻塞时报告依赖、影响及下次核查时间，不静默顺延。

| 优先级 | 判据 | 默认整改目标 |
| --- | --- | --- |
| P0 | 误触危险操作、禁用操作可执行、核心任务无法完成 | 当天处理，修复并复验前阻止发布 |
| P1 | 键盘不可达、状态难以辨认、常用流程或共享控件不一致 | 3 个工作日内完成并复验 |
| P2 | 不妨碍操作的局部排版、间距、提示文案偏差 | 下个迭代内完成；迭代日期未知时标记待排期 |

每项记录：编号、页面/控件、复现步骤、规范依据、期望与实测、优先级、责任模块、目标日期、状态、前后证据。相同根因合并，保留受影响页面清单。只读请求到此交付，不改源码。

整改时先定位来源：跨页一致的问题改主题令牌或 framework-ui，业务状态由逻辑层提供，单页布局改对应模块。不要为通过验收降低对比度目标、弱化禁用语义或隐藏溢出内容。保持原生输入、焦点与表单行为；通用改动至少复验两个不同消费者。

## 4. 关闭条件

在相同数据、主题、视口及动作下复跑，逐项填写“通过 / 失败 / 未测 / 不适用”。运行与改动相关的类型、架构、构建和交互检查。已有浏览器回归可从仓库根目录运行：

- 引擎选择与禁用提示：`node design-ux/review/named-mark-check.cjs`
- 弹窗焦点、Esc 和表单提交：`node design-ux/review/modal-form-check.cjs`

截图、计算样式和命令日志放在忽略的 `test-results/` 下，交付时给出可复核路径。只有原问题复现、修复后的同场景断言通过且共享消费者没有新回归，才关闭该项。最终写明检查覆盖、已修复、未关闭问题及其期限；编译通过不能代替视觉或交互验收。

报告分开写：规范偏差（列规则与实测）、体验障碍（列任务与后果）、待验证假设（列验证办法）。标明证据是测量、专家走查还是真实用户观察；不可把代理走查写作用户研究。先给最影响任务的三项，再列完整清单。判断分歧按用户损失、发生频率及可恢复性排序，不用平均分掩盖关键任务失败。
