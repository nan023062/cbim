# 架构设计的"编译 + 测试"机制（草案）

> **状态：草案（proposal），待讨论。** 本文是一个尚未实现的设计提案，不是当前规则。当前 `module.md` 规范见 [`v1/docs/MODULE-MD-DESIGN.zh-CN.md`](../v1/docs/MODULE-MD-DESIGN.zh-CN.md)。

## 背景与目标

CBIM 的定位不是做成完全 AI-native，而是**尽力提升 AI 产出的正确率，包括架构设计这一层**。AI 不是 100% 可靠是设计前提，不是缺陷。

叶子模块的代码实现之所以可靠度高，是因为它有**客观、即时的护栏**：编译检查（静态、机械可判定）+ 测试用例（可执行的期望）。错误在生成当场就被发现、被喂回去改。

上层父模块的**设计**目前缺这层护栏。它的错误（边界切错、抽象配不上需求）**反馈慢、影响半径大**——往往要等几个月后新需求斜着切进来才暴露。

**本草案的目标**：给上层父模块的设计，装上和叶子代码同等的"编译 + 测试 + 改错环"，把分解错误的反馈从"运行期/几个月后"拉到"生成当场"。

---

## 核心思路：把两个词在架构层翻译清楚

| 代码层 | 架构层（本草案要补的） |
|--------|----------------------|
| 编译器（静态、机械判定） | 对 `module.md` 的图 + 代码做静态检查 |
| 测试用例（可执行的期望） | 架构适应度函数 + 场景路由预检 + 契约一致性 |
| 按编译错误自我修复 | 生成 → 检查 → 喂回错误 → 改 → 重跑，直到全绿 |

---

## 第一层：编译器（静态、机械可判定的检查）

这些检查不需要理解语义，纯在 `module.md` 的依赖图 + 代码上跑。CBIM 已有种子（`audit_run` / `dna_tree` / `dna_fission` / `arch_governance`），把它补全：

| 检查 | 代码层的对应物 |
|------|--------------|
| **无环（DAG）** | 编译期循环依赖报错（已有 `dna_tree`） |
| **引用完整性** | `dependencies` 指向的模块真实存在 = 符号解析 |
| **图↔注册表一致** | 父图每个 `<<module>>` 节点 = 磁盘真实子模块；反之无遗漏 = "声明 vs 定义"对账 |
| **图↔代码一致** | 声明的依赖边 = 代码实际 import 边；**未声明耦合 = error，声明未用 = warn** = 链接器查未定义/未用符号 |
| **单向 / 分层** | 子模块不越界上调父层之外 |
| **粒度 lint** | 退化的单子节点、叶子画了组件框（应升为父模块）、被全员依赖的"上帝模块" |
| **stereotype 正确** | 父用 `<<module>>`、叶用代码级类（`arch_governance` 已部分覆盖） |

这一层能做到和编译器同级：**客观、即时、可重复**。

---

## 第二层：测试用例（可执行的意图断言）

测试的本质是"先写好、能自动判定的期望"。架构层有三种可落地形态。

### 1. 架构适应度函数（fitness functions）

把架构师的意图写成**图查询断言**，纳入治理 / CI，可回归：

```
- "ui 永不直接依赖 db，只能经 service"   → 断言图中无 ui→db 直达路径
- "combat.skill 内部不可被外部 import，只能走它的 contract"
- "任意 feature 到 core 的依赖深度 ≤ 3"
- "service/ 之外的模块，被依赖数 ≤ N"     → 机械地掐死上帝模块
```

这就是**架构的单元测试**：改了 `module.md` 重跑一遍，退化立刻变红。

### 2. 场景路由预检（最高杠杆的一招）

架构师写父模块时，**先声明关键跨模块场景**：

```
场景：玩家放技能 → 施加 buff → 刷新属性
```

然后机械检查：**在当前声明的依赖图 + 单向规则下，是否存在一条合法路径实现这个场景？**

切错边界的后果，就是某个必需交互**无路可走，或被迫成环**——预检当场 fail。

**这把"分解对不对"从"几个月后新需求暴露"提前到了生成期**，正是补上层设计那条最慢的反馈。

### 3. 契约一致性

子模块的 `contract.md` 当"类型签名"，父模块的组合按子契约做"类型检查"：父假设子暴露 X，而子契约里没有 X → fail。

## 第三层：生成期闭环（compile-error 反馈环）

光有检查不够，要像 IDE 红线一样**喂回去让它改**：

```
架构师生成 module.md
  → 引擎跑：静态检查 + fitness + 场景路由 + 契约一致性
  → 有错 → 把错误清单喂回架构师 → 改 → 重跑
  → 全绿才允许定稿
```

和"按编译错误自我修复代码"一模一样，只是对象换成了设计。再叠两招提概率：

- **多采样 + 评委**：生成 N 个分解候选，各跑 fitness，选"通过最多 + 最简"的那个。
- **对抗式反例**：让评审官 agent 专门构造一个"未来需求"去戳穿边界——相当于给设计写**反例测试**。

---

## 在 CBIM 的落地位置（初步）

- **静态检查 + fitness + 场景路由** → 新增一类 audit check（与现有 `dna_tree` / `dna_fission` 并列），可由 `audit_run` 调用。
- **场景声明** → 在 `module.md` 父模块正文里增加一个可选小节（如"## 关键场景"），或放进 `.dna/` 下的独立文件，供预检读取。
- **生成期 gate** → 架构师定稿 `module.md` 前，由执行循环 / `arch_modules` 技能调用上述检查作为门禁，未过则带错误清单回炉。
- **fitness 函数本身** → 以可注册的检查项形式存放（项目可自定义自己的架构约束），随项目演进增减。

---

## 诚实的边界

- 静态检查 + fitness + 场景路由，能把**很大一块**"设计正确性"从**主观→客观**、从**晚反馈→即时**，大幅提升架构设计的正确率。
- 但残余继续上推，机械化不掉，留给人 / 评审官：
  - **场景列全了吗？**（声明的场景集合本身可能不完整）
  - **这个抽象配不配领域的本质？**（语义层面的"对不对"）
- 这与 CBIM 的一贯立场一致：**不是做成 100% AI-native，而是把 AI 产出（含架构）的正确率尽力顶高**；残余风险靠"多层独立、各自不完美的过滤器"（生成 → 自动治理 → 对抗式评审 → 人）一层层乘小，但永远不到零。

## 待讨论的开放问题

1. **场景声明的形态**：写进 `module.md` 正文，还是独立文件？如何保持与"无历史、高密度"的规范不冲突？
2. **fitness 函数的表达方式**：用什么 DSL / 查询语法写架构断言？是否允许项目自定义、如何注册？
3. **场景路由的判定算法**：图上路径搜索如何定义"合法路径"（是否允许经过哪些边、单向约束如何参与）？
4. **gate 的强度**：哪些检查是 error（阻断定稿）、哪些是 warn（提示但放行）？
5. **与治理循环的分工**：哪些检查放在生成期 gate（即时），哪些放在 Dream Tick 周期治理（回归）？
6. **成本**：多采样 + 评委 + 对抗反例的 token 成本，与正确率提升的权衡。
