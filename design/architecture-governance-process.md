# 架构治理规范与治理流程

文档编号：2｜版本：1.0｜日期：2026-11-10｜性质：架构治理必须执行的规范

前置规范：[文档 1：通用项目架构设计规范与原则](project-architecture-standard.md)。任何治理结论和整改实现都必须满足文档 1；本文不重新定义或放宽其设计约束。

## 1. 目标、范围与责任

治理的目标是依据真实变化和影响，发现职责、依赖、状态与抽象的失配，通过可审阅的小步迁移减少变化传播，并保障维护者持续理解系统。

通用流程适用于新边界设计、既有架构评估、依赖整改、公共能力提炼和抽象退出，不绑定具体仓库、技术栈或 Agent 框架。项目须提供文档 1 要求的边界、契约、验证及责任映射。附录 A 是 CBIM 的具体映射及 G01–G09 方案基线，不是通用项目必须照搬的目录或任务。

架构治理 Skill 必须在工作开始前读取文档 1 和本文，并按第 3 节流程执行。小改动可合并说明，已核实且未变化的上下文可复用，但不得跳过对应判断和证据。只读分析执行至可 review 的方案与记录，不自动进入代码实施。

| 责任 | 工作与边界 |
| --- | --- |
| 需求／决策负责人 | 明确目标、业务取舍、授权与兼容承诺；决定正式规则是否生效 |
| 开发／治理执行者 | 调查事实、提出方案、按授权实施、验证并交付完整证据 |
| 维护／review 责任人 | 核对设计原则、消费者影响、契约与认知资料；反馈实际审阅结论 |
| 自动化检查 | 执行已经约定的规则，报告可复核结果；不替代业务判断或人工授权 |

这些是责任角色，不要求增加人员或创建多个 Agent。同一人可承担多项责任，记录中仍应区分事实产出、检查结果和决策。已经授权的范围不逐步重复审批；超出范围、改变兼容承诺或触及另行约定的操作时才重新决策。

## 2. 治理触发与检查分档

检查的触发范围与结果处置分别定义，不把“轻量检查”统一解释为“不阻断”。

| 档位 | 触发与范围 | 输出及处置 |
| --- | --- | --- |
| C1：变更检查 | 每个变更依据实际影响选择相关单元、契约与静态检查；纯文档只检查事实和引用 | 已约定的正确性、依赖和安全约束失败时，本切片不能报通过；新增复杂度等启发式发现进入候选，不自动重构 |
| C2：专题巡检 | 跨模块变更积累、重复问题、抽象失配等证据触发；周期安排由项目另行约定 | 只读被检查资产，允许保存报告；记录版本、范围、证据、影响和待核实项，不直接改源码、正式知识或生效规则 |
| C3：专项治理 | 已识别的系统性边界问题，进入明确授权的整改范围后实施 | 形成方案和迁移切片，逐片验证并 review；超出授权或兼容承诺变化时重新决策，不对已授权步骤重复审批 |

三个档位不替代现有 PR、集成与发布检查，也不自动建立定时任务。C2 发现既有硬约束违规时应按现有流程处理，不能以巡检只读为由将其降为可忽略建议。

## 3. 标准治理流程

### S1：界定目标、基线与授权

读取任务来源、项目约束、当前工作区和已有记录，明确本次是分析、方案维护还是实施。记录版本／diff、范围、业务目标、必须保留的行为和已知限制；旧方案或历史“下一步”不自动成为当前任务。

**输出：** 来源、基线、边界与授权说明。输入缺失时先从已有资料核实；影响后续决策的真实业务歧义再集中澄清。

### S2：核实架构与问题证据

依据文档 1，从受影响的真实入口沿调用链读到契约、状态变化、副作用及结果返回，核对消费者与失败／恢复路径。将问题定位到职责、公共契约、依赖、状态或生命周期，不仅统计文件或画目录图。

记录已核实事实、推断、未知和阅读范围。相似度、复杂度或重复次数只作为线索；无法证明的问题不能直接写成确定缺陷。

**输出：** 有文件／符号或对应专业证据的问题描述、适用原则、实际影响和继续维持现状的成本。未发现值得治理的问题时，记录依据并转 S7，不为完成流程制造重构。

### S3：分析影响、分级并排序

填写第 4 节的变更原因和影响记录，核对公共契约、状态所有权、权限、副作用、取消／恢复、配置及数据格式；追踪实际受影响消费者。依赖图差异可为空，但不能据此认定没有行为影响。

选择 C1／C2／C3 工作范围与 L0–L3 认知等级；两者分别描述检查性质和交付深度，不能互相替代。先依据实际正确性、安全和一致性风险排序，再考虑依赖前置、影响范围、收益与迁移成本。

治理计划可采用 P0（前置）、P1（核心）、P2（外围／收口）；该分级不代表故障严重性。现有硬约束继续执行，不因排入后期而允许新增违规。

**输出：** 影响证据、消费者、分级依据、优先级与前置关系，以及拟选验证范围。

### S4：形成可审阅的方案与切片

比较保留现状与有证据的调整；明确保护的稳定能力、变化点、职责与状态归属、公共入口、合法差异和兼容代价。说明新增一次真实同类需求需要修改哪里，避免只有目录调整而没有变化隔离。

将方案拆为可独立验证、review 和提交的切片；列明每片目标、前置、验收、消费者迁移和回退条件。新规则先作为候选，不能借方案评审自动激活。

**输出：** 具体、可 review 的方案及整改项。仅获分析授权时，到此交付方案并执行 S7 的记录部分；已有实施授权时继续 S5。需要新的决策时，先交付具体方案，不让负责人批准空泛行动。

### S5：按切片迁移真实消费者

先保留或补齐相关行为依据，再引入边界、迁移一个真实消费者，逐步处理其他实际使用方。保留权限、事务、幂等、未知结果、取消、结算和资源释放等相关语义。

结构整理与行为变化分别说明；抽象替换执行第 4.3 节生命周期。只有旧入口的实际使用与兼容需求均核实后才清理，不能只检查静态 import。

**输出：** 可定位的实现 diff、消费者迁移事实和剩余范围。发现新的契约或业务歧义时回到 S2–S4 调整受影响部分，不无依据扩展整轮重构。

### S6：按影响验证并同步维护资料

根据 S3 的证据选择单元、消费者和相关静态检查，执行前简述理由；失败时保留结果、修正相关问题并只补跑受影响范围。验证通过后收尾，不为保险重复检查或自动扩大为全仓测试。

同步受影响源码注释、契约、架构资料及修改入口；只读方案只核对事实与引用，不冒充源码或运行验证。纯文档／Skill 修改按文档检查完成，不运行产品测试。

**输出：** 实际命令／方法、结果、失败记录、未运行范围，以及与代码一致的维护资料。是否需要后续集成／发布验收按真实影响记录，不将日常单元通过等同于这些验收通过。

### S7：交付 review、归档结论并反馈

交付完整 diff、阅读顺序、职责和状态变化、取舍、验证证据及下一次修改入口。保存四问答案，第五问形成规则候选或明确“无”。按授权更新项目现有任务与历史记录，不另建实时进度复本。

分别记录实现、验证、人工 review、合并及发布状态；尚未审阅不能写成已接受。规则候选仅经明确批准后晋升，并记录适用范围与来源。

**输出：** 可接手的交付、真实完成范围和剩余限制。后续出现新需求、抽象失配或重复缺陷时带新证据回到 S1–S3，不自动启动定期扫描或下一项整改。

### 流程中的分支与回退

- **只读发现／方案：** S1–S4 → S7 的报告归档，不执行 S5；S6 仅核对实际产出的资料。
- **范围内实施：** S1–S4 → S5 → S6 → S7；可以引用已核实材料，不逐步骤重复审批。
- **没有治理收益：** 在 S2 或 S4 保留“不调整”的依据，进入记录，不强造抽象。
- **验证失败或迁移失配：** 回到相关 S2–S5，修正后验证实际受影响范围；必要时按已确定条件回退并保留证据。
- **超出授权或兼容承诺：** 在边界前停止该动作，交付调整方案取得所需决策；独立且已授权的工作可以继续。

## 4. 治理记录与配套机制

记录可复用已有任务、决策与开发记录，互相引用；不要求新增服务、数据库或平行台账。以下字段是规范语义，不表示产品已经实现自动推导或 Schema。

### 4.1 变更原因与影响证据

| 字段 | 最小要求 |
| --- | --- |
| `change_reason` | 为什么现在修改；`kind` 使用业务变化、缺陷修复、边界治理、依赖演进、说明维护等原因分类，复合原因可分条记录 |
| `source` | 需求、Issue、缺陷、调用证据或用户直接要求；没有工单时如实注明 |
| `baseline` | 分析版本和实际 diff 范围；未提交时标明工作区差异 |
| `layers` / `scope` | 引用项目实际分层和受影响模块，允许多值；不固定为通用五层 |
| `impact` | 行为、公共契约、状态所有权、副作用、恢复、配置和数据格式的实际变化；包括受影响消费者与未知项 |
| `stable_boundary` | 要保护的稳定能力、原有不变量和允许改变的行为 |
| `verification` | 选取单元的依据、实际命令／方法、结果、证据和未覆盖范围 |
| `cognition_level` | 认知交付等级与判断依据，不仅由 `kind` 或文件数量决定 |

依赖图 diff 是影响证据之一。即使导入关系未变，返回语义、权限或取消行为变化仍可能影响消费者；直接上下游只是起点，应追踪到能够解释影响停止的位置。

### 4.2 L0–L3 认知交付分级

| 等级 | 适用条件 | 必要交付 |
| --- | --- | --- |
| L0 | 仅文字、格式或不影响行为与契约的调整 | 在已有记录中说明依据；不增加独立认知材料，保留原 review 要求 |
| L1 | 局部行为变化，现有职责、公共契约和状态归属保持 | 修改入口、局部调用链、行为差异、选取验证及未覆盖范围 |
| L2 | 公共契约、跨模块协作、状态所有权、权限或失败／取消／恢复语义变化 | 前后边界、消费者、关键路径、兼容／迁移安排及验证证据 |
| L3 | 全局分层或稳定公共核心调整，关键执行／安全／事务边界变化，或有破坏性影响的抽象退役 | L2 材料，加方案取舍、分步迁移与回退、代表性失败场景、维护者 review 结论 |

多条件命中取较高等级。事实不足时标为待判断，并暂按较高的合理影响准备材料；不凭未知自动跑全量或新增审批。等级影响解释深度，不免除源码注释、类图和原有审阅义务。交付材料不代表维护者已经理解或接受。

### 4.3 抽象退出与迁移

正常路径为 `active → deprecated → migrating → retired`。

| 状态 | 进入条件与完成证据 |
| --- | --- |
| `active` | 职责、适用范围、公共契约和实际消费者明确 |
| `deprecated` | 已确认失配原因、替代方向、兼容承诺与授权范围；不再新增旧用法 |
| `migrating` | 迁移方案可执行，消费者和回退条件已列出；按切片验证并记录剩余使用方 |
| `retired` | 在已声明的支持范围内，需迁移的消费者清零，兼容承诺已满足，旧入口清理及相关验证完成 |

消费者包括静态引用、注册／动态装配、配置、脚本、历史数据与外部调用方。`consumers_remaining == 0` 必须附统计范围和证据；未知消费者不能当成零，历史数据仍需兼容读取时也不能只凭源码零引用删除路径。

迁移失败时停止该切片，保留失败证据并按已批准的回退条件恢复；实际状态与剩余消费者重新核实后再推进，不自动标为退役。批准迁移范围后，范围内状态随证据更新；超出范围、改变兼容承诺或触及另行约定的退役操作时才重新决策。

### 4.4 四问归档与第五问候选

| 问题 | 回答必须包含 |
| --- | --- |
| Q1：保护了哪部分稳定能力？ | 契约／模块、不变量、稳定依据；尚属候选时明确标注 |
| Q2：把哪类变化限制在了哪里？ | 业务变化原因、策略／适配位置、装配点；仍需修改核心的原因 |
| Q3：为什么可以只运行这些验证？ | 行为／契约差异、消费者、依赖或状态流证据、选取单元及实际结果；不强制每次必须有非空依赖图 diff |
| Q4：维护者下一次应该从哪里修改？ | 契约、实现、装配及测试的阅读／修改入口 |
| Q5：有什么经验值得成为后续规则？ | 候选规则、适用与不适用范围、证据、收益和代价；无可复用结论时明确填“无” |

规则候选与已生效规则分开记录。晋升需明确的人类批准及生效范围，不因候选归档、测试通过或无人反对而自动生效。首期使用已有记录即可；后续若统计，分别统计候选、已生效及无候选，不以数量激励制造抽象。

## 5. 验收标准

### 5.1 每个源码整改切片的完成定义

以下条件应同时满足，不能用测试通过代替其他项：

- **范围可核对：** Issue／用户授权、基线、目标、允许改变行为和未解决范围明确。
- **边界有证据：** 职责、公共入口、状态所有者和依赖方向与实现一致；迁移消费者和旧出口处理可追溯。
- **行为被验证：** 相关正常、失败及实际涉及的取消／并发／恢复语义有证据；未知结果保留为未知。
- **检查未放宽：** 适用的依赖和静态约束通过；没有通过删除断言、宽泛豁免或零用例制造通过。
- **资料同步：** 更新受影响源码文件头、关键接口／字段说明、契约和项目规定的目录架构文档；关系未变时更新真实职责或行为，不虚构连线。
- **认知可交接：** 四问有回答，第五问有候选或明确“无”；完整 diff、关键阅读顺序和下一次修改入口可获取。
- **结果如实记录：** 写明实际命令、选取依据、结果与未运行范围；实现完成、验证通过、人工 review、合并和发布分别陈述。

部分消费者尚未迁移时，只报告本切片完成，不提前宣布整个治理项或任务完成。方案中的目标验收不能冒充已执行结果。

### 5.2 分析与规范维护的完成定义

仅分析时，完成范围、真实证据、原则对照、影响、优先级、可审阅方案及未核实边界即交付，不要求为证明方案而重构代码。仅维护文档或 Skill 时，规范分工明确、强制引用可读、流程无冲突、链接及多入口一致即可完成资料验证。

上述通过不等于架构整改已经完成，也不证明自动化或模型执行效果已获验证。需要后续实施的事项按项目任务系统及授权处理。

### 5.3 成效复核

在真实后续需求中比较：哪些稳定实现被连带修改、修改落在哪些边界、相关测试范围为何增减、维护者能否定位规则和故障、旧入口是否真正退出。基线和比较口径保持一致，变化原因不足时注明未知。

不设置脱离业务的“减少多少文件／测试／依赖边”指标；不通过压缩验证范围取得表面改善。发现抽象不再适用时收缩、拆分或退役，形成下一次决策的证据。

## 6. 可复用的治理记录模板

以下模板可直接缩写后用于 Issue 或开发记录；能引用已有证据时不重复粘贴长篇资料。

```text
来源与基线：Issue／用户直接要求；版本或 diff 范围
目标与变化原因：业务目的；change_reason；允许改变的行为
边界与归属：layers / scope；公共入口；状态、事务及资源所有者
稳定能力：必须保留的不变量、稳定证据或候选说明
影响证据：行为／契约差异；消费者；依赖／配置／数据变化；未知项
迁移安排：本切片范围；兼容／回退条件；旧入口与剩余消费者
认知等级：L0–L3 与依据；阅读顺序、取舍和下次修改入口
验证：选取理由；实际命令／方法、结果和证据；未运行范围
四问：Q1 稳定能力；Q2 变化位置；Q3 验证依据；Q4 修改入口
规则候选：Q5 候选及适用边界，或“无”；候选与生效状态分开
交付事实：代码与资料；人工 review 结果；已完成范围及剩余限制
```

记录保存实际事实；当前实现、任务进度和历史证据分别在项目规定的位置维护。候选规则与生效规则分别可追溯，统计工具可待有真实需求后再实现。

### A.2 CBIM 当前基线与目标差距

当前 [依赖检查器](../scripts/check-dependencies.mjs) 以物理层约束如下；表内允许同层引用不代表同层内部已经形成清晰的逻辑模块。

| 当前层 | 检查器允许的依赖 |
| --- | --- |
| `backend/core` | 自身 |
| `backend/scheduler-engine` | 自身、`backend/core` |
| `backend/bootstrap` | 自身、`backend/updater`、`backend/main`；计算式固定入口映射真实源码边 |
| `backend/main` | 自身、`backend/scheduler-engine`、`backend/core`、`backend/updater`、`bridge/contracts` |
| `backend/updater` | 自身、`bridge/contracts` |
| `bridge/contracts` | 自身、`backend/core` |
| `bridge/preload` | 自身、`bridge/contracts` |
| `frontend` | 自身、`bridge/contracts` |

源码约定进一步要求 Bridge 只暴露 Core 的公开契约与纯函数。当前层规则对同层模块、Core 内纯规则与 SDK 适配的区分仍较粗，因此 G01 需要补充逻辑边界与公共入口检查。已有文件循环检测继续保留，不用新规则放宽既有约束。

目前 `core/brain` 下同时存在引擎契约及 Pi、Claude、Codex 实现。`main` 同时承担装配和多类服务；这些物理归属不能直接当成目标职责划分。G03–G09 逐片确定和迁移真实边界，而非直接按表移动目录。

本次核对范围为现行协作规范、整体架构、依赖脚本、验证入口及代表性源码入口；复用同一基线上的既有分析，没有重新完成全仓逐行审计或运行依赖检查。目录聚合中的双向箭头也不能直接当作文件循环证据。

### A.3 CBIM 按影响选择验证

| 变化 | 本步验证 | 边界 |
| --- | --- | --- |
| 纯文档／Skill | 事实、格式、本地引用及被修改的多入口一致性 | 不运行产品测试、类型检查或构建 |
| 业务行为、状态或交互 | `pnpm exec vitest run` 加明确测试文件，必要时加 `-t` | 覆盖实际受影响消费者；不无参数启动全仓 |
| 类型或公共接口 | 需要编译验证时执行 `pnpm typecheck` | 不连带扩大行为测试范围 |
| 导入、路径或模块边界 | `pnpm check:dependencies` | 同时检查类图时改用下一项，不重复执行 |
| 源码结构及受影响类图 | `pnpm check:architecture` | 已包含依赖检查；纯说明文字仍只核对事实与引用 |
| 检测器或分层规则 | 对应 `tests/dependencies.test.ts`／`tests/layer-boundaries.test.ts` | 根据实际修改选择，不随每个 Issue 固定重复运行 |

执行前说明测试选择与影响证据；通过后记录并收尾。只有新改动、失败或新增影响证据才补跑相关范围。核心自身及其契约、配置和实际依赖均未受影响时，不重复无关验证；公共语义变化则核对受影响消费者。

完整回归由面向 `master` 的 [PR 验证](../.github/workflows/validate.yml) 执行；打包、桌面、安装升级与发布验收由后续集成／发布承担。日常局部通过不代表这些阶段通过，也不绕过现有检查。用户明确要求的专项验收按其范围执行。

### A.4 CBIM 整改项与优先级

P0 为治理前置，P1 为核心整改，P2 为外围完善与收口；它们不是缺陷严重程度。发现实际安全、正确性或数据一致性问题时，按真实风险重新排序。

| 编号 | 优先级 | 整改项 | 前置关系 |
| --- | --- | --- | --- |
| G01 | P0 | 逻辑分层、模块归属与允许依赖 | 无 |
| G02 | P0 | 局部测试与完整应用装配隔离 | 可独立准备；试点与 G03 配合 |
| G03 | P1 | 知识、团队、工作区的契约与查询编排 | G01、G02 的相关切片 |
| G04 | P1 | 共享调度状态与存储接口收窄 | G01、G02；参考 G03 的边界组织方式 |
| G05 | P1 | 运行循环与具体业务能力分离 | G01、G02 |
| G06 | P1 | 引擎 SDK、进程与平台适配隔离 | G01、G05 中相关引擎契约确定 |
| G07 | P2 | 有类型约束的 IPC 操作契约 | G01；优先迁移 G03 已理清的查询接口 |
| G08 | P2 | 前端业务编排与公共展示分离 | G01、G02；通信变化协调 G07 |
| G09 | P2 | 剩余依赖治理与检查覆盖 | 随各项迁移推进，最后核对完整覆盖 |

每项均按“目标行为、最小切片、证据验收”拆分，不将整组目录移动作为一个不可审阅的大提交。以下验收均为待实施要求。

#### G01：确定逻辑分层、模块归属与允许依赖

- **整改内容：** 为维护中的逻辑模块确定职责、公共入口、状态所有者和允许依赖；区分底层契约与上层编排。将第 2 节检查分档及第 4 节记录、认知规则映射到现有流程与记录位置。
- **交付物：** 有源码依据的模块依赖矩阵、公共入口与状态归属、问题证据和迁移方向；已迁移边界对应可执行规则。实时处理进度只写 Issue。
- **验收标准：** 所有纳入治理的维护模块能定位归属；每条被认定的反向依赖有实际文件／符号和处理方向；类型依赖纳入规则。新边界随迁移启用，不通过宽泛白名单维持旧耦合。
- **验证方式：** 对照真实导入、公共入口与调用链；修改检测器时验证合法依赖、反向依赖、类型环、长环、自引用和漏检场景。
- **阅读入口：** [整体架构](../src/ARCHITECTURE.md)、[依赖检查器](../scripts/check-dependencies.mjs)。

#### G02：隔离局部测试与完整应用装配

- **整改内容：** 将纯数据构造、领域测试环境和完整 `Application` fixture 分离。先迁移 G03 所需测试，再随其他整改扩展。
- **交付物：** 职责明确的辅助模块及已迁移测试；说明哪些是纯规则、契约协作或完整应用测试。
- **验收标准：** 纯规则测试引用辅助函数不再传递加载完整应用；事务、恢复和引擎集成仍保留真实协作验证。现有测试断言及覆盖意图不因拆分被弱化。
- **验证方式：** 只运行迁移测试及实际受影响消费者，核对纯辅助模块导入关系；选择器必须选中目标用例，零用例不能当通过。
- **阅读入口：** [现有测试辅助](../tests/helpers.ts)、[应用装配](../src/backend/main/assembly/application.ts)。

#### G03：拆清知识、团队、工作区之间的契约与查询编排

- **整改内容：** 分离快照契约、领域视图与 `KnowledgeQueries` 查询编排。领域模型依赖必要数据契约，跨域组合由明确的查询编排负责。
- **交付物：** 契约归属、查询组合入口、迁移消费者和严格边界规则。这是建议的第一个源码治理切片。
- **验收标准：** 三组逻辑模块依赖单向；查询结果、刷新幂等和错误语义保持；反向引用能被检查拒绝，不仅是现有文件恰好无环。
- **验证方式：** 团队模型、知识查询／刷新及实际受影响的工具调用方；新增边界规则对应的检测器回归。
- **阅读入口：** [KnowledgeQueries](../src/backend/core/knowledge/knowledge-queries.ts)、[团队模型](../src/backend/core/knowledge/read-models/team.ts)、[工作区模型](../src/backend/core/knowledge/read-models/workspace.ts)。

#### G04：收窄共享调度状态与存储接口

- **整改内容：** 围绕岗位、模块责任、知识来源、执行和预算划分实际需要的读写端口。先迁移一个只读场景，再迁移已有独立提交语义的写入。
- **交付物：** 各领域最小端口、状态／事务归属和真实消费者迁移；底层可以继续共享日志或存储。
- **验收标准：** 迁移后的业务服务不再取得无关状态和修改能力；原事务内读取、原子提交、并发冲突、幂等与回执语义保留。跨域原子命令不得被拆成缺乏一致性保护的多次写入。
- **验证方式：** 被迁移领域、事务投影、重放、冲突和实际参与的跨域命令；按真实影响选择消费者。
- **阅读入口：** [持久化边界](../src/backend/main/ARCHITECTURE.md)、[执行服务边界](../src/backend/scheduler-engine/CONTRACT.md)。

#### G05：分离运行循环与具体业务能力

- **整改内容：** 将求助、检查点、产物采集、验证等业务装配逐项移出通用循环，收窄 `EngineContext`，用明确工具和生命周期契约组合。
- **交付物：** 一次只迁移一种能力，说明运行机制、业务策略与装配各自负责什么。
- **验收标准：** 在既有契约范围内新增同类能力主要修改业务实现与装配；通用循环不新增对应业务分支。授权、日志先落盘、取消、结算和资源释放的语义保持，责任不能在提取过程中丢失。
- **验证方式：** 本次能力、相关运行机制及实际受影响引擎入口，重点覆盖失败、停止顺序与资源释放。
- **阅读入口：** [运行循环](../src/backend/scheduler-engine/assembly/loop-engine.ts)、[引擎契约](../src/backend/core/execution/types.ts)、[工具边界](../src/backend/scheduler-engine/tools/CONTRACT.md)。

#### G06：隔离引擎 SDK、进程与平台适配

- **整改内容：** 以 `AgentEngine` 等明确契约隔离 Pi、Claude、Codex 的 SDK、进程和协议细节，由装配入口选择实现。
- **交付物：** 稳定执行契约、具体适配边界、装配迁移及兼容说明；契约演进与目录调整分别解释。
- **验收标准：** 核心规则和执行机制不导入具体适配器，类型引用也符合约束；供应商差异局限于实现。各实现满足共同生命周期要求，合法的供应商差异显式保留，不伪造一致能力。
- **验证方式：** 每次迁移引擎的契约、启动／停止／恢复及加载入口；真实打包和安装验收留给集成／发布阶段。
- **阅读入口：** [引擎契约与实现边界](../src/backend/core/execution/CONTRACT.md)、[应用装配](../src/backend/main/assembly/application.ts)。

#### G07：建立有类型约束的 IPC 操作契约

- **整改内容：** 建立操作名称到请求和响应的类型映射，逐组迁移 `Bridge.call`、安全桥与主进程分发，保留运行时输入校验。
- **交付物：** 每组操作的公开契约、调用方与处理方迁移、类型及运行时边界验证。
- **验收标准：** 已迁移操作的错误名称、请求参数和响应使用受类型检查约束；非法身份、错误输入在运行时仍被拒绝。公开契约不泄露后端服务实现，类型正确不等于运行输入可信。
- **验证方式：** 类型检查、该操作的输入／身份／错误边界及实际受影响前端消费者。
- **阅读入口：** [Bridge 契约](../src/bridge/contracts/CONTRACT.md)、[Preload](../src/bridge/preload/preload.ts)。

#### G08：拆清前端业务编排与公共展示能力

- **整改内容：** 将会话与任务共用的消息展示、Markdown、工作状态展示归入职责明确的公共模块；业务状态控制仍由所属业务维护。
- **交付物：** 公共展示入口、业务控制边界、消费者迁移及各状态的所有者说明。
- **验收标准：** 会话、任务通过明确入口协作，不互相导入内部实现；公共展示不反向依赖页面或业务控制器。原交互和状态同步语义保持，不以共享可变状态隐藏耦合。
- **验证方式：** 迁移组件和相关会话／任务交互用例；涉及通信语义时协调 G07 的相关验证。
- **阅读入口：** [会话边界](../src/frontend/conversation/CONTRACT.md)、[任务边界](../src/frontend/tasks/CONTRACT.md)。

#### G09：完成剩余依赖治理与检查覆盖

- **整改内容：** 处理 G01 核实的剩余反向依赖，包括主进程治理、持久化、工作区及其他前端模块；清除已迁移切片的旧出口，补齐扫描和归属覆盖。
- **交付物：** 已定义模块对应的规则覆盖、旧入口退出证据及未解决问题的真实结论。
- **验收标准：** 定义的层、模块与维护文件全部纳入检查，新增文件有明确归属；不存在未处理的环、禁止依赖或越过公共入口的引用。不得把项目内部耦合加入宽泛豁免；动态外部加载仅按核实后的精确范围处理。
- **验证方式：** 对应依赖／架构检查；仅检测器或规则变更时增加其回归；运行实际迁移消费者的相关单元。收口不自动触发日常全量测试。
- **阅读入口：** [依赖检查器](../scripts/check-dependencies.mjs)、[目录架构检查](../scripts/source-architecture.mjs)。

### A.5 推进顺序与阶段验收

1. **建立边界与最小记录：G01，配套第 2、4 节机制。** 验收模块归属、依赖方向、公共入口及记录示例；此时明确检查规则，但不先建设庞大巡检工具。
2. **完成一条治理试点：G02 的相关辅助隔离 → G03。** 用真实查询链证明契约可单向依赖、领域测试可局部执行、公共行为保持。G02 可提前准备，无需等待全仓测试辅助都拆完。
3. **治理核心状态与执行：G04、G05，再按相关契约推进 G06。** 每项拆为可独立审阅和验证的切片；迁移公共抽象时同时使用退出机制。G04 与 G05 不要求互相等待，但共享事务或契约变化必须协调。
4. **扩展外围并收口：G07、G08、G09。** G07／G08 可在各自前置满足后推进；G09 的规则补齐和旧入口清理伴随每片完成，末尾核对总覆盖。

首批建议范围仍为 **G01–G03**。阶段顺序表达设计依赖，不是实时排期，也不表示已创建工单。自动巡检和统计根据试点证据另行决定，不作为前置工具项目。
