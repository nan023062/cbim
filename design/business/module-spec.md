# Module 定义与维护规范

> 结构设计：workspace 是根容器，一级 Module 是按领域划分的工程节点，以下是各工程的模块节点。每个 Module 可用的 Workflow 仅为自身 module.json.workflows，不继承父模块或工程节点流程，不设置根级或模块级共享 workflows.json。Agent 任务基于明确的 Module。详见 [Team 与 Workspace 结构设计](../../docs/shared-skills-workflows.md)；工程层级的新增校验尚未实现，不据此自动改写已有工程。

新增、修改模块定义或核实模块契约时按需读取。项目实例、索引位置与实际工作范围由调用方提供；本规范不组织执行者路由。

## 模块层级与物理工作区源

- 模块目录名与 `name` 统一使用小写 snake_case（`xxx_xxxx`），多单词用下划线连接，已有层级编号保留并以下划线分隔，例如 `01_core_engine`。模块 id、导航和结构图同步该名称；真实源码路径、程序集名和类型名保持原有拼写。

- 模块目录层级表达经确认的领域与架构父子关系；每个非根节点只有一个父模块，禁止树内成环。
- 模块树由项目指定的负责人定义并确认，按适用的领域与架构分层组织，不能由物理目录自动反推正式模块树。
- module.json 的 children 是直属子模块的压缩导航清单，必须与实际模块树一致，不保存 parent 字段。module.md 在第三节统一一张结构关系图：正式直属子模块与承载直属内容的虚拟子模块按同层抽象子节点展示；source 是虚拟子模块内容的物理定位依据，不据每条 source 再拆一个虚拟子模块。图以 JSON 的 children、sources 及维护边界为依据，不展开正式子模块内部或重复其 sources。组成关系与经人工确认的架构依赖约束须区分，不从目录推导调用关系。
- sources 定义模块的物理工作区源，`sources.location` 只能引用文件夹，不允许直接引用任何类型的文件，包括无扩展名文件。需要定位某个文件时，登记其所在文件夹，通过 scope 和 overview 说明该文件所属的维护范围。一个模块可以具有多个分散的目录源，可包含代码、配置、资源、测试和文档。
- 同一文件夹内的多个文件合并为一条 source，不为每个文件重复登记所在文件夹。目录引用不扩大维护权限；scope 必须保留必要的范围与排除项。不同模块的文件若位于同一文件夹，须先明确目录的唯一维护归属，其他模块通过知识引用定位，不以不同 scope 重复登记同一目录。
- 同一物理源路径仅保留一份维护声明；同模块内或跨模块的重复声明均应消除，共享使用方通过知识引用定位维护模块，不靠复制 sources 建立所有权。路径别名按同一源处理；父子及祖先模块的同向目录包含是正常关系，不作为问题；跨分支的物理目录包含保留为工程结构存量警告，不自动调整模块树或源码目录。
- sources 自动登记服从调用方提供的模块注册排除规则；命中的路径不单独登记，也不参与源重复或包含关系比较。忽略之前仍须校验路径合法性与 scope，不能用忽略掩盖越界或无效声明。默认配置排除 Unity .meta 伴随文件；它们随对应资产维护，不作为独立 source，也不能因未索引就删除或丢失其 GUID。目录 source 不因包含被排除单独登记的伴随文件而整体失效。排除登记不限制读取、引用、依赖分析或任务授权，不表示该内容不存在；用户明确指定处理时仍可按实际路径定位。
- 开发侧单元测试及其测试程序集、配套文件随被测模块维护；QA 工作区维护 QA 验收与质量验证资产，不因文件位于 Tests/UnitTests 目录或独立测试工程就接管。归属按测试内容、被测对象和已确认职责判定；占位测试不视为已具备功能覆盖。
- sources 仅记录本模块直接维护的范围；已由子模块声明的源不在父模块重复列举或汇总。父模块通过子模块定义定位这些源。纯组织节点可使用空 sources；尚未下沉的直接维护范围仍可保留，宽目录范围须排除子模块已声明部分，不能作为整棵子树的写入授权。
- 模块目录按父子关系和模块标识组织，不镜像源文件夹路径。模块与物理目录并非一一对应；移动或增加物理工作区源时更新 sources，不因此改变模块身份或父子关系。
- 组织父子关系、业务依赖、资料引用和文件所有权分别记录。引用文件不等于拥有文件或获得修改权限。


## 直属文件、直属文件夹与虚拟子模块

在本模块已明确的物理工作区及维护范围内，排除由正式子模块或其他模块登记维护的文件夹后，剩余的文件与文件夹称为本模块的“直属文件”和“直属文件夹”，合称“直属内容”。这里的“直属”表示维护归属，不限定为磁盘目录的第一层。

这些内容因规模小、分散、尚不足以抽象建模并封装为独立子模块而保留，属于正常组成，不是架构缺陷、待拆分任务或游离文件。每个模块的全部直属内容统一归入一个虚拟子模块；即使没有正式子模块，仍可用虚拟子模块承载其全部直属内容。

虚拟子模块是本模块内部的统一归属与表达，不是独立注册模块：不新增实体目录、module.json、children 条目或注册表记录，不增加 Schema 字段。由所属模块的 sources 与 scope 定位范围，在 module.md 的第二节说明，在第三节作为“直属内容（虚拟子模块）”节点与正式子模块并列。其下的文件与文件夹无需逐个建模，多个分散 source 仍按现有规则逐条描述；没有直属内容时无需空建虚拟节点。

虚拟子模块命名固定为以下三项，不加父模块前缀、路径、编号或业务别名：

- 显示名称：`直属内容（虚拟子模块）`，使用中文全角括号。
- Mermaid 图内标识：`CbimDirectContent`，大小写固定。它仅在当前图内有效，不是正式模块的目录名或注册 id，不适用正式模块目录的 snake_case 规则。
- 类型标记：`<<virtual>>`，与正式子模块的 `<<module>>` 区分。

每张图有直属内容时恰好一个该节点，无直属内容时为零；各模块可复用相同图内标识。统一写法为 `class CbimDirectContent["直属内容（虚拟子模块）"]`，另行标记 `<<virtual>> CbimDirectContent`。名称、标识或类型标记偏离、重复声明均须修正；不创建虚拟模块的全局注册名称。

虚拟子模块不接管其他模块已登记的内容，不因物理父目录包含而覆盖已确认的职责排除。未命中任何模块有效维护范围的文件仍是游离文件；归属冲突或尚未明确的范围继续单列核实。只有后续形成值得独立维护的内聚职责并获确认时，才从虚拟子模块中抽出正式子模块，不因文件数量或目录存在而自动拆分。

## 文件覆盖与游离文件

所有未被任何有效模块的 source 维护范围覆盖的文件均为游离文件，必须在知识治理中暴露。文件通过所属目录的 source 被覆盖，不要求也不允许为单个文件新增 source。普通知识链接、依赖引用和历史证据中的提及不等于维护归属。

目录路径命中只产生候选归属，仍须结合 scope 核实；被 scope 排除且没有其他模块接管的文件也是游离文件。边界无法确定时单列“归属待核实”，不得默认计为已覆盖。发现游离文件不自动授权新建模块、扩大目录范围或删除文件；根据职责决定由已有模块接管、调整模块边界或保留待归属状态。

治理报告必须提供检查范围、文件总数、已覆盖情况、游离文件的完整路径清单、归属待核实项及未扫描范围。自动注册忽略规则不证明文件已有归属；未覆盖但命中忽略规则的文件仍须单列，并注明规则与原因，不得从报告静默消失。全量检查覆盖项目文件，局部检查必须注明范围，不能据局部结果宣称全项目无游离文件。

## 混装物理目录的 scope 说明

sources.location 定位模块分散的物理目录根，scope 压缩说明该目录下实际维护的内容。目录可能混装代码、第三方库、资源、配置、文档或生成文件；不能由目录名或整目录路径推断其中全部内容都归本模块维护。

- 新建或更新 source 时，核实目录内容；发现混装时，scope 仅用一句话保留主要维护对象与必要排除条件；混装类别、具体子路径边界、归属判断和未核实细节放入 overview 的“子模块和 source 节点”。没有混装证据时不机械添加“混装”描述；尚未核实则明确待核实项。
- 排除范围尽量用实际子目录、文件类别或用途表达。已知其他模块负责时注明归属；未知时写明归属待确认，不将未知内容默认接管。第三方二进制库与内容资源按实际用途区分，不仅凭扩展名判断。
- scope 作为压缩索引，不列文件枚举、扫描过程或完整核验结论。overview 在“子模块和 source 节点”下集中设置“Source 路径与维护说明”，按 module.json 的 sources 顺序逐条列出完整路径，每条配不超过 250 字的说明（路径标题不计，说明正文含标点与英文字符计数）。说明实际用途、必要边界及待核实事项，不照抄 scope；不汇总子模块的 source。路径以 JSON 为权威，增删或改名时同步正文，不能在正文独立声明 source；sources 为空时无需该小节。扫描过程与统计证据归任务记录。
- 记录现状不授权整理物理目录、迁移文件或删除资源。执行任务仍须按 scope 和本次授权限定具体路径；混装边界不清时先核实受影响部分。
- 正常父子目录包含不要求作为冲突复核；scope 仍说明直接维护边界。精确重复仍须处理，跨分支包含即使有 scope 排除也保留工程结构警告，不将警告等同于职责冲突。

scope 示例（仅示意写法，须按实际内容填写）：“插件集成代码与第三方库；不含示例场景、纹理及音频。”混装现状及具体资源归属在 overview 中说明。

## 模块目录与唯一职责

```text
<模块目录>/
├── module.json       压缩索引与结构化定义
├── module.md       完整模块知识（必需）
├── workflows/        操作流程（按需建立）
│   └── <工作流名>/
│       └── workflow.md 该流程的独立入口
└── <子模块目录>/
    ├── module.json
    ├── module.md
    └── ...
```

每个模块只维护一份与 module.json 平级的 module.md。模块的 Workflow 与 Agent 的 Skill 对偶：分别在 workflows/<工作流名>/ 与 skills/<技能名>/ 下独立成目录。流程目录使用小写 snake_case，入口固定为 workflow.md，可按需包含 scripts/、资源和参考资料。无流程时 workflows/ 可不存在；不建立 dna/ 或重复知识正文。DNA 的唯一正文是 module.md。

| 文件 | 唯一职责 | 不承载的内容 |
|---|---|---|
| module.json | 面向全局检索、导航与路由的压缩索引，遵循 [Module JSON Schema](module.schema.json) | 知识正文、类图、设计论证、操作步骤 |
| module.md | 完整模块知识：定位、子节点、结构图与正式决策、雷区与排障、待抽象观察 | id、结构化 sources 数组、独立的子模块定义、summary 等索引字段和重复的操作流程；source 路径仅作为集中说明的标题 |
| workflows/<工作流名>/workflow.md | 标准操作：触发条件、输入、步骤、出口校验与失败处理 | 模块定位、架构论证和其他已由 module.md 承载的知识正文 |

每项信息只维护一份权威正文，其他位置通过引用关联。summary 是由完整知识压缩而来的检索摘要，语义须一致，但不复制 overview 段落，也不能替代正文作出设计判断。sources.scope 只限定物理源的维护范围，不展开业务机制。正式模块知识是经人工 review 并确认的架构事实、约束与规范。依赖约束统一维护在 overview 的抽象设计决策与结构图，不另设 JSON 依赖索引。代码引用只是实现现状的证据，不能自动升级为架构规则；与约束冲突时记录实现偏差。

共享知识归明确的所属模块维护，使用方引用其 overview 对应章节，不复制正文，也不为了共享资料强行合并模块。

## module.json 定义

以下字段构成模块的压缩索引。id 必须等于模块目录相对项目根的路径；children 只索引直属子模块，不汇总后代节点。

| 字段 | 类型与含义 |
|---|---|
| id | 相对项目根的模块目录路径，统一使用 / |
| name、summary | 名称与 100～250 个非空白字符的单行检索摘要 |
| children | 直属子模块 id 数组，无子模块时为 []；完整、无重复且与目录结构一致 |
| authors | 真人作者 id 数组；无重复，同一已知组；未知为 [] |
| overview | 固定为 module.md，引用唯一知识正文 |
| workflows | name、reference 对象数组；reference 固定为 workflows/<工作流名>/workflow.md；无流程时为 [] |
| sources | location、scope 对象数组；location 仅引用文件夹，scope 限定本模块直接维护的范围 |
| connectors | 连接器逻辑 id 数组，无引用为 [] |

取消旧 boundaries、dna、workflow 字段。模块边界作为定位知识写入 overview；每个流程独立成目录，由 workflows 清单完整登记，名称与入口引用不得重复，不在 JSON 重复维护流程触发条件或步骤。尚未确认的架构推断不得写为正式约束；观察与实现差异按 overview 对应章节记录。

overview 和 workflows[].reference 相对 module.json 所在目录解析；id、children、sources.location 相对项目根解析。parent 不单独维护，通过模块目录层级确定；id 或目录移动时同步 children、相关引用和派生索引，不手动维护第二份注册摘要。


## module.md：完整模块知识

正文必须且只能包含以下五个二级章节，名称与顺序严格一致，不允许新增、缺失、重复或使用旧标题。一级标题仅用于模块名称，不显示模块 id。除第二节用于逐条说明 source 的路径标题及“子模块”“Source 路径与维护说明”分组标题外，不增加三级或更深章节。已有内容按职责归入这五节，不另设“注意事项与待验证项”“结构核验”“维护范围注意”等重复章节。JSON 是结构化索引权威；节点章节解释知识并导航，不维护第二份独立定义。

各章节或字段没有实际内容时，正文只写“无”，不填默认提示、通用告诫或泛泛的待核实事项。已有具体事实、风险、待验证问题或观察不得替换为“无”。“无”仅表示当前无可记录内容，不代表已经验证不存在问题；具体核验限制记入 overview 的“雷区与排障”，执行证据留在任务记录中。结构图和节点已有内容时照常保留，不因没有设计决策而删除。

### 1. 定位

说明模块负责的功能及主要定位，保持精简，不照抄 summary。

### 2. 子模块和 source 节点

正式子模块与直属内容的虚拟子模块都是抽象子节点。正式直属子模块以名称链接到其 overview，不复制子模块内部知识；直属内容统一说明为虚拟子模块，其 source 按 JSON 顺序集中列出完整路径，每条说明不超过 250 字，说明用途、混装边界和待核实事项。没有节点时写“无”。子模块内部的 source 不在父模块重复列出。

### 3. 结构关系图与抽象设计决策

模块类图是经人工 review 并确认的设计规范与约束，包含模块结构及依赖关系，是 Agent 核查实现的架构依据，不是从代码自动生成的现状图。正文用于解释图中的契约与设计理由，不另建重复的依赖索引。代码与类图不一致时记录实现偏差；只有取得人工确认的架构变更决定后，才能修改相应类图与约束。尚未确认的建议或观察不得混入正式类图。

统一一张非空 Mermaid classDiagram，加极简的正式设计理由与依据。正式直属子模块与“直属内容（虚拟子模块）”按同层节点呈现，分别标注 module/virtual 类型。正式节点对应 children，虚拟节点统一对应本模块 sources 排除已归属其他模块后的直属内容，不要求每条 source 各占一个节点。不另建独立注册清单或展开正式子模块内部；没有子节点及直属内容时保留本模块节点。组成关系与经人工确认的架构依赖约束须区分，不从目录推导调用关系。没有抽象设计决策时写“无”，不补通用占位语，也不把观察模式画成已生效规范。

### 4. 雷区与排障

记录潜规则、已知风险、易误用点、失败现象、诊断与恢复知识，以及注意事项、核验限制和具体待验证问题；这些内容直接并入本节，不另设重复章节。不重复节点章节已有说明。重复执行的操作步骤归 workflow，本节引用。未调查不能写成无风险。

### 5. 观察模式-待抽象

记录实践中发现、仍待验证或抽象的规律、证据及适用线索，明确非正式规范身份，可标记 observing、pending_review、hold、reject。普通注意事项、未完成验证和归属待核实不是待抽象规律，应放在“雷区与排障”；没有实际模式时写“无”。数量和相似度仅触发评审，不自动批准抽象。经有效决定后将生效内容迁入第三节，仅留下必要状态与决定引用，避免重复正文。

overview 不再兼容旧四节或文末另列结构图的格式；旧实例必须按上述五节迁移，严格校验不提供章节格式豁免。

## workflows：独立操作流程

没有可用流程时 JSON 的 workflows 为 []，目录可以不存在；有流程时登记对应独立入口。清单须与直属流程目录一一对应，每个目录必须包含非空 workflow.md。旧同级 workflow.md 和 workflows/ 下直接放置的流程文件均须迁移。未知流程是否存在时说明尚未核实，不把未知当成无流程。

每个 workflow.md 描述一个具体工作流，包含名称、触发条件、输入、步骤与依赖、所需专业能力、出口校验、失败分支及适用授权。步骤引用 overview 的知识和契约，不重复解释设计。任务按需选择工作流；与 Agent Skill 的结构对偶不意味着流程与技能必须一一绑定。可复用的确定性操作按需放在本流程 scripts/ 下，运行证据留在任务记录中。

流程声明不等于已部署确定性执行器。标准操作可固定，但内容判断与验收仍须结合实际证据。子模块操作流程由子模块维护，父模块不复制汇总。

## 现有实例迁移

已有文件级 source 迁移时，改为其所在文件夹并合并同目录条目，同步 overview 的 source 节点与结构图，再检查全部模块的目录重复及包含关系。发现跨模块归属冲突时先确认唯一维护方，不机械替换路径或扩大职责。路径类型以实际文件系统或可靠工程证据为准，不凭扩展名判断，带点的目录仍可作为 source。此规则仅限制 sources.location，知识链接、依赖契约和来源证据仍可引用具体文件。

本规范和 module.schema.json 定义目标格式。尚未迁移的旧实例仍可通过 [旧格式 Schema](module.legacy.schema.json) 单独检查，仅用于迁移期识别和验证旧资料，不能据此声明符合新设计。

迁移需逐模块保全已有有效知识：将旧知识归并进 overview 五节，将旧流程按独立工作流拆入 workflows/<工作流名>/workflow.md 并更新引用与锚点，替换入站和出站引用，更新 JSON 字段、id、直属 children 与派生索引。历史依据保留在既有证据位置，不能删除有效知识来凑齐格式。

新建与已迁移模块采用新格式，不同时保留旧目录作为第二份正文。设计更新不等于现有业务实例已迁移；检查结果须明确区分旧格式兼容检查与新格式验收。结构检查不能代替内容去重、类图正确性和语义复核。

## 定位与维护

summary 必须由负责维护的 AI 成员 结合整体模块体系、目标完整定义及相关模块进行语义分析后生成，并完成正向召回与反向区分检查。脚本只同步与校验显式摘要，不从 Positioning 或其他正文段落自动摘录。

先按摘要和目录路径检索，再逐层打开候选入口；仅加载命中节点的相关 DNA、Workflow 和必要依赖，不预读整树。没有可靠命中时限定调查范围并报告缺口，不编造归属。注册表每条记录统一为 id、summary；id 即相对项目根的模块目录路径，定义入口为该目录下的 module.json；summary 说明模块负责的工作内容、关键机制与常用检索术语，并由定义正文提供依据。顶层仅包含 modules 列表。id 使用 / 分隔，不相对注册表位置或当前命令目录解析，不另设路径基准字段。摘要以 module.json 为准，不维护 keywords。作者表示知识维护来源，不在本层规定执行者匹配算法。

成员可新增模块注册条目；已有共享注册条目的修改、合并、删除由项目指定的管理员治理。模块负责人维护其 DNA 与 Workflow，涉及公共边界、稳定层或正式架构变化时提交相应评审。

修改后核对模块目录路径唯一、父子关系、引用有效性、sources 证据、契约与实际产物一致性。模块调整须核对依赖方并记录影响；未解决的知识冲突不静默发布为正式结论。C/B 共享并版本管理；M 仅为可选个人本地短期记忆。


## 依赖与适配边界

模块目录、实际注册表、人员安排和历史资料兼容方式由项目扩展层维护，不写入 core。扩展层负责将实际数据对应到本规范的语义，core 不根据某个项目的存量格式定义自身结构。

实例迁移需要项目侧确认目标结构，保留来源证据，同步更新目录路径、注册表与相关引用。结构约定本身不构成移动、重命名或删除既有资料的授权。

## connectors 列表

connectors 是无重复的注册表逻辑 id 数组，无引用时为 []。按 [插件声明规范](../connector/connector-spec.md) 引用 Cindy 插件，不指向本地实现目录。所属任务将唯一 AI 成员与全部作业模块的声明合并，作为任务连接器需求集合；不表示独占或操作授权。实际外部工具接入仍需适配器；当前声明不证明工具已可调用。
