# Agent 定义与维护规范

CBIM 团队中的专业角色称为“AI 成员”，由 CBIM AI 助理组织和派发任务。Agent 是 AI 成员的能力定义抽象；`agent.json`、Schema 字段及类型名称保留技术标识。

新增、修改能力定义或核实能力契约时按需读取。项目实例、索引位置及有效授权由调用方提供；本规范不组织任务调度。

## 二、能力对象模型

agent.json 通过名称与摘要表达职业和技术定位，具体技术能力与局限分别写入 capabilities 和 limitations。Agent 所属组由目录表达。


| 核心属性 | 解决的问题 | 组成 |
|---|---|---|
| 领域 | 具备什么专业能力及局限 | 名称、摘要、能力范围与局限 |
| 工作原则 | 如何判断与取舍，做到什么程度 | 判断与取舍原则、质量要求、参考资料 |
| Skill 列表 | 有哪些可用的专业方法 | Agent 自己目录下全部可用 Skill 的名称、用途与入口引用 |

三项属性相互补充：领域说明专业能力与局限，Skill 列表提供专业方法入口，工作原则指导判断与验收，并具有 Agent 内部最高优先级。职责与能力边界不再单列属性，具体任务责任、处理对象和授权由任务与环境确定，不由能力声明授予。


### JSON 字段

| 字段 | 类型与含义 |
|---|---|
| name、summary | 名称与 100～250 字检索摘要 |
| authors | 真人作者 id 数组，引用人员花名册；不得重复，所有作者必须归属同一个已知组；未知作者为 [] |
| capabilities、limitations | 专业能力与局限的字符串数组；未知局限不凭空补写 |
| work_principles | 工作原则 Markdown 路径，读取后执行其中的判断与质量要求 |
| skills | name、purpose、reference 对象数组，完整引用自身 skills/ 下的 SKILL.md |

对象目录路径即身份，不在 JSON 中重复保存 id。工作原则和 Skill 引用相对 agent.json 所在目录解析；工作原则仍是 Agent 内部判断与验收的首要依据。说明性字段直接使用自然语言字符串；长篇规则与流程通过 Markdown 引用维护。


## 三、任务上下文与专业方法

执行者接收明确目标、输入、工作范围和验收要求，依据专业原则与方法使用CBIM 内部大脑循环 完成工作、验证并回报。输入不足或超出能力、授权范围时，返回证据与缺口，不自行扩大职责。

专业能力可以服务不同类型的工作，不固定绑定某一种业务或治理流程。专业 Skill 封装具体操作方法，工作原则指导判断和质量；本层不规定需求拆分、模块组合或任务调度。

### Skill 列表与 Team 树

能力侧是一棵树：根节点是 Team，中间非叶子节点是小组，只有叶子节点是 Agent。小组可继续包含小组或直属 Agent，Agent 不包含小组或其他 Agent。目录表达唯一父子关系，小组不限定层数，不新增 Leader 调度职责。现有规范及文件格式中 Team 可泛指组织节点；产品层级明确区分根 Team 与小组。Team、小组、Agent 都有自己的 Skill，Agent 可用 Skill 是自身与沿父链递归到根 Team 的全部祖先节点 Skill。空团队初始化时根仍为 Team，不能按空目录推断 Agent；详见 [结构设计](../../docs/shared-skills-workflows.md)。

Agent 的 `agent.json.skills` 只登记专属方法，入口为自身 `skills/<skill-name>/SKILL.md`。共享方法归属于能覆盖实际使用者的最近共同 Team，存入该 Team 的 `skills/`，由同级 `skills.json` 登记 name、purpose、reference；结构遵循 [Team Skill Schema](team-skills.schema.json)。全团队通用的方法放在 team 根。没有共享方法可不创建 skills.json；显式空清单写 `{"skills": []}`。不得将共享方法复制或重复登记到每个 Agent。

每次加载 Agent，必须按“自身 → 直属 Team → 逐级祖先 Team → team 根”读取完整 Skill 清单，保留来源和入口，不能跳过空层、只加载直属 Team 或越过根。不继承兄弟 Team、后代 Team 或其他 Agent 的专属方法。执行前按任务相关性读取方法正文及必要引用；完整加载清单不等于无差别执行或读取所有方法正文。公共能力可见不代表获得执行授权或具备对应专业能力。

同一继承链中名称或 Skill 目录名重复时显式报错并定位两处来源，不按距离、加载顺序静默覆盖。加载工具由入口作为任务工具提供，派发与恢复须保存解析链、目录清单和实际采用正文的版本。任一层缺失入口、未登记 Skill、非法路径或冲突时修正后重新解析，不以部分清单继续派发。

本地清单必须与该节点 skills/ 实际入口一一对应。references/、assets/、scripts/ 等资料目录不是 Team；Skill 辅助文件不单独登记。方法新增、移动和删除时同步所属清单及引用，继承所得条目只存在于加载结果。

## 五、文件组织与职责

```text
team/
├── registry.json
├── skills.json                 # 可选：根 Team 公共清单
├── skills/                     # 根 Team 公共方法
└── <team>/
    ├── skills.json             # 本层共享清单
    ├── skills/
    ├── <subteam>/              # 任意深度，规则递归相同
    │   └── <agent>/
    │       ├── agent.json      # 仅登记专属 Skill
    │       ├── principles.md
    │       └── skills/
    └── <another-agent>/
```

这是抽象布局约定，不指向任何实际目录；扩展根的位置与实例由项目侧确定。agent.json 是字段与引用的唯一来源，遵循 [Agent JSON Schema](agent.schema.json)。Markdown 仅保存工作原则、Skill 等正文，不复制 summary 或作者字段。读取 JSON 后按引用加载执行指令，JSON 本身不是确定性执行器。Agent Schema 定义单个 AI 成员，Team 的嵌套关系由目录树表达；groups → agents 是树的扁平检索索引，不限制 Team 深度。组织层级不新增 Leader 或任务调度职责。


## 六、注册表设计

### 定位

能力注册表是 CBIM AI 助理快速查找具体 Agent 的索引，其位置由项目侧入口提供，core 不绑定具体文件。它提供任务匹配线索与定义位置，不复制完整能力说明。

检索路径是：先定位候选组，再匹配 Agent 名称和职责摘要，按 id 定位定义，核实能力边界并读取其工作原则。任务需要时扩大到其他组。未命中表示存在能力缺口，不能只凭名称相近就认定适用。

### 最小数据结构

顶层仅包含 groups 列表，每项包含 Team 的完整目录 id 和直属 agents。任意深度的 Team 均进入索引，父 Team 由目录父路径确定；Agent 仅归直属 Team，空组保留 agents: []。team 根为隐式根，有直属 Agent 时也登记根项。候选检索可以展开指定 Team 的子树，Skill 继承仍只沿祖先链。所有 id 均相对项目根目录（包含 .cbim/ 的目录），使用 `/` 分隔；不相对注册表位置或当前命令目录解析，不另设路径基准字段。每个 Agent 条目保留两个字段：

| 字段 | 设计用途 |
|---|---|
| id | 相对项目根的 Agent 目录路径；定义入口为该目录下的 agent.json |
| summary | 100～250 字的检索摘要，说明能力范围、适用任务、专业方法与必要边界 |

摘要以 Agent 定义为准；工作原则与 Skill 列表留在 Agent 定义中。索引与定义保持主从关系，避免维护两套能力真源。

### 职责摘要设计

summary 必须由负责维护的 AI 成员 结合整体能力体系、目标完整定义及易混淆角色进行语义分析后生成，并完成正向召回与反向区分检查。脚本只同步与校验显式摘要，不从专业能力或正文段落自动摘录。

summary 采用 100～250 字的检索摘要，覆盖核心能力、适用任务、常用术语和必要边界，允许自然混用中英文。按非空白字符计数，字母、数字与标点均计入；允许多句，保存为单行。内容必须由定义正文支持，不能以重复文字凑长度。

摘要不包含详细步骤、宣传性评价或泛泛的支持承诺，不堆叠无关关键词。需要审批的活动保留必要限定，例如“实施获批重构”；摘要不固定绑定具体业务模块，也不代表操作权限。

### 一致性维护

新增 Agent 对应新增索引条目；职责摘要或目录路径变化时同步相关记录。id 的值就是目录路径，同时承担标识与定位职责，不另设 path 或 definition_path 字段。目录移动时同步注册表及相关引用，保留无关条目。索引质量由路径唯一、入口有效、字段与定义一致、摘要能够辅助任务匹配四方面判断。

登记仅表示可以找到定义，不证明已部署或通过真实任务验证。采用人工维护还是自动发现、汇总，由项目侧实现决定；本设计不假定相应机制存在。


## 七、协作与治理边界

执行者按输入上下文完成专业工作并回报；超出能力或指定范围时返回缺口，不自行改变工作范围。

能力声明与执行授权分别管理。业务实现角色和架构重构角色都不自动获得保护对象写权限或人类审批权。实际工具、引擎、执行环境及有效授权共同决定能否执行。

成员可以新增能力节点；已有共享定义的修改、合并和删除由项目指定的管理员治理，能力负责人提供验证依据。能力升级保留版本及影响说明，避免在途任务无意识地切换依据。

## connectors 列表

connectors 是无重复的注册表逻辑 id 数组，无引用时为 []。按 [插件声明规范](../connector/connector-spec.md) 引用 Cindy 插件，不指向本地实现目录。所属任务将唯一 AI 成员与全部作业模块的声明合并，作为任务连接器需求集合；不表示独占或操作授权。实际外部工具接入仍需适配器；当前声明不证明工具已可调用。

成员索引遵循 [注册表 Schema](registry.schema.json)。真人花名册保持独立，遵循 [人员 Schema](people.schema.json)，不嵌入成员索引。静态成员身份由本地定义目录确定，动态成员使用独立 AgentInstance 与逻辑会话；内部调度绑定定义版本、原则和有效 Skill，再由大脑执行。当前成员收件箱自动执行尚未接通，不能把定义读取或可靠入队说成成员已执行。
