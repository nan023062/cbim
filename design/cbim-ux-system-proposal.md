# CBIM UX 与风格系统提案

日期：2026-11-15。状态：设计提案，供评审；不代表当前产品已实现，不改变已批准的产品规则。本轮不实施产品代码、不发布、不提交 Git、不创建实时待办。

## 1. 定位与设计判断

**让一个人清楚地指挥一支 AI 开发团队，并检查它交付的结果。**

CBIM 是本地／多端的 AI Native 工作流工具，当前面向单人使用，不是多人协作平台。主要使用者同时承担目标提出、业务决策和成果检查；不应要求他们逐次管理工具调用、Agent 派发或模型线程。成功体验是：说清目标后，Agent 在授权范围内持续推进，只把必要决定交给用户；最终交付实际产物、验证证据和剩余限制。

参考 Cindy 的目标驱动、低干扰进展、渐进展开与语义视觉；保留 CBIM 的工作区、办公室、话题、责任岗位、验证与知识沉淀。工程业务的团队协作未来通过插件和链接器接入 P4、Git、飞书等外部工具，不另建独立账号或协作服务。多端是产品定位；具体端能力、同步和执行归属须以实际实现为准，窄屏原型本身不证明已支持移动客户端或远程控制。

主线：**提出目标 → 团队理解与分工 → 执行与协作 → 验证与必要返工 → 可检查的交付 → 有依据的知识沉淀**。

## 2. 事实基线与设计差异

本提案以当前仓库 README、`src/view/shell/App.tsx`、`src/view/tasks/OfficeScene.tsx`、`office-scene.css`、`design/task/team-office-topics.md` 和品牌说明为依据。属于源码/文档核对，未进行当前桌面版的可用性实测。

| 已观察到的结构/约束 | 设计判断与建议 |
| --- | --- |
| 侧栏并列运行管理、新建工作区、链接器、人才市场、业务模板 | 高频位置优先放工作区与办公室；管理入口集中为次级区，减少开始工作前的概念负担 |
| 主会话含对话/任务视图，右侧扩展承载架构、浏览器、终端等 | 保留三块职责，右侧增加明确的“成果与证据”聚合入口；不同模式共用真实对象，不复制执行状态 |
| 一个主 Session 是办公室；普通输入排队，补充指定话题会暂停相关参与者 | 输入框显式区分“新话题”和“补充当前话题”，发送前说明影响；浏览成员对话不打断任务 |
| 办公室已有模块工位、人物和事件动画 | 保留为空间视图；同时提供紧凑任务列表，动画不承担状态判定，也不作为唯一操作入口 |
| 成员完成/回流不等于业务验收 | 把“执行已结束”“验证通过”“交付已接受”分开；不默认增加人工批准关卡 |
| 本地优先，跨设备调度不属本阶段目标 | 常显工作区和实际项目，设备信息在确有歧义时展示，不把云账号/设备选择做成任务必经步骤 |

这些是基于界面结构的设计假设，需要后续用户验证；不能直接称为已测得的用户痛点。

## 3. 信息架构与命名

### 对象层级

工作区（长期项目、业务知识、岗位配置）→ 办公室（独立主会话）→ 话题（用户目标及其排队/执行周期）→ 成员任务（分工）→ 执行记录与证据。

同一办公室的不同话题不能被 UI 合并为同一上下文；同一 Agent 的长期对话也不等于它每次运行的上下文。普通界面用“办公室、话题、成员、成果”；详情才出现 Session、Run、模型和工具。

### 全局导航

- 顶部：CBIM 品牌、工作区选择/搜索。
- 主要区：新建办公室、当前工作区的办公室列表；按需展开成员对话。
- 次级区：团队与业务、知识与资源、运行管理、设置。原有能力仍保留，具体入口迁移需核对已有访问路径。
- 工作区切换器内：最近工作区、添加已有项目目录、工作区设置。不要把“新建工作区”写成会创建业务文件的承诺。

### 工作面

1. 顶栏：工作区 / 办公室；当前话题标题与状态；“查看成果”入口。
2. 中央：对话、协作两个一级视图。协作内切换“任务列表 / 办公室”；沿用已有任务图作为深入检查入口。
3. 右侧：用户打开的成果、变更、证据或专业工具；没有内容时收起。用户关闭后，不因新事件自动重开。
4. 底部：输入草稿、明确的输入归属、本次有效上下文、发送/加入队列/提交补充。

### 渐进展开

默认层回答“做什么、进展如何、是否需要我、结果在哪”；展开层回答“谁负责、改了哪里、凭什么通过”；诊断层才展示引擎、工具参数、完整日志、重试身份。工作语言在前，技术身份可以复制查询。

## 4. 核心流程

### A. 首次进入与提出目标

没有工作区：主操作“选择项目文件夹”，说明将在项目建立 CBIM 工作知识。已有工作区：主操作“新建办公室”，输入“这次希望团队完成什么？”。模型配置有效则沿用；无效时指出缺失配置，不静默换引擎或供应商。

输入建议采用真正的工作目标：“修复一个问题”“交付一个功能”“检查当前方案”。仅填入草稿，不自动发送。允许先输入自然语言；目标、范围与成功标准缺失时只询问会影响实施的必要信息，不要求每次填计划表。

### B. 分工与执行

主 Agent 给出简短理解与下一步；只有存在真正决策时才提出问题。分工摘要显示成员、负责模块、当前动作和依赖。没有已配置自定义岗位时保留主 Agent 直接处理的能力；不为团队视觉强造多个成员。

当前话题在执行时，普通新消息以“加入队列”发送，不暗示立即打断；队列显示顺序与移除入口（仅能力支持时）。不能仅因有排队项就显示它们已经开始执行。

### C. 补充与接手

输入框模式明确为“新话题”或“补充：导出筛选结果”。补充模式显示“提交后将请求暂停此话题的参与者，再由主 Agent 重新协调”。只有提交补充才触发；切换模式、读成员对话、打开成果都不暂停。

停止请求发出后显示“正在停止”，等待真实结束回执；未确认的工具结果进入“待核实”。已完成话题的补充建立关联后续话题，历史输入和验收记录不回写。主 Agent 统一接收用户输入，即便用户在成员对话视图中发送，也要标明该路由。

### D. 审阅与交付

交付面提供：成果摘要、文件/对象位置、责任成员、变更范围、对应版本、已执行的验证及范围、未验证项、剩余问题、后续操作。

“通过”必须能定位证据；“未执行”不伪装成失败，“执行结束”不伪装成验收通过。验收依据既有契约：允许自动判定的由系统判定；确需业务判断的才显示“接受交付”。不得把每次交付都强制变成人工审批。

普通主操作“查看成果”；有未决业务问题时主操作变为具体决策。查看差异、请求修改作为次操作；撤销仅在实际支持且范围明确时呈现。知识沉淀显示来源和适用范围，走现有知识事务与权限，不把模型总结自动升级为事实。

### E. 异常与恢复

错误就地显示：已完成什么 → 哪一步受阻 → 原因 → 有依据的下一步。工作区失效不自动切到别的目录；岗位失效不悄悄换负责人。应用重启后先核对历史和副作用；无已实现的恢复入口时只提供检查与创建关联后续工作，不画“原地继续”的虚假承诺。

## 5. 状态与文案规范

状态从权威业务事实派生，View 不维护另一套执行状态机。以下为展示状态设计，实施需逐一映射已有契约。

| 展示状态 | 判据 | 文案例子/操作 |
| --- | --- | --- |
| 排队中 | 话题已登记尚未开始 | 前面有 1 个话题；查看队列 |
| 执行中 | 有真实活动执行 | 实现成员正在调整导出逻辑；停止此话题 |
| 等待依赖 | 等待内部任务/资源 | 等待接口结果；默认无需用户处理 |
| 需要你决定 | 存在明确待处理事项 | 导出哪些记录？当前筛选 / 全部记录 |
| 验证中 | 验证工作确已开始 | 正在检查导出文件；查看验证范围 |
| 正在返工 | 验证发现问题且已重新派发 | 发现空列表问题，正在修复 |
| 正在停止 | 已请求取消但尚未确认结束 | 正在等待写入操作结束 |
| 已停止 | 已确认相关执行退出/结算 | 保留 2 处修改；查看改动 |
| 待核实 | 副作用/结果尚未知 | 保存响应中断，需要核对文件 |
| 部分完成 | 有成果但目标仍有缺项 | 功能已实现，验证尚未完成 |
| 已交付 | 对应版本满足验收契约 | 已按约定验证；打开成果 |

状态不只靠颜色：文字 + 图形标记；错误常驻至解决，不只用 Toast。Toast 只承载非关键短反馈。未知剩余时长不显示倒计时；缺少真实总量不显示百分比。

## 6. 风格系统：安静、精确、有团队温度

### 原则

- 中性色承载长时间阅读；主操作使用高对比中性色。品牌与工作状态分离。
- 层级依靠留白、字号、细线和局部表面区分；无装饰渐变、无大面积彩色工作卡片。
- 保留现有 CBIM 标志，正式实现引用 `assets/branding/cbim-mark.svg`，不仿制 Cindy 标志。原型仅使用 CBIM 文字标识。
- 办公室人物与工位用于表达真实团队活动，避免把游戏式动画当工作主反馈；使用与正文一致的线条与中性色。
- 可用性优先于极简：停止、未决事项与失败原因不能藏在溢出菜单。

### 建议令牌（提案，不代表已迁移）

| 语义 token | 浅色 | 深色 | 用途 |
| --- | --- | --- | --- |
| `surface.canvas` | `#F7F8FA` | `#17191D` | 全局画布 |
| `surface.panel` | `#FFFFFF` | `#202329` | 输入、弹层、局部成果 |
| `surface.subtle` | `#ECEEF2` | `#2A2E36` | 悬停、次级区域 |
| `text.primary` | `#20242C` | `#F0F2F5` | 正文、标题 |
| `text.secondary` | `#596270` | `#ADB5C2` | 辅助说明 |
| `border.default` | `#D8DDE5` | `#414854` | 非交互分隔 |
| `border.control` | `#7D8796` | `#7F8A9A` | 需独立识别的控件边缘 |
| `action.primary` | `#20242C` | `#F0F2F5` | 主按钮；文字取反色 |
| `status.active` | `#8C4A10` | `#F0B575` | 真实运行状态 |
| `status.success` | `#246642` | `#88D0A2` | 已有证据的通过 |
| `status.danger` | `#B13737` | `#FFAAAA` | 失败、破坏性操作 |
| `focus.ring` | `#2459BC` | `#9BBDFF` | 键盘焦点 |

业务模块不得各自硬编码新色。正式令牌迁移先盘点现有 `--bg / --surface / --line / --muted / --accent` 的真实用途，再建立映射，避免把同一个旧 accent 同时用于品牌、选中和运行状态。

### 排版与尺度

- 字体：系统无衬线（Windows 使用 Segoe UI / Microsoft YaHei，macOS 使用系统字体 / PingFang SC）；不要求联网字体。代码使用系统等宽字体。
- 正文 14px / 1.65；窄屏正文 15px / 1.65；辅助 12px / 1.5；区块标题 16–18px / 500–600；页面标题 22–24px / 600。字重以 400、500、600 为主。
- 间距：4、8、12、16、24、32、48px；正文宽度建议 640–760px，长说明不铺满屏幕。
- 圆角：6px 小控件，10px 输入/卡片，16px 弹层；999px 仅用于状态/标签等胶囊元素。不要所有内容都装进大圆角卡片。
- 桌面普通控件高度 36px，图标按钮至少 36px；窄屏主要触控目标至少 44 × 44px。
- 图标：采用 [CBIM Outline 图标、动效与提示规范](cbim-icon-motion-system.md)，24px 母版、1.75 单位圆端描边，按 14/16/18/20/24px 使用；不可单独用不熟悉图标表达危险操作。
- 动效：交互反馈 120–180ms，面板 180–220ms；仅使用 opacity/transform。系统减少动态时禁用位移动画与循环呼吸，保留完整状态。

### 核心组件及契约

| 组件 | 必须表达 | 变体/边界 |
| --- | --- | --- |
| WorkspaceSwitcher | 当前工作区、可识别路径 | 工作区失效、加载、无项目；不静默替换 |
| OfficeNavItem | 办公室名、必要的运行/待办提示 | 展开成员；不把每个执行实例变成导航节点 |
| TopicStatus | 当前话题、真实阶段、下一步 | 等待依赖与等待用户分开；不显示推测进度 |
| GoalComposer | 草稿、归属、发送影响 | 新话题/补充/只读；IME 组合输入不能触发发送 |
| MemberActivity | 成员、责任模块、当前工作 | 展开事实流；历史配置与当前配置分开 |
| DecisionCard | 决策对象、选项、影响、处理状态 | 只在显式提交后生效；重复提交不能重复执行 |
| ArtifactPanel | 对象与版本、改动、验证与限制 | 预览/变更/证据；无成果时真实空状态 |
| EvidenceRow | 检查范围、方法、版本、结果 | 通过/失败/未执行/过期；旧证据不沿用到新版本 |
| RecoveryNotice | 已完成、未知部分、合法下一步 | 不提供未实现的继续/撤销 |

## 7. 布局与可访问性

图标、状态反馈、悬停/聚焦提示、禁用原因与触屏替代入口统一遵循 [图标、动效与提示系统](cbim-icon-motion-system.md)。[风格页](cbim-ux-prototype.html#icons) 提供可搜索图标目录、尺寸和状态样例，以及减少动态、反馈和 Tooltip 交互示例。

≥1280px：约 224px 导航 + 弹性主区 + 320–400px 可选成果区。960–1279px：保留导航，成果作为抽屉，避免三栏压缩正文。600–959px：折叠导航，单主区。320–599px：单列，成果全屏，导航抽屉；长路径可折行，图表提供列表替代。

主内容先于辅助内容进入阅读顺序。焦点可见，弹层支持 Escape 关闭、焦点约束及关闭后返回触发按钮；抽屉不让焦点落到遮挡区域。草稿与阅读位置按办公室/话题保留，开关面板不清空。状态通知使用适当的 live region，不逐 token 播报。图形旁有文字，触控不依赖 hover。

目标是 WCAG 2.2 AA：正常文字对比度至少 4.5:1，关键控件/焦点至少 3:1；正式组件上线时测量实际配色与禁用/悬停状态。原型中的配色是候选值，未完成全套无障碍审计。

## 8. 原型范围与评审路径

同目录 [cbim-ux-prototype.html](cbim-ux-prototype.html) 为自包含设计原型，可直接用现代浏览器打开，无需安装依赖或启动服务。所有样式和交互脚本内联，无外部字体、图片、网络请求或存储依赖。所有成员、项目、状态、文件和验证均为示例。操作只影响页面演示状态，不调用模型、不修改工程、不代表真实验证完成。

可评审：对话/协作切换、办公室空间、成员详情、待决事项、成果/变更/证据面板、新话题队列、补充当前话题、停止过程、浅色/深色、窄屏布局、风格参考。原型不实现真实权限、文件预览、模型执行、持久化恢复和发布。

原型的“成果与证据”使用可关闭的侧边模态抽屉，浏览器原生 dialog 负责焦点约束、Escape 关闭与焦点恢复；桌面并列停靠面板是目标布局，尚未在此原型实现。“窄屏预览”把工作面限制到 390px，实际 320px 窗口另由响应式样式适配。办公室增加明确标注的独立协作模拟，人物动画不写回主话题状态。新话题仅进入演示列表，停止仅变为“正在停止”，后续状态由顶部预览控件显式切换，不以定时器模拟真实完成。

### 办公室协作剧场（v0.2 基础设计）

用户要求增加人与人协作、对接的模拟，让办公室表现更生动。本轮只扩展设计原型，不增加真实团队岗位、运行权限或产品功能。

- **五位具象人物**：林（主 Agent）、乔（交互设计）、陈（前端实现）、许（接口实现）、周（验证）。不同发型、眼镜、耳机和记录板帮助辨识；角色名及职责始终可读，不依赖形象或颜色辨识。
- **八步完整情境**：目标派发 → 设计交接 → 接口协商 → 样例返回 → 提请验证 → 问题反馈 → 修复复验 → 汇报交付。体现成员之间直接对接，不把所有沟通都画成主 Agent 的单向派发。
- **三个情境入口**：完整协作、接口对接、反馈返工；短情境复用相同的交接事实与角色。
- **人物行为**：当前发起者离开自己的工位，沿路线走到接收者处，停留交接再返回。原工位人物淡化以提示位置变化；当前双方高亮，并显示各自的工作状态。走动由本页编排的示例步骤驱动，正式产品仍须由真实事件驱动。
- **每次对接有具体内容**：展示发起者、接收者、双向对话、协作原因，以及说明、接口约定、样例、候选版本或验证记录等交接物。移动结束不代表验收完成。
- **可控制节奏**：播放/暂停、下一步、重播情境、3/5/8 秒节奏和人物走动开关。播放在情境末尾停止；切换情境会重置步骤与记录。暂停保留当前内容，正在走动的人回到工位。
- **不打扰真实工作**：切离协作视图、切到任务列表、页面进入后台或打开人物详情时暂停模拟；不会恢复后擅自继续播放。点击人物查看职责及当前对接内容，关闭详情后手动继续。
- **减少动态**：系统启用减少动态时禁用人物走动；完整内容仍可播放或逐步阅读。窄屏将工位排成双列，文字不随整张办公室缩小；人物路径按实际位置计算。
- **明确隔离**：模拟拥有独立步骤和记录，既不改变顶部主话题状态，也不改变交付证据。主话题快照单独折叠展示，五位模拟人物不冒充三位示例执行成员。

直接打开 [办公室模拟](cbim-ux-prototype.html#office) 即可进入协作视图；默认不自动播放。点击“播放协作”开始，或用“下一步”逐步审阅。

### 任务全过程与异常处理（v0.3 当前原型）

在 v0.2 的五位人物和工位基础上，完整情境扩展为 **18 步**，覆盖目标确认、设计与分工、协作实现、验证与返工、交付、知识归档六个阶段。情境入口扩展为六个：任务全过程、依赖阻塞、方案冲突、交接失败、接口对接、反馈返工。

**可见状态分三层：**

1. 生命周期条表达当前处于哪个阶段，不用步骤数量伪装完成百分比。短情境中未播放的早期阶段标为“前置”，不冒充已验证完成；归档结束显示完成标记。
2. 模拟任务状态区常驻显示“前一状态 → 当前状态”、原因、影响成员及下一步。错误必须有文字说明，不能只通过人物颜色表达。
3. 工位显示每位成员当前在做什么，包括未参与本次对话但正在等待、准备或继续工作的成员；任务被局部依赖阻塞不等于所有人都停止工作。

完整过程的状态序列：

> 目标确认中 → 规划中 → 设计对齐 → 接口对接中 → 依赖阻塞 → 恢复执行 → 冲突待协调 → 恢复执行 → 实现中 → 交接待核实 → 交接失败 → 恢复执行 → 验证中 → 返工中 → 复验中 → 约定验证通过 → 已交付 → 已归档。

| 情况 | 表现与影响 | 显式处理和恢复 |
| --- | --- | --- |
| 依赖阻塞 B-01 | 缺少正常、日期边界与空集合样例；接口等待，前端接入暂停，设计仍可核对文案 | 点击“补齐样例，解除阻塞（演示）”，保留原目标与责任并恢复对接 |
| 方案冲突 C-01 | 页面按北京时间解释日期，接口按 UTC 截断；暂停相关实现与验证标准确认 | 选择统一北京时间，或统一 UTC 并显示时区；显式确认后同步参与者，决定出现在后续对话、契约和记录中 |
| 交接待核实 H-01 | 发送结束但接收回执中断，接收版本未知；前端暂停消费，接口不重复发送 | 先点击“核对接收情况（演示）”，展示核实结果，不直接声称重试成功 |
| 明确交接失败 H-01 | 核实确认已收到且无重复，但缺少契约版本，接收方明确拒收 | 点击“补齐版本，重新交接（演示）”；用 H-02 附契约 v2 与校验摘要，取得明确接收回执 |
| 验证失败与返工 | 空列表产生文件，不符合约定；候选 v1 的失败证据保留 | 修复生成候选 v2，再验证相同缺陷和正常路径；新候选不继承旧通过结果 |

上述四个异常节点是**原型的交互停留点**：自动播放到达后暂停，禁用普通播放与下一步；只有对应的处理动作才能推进。处理后保持手动暂停，由用户决定继续播放或逐步检查。真实产品可以由已授权 Agent 自动处理可恢复问题，本原型的停留点是为了可审阅地展示恢复语义，不新增产品强制人工审批规则。

协作记录保存状态、交接物与明确的处理决定；H-01 的待核实/拒收记录和 H-02 成功记录同时保留。切换情境或重播会清空本段记录与日期选择，防止不同模拟串用决定。播放到结尾不循环，也不修改主话题或交付面板里的其他示例状态。

归档阶段仅展示带来源的知识草稿 K-01，来源包括目标 G-01、冲突 C-01、交接 H-01 和证据 E-02；不会向真实知识库写入内容。完整回归、安装与发布始终保持“本次范围外 / 未执行”。

建议走查：先播放全过程观察阻塞自动停留 → 补齐样例 → 在冲突处选择日期规则 → 核对失败交接并补齐重交 → 观察返工与复验 → 查看交付及归档 → 展开协作记录对照失败与恢复过程。

建议评审顺序：执行中 → 切协作看责任 → 返回对话 → 需要决定 → 选择范围 → 查看交付和证据 → 切已停止/待核实 → 试窄屏与深色。演示状态由独立“原型预览”控件切换，不与真实产品控制混淆。

## 9. 实施边界与验证目标

本节是设计落地顺序，不是实时开发清单；实际开发仍以 GitHub Issues 为唯一任务来源，每项独立实施与验证。

1. 对齐信息归属与文案：办公室/话题/成员身份、新输入与补充的区别、停止与未知结果。先保护现有业务行为。
2. 建立语义令牌及核心组件：先外壳、输入框、状态、决策，不一次重写全部页面。
3. 组织协作与成果：复用原任务图和证据来源；增加摘要与聚合入口，不复制状态所有权。
4. 完善窄屏、键盘、减少动画、异常空状态；桌面仍为当前产品交付目标。

四层约束：Logic 继续拥有业务状态与验收；Bridge 提供真实操作/事件契约；View 负责布局、选择、草稿与展示派生；不为视觉方案在 Core 增加业务模型。UI 新动作必须先检查已有服务是否支持，不用假按钮承诺恢复或撤销。

设计验证采用真实任务访谈/走查，建议 5 位目标用户、每人 30–45 分钟，先记录现有版本基线。指标是待验证目标，不是既有测量结果：

- 5 秒内说出当前工作区、话题和是否需要自己处理。
- 不依靠说明区分“新话题排队”和“补充当前话题”，关键误发为 0。
- 从交付摘要两次操作内找到改动与验证范围。
- 正确区分成员结束、验证通过、目标验收；不能因看到绿色就误判全部完成。
- 执行中查看成员/成果不打断任务，关闭页面不被误认为停止。
- 320px 下不横向滚动，停止/待决操作可达，键盘能够完成所有关键操作。

本轮校验范围：设计与已读取源码/规则的一致性、原型静态结构和能实际执行的浏览器交互；不运行产品测试、类型检查或构建。受环境限制未做的验证须在交付时明确，不能据设计原型宣称产品可用性已通过。
