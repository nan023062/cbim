# 四层架构的核心取舍

将技术机制、业务决策、可信宿主和界面分开，是为了让变化停留在其真正的责任范围内。源码层级已落地；本文只保留选择理由，当前类和子模块关系从 [源码架构](../src/ARCHITECTURE.md) 逐层阅读。

| 层 | 负责什么 | 为什么单独封装 |
| --- | --- | --- |
| Core | 独立技术机制、便携算法与平台实现 | 技术复用不应反向认识业务身份、授权和事务；平台入口与便携入口分离 |
| Logic | 业务规则、服务、状态和应用生命周期 | 同一业务事实只有明确的所有者，业务不依赖 Electron 或页面运行 |
| Bridge | 通信协议、可信宿主及平台装配 | 把消息传输、系统权限与业务决策分开，界面不直接持有服务和凭据 |
| View | 页面、交互和展示状态 | 展示真实业务事实；展开、选择和加载状态不成为另一套业务账本 |

## 依赖方向与代价

Core 不依赖业务；Logic 使用 Core，不依赖 Bridge、View 或 Electron；Bridge 通过公开入口组合 Logic 和平台机制；View 通过通信边界访问业务。类型引用与运行时代码同样需要保持单向无环。

同层目录并不意味着任意互引。稳定规则不加载运行服务，普通服务不反向认识 Application，具体引擎在装配点选择。公开入口按真实消费者保持细粒度，不能用一个全域聚合出口掩盖类型环。代价是需要显式端口与装配，但平台替换和业务迭代不会沿隐式依赖扩散。

## 状态与组合

业务事实、授权、事务和恢复由 Logic 拥有，生命周期由 Application 统一装配；Bridge 负责传输和可信平台适配，View 只投影与交互。跨领域需要原子提交的事实不能仅为整理目录而拆开。

可复用机制不自动成为共享单例。队列、缓存和集合由真实使用者持有；权限、文件、事务和领域状态仍各归其主。源码目录是内聚封装，直接子模块在父层被视为虚拟类边界；这不表示实际存在嵌套类或继承。
