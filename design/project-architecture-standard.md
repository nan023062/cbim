# 通用项目架构设计规范与原则

文档编号：1｜版本：1.0｜日期：2026-11-10｜性质：设计与开发必须遵守的规范

## 1. 目标与适用范围

**控制变化传播，让稳定能力可以长期复用，让修改、测试和代码理解都局限在清晰的范围内。**

本规范适用于项目架构设计、功能开发、缺陷修复、公共能力提炼和重构，约束系统、模块、类及接口的职责、依赖、状态、验证与维护交付。具体技术栈、分层名称、目录和工具由项目映射，不将某个仓库的组织方式作为通用前提。

开发 Skill 必须在设计和实施前读取并遵守本文；架构治理 Skill 也必须遵守本文，并执行 [文档 2《架构治理规范与治理流程》](architecture-governance-process.md)。本文定义“设计必须满足什么”，文档 2 定义“发现问题后如何治理”。已读取且内容未变化时可复用上下文，不重复机械阅读。

“必须／不得”为约束，“应”为默认做法，“可”为按实际情况选择。项目映射不得用目录重命名、接口包装或检查豁免规避约束；文档不自行授权代码修改、外部写入、合并或发布。

## 2. 十二条架构原则

### P01：按业务语义和变化原因划分职责

一个封装围绕同一类业务决策组织。判断职责时说明业务对象、变化原因、权威状态和消费者；互不相关的变化不应反复迫使同一封装修改。单一职责不以文件小、方法少或类名统一为依据。

### P02：稳定机制与易变策略分离，遵守开闭原则

通用机制负责可靠执行，业务策略负责条件与选择。变化频率不同的代码应分别封装，通过稳定契约组合；频率依据真实需求和变更原因，不能只数提交次数。

对已经识别的变化，主要通过新实现、策略、适配和装配扩展，减少对稳定核心的连带修改。真实契约变化和核心缺陷修复仍可修改核心，但必须解释原因、兼容代价和影响。不预建未知扩展框架，也不用大量开关假装实现开闭原则。

契约与实现的稳定性分别判断。长期无人使用或长期未改不能证明成熟；缺少证据时标为稳定候选。

### P03：分层明确，依赖单向且无环

先定义职责与允许依赖，再组织目录。层、实际逻辑模块和文件的依赖必须形成有向无环结构，类型引用、重导出及可识别的动态引用同样受约束。

运行返回、回调和数据流应与源码依赖方向分开说明。目录聚合中的双向边不直接证明文件循环，但需要核实是否混合了不同逻辑边界；文件无环也不代表模块已经解耦。

### P04：核心规则不依赖外部实现细节

核心通过自身需要的稳定端口使用存储、模型引擎、网络、文件和平台能力，由外部适配实现并在装配入口连接。UI、数据库、SDK 和供应商差异应尽量停留在对应实现。

端口及其类型不得反向引用具体实现。不得通过全局状态、服务定位器、动态加载或事件转发隐藏依赖；事件也必须明确协议、所有者和生命周期。

### P05：通过小而明确的公共契约协作

调用方只取得完成职责所需的能力，不直接读写其他模块内部状态或依赖其私有执行顺序。契约必须明确参数、返回、身份、权限、空值、错误和兼容边界中容易误解的部分。

公共类型与可序列化数据不得泄露服务实例、存储对象或平台句柄。编译期类型约束与运行时边界校验各有职责，不能互相替代。

### P06：共性抽象必须有业务语义依据

抽象前必须核对真实消费者、共同不变量、变化方向和合法差异，区分重复领域规则、重复技术机制与偶然相似。共用日志或存储不等于属于同一业务职责。

优先使用内聚纯函数、领域封装、组合与接口多态；使用继承时，子类型必须满足基类不变量、前后置条件及错误、取消和资源契约。子类需要禁用父类能力或扩大权限时，应重新评估设计。

允许暂时重复，说明暂不抽象的原因和再评估触发条件。不以重复次数、行数减少或假想消费者自动决定提取，也不强迫不同语义共用万能 Base／Manager。

### P07：状态、事务与资源必须有明确所有者

每份权威状态必须明确维护者、写入入口、生效时点和一致性要求；持久事实、派生视图、缓存与临时上下文分别说明。

事务边界由原子性要求决定，不为拆模块破坏事务内读取或原子提交。共享存储可以保留，暴露给业务的读写能力仍应收窄。进程、锁、连接、队列及临时资源必须有明确创建、取消、释放和恢复责任。

### P08：副作用与失败语义必须进入契约

必须说明操作修改的状态及外部副作用，区分未执行、部分完成、已提交和结果未知。失败、超时、取消、重试、幂等及补偿不能依赖调用方猜测。

调用报错不等于没有执行；未知结果不得未经核实重放。重构应保持相关权限、并发、日志／提交顺序、取消和资源释放语义，授权改变的行为应单独说明。

### P09：验证范围跟随真实影响

依据实际 diff、行为、公共契约、调用方、配置和数据格式选择相关单元及受影响消费者。依赖图只是证据之一：导入关系不变不代表行为不变，直接上下游也不一定是影响终点。

所有单元测试以一个明确责任模块为被测对象，按模块契约组织断言、数据和所需替身；不得直接或经共享辅助加载完整应用，不依赖其他测试套件、执行顺序或遗留可变状态。纯断言、数据构造、局部资源夹具和应用装配分开。不能只靠目录或名称判断单元隔离。

跨模块联合契约、事务、恢复、引擎和平台协作另保留必要的真实边界验证，并明确属于契约或集成测试。无关责任混在一个套件时应拆分，不能简单改名为集成测试。未受影响的稳定能力不重复验证，公共语义变化必须分析消费者；不得为了缩小测试范围降低原有断言或删除协作覆盖。

### P10：架构约束必须可以持续检查

将允许依赖、公共入口、循环和契约约束转为可核对的规则与检查。无法自动判断的职责混杂、接口过宽、依赖过密及共享状态耦合由代码 review 补充。

既有硬约束按既有规则执行；复杂度、相似度等新信号先形成有证据的发现，不自动成为阻断规则或触发重构。无法解析的依赖不能被当作不存在；动态引用需要说明可验证范围。

### P11：采用小步、可验证的渐进演进

每片围绕明确边界问题，依次建立行为依据、引入边界、迁移真实消费者、验证并清理旧出口。说明兼容及回退条件；区分结构重构与新增业务行为。

目录移动、增加接口或建立事件总线本身不算解耦。必须能够说明独立变化被限制在何处、保留了什么稳定能力。抽象失配时允许收缩、拆分或退役，不因既有投入继续扩大错误抽象。

### P12：维护者可理解、可接手属于完成条件

源码、注释、契约和架构图必须描述同一实际系统，区分代码事实、执行证据与推断。重要职责、公共契约、状态归属或生命周期变化时，必须说明原因、关键路径、设计取舍、验证边界和下一次修改入口。

完整 diff 和真实代码 review 不得被摘要、图示或测试通过替代。材料交付、行为验证、人工接受分别记录；不得声称维护者已经理解或接受尚未确认的内容。

## 3. 参考职责与依赖模型

以下是可映射的职责角色，不要求逐项建目录，也不规定所有项目采用相同层数。具体模块及其允许依赖由项目按业务边界明确，最终形成有向无环结构。

| 职责角色 | 负责内容 | 依赖边界 |
| --- | --- | --- |
| 表现层 | 展示、交互、页面本地状态 | 通信契约、公共展示能力；不依赖后端服务或存储实现 |
| 通信边界 | 操作定义、请求／响应、序列化与边界校验 | 独立公开契约及必要纯类型／纯函数；不承载业务编排 |
| 应用编排 | 组织用例、组合领域与跨域能力 | 领域／执行公共契约和所需端口；实现由装配注入 |
| 领域规则 | 业务对象、不变量、领域状态转移 | 本域规则及明确公共契约；跨域依赖必须显式允许且无环 |
| 执行机制 | 授权执行、日志、取消、结算和生命周期 | 必要执行契约及端口；不认识具体业务策略和供应商 SDK |
| 技术适配 | 存储、文件、SDK、网络与平台实现 | 被实现的端口、纯契约与外部库；不反向决定领域规则 |
| 装配入口 | 创建实例、选择实现、注入与应用生命周期 | 可认识要组合的能力；其他模块不得反向导入装配入口 |

规则和机制声明所需能力，适配器实现端口，装配连接二者。公共契约由有权定义语义的边界拥有，不能为消环将不相关职责堆入万能公共层。

## 4. 模块设计最小契约

模块的现有契约或架构资料必须能够回答以下问题；小模块可简写，不要求每项独立成文。

| 项目 | 必须明确的内容 |
| --- | --- |
| 职责 | 负责什么、不负责什么，按哪类业务决策划界 |
| 入口与依赖 | 公共入口、允许依赖、实际消费者及不得穿透的内部实现 |
| 状态与资源 | 权威数据、写入者、事务、生命周期和释放责任 |
| 行为契约 | 输入输出、权限、副作用、失败、取消、恢复和兼容语义 |
| 稳定与变化 | 稳定能力与证据、策略／适配／装配位置、真实扩展路径 |
| 验证与维护 | 受影响单元、边界协作验证、阅读顺序及下一次修改入口 |

原则存在取舍时，必须描述实际不变量与影响，例如模块拆分不能破坏原子性；不能用“更符合分层”笼统覆盖业务正确性。

## 5. 验证与维护交付要求

1. 实施前明确范围、业务语义、依赖方向、状态归属以及允许改变和必须保持的行为。
2. 运行验证前说明相关单元和消费者的选择依据；选择器必须选中目标用例，零用例不能当作通过。
3. 静态检查按类型、依赖、模块边界或架构资料的实际变化选择，不设置每次修改固定必跑的检查套餐。
4. 相关验证通过后收尾；只有新改动、失败或新增影响证据才补跑。全量回归集中在后续自动化集成，真实制品验收在集成／发布阶段完成；不绕过项目既有检查。
5. 纯文档及 Skill 修改只核对事实、格式、引用和多入口一致性，不运行无关产品测试、类型检查或构建。
6. 源码改动同步维护相关注释、契约和架构资料；范围、文档形式及检查入口按项目映射。不得将未来目标写入当前实现说明。
7. 交付完整改动、真实验证结果和未覆盖范围，并分别陈述人工 review、合并与发布状态。

每次设计或开发必须能回答：保护了哪部分稳定能力；把哪类变化限制在何处；为何选择这些验证；维护者下次从哪里修改。答案可放在已有记录中，不额外制造审批或重复文档。

## 6. 项目映射与规范验收

项目应提供四类映射：**边界与公共入口、状态与契约、验证与证据、维护与决策责任**。可引用已有资料，不要求另建平台或特定文件结构。

设计符合本规范，必须能够用真实契约、调用链与消费者证据说明：职责按变化原因划分，依赖单向且可检查，状态和副作用归属明确，已识别的变化有受控扩展位置，验证及维护范围有依据。不能仅凭目录名称、无环统计或测试数量宣布符合。

CBIM 的具体映射及 G01–G09 整改见文档 2 的项目附录。本规范不维护工单进度，不表示既有代码已全部符合目标，也不把架构评估自动转为代码实施。
