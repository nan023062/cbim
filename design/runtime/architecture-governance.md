# 架构治理

遵循[通用规范](builtin:common-rules)、[架构评估规范](builtin:architecture-spec)与[Module 规范](builtin:module-spec)。读取本流程不批准架构变更。

1. 从职责重复、边界失配、依赖恶化、契约变化或不适用抽象等实际信号出发，限定受影响模块和治理目标。
2. 查询模块知识及相关 Agent，建立有证据的模式观察，区分重复代码、重复责任、偶然相似和稳定规律，不先设定必须抽象的结论。
3. 比较保持现状、局部整理、边界调整与新抽象的收益、复杂度、迁移成本和长期维护责任。核对源码事实与已有契约；证据不足时补查或保留未知。
4. 给负责人清晰的取舍、影响和验证方案。观察、暂缓或否决都是有效决定。需要人工确认的结构决定必须取得实际确认，不能用程序校验或 AI 自评替代。
5. 获授权后按模块渐进实施，明确依赖、回退、兼容边界和行为保持要求，避免大范围无序并发写入。
6. 核实结构、业务行为、回归和负责人理解；图示美化不等于架构改善。实现偏差不能自动改写正式契约。
7. 将已确认的规则与边界通过 MCP 预览并提交到正式知识，服务更新相关定义与注册表，宿主不得直接编辑 .cbim。保留观察与正式约束的区别，不复制第二套权威知识。
8. 返回原任务，记录决定、证据、未解决项、治理责任和复查触发条件，不因一次检查通过宣称长期健康。
