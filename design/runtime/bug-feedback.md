# BUG 反馈

适用于用户点击对话窗“+ → BUG 反馈”，或明确要求调用 BUG 反馈 Skill。遵循[通用规范](builtin:common-rules)。这是产品反馈收集，不是当前工作区的业务开发任务。

## 首次调用

先核对本轮实际活动工具，`cbim_knowledge_tool_catalog` 只列知识族，不能据此判定反馈工具缺失。提交和核实工具应同时存在；任一缺失时先调用本轮提供的 `cbim_feedback_status`，按真实错误码提示，保留已经填写的上下文，不让用户反复重填。连接诊断不证明原提交结果；只有尚未发起过的反馈才能称“尚未提交”，已有未知提交始终保持待核实。

- `GITHUB_NOT_CONNECTED` 或 `GITHUB_EXPIRED`：说明尚未提交，按诊断提示连接或重新连接账号，之后发送新消息继续。
- `GITHUB_AUTH_PENDING`：本机还在等待授权结果，请回到 GitHub 反馈设置页并保持打开直到显示已连接；网页授权完成后不要求再授权一次。
- `FEEDBACK_NEW_TURN_REQUIRED` 或 `GITHUB_CONNECTION_CHANGED`：账号已连接或连接已变化，请发送新消息开启新一轮，沿用原上下文；不要要求再次授权，不自动重发未知提交。
- `FEEDBACK_TOOL_NOT_LOADED`、`GITHUB_SETTINGS`、`GITHUB_SECRET_STORAGE`：按返回事实说明组件、设置或安全存储问题，不解释为账号未连接。
- 状态工具也不存在，或状态称就绪但实际仍缺工具：说明“尚未提交，本轮反馈工具不可用，连接状态尚未核实；请检查 CBIM 版本或重启应用并查看运行日志”，不声称重新连接一定能解决。

先告诉用户“请按下面的格式补充，暂不清楚的项可以写‘不清楚’；填写后会直接提交到设置中已连接的 GitHub 仓库，请勿填写凭据或不愿分享的信息”，展示以下可复制格式，然后等待用户回复：

```text
问题简述：
复现步骤：
1.
2.
实际结果／报错：
期望结果：
CBIM 版本、操作系统：
出现频率（可选）：
截图或相关日志（可选）：
```

用户已经给出部分内容时，先按格式归位，只问影响理解或复现的缺口；不要求重复填写。环境没有可靠来源时保留“不清楚”，不猜版本、复现过程、影响范围或根因。截图与日志使用现有附件入口，由用户自行选择；不读取、上传完整工程、会话或凭据。

## 收到上下文

整理标题、复现步骤、实际结果、期望结果及已知环境，保留用户原意，明确尚不能复现或缺失的事实。反馈授权不等于修复授权，不创建业务目标、不派工、不更改文件。

上下文齐备后直接调用 `cbim_feedback_submit`，不增加草稿确认或逐条审批。传 `kind:"bug"`，将问题简述、复现步骤、实际结果、期望结果和环境分别填入 `summary/steps/actual/expected/environment`；可选补充填 `extra`。只使用用户愿意提交的内容，不把推测、完整会话、工作区资料或附件全文自动加入。用户明确说“不清楚”的字段保留原意；空缺且影响理解时继续追问。附件仅在用户明确提供可分享链接或说明时加入 `extra`，本工具不自动上传本地截图或文件。

只有实际工具返回 `status:"submitted"` 才表示创建成功。此时立即结束反馈流程，**不再输出“已提交”、Issue 编号／链接、回执、总结、后续处理说明或其它结果消息**。不查询开发进度。

如果本轮没有提交工具，按上面的可用性检查区分原因；如果只读权限拒绝提交，说明需切换允许写入的会话权限。连接授权只允许这个固定仓库，不可用浏览器填单、命令、任意网络工具或模型参数改变目标。GitHub 明确拒绝时保留原上下文并简短说明错误，不循环重试。超时、取消、未知或坏回包后仅在 `cbim_feedback_receipt` 实际可用时核实原提交一次；核实成功同样静默结束，仍未知或核实工具不可用则说明“提交结果待核实，未自动重发”，不要换正文、调用 ID 或会话重发。原提交核实不是开发结果回访。

后续处理结果统一进入软件版本更新日志；本 Skill 不建立“我的反馈”、进度订阅或逐条结果回访。

`GITHUB_PENDING_OTHER` 表示当前工作区另有不同内容的待核实提交：停止本条提交并保留用户正文，不把其它原提交的回执当成本条成功。硬中断后可在新会话明确要求核实原提交；同一工作区相同账号／仓库／内容跨会话也只创建一次。核实有界，原 Issue 被改写或未找到时保持未知，不承诺自动恢复。
