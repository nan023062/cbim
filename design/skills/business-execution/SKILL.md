# 需求实现循环

这是 CBIM AI 助理内置的需求实现 Skill，保留 `business-execution` 标识。新功能、修 bug、业务排查、测试与获批方案实施使用本循环；只要求分析时交付分析结果，不自动实施。

输入：用户目标、当前问题或预期行为、范围与授权、调用方提供的项目索引及必要知识、已有任务与结果。输出：实际产物、逐项验收证据、知识同步需求、演进信号、未完成条件及返回位置。必要验收全部满足才结束为完成；缺少条件时保存进展并返回，不空转循环。

由 CBIM AI 助理执行以下步骤，AI 成员 按已派发的任务上下文、自身工作原则和专业 Skill 完成子任务。索引位置及路径基准由调用上下文提供。按顺序推进；条件不满足时按对应分支返回或暂停，不以介绍流程代替执行。

开始任务时读取并执行 [任务知识基线与恢复](../../task/task-baseline.md)，在实际使用知识时建立绑定，派发、恢复与验收前复核。

任务构建与调度统一使用 [Task Loop](../../task/task-loop.md)。本 Skill 提供业务目标、复用约束、验收与认知交付要求；其他类型的问题返回调用方决定，不直接加载其他 Skill。


涉及架构评估或高影响认知交付时，按 [架构评估与认知交付规范](../../task/architecture-spec.md) 核对必要约束。

## 1. 建立目标与当前基线

对明确选中的知识或产物文件，使用 [文件基线脚本](scripts/file_baseline.py) 保存与复核，不临时生成快照或哈希比对脚本：

```powershell
python -B design/skills/business-execution/scripts/file_baseline.py --root "<工程根>" snapshot --path path/to/file
python -B design/skills/business-execution/scripts/file_baseline.py --root "<工程根>" verify --manifest <用户主目录>/.cbim/<项目标识>/task-records/<记录目录>/manifest.json
```

公共参数 `--root <项目根>` 放在子命令之前；省略时使用当前工作目录。`--path` 可重复，且只接受项目内显式文件。snapshot 写入独立本地任务记录，保留内容快照、哈希与清单；verify 只读报告未变、更改或缺失，核对历史快照是否被篡改。退出码 `0` 保存成功或全部未变，`2` 当前文件有变化，`1` 输入、快照或读取错误。它不回滚文件、不检查清单外新增文件，也不替代复现、构建、测试或业务验收。任务授权与恢复决定继续按本 Skill 和任务基线执行。

- 从用户输入整理目标、当前问题、期望结果、不变事项和已有授权。将验收条件写成可检查的结果，例如操作结果、接口行为、资源效果或有依据的分析结论。
- 修 bug 时记录触发条件、实际与预期行为、复现证据及回归范围；无法复现时保留不确定性，不声称根因已证实。新功能明确使用场景、输入输出、兼容边界及验收样例；调查所得再用于调整实现任务。
- 查看现有产物和进行中的修改，区分本次工作、用户已有修改及其他任务产物。恢复任务还须核实已发生操作，不能重复执行已完成的发布或修改。
- 缺少影响下一步的信息时只问必要问题；能够独立推进的部分继续。仅分析的请求保持只读。
- 按影响确定认知交付要求：局部、易逆转的改动在结果中说明意图与使用注意即可；涉及公共契约、数据迁移、发布运行、跨模块状态或难以逆转的效果时，明确需要理解和接管的负责人、关键决策及验证场景。负责人按本次任务确认，不能由 authors 自动推定；缺少负责人只暂停依赖其决定或接管的步骤。

产出：目标、验收条件、范围与基线。足以开展定位后进入步骤 2。

## 2. 定位模块、检查已有知识并匹配能力

- 通过 Task Loop 取得模块定位与实际工作范围，将所需业务事实及契约列入任务上下文。
- 读取 overview 中经人工确认的契约和架构依赖约束，并以实际引用核查实现是否符合。缺少声明不等于没有依赖；发现冲突时记录实现偏差，不以代码现状覆盖架构约束。
- 在提出方案和拆分实施任务前，从候选模块及相关上级、依赖模块的 DNA 中按需检索正式抽象（established_abstractions）、观察模式（observed_patterns）和历史处置决定。沿权威引用读取适用范围、不变量、扩展点、不适用条件及当前生效状态，再核对实际产物；这些是知识类别，不假定存在同名目录或独立注册表。
- 对命中的候选逐项判断：仍有效且契合当前目标的优先复用，将契约与扩展约束带入任务；不适用的记录具体差异与不采用理由，不强行套用；已废弃或被替换的按当前迁移约定处理，不直接沿用旧入口。需要改变公共契约或扩大抽象适用范围时先向调用方返回结构决定请求，不以“复用”为名静默修改边界。
- 观察模式只提供证据与线索，不作为强制实现要求。对照已有暂缓或驳回理由及复查条件；没有新依据时沿用有效决定，有新需求或反例触发复查时向调用方返回结构复查请求。未找到可用抽象时记录检索范围，在已有授权和契约内允许局部实现，不宣称全项目不存在可复用机制。
- 发现重复职责、边界失配、公共契约变化或既有抽象不适用时，将证据与受影响范围作为结构评估请求返回调用方。记录本步骤为返回位置；不阻塞当前目标的观察允许业务继续，必要结构决定未解决时仅暂停受影响任务。
- Agent 匹配、维护依据与缺口处理使用 Task Loop 的结果。
- 对实际承担工作的每个模块核实候选 Agent 的维护依据与本次能力适用性，区分已确认、未知和有冲突的归属；作者同组和能力匹配只提供候选，不能代替维护依据。仅需读取的模块列为上下文引用，不自动加入 Task 的模块集合。维护归属未确定时先调查，不把未经核实的组合标为可派发。
- 没有可靠模块归属时限定调查范围，不虚构模块；没有合适能力时明确缺口，不强派其他专业角色。需要先修正必要知识时向调用方返回知识修正请求，取得处理结果后重做本步骤。

产出：模块与AI 成员 的匹配、必要知识入口、复用或不采用的结论与依据、待核实事项。检索与适用性判断完成后才进入方案和实施任务拆分；调查任务可先行。

## 3. 提供业务任务上下文

按 [Task 定义](../../task/task-spec.md) 提交目标、业务验收条件、不变事项、复用依据、输入产物及知识基线。必要的设计意图、失败路径、负责人认知要求和回退条件一并进入上下文，不重定义 Task 字段或分组算法。向用户展示计划时使用自然语言结果。

## 4. 构建与检查业务计划

使用 Task Loop 构建、匹配和打包任务，并检查依赖及并行范围。复核计划是否覆盖全部业务验收目标；缺少目标回步骤 1，复用约束失效回步骤 2。就绪条件、依赖环与冲突处理遵循 Task Loop，不维护第二套规则。

## 5. 执行业务任务

由 Task Loop 使用 [execute(task)](../../task/base-task.md#execution) 派发就绪任务。业务结果包含实际产物、适用验证、未运行项与实现取舍，尤其说明对调用方的影响、排障入口和恢复方法。派发、失败及结果覆盖要求遵循执行接口。

## 6. 判断业务反馈

使用 Task Loop 验证结果、更新任务与依赖。业务条件或方案意图变化时更新输入，只重开受影响部分；需要其他专业决定时，向调用方返回证据、影响、阻塞判断和继续位置。无新修正依据时不重复尝试。必要条件未解决则保持受阻，独立任务可继续；全部必要任务通过后进入步骤 7。

## 7. 验证整体、复查演进信号并同步知识

- 将子任务结果逐项对应步骤 1 的验收条件，检查接口衔接、共享文件一致性、受影响调用方及必要的跨模块回归。
- 核对AI 成员 按工作原则提供的适用自测、构建、运行或资源验证证据。结构与索引校验不能代替业务效果验证，子任务通过不能代替整体验收。
- 按步骤 1 的影响范围交付设计意图、关键不变量、输入输出与状态或资源流、已知失败路径、排查入口及恢复条件。可直接在交付记录中说明或引用现有权威正文，不要求另写固定份数的文档。
- 对需要人工认知确认的高影响任务，用代表性使用场景或故障推演帮助负责人说明“输入从哪里来、状态归谁、失败影响谁、先查哪里、如何恢复”。记录实际反馈与尚未理解的部分；只发送文档或 AI 自评不能标记负责人已理解。属于本次必要接管条件的缺口保持待确认，独立工作可继续。
- 整体验证失败时定位负责模块，将修正任务加入步骤 3，并复查修正影响范围。必要工具或环境缺失时明确未执行项，保持待验证或受阻。
- 在本轮结束前，CBIM AI 助理汇总实际变更、执行者新发现与验证结果，对照步骤 2 的复用判断和已有观察，检查本次是否新增重复职责、同源语义多处变化、依赖或边界压力、契约偏差、抽象不适配，以及是否满足已有观察的复查条件。检查限于本次影响范围，不要求全项目扫描；受阻或部分交付时也保留已发现信号。
- 对信号明确分类：纯知识遗漏向调用方返回知识修正请求；局部实现缺陷返回修正；结构性信号或已满足的复查条件向调用方返回结构评估请求，传递新旧证据、相关观察位置、影响范围、是否阻塞原目标，并记录本步骤为返回位置。仅相似或重复次数增加不直接触发实施重构。
- 调用方提供继续观察、暂缓或驳回决定时，保留理由和复查条件；非阻塞后续治理作为独立事项，不延长已经满足验收条件的原业务任务。影响当前正确性、必要契约或验收的缺口必须解决后才放行。若从架构治理转入的实施任务没有新信号，直接向原任务回报结果，不重复发起相同评估。
- 本次未发现新结构信号时，简要记录检查范围与“未发现”的结论，不编造观察条目，不宣称全局架构健康。需要长期保存的信号作为独立事项交由调用方安排固化；尚未写入时明确待处理事项，不以聊天线索冒充已固化知识。
- 对需要固化的事实、契约和流程变化向调用方返回知识同步请求，附证据、范围与待同步内容。取得处理结果后复核知识与最终产物一致；若改变任务依据，重新检查受影响结果。
- 验收前再次核对知识基线与验证所对应的产物，尤其检查治理刚更新的依据是否改变验收要求。对需要交付后深度复盘的任务，记录负责人、复盘内容、时间或触发条件及安排确认状态；不代替负责人承诺排期，也不默认创建定时任务。

产出：整体验收结果、演进信号与处置结果、必要知识同步结果及非阻塞后续事项。仅在必要验证与阻塞项全部满足后进入完成交付，不要求每次任务产生新抽象。

## 8. 统一回复用户

说明实际结果、产物位置、验证方法与结果，以及残留风险和待处理项。涉及发布或写入外部系统时，核实实际回执、目标位置与产物版本；回执缺失或结果不明时先查询实际状态，不能以发出请求代替交付成功，也不能直接重复执行。保留可追溯证据；未执行、失败、受阻如实列出，不将局部成功包装为全部完成。分析任务交付结论与依据，不声称实施完成。

交付记录关联最终知识与产物基线，说明必要认知确认结果和后续复盘安排。区分“业务已验收、后续复盘待进行”和“必要接管尚未通过”；后续复盘产生的事实或结构信号按类型返回调用方，不把已交付任务无限延长，也不隐瞒当前阻塞。

调用方委派的业务子任务返回产物、证据、剩余条件与继续位置。获批方案失效时返回重新评估请求，不自行扩大变更。
