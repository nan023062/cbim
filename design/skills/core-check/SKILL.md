# Core 检查

仅在用户明确要求执行 Core 检查时使用。CBIM AI 助理和 AI 成员不得自行触发，也不得因 core 发生变更、其他流程返回问题或进入交付阶段而自动运行。此 Skill 不列入核心工作流；用户发起后，可由 CBIM AI 助理按指令执行。后续复查同样须在用户明确要求的范围内进行。

本 Skill 只负责检查与反馈，不替代知识修正或架构决定。输入为 core 根目录、启动入口、变更范围、已有检查结果，以及调用方提供的校验工具和参数。默认检查整个 core，并包含启动入口、team 和 workspace 的执行引用；增量检查须覆盖变更文件的引用方，不能将局部通过描述为整体通过。

输出包含检查范围、所用版本、依赖检查、README/docs 隔离检查、Team 与 Skill 继承检查、具体问题、未检查项和返回位置。检查完成与检查通过分别报告。需要任务拆分时使用 [Task Loop](../../task/task-loop.md)，纯 core 检查使用明确检查对象，不虚构业务模块；版本与恢复遵循 [任务基线](../../task/task-baseline.md)。

## 1. 建立检查清单

核实当前文件与已有修改，记录实际使用版本。枚举 core 下的 Markdown、Schema、脚本及入口引用，排除缓存与本地历史快照。README 文件名与 design/docs 路径按大小写不敏感识别：两者面向人，不作为执行起点；其余可被 Agent 作为规则、抽象、流程或知识输入的 Markdown 及 JSON 引用字段属于执行检查范围。用途不明的文件单列待核实，不能借标成说明文档绕过检查。

README 与 design/docs 可作为本次审查对象读取，但不作为启动、路由、执行或验收规则的来源。

## 2. 检查依赖方向

运行调用方提供的依赖校验工具，记录真实命令、退出码与输出。执行依赖只能是 skills → task → business / capability → connector，以及独立分支 memory → task；Memory 由入口装配，其他抽象不得反向依赖 Memory，Memory 不跳过 Task 依赖其他抽象；允许层内必要引用，但不同 CBIM AI 助理 Skill 不相互加载。下层不能反向加载上层，Skill 不能跳过 Task 直接依赖业务或能力抽象，business 与 capability 不互相依赖；它们可依赖 connector，connector 不反向依赖任何上层。

检查越界路径、缺失目标及依赖环。再复核正文中的“读取、加载、执行、调用”等指令，识别没有链接的反向依赖及跨 Skill 调用。调用方传入的检查对象是数据，不等于引入执行依赖；不能把实际流程调用伪装成数据。自动脚本不覆盖的语义和循环检查须明确记录人工走读结果。

README 与 design/docs 均为人类阅读材料；检查入口、team、workspace 及 core 执行文档的直接和间接引用，防止把人类设计说明重新加载为执行规则。用户要求修改文档时作为任务对象读取不受此限制。

## 3. 必执行的 README/docs 隔离检查

明确收到用户的 Core 检查请求后，统一调用 [固定检查入口](scripts/check_core.py)，不临时生成引用分析脚本。该入口复用已有权威检查器并保存真实命令、退出码及原始输出：

```powershell
python -B design/skills/core-check/scripts/check_core.py --root "<工程根>" --user-requested
```

`--user-requested` 仅记录本次确有用户请求，不构成新授权，不得由其他 Skill 为自动触发检查而添加。缺少该参数时脚本直接拒绝且不运行检查；两个子检查全部返回 0 才退出 0；任一失败或未完成均退出 1，逐项保留原始退出码与输出。默认项目根为当前工作目录，可用 --root 显式指定；必要自然语言语义复核仍按本 Skill 执行。

每次用户发起 Core Check，必须运行隔离检查，不得仅做关键词搜索或以注册表通过代替。项目根目录下执行：

```powershell
python design/scripts/check_core_dependencies.py --root "<工程根>"
```

该命令同时检查分层依赖与人类文档隔离。记录实际命令、退出码、`Human-document isolation` 结果及全部违规链；步骤 2 已对同一版本运行此命令时复用回执，不重复运行。工具入口由调用方提供，无法执行或输出不完整时记为未完成，不视为通过。

覆盖 core、入口、team、workspace 的执行 Markdown 与 JSON：检查行内链接、引用式链接、HTML 链接、显式内联路径，以及 JSON 的知识、工作原则、Skill、Workflow、Schema 引用字段。执行文档直接或经中间执行文档引用 README 或 design/docs 均失败。相对路径按来源文件解析，项目根路径按项目根解析；大小写变体也应识别。报告来源、位置、目标及引用链。

README 与 design/docs 可面向人导航到规范；它们自身不作为执行起点。sources 中的路径仅声明工作范围，不自动视为指令导入；若正文要求从这些路径加载执行规则，仍须报告。用户明确要求审查或修改人类文档时，可以作为任务对象读取，不能借此将其作为执行规范。

自动脚本之外，复核没有显式链接的自然语言加载指令。纯文字禁止加载不是违规；不能把路径命中数量直接当作违规数量。

**失败条件：**任何直接或间接违规引用都会使命令返回非零退出码，Core Check 必须报告未通过，不忽略退出码、不降级为提示。即使脚本返回 0，人工复核仍发现加载指令时，整体隔离结论也为未通过。工具失败、缺失或必要覆盖未完成时报告未完成，不能宣称通过。

## 4. 检查 Team 树与 Skill 继承

固定检查入口同时运行 Team Skill 权威校验器，单独保存 `team-skills` 回执；不调用知识治理 Skill，也不修改清单或注册表。覆盖完整 Team 树，包括没有 Agent 的 Team、任意深度子 Team 和 team 根。检查各层清单与实际入口一致、引用边界、重复登记，以及每个 Agent 从自身逐级到根的继承链；兄弟和后代 Team 的方法不得混入，名称或目录名冲突不得静默覆盖。任一错误使整体检查未通过，不能用依赖检查通过代替。

按调用方提供的 Agent 规范，人工复核专属方法只登记在 Agent，共享方法位于合理的共同 Team；继承结果不重复写回 Agent。沿启动、派发和恢复路径核对完整清单确实进入任务上下文，包含来源与版本，必要正文按任务读取；失败不得退回私有或部分清单。目录结构校验不能证明方法归属合理，也不能证明宿主实际加载或业务执行成功。未运行的加载路径只能报告走读结果。

## 5. 检查人类文档与执行规范职责

核对 README 是否说明用途、目录和使用方法，design/docs 是否解释设计与理由。若某个执行所必需的规则仅存在于这些人类文档，报告“执行规范缺失或放错位置”，不能简单建议删除链接导致规则丢失。

建议将必要规则迁至所在层的专用规范正文，再让执行文档引用规范，人类文档保留概述、设计理由和导航。检查重复规则是否冲突、人类文档描述是否过期；不要复制两份权威规则，也不要仅改文件名后宣称完成职责分离。

## 6. 汇总问题与修正建议

每项记录：类别、来源与位置、证据、违反的约定、影响范围、建议处理方式。区分已确认违规、需语义确认和工具未覆盖项。格式化输出建议使用“依赖方向 / README/docs 隔离 / Team 与 Skill 继承 / 职责与一致性 / 未检查项”五组，合并相同根因但保留所有受影响引用。

检查只读，不自动删除、改名、迁移规则或重写索引。将修正请求及返回位置交给调用方，由 CBIM AI 助理按已有授权安排后续流程；不直接调用其他 Skill。

## 7. 复查与交付

收到修正结果后比较新旧版本，重查受影响文件、引用方和依赖链；规则迁移同时检查新目标存在、正文完整及旧链接残留。无新证据时不反复重跑同一失败项。工具不可用时完成可做的静态审查，并列出缺失覆盖及继续条件。

最终分别报告三项结论：依赖检查、README/docs 隔离、Team 与 Skill 继承是否通过；机器结果与人工语义复核分别说明。还有明确违规或必要检查未完成时不得宣称 core 检查通过；完整列出问题可以表示本轮检查已完成。注册表检查不能代替这些检查，结构检查也不能证明业务运行正确。
