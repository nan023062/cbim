# 知识检查与治理循环

这是 CBIM AI 助理内置治理能力中的知识分支。输入为检查或维护目标、范围、权威资料、适用规范与工具、有效授权及已有证据；输出为格式检查和事实语义检查结果、问题位置与依据、授权内的修正、未检查项及返回位置。

默认检查模式只读，步骤 1～3 后执行步骤 6～8；用户已要求新增、修正或清理知识时使用维护模式，执行全部适用步骤，不重复索取已有授权。检查发现问题不自动切换成维护模式。完整查明并报告错误可以完成检查任务，但不能宣称知识通过校验；必要检查未执行时只能报告部分完成。

由 CBIM AI 助理按以下步骤执行。能力知识与业务知识独立维护；治理负责权威归属、证据和一致性，不替代业务实现。仅评审时沿只读分支完成，不因加载 Skill 自动修改。

本 Skill 根据事实和有效决定维护知识，不通过修改文档自行批准新架构。需要结构取舍或其他专业处理时，返回问题、证据及继续位置，由调用方决定后续流程，不直接调用其他 Skill。

开始任务时读取并执行 [任务知识基线与恢复](../../task/task-baseline.md)，绑定所用规则、定义与正文，记录治理前后内容的对应关系。

需要构建和派发模块任务时复用 [Task Loop](../../task/task-loop.md)，由本 Skill 提供治理范围、权威知识归属及一致性验收条件。分析模块与 Agent 关系后，先检查依赖再确定 Task 分组；执行结果返回本 Skill 对应步骤继续核实与治理。纯 core 或能力维护仍使用明确维护对象，不为进入循环虚构业务模块。

## 1. 明确治理目标与基线

- 确认要解决的知识问题、目标对象、期望结果和已有授权，例如新增 Agent、修正模块边界、迁移引用或清理重复定义。
- 读取当前文件及必要引用，核实已有修改。记录事实依据、已确认决定、推断和待核实线索，避免将旧记录直接覆盖当前文件。
- 若调用方提供既有业务结果，接收实际变更、验证证据、待同步知识和返回位置；恢复任务先确认哪些变更已经发生。
- 记录当前知识的可恢复基线及正在使用这些知识的已知任务。恢复时先比较绑定版本与当前内容，相关语义变化须重新核实决定和验证范围，不凭文件自述的版本说明继续。

产出：治理范围、当前基线及证据清单。缺少必要依据时先调查，独立部分可继续。

## 2. 确定知识归属与权威文件

将目标对象、权威资料位置、适用规范和维护工具作为 [Task](../../task/task-spec.md) 的上下文输入，由执行任务按需读取和核实。调用方提供项目文档与工具入口，缺失时返回缺口，不将目标资料变成本 Skill 对底层目录的固定依赖。

需要区分能力定义、业务知识、任务抽象、入口规则和派生索引的权威归属。治理对象本身可以是任意层的文件，这是被检查或修改的数据，不表示本 Skill 需要导入其实现或执行其中流程。仅读取与本次维护目标有关的规范。

区分结构化定义与正文：JSON 是字段与清单的唯一来源，Markdown 承载原则、知识和流程。共享知识确定一份权威正文，其他位置通过引用复用。观察线索不能直接写成已确认契约；个人短期记录不能替代共享证据。

涉及能力知识时，按调用方提供的规范区分 Team 与 Agent 的所有权：Team 是任意深度的树；专属 Skill 仅登记在 Agent 的 agent.json，共享 Skill 在所属 Team 的 skills.json 登记。共享方法放入覆盖实际使用者的共同 Team，全团队通用方法放入根；不复制到每个成员，也不将 CBIM 助理 core Skill 混入专业能力继承。

产出：每项知识对应的权威文件、必要引用方与拟处理方式。

## 3. 分析影响并列出改动项

- 检索相关定义、上下级模块、依赖方和引用方，列出需要新增、修改、迁移、删除或保持的文件及原因。
- 模块直属文件与直属文件夹统一归入虚拟子模块，按 Module 规范表达；它们规模小、分散、尚未独立建模属于正常组成，不以此报错、强制拆分或当作游离文件。虚拟子模块不独立注册，不覆盖其他模块的既有维护归属。
- 模块类图是人工确认的设计规范与约束；对逻辑模块关系以类图及已确认边界为准；对物理工作区核对 sources 和 scope，不从源目录结构自动推导模块树。
- 若问题涉及职责重组、依赖方向、公共契约或抽象取舍，向调用方返回结构决定请求，附事实、冲突与继续位置；依据已确认结构修正文字或类图可直接继续。取得有效决定后再更新，不把“文档与实现不一致”一律解释为应修改实现。
- Team 移动或共享 Skill 变更须沿子树识别全部受影响 Agent，比较变更前后的继承链、可见方法、来源与冲突；同时检查祖先和兄弟边界，不能只验证直属成员。
- 对迁移或删除列出引用替换方式、应保留内容与现有授权。读取引用不代表取得修改被引用模块的权限。
- 并行治理同一文件时指定一个写入者或串行交接；出现相互矛盾的契约时核实实际产物和决定依据，不按读取先后裁决。
- 仅评审的任务记录检查范围、问题、证据和建议，跳过写入步骤 4～5，进入步骤 6～7 完成格式与语义检查，再交付。确需用户决定的边界或取舍集中说明；已有授权内的常规修正继续执行。

产出：具体文件改动项与检查方式，不新建一套重复的永久知识目录。

将检查或改动目标、适用规范、维护依据、引用一致性与整体验收要求作为 Task Loop 输入。检查模式的验收是完成约定检查并提供可追溯发现，不要求执行者擅自消除被检查对象的错误。分组、冲突、派发、模块变化和下游放行使用 Task 层规则；本 Skill 核实治理结果，不重定义调度。纯 core 或能力维护使用明确维护对象，不虚构业务模块。

## 4. 更新权威内容

逐项执行步骤 3 的改动，保留无关内容与其他任务的有效成果：

- 定义变化先更新对应 JSON，再同步受影响正文；正文变化不复制结构化字段形成第二份定义。
- 新增或移动知识、Skill、Workflow 时同步所属对象清单与入口引用；CBIM AI 助理专属 Skill 由主入口路由，不塞入专业 AI 成员 的本地列表。
- Team 或 Skill 迁移同步原归属与新归属清单、相对引用及树索引；继承清单只作解析结果，不展开写回 Agent。专属与共享归属不明时记录待核实，不因脚本通过自动认定共享边界。
- 模块目录变化同步目录 id、引用与索引来源；物理源变化更新 sources，不因此改写逻辑父子关系。
- 修订流程时写清触发、输入、操作步骤、检查结果、失败处理和完成条件，不只保留定位介绍。
- authors 引用已知真人，同一对象多位作者须属于同一已知组；未知使用约定状态，不猜测人员归属。
- 架构事实、约束与规范须经人工 review 确认后写入正式模块知识；核查证据只支持对应范围的实现结论，代码偏差不能自动改写架构约束。
- 变更后保留前后版本依据、差异及适用范围，向已知受影响的在途任务回报，不直接覆盖其历史绑定。修改本次使用的入口或 Skill 时也记录变化，按共用规则判断是否需要调整当前流程；不静默切换步骤或以旧版本绕过新约束。

若必须改变实际业务才能解决知识失配，先区分局部实现修复与结构调整：前者向调用方返回实现修正请求，附目标、范围、授权与证据；后者返回结构决定请求。取得实际结果后返回本步骤；读取源码取证本身不要求切换流程。

直属内容图示批量迁移使用 [结构图更新工具](scripts/update_module_diagrams.py)：默认 `--root <项目根>` 只列出待迁移模块，已有批量维护授权时增加 `--write`。工具将 source 节点合为一个 virtual 节点，保留正式子模块及原有类型、依赖关系；缺少唯一图示、子节点映射不明确或基线变化时停止。无 sources 的组织模块不创建空虚拟节点。执行前后快照与结果写入本地任务记录；再次只读运行应无待迁移项。退出码 0 表示完成或无待迁移项，2 表示只读发现待迁移项，1 表示失败。图外的旧说明需结合原文同步核实；工具不变更 source 归属、Schema 或业务源码。

文件级 source 迁移使用 [目录引用迁移工具](scripts/migrate_file_sources.py)：传入 `--root <项目根> --plan <迁移清单.json>`，默认只读预检；已有维护授权时增加 `--write`。清单明确每个目录的唯一归属、scope、正文说明与原文件声明，共用父目录先核实归属，工具不自动推断。原声明变化、文件缺失、清单遗漏或目录重复登记时停止；执行记录保存原定义、原文件哈希和逐条迁移关系。完成后运行知识检查入口，同步注册表并复核范围与图示；目录引用不自动扩大维护职责。

## 5. 维护检索摘要

- 对新增或职责变化的 Agent、模块，结合完整定义、注册表中的相关候选和必要上下级知识做全局语义分析。
- 在定义中生成 100～250 个非空白字符的单行 summary，覆盖真实职责、常见需求表达、关键术语及边界；不凭目录名拼接，不堆无关词。
- 至少构造三种正向查询与两种易混淆的反向查询，对照候选摘要核实能否召回及区分。记录查询、预期候选和复核结论；不足则调整摘要再检查。
- 仅移动目录或不改变职责的正文修订，核实原摘要仍准确即可；未改变摘要不机械重做语义生成。

产出：适用时更新后的 summary 与检索复核依据。不得把人工复核包装成量化召回率。

## 6. 同步索引并检查结构

Team Skill 继承、注册表与 source 校验统一通过 [知识检查入口](scripts/check_knowledge.py) 运行；入口复用现有权威校验实现，不复制实现、不触发 Core Check。默认只读，接受 `--root <项目根>`，结果和各命令原始输出写入本地任务记录：

```powershell
python -B design/skills/knowledge-governance/scripts/check_knowledge.py --root "<工程根>"
```

已有索引维护授权时显式传 `--write`，写入成功后自动只读复核。模块治理需要文件覆盖检查时加 `--include-file-coverage`，或引用已完成且版本适用的覆盖检查回执；未启用不能声称完成全量治理。退出码 `0` 已执行的机器检查通过、`2` source 或覆盖检查有待处理发现、`1` 工具执行失败或发现错误。各子工具结果必须逐项查看，不能只看汇总退出码。source 检查自动导出逐项 Markdown 清单与原始 JSON，路径见 sources 回执的 report 字段；每项保留双方模块、sources 下标、完整 source 路径、scope 和待复核问题，不把包含关系自动判为职责冲突。

固定入口单独运行共享 Team 校验器并保存 `team-skills` 回执，覆盖所有 Team（包括无 Agent 的节点及根）的清单完整性、引用边界，以及全部 Agent 的逐级继承与同名冲突。任一 Team 校验错误汇总为退出 1，不能被 source 的待复核状态覆盖。注册表同时校验这些约束以阻止无效写入，但不能省略独立继承结果。此检查复用底层工具，不调用或自动触发 Core Check。

文件覆盖检查统一使用本 Skill 的 [游离文件扫描脚本](scripts/scan_orphan_files.py)，复用既有实现，不再为每次扫描生成临时脚本。脚本位置以本 Skill 目录为准；通过 Python 执行脚本并传入 `--root <项目根目录>`，省略时扫描当前工作目录；外部工具调用建议显式传入 --root。

脚本只读取项目文件与模块定义，报告写入项目内带时间前缀的本地任务记录目录。一次执行生成按目录展开的完整路径报告、游离文件 CSV、目录汇总、scope 待核实清单、source 类型诊断、链接别名映射及 JSON 回执；包含忽略项，核对导出计数和扫描前后模块定义哈希。现有文件级 source 只标记问题，不扩展其父目录。

读取 `summary.json` 判断完成状态：退出码 `0` 表示没有发现待处理项；`2` 表示遍历完成但存在游离、scope 待核实或 source 迁移问题；`1` 表示输入无效、扫描缺口、证据变化或导出失败。不能把 `2` 当作执行失败重跑，也不能把目录命中当作语义归属已验证。脚本只识别明确的 bin/obj 排除表达，其他自然语言 scope 必须继续人工复核。链接目标在项目内且实体已遍历时去重，未解析、越界和循环链接单列缺口。失败时保留已生成证据，修复原因后重新调用；不手写第二套扫描实现。

涉及模块知识检查、模块新增或迁移、sources 调整时，还必须检查文件覆盖情况，暴露未被模块维护的游离文件：

- 从治理范围内的实际文件清单出发，对照全部有效模块的目录 source，不能仅遍历已登记目录，否则会漏掉未登记目录中的文件。全量治理覆盖项目文件；局部治理明确扫描根与未扫描范围。
- 目录命中后结合 scope 判断维护范围。没有任何模块覆盖的文件列为游离文件；被所有候选模块排除的文件同样列入。无法判断自然语言范围或归属冲突时单列待核实，不默认算作已覆盖。普通文档提及与历史引用不视为 source 归属。
- 保留逐文件路径清单，并可按所在目录汇总数量；分别报告已覆盖、游离、归属待核实及未扫描情况。命中自动注册忽略规则的未覆盖文件仍单列路径与忽略原因，不能用忽略规则掩盖归属缺口。权限错误、离线源、失效链接或扫描中断必须报告检查不完整。
- 检查模式只报告归属缺口与处理建议；维护模式按已有授权处理，涉及职责取舍时返回决定请求。登记文件时使用所在目录并去重，不以兜底宽目录消除报告，也不自动为每个游离文件新建模块。
- 使用调用方提供的文件清单与覆盖检查能力，保留实际命令、范围和完整结果。仅执行注册表或 source 重复检查不等于完成文件覆盖检查；缺少可用清单或工具时明确此项未完成，不能宣称无游离文件。修正后复查受影响范围及模块间归属。

涉及模块知识检查、模块新增或迁移、sources 调整时，必须执行调用方提供的模块源唯一性检查工具，对全部有效模块定义进行交叉检查，不能只查本次修改节点或仅查注册表。扫描同一模块内、不同模块间以及祖先与后代模块间的重复物理源；归档和本地历史快照不作为当前声明。

- 相同路径及其规范化别名重复声明属于错误，报告双方模块、sources 下标和原路径；scope 文字不同不能自动豁免。
- 父子或祖先模块的同向目录包含是正常组成关系，不列为待处理问题；父模块的直接维护范围仍由 scope 说明。跨分支模块的物理目录包含作为工程结构存量警告保留，不自动迁移源码或改写模块树；同模块冗余包含及层级方向相反仍提示复核。
- 保存工具退出状态及完整结果。区分无冲突、重复错误和范围待复核；存在跨分支警告时应区分已知工程结构与实际职责冲突，不把正常父子包含计入待处理项。工具不可用时记录未完成项，不跳过。
- 检查模式仅报告；已有维护授权时消除重复并重跑，涉及职责取舍则返回决定请求。对允许的剩余范围记录复核依据和版本；机器不能解析自然语言排除项，不用一次人工复核永久豁免后续变化。

- 检查范围内现有及变更的 JSON 是否符合适用 Schema；核对必填字段、类型、标识、正文清单、文件路径、相对路径基准、章节锚点与跨模块引用。Markdown 检查适用的元数据、清单与流程格式，不能只检查 JSON。按项目约定检查显式依赖方向。
- 检查模式使用只读校验核对定义与派生索引是否一致，不运行写入或自动修复参数；发现格式、引用或索引错误时记录位置、违反的规则、影响与建议。
- 对影响索引的变化，将索引同步与只读复核作为任务验收项，由任务使用调用方提供的维护工具完成；不手工编造派生索引。只改正文且不影响索引时检查引用和语义，不无故重写索引。
- 校验工具及其参数由项目上下文提供，返回实际命令、退出状态、验证范围与证据。写入中断后核实已有产物，不能假定多个索引同时成功；再按工具的恢复约定处理。
- 维护模式下，授权内的校验错误回步骤 4 或 5 修正，再重跑受影响检查；检查模式记录错误并继续能够执行的检查，不自动写入。写入中断时先核实产物，再按维护规则恢复，不能假定两个索引同时成功。
- 工具或依赖缺失导致无法检查时，明确未完成项及下一步，不将其标记为通过。

产出：与本次检查或变更范围相符的格式、引用、索引检查结果及必要同步结果；涉及模块时同时交付文件覆盖、游离文件和归属待核实清单；涉及能力时交付 Team 检查回执、受影响 Agent 的继承链及共享归属复核结论。区分发现的错误与工具未能执行的检查。

## 7. 复核语义与执行路径

- 对照步骤 1 的目标逐项检查：事实是否有证据、知识是否符合当前产物与有效决定、未知是否如实保留、权威正文是否唯一、原有有效内容是否仍在。检查模式记录错误知识、过期内容、冲突与无法判定项；维护模式还须核实目标问题是否消除。实际实现与文档冲突时核对有效契约，不默认任一方正确。
- 能力治理需复核共享方法的真实使用范围与所有权，并从每个受影响 Agent 追踪“自身 → 直属 Team → 逐级祖先 → 根”的清单加载；不能遗漏空层、越过根或混入兄弟 Team。检查派发及恢复传递来源和版本、任务所需正文，并用缺失入口和冲突场景确认失败不会退回部分清单。结构检查不替代这些语义结论。
- 从实际使用入口追踪受影响路径，确认能找到定义、正文、流程及实际工作区。对流程修订用正常场景、缺失条件场景和失败或恢复场景走读，核对下一步及返回位置是否明确。
- 检查变更后是否引入知识冲突、重复索引或无依据的权限扩展。结构校验通过不代表知识正确，也不代表实际业务运行通过。
- 核对检查结果对应最终知识版本。流程、契约或职责变化向受影响使用者说明变更原因、使用差异和接管注意；必要的负责人决定或理解确认须有实际依据，不以文档已更新代替。
- 检查模式汇总问题与建议；维护模式中授权内的问题可修正则回步骤 4。需要新证据则回步骤 1 调查；无新依据时只暂停受阻项，不在 Skill 间循环转交。

产出：语义复核与入口走读结论。未实际运行的流程只能报告走读结果。

## 8. 交付或返回原任务

说明修改或审查了哪些对象、依据是什么、影响哪些引用与调用方、执行了哪些检查，以及未解决事项。仅评审时交付问题与建议，不声称已经修复。

将结果、证据、剩余条件和继续位置返回调用方。检查模式分别报告覆盖范围、格式与事实语义结论、错误与未知；完成检查不等于知识无错误。维护模式只有必要变更、引用同步、适用校验和语义复核完成，才宣称本轮修正完成。观察模式与正式抽象按输入的有效决定及证据维护，不擅自提升生效状态。
