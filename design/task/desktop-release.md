- 首个平台为当前工程已验证的 Windows x64。现有 Forge/Vite 和 Pi 打包继续使用，新增 NSIS 每用户安装包，安装目录与 `~/.cbim` 用户数据分离。

## 产品行为

更新程序独立放在 `src/logic/updates/service/`：发布读取、版本筛选、状态机和 NSIS 适配不得混入运行时资源服务。依赖检查将更新服务限制在本域契约、获准的便携 Core utility 及系统/第三方库；Bridge 桌面宿主保留装配、IPC 和正常关闭回调，更新服务不得依赖普通 Logic 应用服务。安装产物与下载缓存也独立保存。

1. 正式安装版启动 10 秒后、定时器每 1 分钟读取桌面通道的稳定版本，也可手动检查。离线期间不即时推送；开发模式／普通便携包不自动检查安装更新。
2. 软件内提示可用版本；左下角账号菜单展示当前版本，提供唯一“版本与更新”和最近检查时间。发现新版时菜单高亮、用户栏绿点提醒；更新弹窗展示日志与检查操作，关闭后回到原页面。检查不需要登录或 GitHub 反馈授权。
3. 用户点击才下载，显示进度；校验完成后显示两秒重启提示，再等待业务正常关闭并自动安装重启。普通退出先取消尚未安装的流程，下次启动不自动安装缓存；下载/排空失败只由用户明确重试。离线错误仅在更新页显示，下一分钟继续检查。
4. 安装前按产品正常关闭路径停止任务、排空文件／网络操作；关闭失败时保留当前程序并报告，不越过已有退出门禁。安装不清空用户目录、工程文件或反馈凭据。
5. 正式 APP 预置公开 OAuth Client ID `Ov23liSMDZneBd3gSyTo` 及 `nan023062/cbim`；用户授权自己的 GitHub 账号后，通过对话加号菜单的两项 Skill 按格式提交。成功继续静默，修复及功能变化通过版本日志查看。

## 验收

- 版本筛选：排除旧内核、草稿、预发布、同版本／降级和缺失安装附件；网络错误保留可用信息并允许手动检查。
- 更新状态：检查不下载；一次下载自动接续校验和安装；重复点击不并发；失败只明确重试；下载完成后检查不覆盖待安装版本；只接受可信桌面发布地址与匹配版本。
- 安装：真实 NSIS 安装、启动、正常退出；真实旧版到正式版升级，核对版本与既有数据；报告区分本机验收包和公开正式包。
- 反馈：在正式包中完成真实 Device Flow、重启后连接保存，再经真实产品 Skill 创建唯一测试 Issue。使用确定性模型时明确标注；GitHub 连接／发单不可用 HTTP 替身冒充。
- 同步源码注释、受影响类图、协议及实际验证报告，在已有授权内回填关联 Issues／PR。未通过的线上步骤不标记完成，不重放未知 Issue 创建。

当前实施进度以 [GitHub Issues](https://github.com/nan023062/cbim/issues) 及关联 PR 为准；OAuth 操作见[配置指南](github-feedback-setup.md)。

## 后续发新版的操作

### 验收进程与发布复验

验收进程统一由 `scripts/desktop-acceptance-process.mjs` 的 `DesktopAcceptanceProcess` 管理。Playwright 启动后由 `ownLaunchedDesktop` 读取实际 Electron 的 process.pid/EXE 并核对身份，不能使用可能属于 cmd 启动器的 application.process().pid；原生接回则验证实际 PID/EXE。接入时冻结 PID；连接可用时才允许 evaluate/firstWindow。普通 quit、资源 UI 重启、安装 UI 交接共用 `active → stopping → closed/failed`，先观察原生退出、只执行一次动作、释放调试连接，再确认真实 PID 已退出。窗口关闭、调试断开和安装成功是不同事实，新版本和原用户目录仍由主验收脚本核实。

失败/未知的 UI 动作不自动重发，重复 cleanup 只等待原操作；释放错误不能覆盖原失败。原生资源重启仍先验证 PID/EXE，再接主进程被动网络观测和页面；中途接入失败也释放已建立连接。`process-lifecycle.json` 记录每个 PID 的交接阶段，供定位失败。该所有者仅属于验收工具，不改变产品进程、下载定时器或状态。

Windows 观察由同目录 `desktop-acceptance-process.ps1` 完成：枚举进程和读取 Path 之间可能退出，取路径前后均核原生句柄 HasExited；已退出的空路径不误判为 PID 被替换，仍运行时的错误身份与超时必须失败。该脚本只读状态，不主动关闭或终止被观察进程。

`mode=online` 现在也先用独立 fresh-user 完成目标公开制品全新安装与固定 Pi 引擎下载/执行，再用另一 profile 安装真实旧版并走自动发现、差分、普通退出、缓存复用和 UI 安装。`mode=candidate` 保留草稿身份核对与直接覆盖升级。重验已公开版本直接使用 online，不创建同版本草稿、不替换附件、不重打未变化制品。

开发阶段按 [CI 验证范围](ci-validation.md) 保持草稿 PR、先做定向和隔离验收，稳定后转 Ready 运行精确提交完整四片；不要在每个中间修复后手动派发全量。通过后的运行链接和最终回执回填 PR，避免为补最终 SHA 反复提交并重触发产品全量。

完整操作使用项目级 [cbim-release](../../.agents/skills/cbim-release/SKILL.md)，其配套资料包含分阶段草稿验收、故障恢复和证据门槛。该 Skill 复用下列脚本，不加入 APP 内置业务 Skill，也不额外授权发布。

2026-11-09 用户确认个人开发阶段先发行未签名版，取得证书后通过更高版本切换签名。默认命令仍要求签名；未签名发行必须在构建、校验和发布三步均显式指定 `--unsigned`，不因缺少证书或签名失败自动降级。两种方式使用相同应用标识、安装目录规则、数据目录及桌面更新通道，签名情况必须写入版本说明。证书配置和签名校验详见[Windows 签名指南](windows-signing.md)。

1. 将 `package.json` 的版本号增加为新的稳定三段版本，并创建 `design/releases/desktop-v<版本>.md`，只写本版实际完成的修复、改进和新增功能。
2. 完成类型、依赖／架构和相关测试后，提交并冻结干净源码，再执行 `pnpm make:desktop`；未签名发行使用 `pnpm make:desktop --unsigned`。产物单独位于 `build/desktop-release/<版本>/<signed或unsigned>-<时间>-<随机标识>/`：安装 EXE、blockmap、`latest.yml`、`SHA256SUMS.txt` 和本机构建回执。同版本产物不会被构建脚本静默覆盖。
3. 核对冻结源码、构建内容和真实安装运行，通过后推送对应源码；给该提交创建独立 `desktop-v<版本>` 标签，不移动既有标签。后续发布／验收记录可单独提交，不替换已验收的源码标签。
4. 执行 `pnpm verify:desktop <候选目录>` 重新核对签名、时间戳、发布者与更新摘要（未签名追加 `--unsigned`）。按 Skill 分阶段创建唯一草稿、上传四附件并在隔离 Windows runner 验证全新安装和真实上一版升级；完整 CI 和 PR 合并通过后，重新核对候选、附件与标签，再公开同一 Release，保持旧 Python latest。验收工作流必须传 previous_version，当前支持 0.1.1／0.1.2 的两步界面与 0.1.3／0.1.4 的自动安装界面、未签名断言和更高的 0.x 目标；其他旧版交互或签名模式须先核实并适配。
5. `pnpm publish:desktop <候选目录>`（未签名追加 `--unsigned`）是一体建草稿／上传／公开命令，没有暂停验收或恢复参数，只能在同制品已有完整前置验收且没有待恢复草稿／日志时使用。新版本不使用 `--replace`；中断先按 ID 与日志核实，不重复建草稿、不覆盖附件或移动标签。同版本签名替换仅在单独授权后按签名指南备份执行。
6. 公开后从真实上一桌面版本实际发现、下载：旧两步客户端还需点击「停止任务并重启安装」；采用 #19 的客户端在下载后自动完成。分别验证普通退出取消尚未安装的流程、真实重启版本及既有设置／对话保留；记录真实验收证据。安装测试必须使用无用户安装的隔离 runner，单独 `/D` 目录不阻止 NSIS 卸载已有注册安装。最后按公开回执同步官网，经 master 部署核实匿名内容并同步 develop。不要以“Release 已创建”代替完整客户端升级与分发验证。

当前源码的「版本与更新」合并日志和检查入口，查看不触发下载，也不卸载原页面或清空草稿；点击下载前提示先保存未提交编辑，因为后续会自动重启。关闭弹窗不取消已授权的下载/安装。关闭程序或离线不会收到即时通知；现有安装版的实际间隔和交互以其版本为准。

原公开 0.1.0／0.1.1 尚未签名，发布页保留当时事实。未签名版可能触发 Windows 未知发布者／SmartScreen 提示，受管控电脑或 Smart App Control 可能阻止运行，不指导用户关闭系统保护。签名流程已经接入，但真实签名仍需证书；切换签名时发布更高版本并验证上一未签名版的升级及数据保留，不能保证新签名立即消除 SmartScreen 提示。
