# 异常影响核实与新修复关联

## 交付目标

让用户沿一条可查链路处理异常：选择原调用 → 查看真实影响及仍未知部分 → 保存明确处置 → 按已有资格创建新只读核实／新业务修复 → 查看新任务的结果。原调用、原失败、原 unknown 和原人工意见始终保留；新任务完成不把旧工具改写成成功。

复用现有成员执行报告、文件基线、原主命令报告、只读核实周期、业务重规划和唯一 DispatchStore。不要另建恢复调度器，不向原失败 native 添加重启入口。

## 原身份与观察协议

新增纯来源联合，分别表示 `member_run` 与 `main_run`；客户端只传 workspace/root、明确原 run、成员 task（仅成员分支）、原 toolCallIds 和预期依据。scope、工具名、授权、原输入摘要、规范化路径与实际副作用分类由服务读取原记录确定，不能由模型或界面自报证明。

报告至少区分原调用状态、当前真实观察、覆盖范围、限制和业务验收。覆盖使用 `control_commit_only`、`selected_files_now`、`unsupported` 等明确值，不提供含混的 `resolved: true`。文件不存在是独立观察，不伪装成零字节文件；哈希是当前字节摘要，不冒充原 after 状态。正文、私有备份路径、模型凭据和原生会话均不返回模型。

文件数和读取字节沿用平台现有限制（16 个、每个 8 MiB、总计 32 MiB），只处理明确原调用能定位的业务文件，不递归扫描目录。路径仍经过实际边界、链接和保护目录检查。身份、日志前缀、原请求、文件集合与当前观察共同形成 basis；读取前后变化明确标记不稳定，不能保存为确定结论。本应用读占用不代表隔离了外部程序。

## 处置与后续关联

本机用户可显式记录“继续核实”“新业务修复”或“保留未解决”，附理由和精确观察依据。actor 由本机入口确定，仅表示本机操作，不冒充登录身份或专业验收。模型只能提供资料和建议，不能通过参数签署用户决定。

处置记录保存于原 DispatchStore 的有界、不可变附录，以稳定 commandId 幂等查询；不修改已关闭 scope，不复制 canonical 或另建一份宣称成功的账本。提交先查原命令，再重建观察，最后短事务核版本；同 ID 异参拒绝，结果未知只查原请求，不换 ID 自动重发。观察、处置和原命令报告均不是业务完成证据。

现有 `ScopeRecoveryService` 扩展真实主来源，但保持独立新上下文、read 权限、原周期关闭／无活动成员和依据核验。没有原可信业务计划的主异常允许新只读核实，不凭空补原模块及人工条件。成员原业务修复继续经过现有 `validateCompletedInspection`、replan 预览和显式提交；新的处置／观察引用是额外真实关联，不能削弱已有门禁。

无原计划仍须有可信、唯一且已关闭的原 scope；旧主日志缺 scope/runTracking 时报告来源不足，不能为满足入口补造周期。处置／观察引用在创建新 recovery/replan 意图时原子冻结，已有不可变意图不回填链接；后续关系只从已核实的追加记录派生。

关系查询从原来源、处置、新核实周期、新业务周期、任务及实际候选／审阅派生。显示进行中、等待、停止、失败和新目标完成，保持“新修复完成”与“原操作成功”的区别。新业务仍核当前岗位、模块责任、来源、模型、权限、预算、Workflow 和人工条件。

普通 chat 的历史 `reconciledToolIds` 保留可读，但新 unknown 不能仅凭勾选 ID 取得原 native 续跑许可；转到显式新只读核实。安全结束且没有未决工具的正常续聊保持原行为。界面不自动清除未知、改变权限、消费草稿或启动后续任务。

## 模块边界与顺序

1. Core 定义来源、观察、处置及关联 DTO/不变量，列明旧记录兼容；Store 接不可变附录、幂等与重放，禁止查询触发初始化。
2. Scheduler 组合原报告、canonical 与平台文件观察，IO 在 Store 事务外；现有 recovery/replan 内的 canonical IO 也须随本片重构为外部取证与最终版本 CAS，不仅约束新服务。Main 复用已经打开工作区的真实端口。知识／模型／任务队列不得反向等待。
3. 扩现有 recovery/replan 的来源与可选关联，保留旧读协议及完整恢复资格；同步收紧裸 ID 的新 unknown 续跑入口。
4. Bridge/UI 提供显式观察、处置及关联结果，固定原身份和请求；只读失败保留原报告，迟到响应不能切换目标，不增加每秒全文回读。

这是一片可验收的完整处理链，不要求每个模块单独提交；实现和验证完成后按用户要求独立 Git 提交。必要时依据实际风险拆分，但不能只交记录对象就宣布修复链完成。

## 验收矩阵

- 真实 Pi 写入已发生后丢失结果：无成功基线仍能从原授权路径观察当前文件，原 unknown 不变。
- 当前文件旧内容／新内容／缺失／链接／越界／读取中变化分别报告；不把当前相等解释成全部作用已消除。
- 主与成员来源分别通过；跨 workspace/root/run/call、重复调用、坏 canonical 和不完整尾行不取得结构化证明。
- 原工具失败而控制面 committed 两事实并存；报告和处置不能作业务验收。
- 完成真实只读核实 → 明确新业务重规划 → 当前岗位独立修复 → 实际文件／验证证据 → 新审阅；旧日志、绑定和人工意见不改。
- 缺原计划／模块覆盖／人工约束／当前知识／有效观察时仍拒绝不具资格的新业务。
- 稳定命令重复／异参／保存后丢回复／停止／重开／CAS 冲突／选择切换不造成重复记录或执行。
- 正常 chat 续聊不受影响，unknown 裸 ID 不再单独放行；旧记录可读。
- 最终 EXE 至少两场：真实未知写到新修复完整链；文件变化或不支持影响到原命令查询，零自动重放。确定性模型、实际 Pi 和打包界面各自如实记录，不替代在线业务质量判断。
