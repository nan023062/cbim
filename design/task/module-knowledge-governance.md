# 模块知识的渐进治理

状态：2026-11-07，Step18a 已完成，承接 `21756c0` 的真实外部资料读取与范围回执。最终 EXE `20261107-135435` 三场景通过；初轮完整回归发现的两项关闭/重启回归已修复，相关 71 项测试通过，见[验证记录](../verification/module-knowledge-governance-20261107.md)。属于 roadmap 第四阶段首个可验证闭环；不把本片称为完整业务迁移或所有治理能力。

## 目标与范围

用户在业务架构中明确选择一个现有 Module，登记保护其真实 `module.json` 与已绑定 overview。默认不冻结整个项目。首片提案只更新该 overview 正文；不提供修改定义、移动、删除、解除保护或业务代码迁移的批准入口。

流程为：登记 → 读取真实校验/文件依据并记录观察 → 冻结精确差异、理由、替代方案、不变量与恢复说明 → 独立保存本机批准/驳回/暂缓 → 明确实施原方案 → 核实原知识事务和当前内容。模型解释与确定性观察分开，本机操作者不冒充已认证负责人。

## 架构与状态

- Core governance 只保存严格协议、身份、basis 与纯保护规则，不依赖存储实现。
- Main 的工作区治理服务管理私有观察/提案/决定/意图；正式知识提交仍只有 KnowledgeStore 一处。登记、决定和实施与普通知识写使用同一串行边界。
- 普通 ChangeRequest 不携带 permit、actor 或批准字段。可信实施入口只加载真实私有意图，核验最新决定、原提案与知识/保护版本，再提交唯一 overview 差异。
- 完整最终投影必须保留受保护定义、正文绑定与可见 Module；原始 CRUD、架构表单、整包应用、移动和忽略规则不能绕过。
- 前端业务架构节点展示独立治理面板，人工决定和实施是两个动作。请求冻结原身份/版本；未知结果只查询原命令，不默默新建修改或切换目标。

## 持久与并发

提案不可变，变更方案新建提案；决定按提案 CAS 追加，只允许最新有效批准实施。apply 先可靠保存原 ChangeRequest 与精确关联，原知识 journal 才是成功证明；不能凭正文相等或批准状态推断已提交。

旧 journal 保持兼容。准备/提交中故障沿既有事务恢复，外部冲突保留现场。知识已提交后治理缓存失败不回滚成功知识；重开只核实原日志并恢复展示，不自动执行。原实例退役后允许查询历史，不把旧请求换为新实例重发。

## 本步验收

1. 原始提交、对象 CRUD、架构修改、模板覆盖及隐藏 Module 均不能绕过已登记保护；未登记模块和无关知识保持原工作流。
2. 未批准、驳回、暂缓、旧决定/版本、跨工作区/实例、变更的方案均拒绝；精确批准的正文可提交一次，重复命令只返回原结果。
3. 保存意图前后、知识提交中及提交完成后的失联/重启能区分真实状态，无自动重放；外部修改显示漂移而非补造成功。
4. 本机最终 EXE 完成登记、观察、精确提案、决定、独立实施与历史查看，重开不重放；零模型和业务执行者请求。该桌面切片不装配模型治理工具。
5. 按顺序完成类型、依赖/类图、边界及行为测试，维护中文注释、CONTRACT、ARCHITECTURE、roadmap 和验证报告，再单独提交。

专业语义判断、通用治理提案、业务产物迁移、解除保护、模型发起治理及跨账户认知反馈继续按后续步骤接通。资料或模型建议本身不能批准正式规则。
