## 本片完成条件

主 Agent 定位模块后查询负责人，保存绑定岗位和责任版本的计划，再按同一负责人派发。执行者实际领取时再次核对岗位、能力、来源及模型，使用该岗位自己的模型、Skill和项目适配执行。不同负责人拆任务；无负责人或失效配置返回明确缺口，不暗中回退主模型、最近角色或内置执行者。

当前默认执行者仍可登记成项目岗位，但必须明确设置模块责任后才参与新正式业务派发。真人维护关系继续独立检查，不能以AI负责人替代。主 Agent 的知识治理和普通聊天保持原职责，不需要伪造业务任务。

本片覆盖新任务的计划、派发、领取、同周期检查点预约/实际领取、原结果审阅及显式IPC。R02-D的存量交接与暂停任务放弃另片实现；本片拒绝过期领取并保留历史，不冒称完成移交。

## 核心协议

- `OwnerExecutionSelection`只传预期：稳定memberId、成员revision、能力/公开模型指纹和逐模块bindingId/revision/ownerMemberId。预期不充当来源证明；后端按同一权威登记重建。
- `OwnerExecutionBinding`记录实际派发事实：工作区与岗位身份、已采纳能力及来源、模型引用/公开指纹、逐模块关系和模块来源。任务创建后不可改写；运行实例、原生会话、run继续保持独立身份。
- 业务目标分配保存可信绑定，主治理分配不得携带业务负责人选择。Task、PreparedContext与Run关联同一绑定；能力正文复用既有解析器，适配保存到该次冻结上下文，不修改通用Agent定义。
- 模块集合严格匹配、无重复且负责人一致。父模块责任不隐式继承给子模块；同Agent的两个岗位仍按不同memberId分开，不因角色相同复用实例或模型。
- 公开查询返回有界分组、选择依据和缺口；“可形成选择”不是未来执行许可，也不证明密钥或远端供应商可用。凭据不进入任务、指纹、工具回包或界面。

## 单一裁决与运行配置

岗位、责任、计划和派发共用现DispatchStore。知识来源和模型配置在外层固定，锁序保持：Knowledge串行快照 → 模型配置队列 → Dispatch事务。不能在Store回调中再排知识/模型队列、查询同Store或等待长期运行。

1. 先查询原命令回执并释放Store；相同已提交请求只返回原事实，不重新解析模型、启动任务或发送HTTP。
2. 固定实际知识快照及来源状态。source pending、缺失/退役/未采纳、能力内容差异均拒绝新的业务计划、派发或领取。
3. 在同事务内核关系、成员状态和版本；A→B→A仍因关系版本变化使旧请求失效。目标分配和派发选择必须一致。
4. 公开模型配置修改与领取有明确先后裁决；取得配置后保留到短领取提交，不发送模型请求。先修改则旧领取拒绝；先领取则本段用原冻结配置，不被后续主聊天选型或岗位编辑热替换。
5. 真实领取提交后才释放锁并启动已捕获的引擎。名额/文件占用等待不持知识或模型长锁，重试重新核原绑定；停止仍在各异步边界复验。
6. 模型密钥不可用按真实启动错误结算，不降级模型。工具授权、业务范围、并发、预算、证据及完成门禁继续有效。

## 旧数据和入口迁移

存储必须区分旧日志回放与新的写入协议，不能只把ownerBinding设成可选字段。新事务协议标记由Store生成，客户端不能设置；旧前缀原字节可读，新协议开始后不得回退旧写法。通用mutation也须通过相同的纯不变量，不能夹带岗位/责任修改伪造任务。

| 对象或入口 | 本片行为 |
| --- | --- |
| 新`cbim_dispatch_task`与显式`dispatch.task` | 共同要求active主周期、真实计划和当前负责人选择，禁止无scope旁路 |
| 旧`loop.start`的业务execute及新续轮 | 明确拒绝新启动，提示经主调度正式派发，不建设第二套运行通道 |
| 已持久化的旧starting/running | 按原身份、原模型和原运行事实收束，不补造责任 |
| 旧无绑定queued/waiting | 可读、可查询原回执；新领取明确要求重新规划派发，不从agentId猜岗位 |
| checkpoint与已预约恢复 | 预约及实际领取都核原绑定；无绑定或过期不消费检查点、不换原生会话、不自动恢复 |
| 原候选、证据、人工决定 | 依原任务/运行身份解释；不把A的成果当B的新任务，也不把旧人工接受升级为新责任依据 |
| 依赖追加/替换 | 保留原任务绑定，未启动闭包重核，不能借改边升级身份；已完成候选仍是原历史事实 |

当前关系改变不把已完成历史结果改成失败。新计划若要复用旧结果，仍须匹配真实原分配与证据规则，不能自动搬运。等待交接的未完成工作仍阻止目标完成。

## 代码分工与架构边界

- Core team提供严格选择/绑定叶子协议；tasks保存目标、任务、运行与检查点的关联和不可变规则。Store负责新旧事务协议及重放，不导入Main服务。
- Scheduler统一目标计划、派发、领取、恢复及依赖调整的核验，复用知识解析与实际模型端口，不另建责任索引或来源存储。
- Main装配同知识快照、公开/真实模型配置和实际引擎；调用方不能提供解析好的模型或来源证明。旧直接业务启动在服务入口明确拒绝。
- Bridge只公开可序列化协议。前端展示原任务负责人、冻结模型、版本和当前配置差异；迁移状态与旧待办缺口可见，查询不自动采纳或重派。
- 相关src文件头、关键接口、CONTRACT与目录类图按真实实现同步；旧接口或未来能力不能写成当前已接通。

## 验收矩阵

1. 一个Agent登记两个岗位、不同模型/适配，分别负责模块；主模型为第三种。真实Pi完成两次派发，核HTTP模型、实际Skill/适配、实例/Session/Run及结果归属。
2. 同负责人多模块通过，不同负责人合并拒绝；父子责任不推导；未分配、暂停、缺源、未采纳及禁用模型无成员请求、不保存新领取。
3. 计划后换人、A→B→A、岗位配置变化或profile原位更新使旧派发失效；显式采纳并重新规划后才通过。跨工作区、假assignee、遗漏预期拒绝。
4. 负责人、岗位、来源及profile变更与领取各测两种先后；先变更不消费outbox/不建run，先领取保留原配置和历史。覆盖source pending及同字节重建。
5. 检查点预约前/预约后实际领取前变化分别拒绝且不消费原检查点；主模型变化不能替换岗位模型；停止/重开不重放。
6. 通用伪mutation、删除/替换任务绑定、旧格式新写和夹带责任修改拒绝；真实旧日志可读、旧在途可结算、旧待办不能新领取。
7. A候选完成后换B，历史及原模型不变；不能作为B的成果或借旧人工接受签发新完成。
8. 已提交后坏回包/丢回复仍只查原命令，无重复模型解析或任务；领取前停止拒绝，领取后停止保留真实starting意图再收束。
9. 实测旧直接业务入口拒绝，显式IPC与模型工具一致；普通聊天、知识治理、原权限/预算和依赖门禁回归通过。
10. 最终打包EXE验证双岗位真实执行、负责人变更阻旧待办/恢复及重开只读无重放。可控本地模型和在线专业业务效果分别报告。
