# 负责人变更后的存量任务交接

Step34 / R02-D。状态：待实施，须在 Step33 的全仓回归、桌面验收和独立提交完成后启动。本文件先明确接续范围，当前进度仍以[路线图](../tool-architecture-roadmap.md)为准；不能据此调用尚未实现的工具。

## 交付目标

在同一活动主调度周期内，负责人改变后，明确处置旧未领取任务和未恢复的检查点，再按当前负责人创建新任务。旧任务、原运行及成果归属始终保留，完成目标仍依赖真实新候选及逐项审阅。

复用已有责任更换预览/提交、负责人领取复核、未领取依赖闭包撤销、目标重规划和 `superseded` 审阅。新增的核心能力只有：**主调度显式放弃尚未被领取的检查点，及其尚未领取的恢复预约**。不在原任务上换人，不把责任更换回执视为所有旧任务已交接。

本片覆盖三条实际路径：

1. 旧任务从未领取：明确撤销完整未启动依赖闭包，按新负责人重新规划和派发。
2. 旧任务已保存可靠检查点，未恢复：明确放弃检查点待办；原检查点及已完成段保留，再创建新任务。
3. 旧任务已经领取：本段仍以原身份执行及结算；不能用放弃接口伪装成未执行。停止、未知副作用和通用恢复继续使用原协议及 R03。

## 主调度窄协议

拟增加 `cbim_dispatch_abandon_checkpoint`。请求严格包含当前图游标、目标版本、任务 ID/节点版本/计划版本、检查点 ID、预期恢复预约 ID（`null` 明确表示尚无预约）及原因。workspace/root/scope/mainRun/command 身份由可信主工具闭包提供。

任务新增不可变 `checkpointAbandonment`，类型为 `abandoned_by_handoff`：记录真实命令、主运行、原检查点/原运行/预约、图与目标依据、旧任务版本/租约、原因与提交时间。公开回执只证明该次处置已保存，不证明已回滚业务副作用或完成目标。

既有 `checkpoints`、`resumeRequest`、`ownerBinding`、目标、模块、Workflow、原运行、原生会话及证据不得改写或删除。新任务通过既有目标分配和派发建立自身绑定；旧证据及旧人工接受不能冒充新负责人的成果。

## 提交与竞争

- 先查原命令回执；已保存请求直接返回原事实，变参复用拒绝。未知回包不重新操作原生会话。
- 历史 canonical 与冻结检查点证明在任务事务外读取。处置不要求当前模型可用或当前知识/业务文件仍与旧基线一致，否则更换负责人后会无法结束旧待办；这些条件继续用于任何新执行。
- 最终短 Store 事务核对原图、目标、任务、原运行/证明、会话、成员租约及原预约；操作期间停止由明确存活检查和最终 CAS 裁决。不能在 Store 回调中再排 Knowledge 或模型配置队列。
- 只允许活动周期、未消费检查点、一个已完成原运行、无活动运行/候选/求助、原实例仍空闲。恢复预约存在时必须原信封 pending 且未 claim；不存在预约不得造信封。
- 精确提交只取消原任务、追加处置事实、清理明确的未领取恢复信封并提升原成员租约及图投影。原依赖边、目标计划、岗位/责任登记、知识、原运行和原生文件均不变。
- 新处置提交时租约必须恰好增加 1；审计固定当时前后值。以后周期关闭仍可再次递增，不能用历史处置记录要求成员当前租约永久不变。
- 放弃先提交则迟到恢复领取拒绝；领取先提交则放弃拒绝，走既有停止与核实。已落盘后的停止或坏回包不能被报告为未发生。
- 原 checkpoint 结果信封与 resume assignment 分开处理。结果回注后的迟到收件确认仍可完成，不要求放弃接口替它确认；只消费明确的恢复预约。
- 新的状态不变量须允许原 checkpoint 信封后续纯 ACK；先核实精确放弃变更，才允许活动周期内的未消费检查点进入 cancelled，不用宽泛的状态放行替代该证明。
- 通用 mutation 与重放执行同一纯不变量。不能凭事件名或附一个审计字段就获得放行；处置一经保存不可改写或追加新运行。

Auto 协调器记录本次处置操作、等待收口、撤销对应准入票据并从当前待运行批次移除旧恢复任务。它不扫描历史邮箱重启工作；新任务仍由本轮明确派发后正常领取。

## 后继与目标完成

原依赖后继不会因放弃自动解锁。主调度明确取消仍未领取的完整后继闭包，再按当前负责岗位建立新 DAG；旧节点、旧边及原原因可追溯。

完成审阅必须逐个用后来创建、同周期且覆盖原模块的真实候选替代旧失败/取消任务；原验收项及人工要求仍有效。不能用“交接成功”、责任变更、撤销或放弃回执充当业务证据。保留旧后继实例而只替换 cancelled 检查点来源边，归 R04 的依赖修订，不在本片暗中扩大资格。

## 界面与兼容

- 原任务详情的检查点卡区分“等待恢复”“新轮已领取”“随周期封存”和“已为交接放弃”，展示原因和真实审计；普通取消不能显示该标签。
- 继续显示本任务原负责人与模型；当前模块负责人独立核实。目标审阅中的替代关系提供原/新任务定位，不伪造任务执行边。
- 本片使用主 Agent 的真实工具闭环，不新建让渲染进程冒主身份的处置按钮。
- 旧历史缺少新字段仍可读。已关闭/中断周期只读保留，不因升级重建 active scope 或自动放弃；可靠旧检查点的处置仍需满足原活动周期资格，绝不补造负责人绑定。
- 原记录缺失、未知或损坏不能伪装可靠检查点；保留实际问题，交由明确核实/通用恢复，不能通过修改日志令测试通过。

## 验收

1. 新负责人接替旧未领取任务及两级后继：旧领取拒绝、完整闭包撤销、新 DAG 实际执行及真实替代审阅完成。
2. 可靠检查点分别在未预约及已预约未领取时放弃；原检查点/canonical/native 字节保持，无第二 run，恢复信封最多处置一次。
3. 放弃/领取两种先后，以及准备中停止、提交后停止、回复丢失：保留真实裁决，原命令查询不多启动或重放。
4. 错误 workspace/root/scope/主运行、版本、检查点/预约以及夹带其它 mutation 拒绝；失败不部分取消或改租约。
5. 岗位暂停、模型/来源变化不阻合法旧待办处置；新任务仍必须通过当前负责人、来源、权限、预算及并发门禁。
6. 旧运行结果与人工决定不能变成新候选；模块覆盖不全、有未完后继或缺少真实替代时不能 complete。
7. 实际 Pi 与最终打包 EXE 完整执行 A 检查点→界面更换 B→主工具放弃/重规划→B 执行→真实目标审阅；另验停止、不确定回包及重开只读。可控 localhost 模型不代替在线判断。

每个实际交付步骤完成单元/集成、类型/架构检查、最终 EXE 冒烟后更新路线图及记录并单独提交。本片结束时核对 R02 四片整体范围，不能只因新增工具通过就将未解决交接项标为完成。R03–R17 继续依路线图推进；第 9 组仅保留计划。
