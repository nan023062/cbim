# 原命令核实与异常恢复分流

Step35 / R03-A。状态：待实施。承接 R02 的负责岗位派发与显式存量交接；先完成 Step34 最终回归和独立提交，再进入本片。R03 全包仍包含更广异常核实、显式修复关联及必要补偿，本片不能替代完整交付。

## 解决的问题

工具输出可能在真实事务提交后丢失或校验失败。现有图查询能够看到当前任务，却不能统一证明某一次原调用到底保存了什么。新能力只核实原命令，区分原工具结果、事务是否已保存和业务是否完成；不重新执行工具、不改原日志，也不自动恢复原 native。

新报告以明确 workspace、rootSession、原主 runId、toolCallId 为入口。可信服务读取原 canonical，核主会话绑定与唯一周期归属，确定原工具名、真实调用输入与稳定命令；调用方不能自报 commandId、fingerprint、scope、actor 或原执行结果。

## 支持矩阵

本片完整接入以下八个具有稳定主命令的写工具：

| 工具 | 需要核对的原事实 |
| --- | --- |
| `cbim_goal_plan` | 原主运行/调用、原计划请求与存储指纹，严格公共目标回执 |
| `cbim_goal_review` | 原审阅请求、目标版本及原工具绑定，不借当前审阅替代 |
| `cbim_dispatch_task` | 原请求及 Auto 当时注入的真实父版本、原派发回执 |
| `cbim_dispatch_cancel` | 原周期、图游标、节点版本及精确未领取闭包；该请求没有目标版本 |
| `cbim_dispatch_replace_dependency` | 原边与新候选的精确替换请求和审计 |
| `cbim_dispatch_add_dependency` | 原前置/目标任务、版本及追加审计 |
| `cbim_dispatch_resume` | 原检查点、原图/目标/节点依据及预约回执，不能标为已启动 |
| `cbim_dispatch_abandon_checkpoint` | 原检查点/预约、处置请求与审计，不能标为回滚或成功交付 |

两个 inspect 主工具没有写命令，明确显示不适用。岗位、责任、治理、知识、资源和原生工具仍使用各自已有查询能力；本片不猜测它们的命令算法。其它工具显示未接入，而不是调用执行入口探测旧回执。后续适配须明确原始请求、稳定身份、私有数据投影和恢复边界。

## 唯一 Store 的历史依据

`dispatch_task` 的隐藏 `expectedParentRevision` 不能从今天的 root revision 猜测。拟在现有 commands 内存索引旁派生窄 `commandEvidence`：原 fingerprint/receipt、真实事务序号/校验值/协议，以及有图事务的前后游标和提交前 root revision。

依据从现有 live publish 和 load 的已验证原事务前态产生，live 必须已经可靠保存，load 必须已经通过原重放校验。保持原 `commandReceipt` 两字段行为；不改写旧 journal、不另建持久账本，不在每次查询时重新扫描或重放全历史。缺少可信原前态时明确不可核实，不能补造父版本。

这些内部事实不是直接给 UI 或模型的回包。领域适配先重建完整原 fingerprint，核对实际原请求，再复用既有严格公共输出投影及绑定校验。不得泄露 Prepared、私有路径、native、模型凭据或整个事务帧。

canonical 原始 `inputHash` 与领域 fingerprint 分开核对：后者须重现原服务的解析、缺省值、trim、字段映射及序列化顺序，例如 prerequisites 缺省 `[]`、agentId 映射为 assigneeAgentId。不能直接对 raw input 求 hash，也不能为适配新报告修改全局序列化算法。Store 的 `executionProtocol` 不是工具 Schema 版本；历史原命令查询不能套用今日 ownerSelection 新执行门禁，无法明确辨认的旧调用才报告不支持。

## 报告与竞争

- 原调用身份和输入必须来自完整、无歧义 canonical；缺失、坏尾部、错身份、重复 toolCall、未支持旧协议均有明确不可核实原因，不能借当前同名工具或任务状态替代。
- 分别显示 canonical 里的调用状态，以及原账本 `committed`、`absent`、不可读取或不一致。空回执永远不是“从未执行”或自动重试许可；没有持久拒绝证据不生成“已拒绝”结论。
- 已保存事务与原工具失败允许同时成立。报告展示原公共回执及有限身份，不修改原回执、工具成功/失败、目标、候选或验收结果。
- IO 前后比较原记录依据；查询期间原调用仍在变化则明确过期/不稳定，不将两次观察拼成确定结论。原已保存命令仍可在周期关闭、责任更换或停止后只读查询。
- 查询不使用当前模型、不签发执行资格，不取得业务写锁或反向嵌套知识队列；重复读取、重开、迟到结果均不得产生模型请求或事务重发。

## 入口与恢复分流

先固定 Core 的请求/报告及实际支持工具清单，再接调度服务和 Main canonical/账本端口、只读 IPC 与前端。查询仅使用已经打开且初始化完成的工作区，不隐式 open/init 或执行恢复。界面按原会话/运行/调用隔离，显式点击才查询，不建立每秒全文轮询；无变化保持原视图，切换选择不被迟到报告覆盖。失败保留上次报告并明确可能过期，不影响草稿或附件。

同时提供主工具 `cbim_dispatch_command_report({runId,toolCallId})`，可信闭包固定 workspace/root，原 scope 从唯一 runTracking 归属推导；同 root 的明确历史主运行可查询，不能跨 root 或转借执行资格。与桌面共用同一服务和 DTO，不维护第二套查询算法。该工具只有 read 效果、没有写 commandId，不触发 Auto.workRequested，不计为业务证据，不给执行成员；允许主模型在已收到坏输出后核实原事实再正常决策，不自动清理 unresolved/unknown 或勾选核实。

原调用核实不直接成为 `recoveryStart` 依据。已有成员执行报告、新只读核实周期、新业务预览与显式提交继续走各自真实资格；主命令不伪装为成员 DispatchRun。当前没有适用恢复入口时明确说明缺项，不给任意旧 native 新增重启按钮，不自动传 `reconciledToolIds`。

当前普通 chat 的人工核实勾选不等于结构化副作用证明；本片报告也不能自动替用户勾选或证明任意 shell 的全部效果。通用修复关联、文件操作核实及有真实 before bytes 的补偿，仍属后续 R03 子步骤。

## 验收

1. 八个支持工具分别验证实际原输入、命令与严格回执；派发隐藏父版本来自真实事务前态，当前 root 变化不能影响原依据。
2. 原 journal 重开可重建相同索引，原前缀字节不变；错误 fingerprint、异参复用、跨 workspace/root/run/call、缺前态不得核实成功。
3. 真实提交后坏回包/丢回复仍能核实原事务；无提交、尚在途、缺失/损坏记录、查无回执分别保持真实未知，不重放或补造拒绝。
4. 查询与停止、重开、原日志追加及选择切换竞争；不污染新报告，不启动模型、不改目标和原 canonical。
5. 界面同时展示“原工具失败”和“原事务已保存”，及仍未知的情况；原任务/成员恢复沿已有入口与资格，不能查询即执行。
6. 单元/集成、真实 Pi、本机最终 EXE 至少覆盖一次真实已提交的坏输出和一次仍未知无自动执行。测试故障注入不成为产品后门；确定性模型不代替在线判断。
