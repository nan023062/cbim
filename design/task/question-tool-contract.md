# 结构化提问的严格回包与证据边界

状态：2026-11-07，Step25 已完成，承接 `9a03ebe`。严格提问回包、一次性回答与业务证据隔离已通过最终18文件144项、13项边界及类型/架构检查；同一 Windows EXE `20261107-182341` 的正常、停止、消费后丢回复三场冒烟通过。见[验收报告](../verification/question-tool-contract-20261107.md)。本片不与模块负责人索引设计混合。

## 已有事实与问题

主调度和执行成员共用 `QuestionQueue` 与 `QuestionCard`，用户可选择选项、添加补充或填写其他答案；停止和关闭会取消等待。实施前提问工具只声明输入，返回正文缺少严格领域输出校验；公开问题列表还直接引用队列对象。

提问工具的正常回答与 `{cancelled:true}` 都可能成为成功工具回执。实施前步骤、成员候选、Workflow 交付和目标审阅存在把该回执当作业务完成证明的入口，现已逐处排除。问答事实继续保留，不能替代业务产物、工具授权或持久人工验收决定。

## 实施边界

- 保留已有答案 wire：`{answers:[{question,answer,supplement?}]}` 或 `{cancelled:true}`，不补造用户认证、批准或运行身份。严格校验嵌套输入、数量、长度及排他输出形状。
- 排队时冻结原题与选项，列表返回独立副本；回答只能按原始选项索引或明确其他输入构造。包装器在等待前另留校验依据，输出问题的数量、顺序与正文须匹配原题。
- 领域等待只调用一次，复用唯一 JSON wire 校验。回答已消费后损坏输出标记 `TOOL_OUTPUT_INVALID`，不重新弹题、回滚或自动重问。
- 停止、关闭与调用取消清理原等待；回答与取消只有先发生者生效。工具目录准确声明等待期间可取消及用户交互不可盲目重放；不扩大执行权限。
- 收紧 `isProgressEvidence`、`memberCandidate`、`evaluateWorkflowDelivery`、`ScopeGoalService.receipt` 四处完成证据入口。旧日志仍可阅读；历史/合成进度也不能绕过。提问后取得的真实业务证据仍可用于交付，不能把提问过的整轮都判为无效。
- 文件基线、检查点和 JSON 验证已有精确白名单，不扩张范围；帮助记录可保留真实提问尝试。普通回答“同意”不产生人工验收、权限批准或自动继续意图。

## 验收与交付

单元覆盖选择与补充、其他答案、全部问题、跨任务/重复回答、列表变异、停止竞争、唯一编码及消费后的坏回包。业务回归覆盖 answers/cancelled 均不作证、混合伪证拒绝、真实文件证据保留、旧 Workflow 与候选不能绕过。

真实 Pi 使用本地确定性供应商，覆盖主会话和成员的实际问题/答案链；最终 Windows EXE 验证原有选项卡、其他输入、“提交并继续”、停止和重开不重放。该验证不证明在线模型自主决策质量。
