# Task 构建与维护规范

构建、调整或验收单一任务时读取。本文件是字段语义、维护依据与分组规则的权威正文；任务调度由调用方安排。

Task 组合 [Agent 契约](../capability/agent-spec.md) 与 [Module 契约](../business/module-spec.md)，只在需核实下层字段或维护约定时读取对应部分。Task 不引入执行者内部循环，不建立项目任务注册表，也不反向加载上层 Skill 或项目入口。

Task 绑定唯一 Agent 与一个或多个由其维护的模块；调用方提供目标、约束及下层对象定义。维护对象是 core 或能力定义时使用文末约定。

## 一个 Agent 维护多个模块的前提

CBIM AI 助理派发前逐模块核实该 Agent 的维护责任与能力适用性。依据可以是现有权威知识中的明确维护约定，或用户、项目负责人的有效指定；记录依据位置、适用范围及知识版本。Agent 能做某项工作，不自动证明该模块由它维护。

当前 Agent 与 Module 的结构化定义没有直接维护关系字段。不得把 authors、作者所在组、目录相邻、能力相似或此前处理过某个任务当成维护关系，也不得用本次派发本身循环证明维护资格。维护依据缺失或冲突时，先核实相关模块的维护归属，仅暂停依赖该结论的派发。

维护责任不等于任意写入授权；仍需核实本次目标、读写范围、公共契约和有效授权。Task 引用维护依据，不在任务记录中创造另一份长期维护关系真源。


## 任务内容

以下是逻辑字段，不要求另建固定格式的存储系统。可以由宿主任务能力或本地任务记录承载，但含义与交接内容必须完整。

| 内容 | 含义 |
|---|---|
| id、目标 | 本次需求内唯一的任务标识，以及可验证的单一结果 |
| agent | 唯一AI 成员 的定义路径；不接受多个AI 成员 混在一个 Task 中 |
| modules | 非空、无重复的模块集合；每项引用模块定义及该 Agent 对它的维护依据 |
| 模块工作范围 | 每个模块在本任务中的具体工作、读写范围、禁止改动内容及验收要求；通过模块 sources 核实物理工作区 |
| 上下文与基线 | 用户目标、有效决定、必要知识、当前产物与版本记录；只读依赖引用不自动加入维护模块集合 |
| 前置依赖 | 必须先验收的任务及所需产物，不把依赖任务的模块自动纳入本任务 |
| 验收与回报 | 模块内检查、模块间接口或数据一致性检查、整体任务目标、产物和证据位置 |
| 状态与进展 | 待执行、执行中、待验证、受阻、已完成或已取消；记录已发生操作、未完成部分及下一步 |

路径相对项目根解析；Agent、Module 引用指向各自定义文件。知识与产物版本按 [任务基线与恢复规则](task-baseline.md) 保存，不复制定义成为新真源。


## 合并与拆分规则

- 同一 Agent 确实维护相关模块，且这些模块共同服务于一个可验收目标时，可以放入同一 Task；跨模块本身不是拆分理由。
- 属于不同负责维护的 AI 成员 的模块必须拆成不同 Task，由 CBIM AI 助理协调前置依赖与交接。不能仅为减少任务数量，把不同专业职责临时塞给同一 Agent。
- 即使由同一 Agent 维护，目标独立、交付时点不同或范围过大时，也可以拆成多个 Task；同一 Agent 可以承担多个任务。
- 父模块不自动包含所有子模块的维护范围。明确列出实际承担工作的模块，不因目录层级扩大任务。
- 只需读取其他模块的契约或证据时，将其作为上下文引用；需要修改不在集合中的模块时回报 CBIM AI 助理。CBIM AI 助理核实维护关系与授权后更新原 Task 或新增 Task，再核对依赖和冲突。
- 多模块的 sources 可能重叠；CBIM AI 助理按实际文件、资源和运行环境检查任务之间的冲突。同一个 Agent 名称或不同模块 id 都不能证明并行安全。


## 派发、验收与恢复

派发前核对唯一 Agent、非空且无重复的模块集合、每项维护依据、工作范围、基线、前置产物和验收条件。未解决的维护归属不能伪装成已确定工作区。

执行者在明确范围内安排具体操作，完成适用验证后向 CBIM AI 助理回报。CBIM AI 助理验证各模块结果、模块之间的衔接及整个任务目标，全部必要条件满足后才将 Task 标记为已完成；某个模块通过不代表整个 Task 完成。

恢复时核对任务绑定、维护依据、模块范围、知识版本和实际产物。变更只重验受影响部分，已完成操作不重复执行；历史 Task 保留原绑定，新范围保留变更依据。

任务实例与恢复证据位于项目根 `<用户主目录>/.cbim/<项目标识>/task-records/` 或已约定的宿主任务记录中，不默认跨设备共享。`design/task/` 仅保存抽象与规则。纯 core 或能力定义维护仍以明确维护对象开展，不为套用业务 Task 而虚构模块。


## 场景核对

| 场景 | 处理 |
|---|---|
| 同一负责维护的 AI 成员 修改两个模块以完成一个联动目标 | 一个 Task，列出两个模块的范围，并验证联动结果 |
| 两个模块分别由不同 Agent 维护 | 两个 Task，由 CBIM AI 助理协调依赖 |
| 同一 Agent 完成两个互不相关的目标 | 可拆成两个 Task，各自验收 |
| 维护关系未知但能力看似匹配 | 核实维护依据后再派发，不凭能力猜测 |
| 本任务只读取其他模块契约 | 保留只读引用，不扩展任务维护范围 |

## Cindy 插件注入

Task 的插件集合等于唯一 Agent 与全部作业 Module 的 connectors 并集，经连接器注册表解析为准确的 ghost_id 与 namespace，去重并保留声明来源。不引入只读参考模块、其他成员或未列入作业对象的父子模块插件；空集合不注入业务插件。

每次拉起 subagent，CBIM AI 助理自动计算此集合，实时核实宿主插件身份与可用性，将该任务专属的插件声明、简短用途及宿主发现调用入口作为 TaskContext 注入。具体工具参数和必要手册由执行者按需发现，不预读全部工具 Schema，不复制全量宿主插件清单。不得把完整父会话上下文当成精简注入。

严格工具可见性与调用隔离由 Cindy 的派发能力实现；请求与回执分别记录插件集合。只有宿主实际确认了过滤后的插件访问范围，才可称隔离已生效。仅传入文字声明不等于限制了工具调用。宿主缺少过滤入口时报告 blocked，不用继承全部插件或提示词约束冒充已实现隔离。

CBIM 不管理连接、认证、连接池或回收，不要求每次启动重连、每次结束断连。实例结束由宿主结束该实例的上下文与访问范围，不关闭共享服务或其他任务会话。恢复和重新派发时重新核实插件映射、可用性与授权，不复用失效的发现结果。

插件身份未映射、插件停用或账号缺失时保留缺口，不自动替换到同名其他命名空间、不自动安装或登录。插件写操作仍受任务目标和授权约束。
