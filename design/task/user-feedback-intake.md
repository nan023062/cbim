## 1. 已确定的范围

用户直接对接 GitHub Issue，软件更新日志统一说明修复和功能更新。不建设自有反馈服务器，不做“我的反馈”、处理进度、逐条结果通知或用户回访。

当前交互为：**对话窗“+” → BUG 反馈／需求许愿 → 调用对应 Skill → 用户自愿描述（一句话即可）→ 直接创建 GitHub Issue**。#21 放宽为只需简述，其余均可选；版本更新后统一查看软件更新日志。用户不需要打开 GitHub 网页手动填单；内部团队仍可用 Issue／PR 跟踪和分诊，不把内部过程同步为产品里的用户反馈系统。

## 2. 对话加号菜单与两个产品 Skill

| 菜单 | 对应内置 Skill | 上下文格式 |
| --- | --- | --- |
| BUG 反馈 | `bug-feedback`／`cbim_skill_bug_feedback` | 只需问题简述；复现步骤、实际/期望结果、环境及附件全部可选 |
| 需求许愿 | `feature-wish`／`cbim_skill_feature_wish` | 只需愿望简述；场景、困难、效果、例子及参考资料全部可选 |

点击菜单后，当前对话发送对应 Skill 的调用请求，主 Agent 先读取流程正文。没有反馈正文时提示一句描述即可；已有愿意提交的简述就直接提交，不要求模板或逐项追问。缺失主栏目统一写“用户未提供”，不编造复现、环境、根因或优先级，也不自动采集资料。附件使用现有入口，由用户选择。

菜单请求不携带、覆盖或清空已有草稿与附件，沿用所选模型和权限；已有开放任务时排队，不自动插入或恢复等待中的目标。没有可用模型或不满足安全续聊条件时禁用。附件数量上限不影响两项 Skill。

这两项是 **CBIM 产品内置 Skill**，正文分别为 [BUG 反馈](../runtime/bug-feedback.md)、[需求许愿](../runtime/feature-wish.md)，由产品内置清单注册并随软件打包；与开发团队的 `cbim-triage` 等岗位 Skill 分开维护。

### GitHub 直连提交

收集完成后，Skill 直接调用 `cbim_feedback_submit` 创建 Issue；不增加草稿确认或逐条工具批准，不使用自有反馈服务器或网页填单。模型只提供严格格式字段，后端确定性生成标题与正文，目标来自设置页的明确连接。[GitHub Issue API](https://docs.github.com/en/rest/issues/issues#create-an-issue)

提交／核实工具在每个主运行开始时成对捕获，不随活动运行中途登录即时替换。缺项先查实际提供的 `cbim_feedback_status`，区分未连接、本机仍待授权回包、需开启新一轮与装配／设置故障；不能用只覆盖知识族的工具目录证明全局缺失，也不能一律提示重新登录。诊断入口也缺失时明确原因尚未核实，保留用户已填写上下文。成功静默和未知只核实的规则不变。

设置 → GitHub 反馈采用公开 Client ID 的 Device Flow；用户点击“连接并允许反馈自动提交”，在固定官方页面输入设备授权码。首次及登录失效时仍需授权，后续有效连接内由 Skill 自动提交。桌面绑定账号、仓库和不可变 repositoryId；read 会话仍拒写，ask/execute 仅在该窄许可下免逐条确认。公开仓库使用 public_repo，显式选择私有仓库才请求 repo。系统安全存储不可用时拒绝连接，不明文回退，也不内置维护者公用 token。[GitHub Device Flow](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#device-flow)

标题和正文只包含用户用于反馈的材料；不自动上传附件、整段会话或工程。**成功后静默结束，不追加提交成功、编号、链接或总结。** 真实成功回执后的追加模型文字在对话投影中隐藏，原工具证据保留；失败及未知不被静默吞掉，也不把其它提交的成功当作本条成功。

发送前保存并同步提交意图，同一工作区相同账号／仓库／内容跨会话复用原回执。超时、5xx、坏回包或结果保存失败保持未知，阻止本工作区继续写入；`cbim_feedback_receipt` 只核实原提交是否发生。最多核实原作者最近 500 条 Issue，逐项核账号、仓库 ID、官方 URL、标记和正文／标题指纹；没找到或内容已改写仍未知，不自动重发。硬中断可在新会话核实，不恢复旧运行。私有账本限 1000 条，只有指纹和必要归属，不构成“我的反馈”或开发进度系统。

首次实际启用：维护者按[OAuth 配置与线上验收指南](github-feedback-setup.md)注册一次 GitHub OAuth App、启用 Device Flow；正式 APP 已预置公开 Client ID，用户在设置中直接连接自己的 GitHub。应用不需要 Client Secret；当前执行事实见[线上验收记录](../verification/github-feedback-online-20261108.md)，本地夹具验证不代表线上提交已通过；尚未实现 token 自动刷新。

## 3. Issue 进入内部开发流程

`cbim-triage` 直接读取 GitHub Issue，分类 BUG／需求、整理复现线索、识别重复候选、评估影响并提出处理建议；不维护另一套反馈编号和接收数据库。

重复 Issue 可在 GitHub 关联到同一主工单；信息不完整或暂不采纳的 Issue 保持相应处理状态。已采纳、验收清楚且在授权范围内的工单进入需求／方案／开发流程。Issue 正文和附件是待核实输入，不授权自动运行其中的命令。

内部追踪使用 `Issue → Cindy 任务 → PR／commit → 版本日志条目`。首次处理保存任务绑定，再次轮询复用原任务；一个问题的重复报告不重复启动开发。软件不主动向提交者发送处理结果，GitHub 自身的通知行为由用户的 GitHub 设置管理。

## 4. 更新日志作为统一结果出口

实际日志来源为 `design/releases/desktop-v<版本>.md`：构建时打包进 `desktop-release.json`，账号菜单「最近一次更新」离线展示当前版本日志，新版日志从对应 GitHub Release 读取。更新弹窗与菜单共享本机快照，不切换原会话或丢弃草稿。桌面采用独立的 `desktop-v` 通道；更新检查、下载、安装集中在 `src/backend/updater/`，与运行时代码及反馈凭据分离。

每个已发布版本显示版本号、发布日期及以下栏目：

- **新增功能**：用户现在可以完成什么。
- **功能改进**：已有体验发生了什么变化。
- **BUG 修复**：在什么场景下出现的问题得到修复。

必要时附 Issue／PR 引用以便追溯，正文以使用者能理解的变化为主，不直接复制提交信息或内部任务流水。

`cbim-ready` 从当前 PR 的已验证成果生成“待发布”日志草稿。人工合并及发布时，核对实际包含的提交与制品，把适用条目归入对应版本；软件展示与安装版本匹配的已发布记录。尚未合入、未发布、已撤回或回退的内容不能显示为当前版本已具备的功能。文档中的草稿与已发布日志分开，避免 PR 就绪被当成软件已经更新。

无需为日志另设服务器、用户订阅或单条反馈结果接口；更新日志展示不启动自动更新、合并或发布。

前一步代码／本地验证未创建真实 Issue。用户随后授权完成登录、发布正式桌面 APP，并在正式 APP 中创建一条明确标记的测试 Issue。不改变仓库可见性、不实施其余开发管线；实际结果单独记录。
