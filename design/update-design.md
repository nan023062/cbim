# 分层更新的核心取舍

CBIM 的业务代码与界面变化频繁，Electron 和本机运行基础变化较少。采用 C/R/E 分离，让更新范围跟随真实变化，减少每次业务修复都替换整套应用的成本。

| 单元 | 责任 | 变化边界 |
| --- | --- | --- |
| C：冷基础 | Electron、宿主原生能力、最小引导与信任根 | 平台运行时、冷壳契约或信任身份变化需冷更 |
| R：运行资源 | 编译后的业务、界面、preload、worker 与内置资料 | 同一 C 下作为一个经过验证的兼容单元切换 |
| E：引擎包 | 独立循环实现与固定依赖 | 按宿主契约和冻结身份准备、选择与使用 |

R 精确匹配 C，不能提高资源版本绕过冷基础要求。E 的身份、支持登记和独立版本规则见 [引擎设计](engine-design.md)。包签名与 Windows 安装器签名解决不同问题，不能相互冒充。

## 先准备，再明确切换

后台下载、展开和校验候选，不修改活动目录；只有用户明确应用才排空、持久记录激活意图并短重启。普通退出不等于批准安装，准备失败不应关闭旧程序。

固定一次切换的版本、摘要、安装和用户目录身份、进程代际。业务入口、界面、preload 与 worker 使用同一 R，不能在运行中重新读取 latest。窗口出现、资源已加载和工作区可用是不同阶段，成功以对应真实握手判定。

不可变版本目录与小型激活记录减少新旧文件混用，也要求额外空间、可靠日志和保守清理。清理不能删除在用版本或唯一恢复依据。

## 恢复首先保护数据

候选尚未访问原数据且证据明确时，才可能安全回到已确认版本。已经访问或状态未知时保留数据与日志，进入恢复流程；保留旧代码不证明新数据可被旧代码读取。

原数据包含配置、会话、profile、localStorage 和业务知识。未知写入先核实，不自动重放任务，也不循环重试同一个坏包。引擎原生历史同样有格式兼容边界，不能靠切换 E 目录宣称完成迁移。

## 传输粒度的取舍

完整 R/E 包减少安装工作和组合复杂度。ZIP 本身不表示增量；文件差分或块差分需要准确基线、目标重建、完整校验与全包兜底。是否引入差分取决于真实带宽收益和恢复成本，不能仅因旧 NSIS 使用差分便认定可直接复用。

独立页面 reload、主进程 HMR、自动回收缓存和更宽的回退范围各有不同前置条件，不能由“热更新”一词推导为默认保证。具体已支持能力回到当前源码核实，旧方案中的阶段状态不在本文维护。

当前模型见 [冷壳](../src/bridge/server/bootstrap/ARCHITECTURE.md)、[更新服务](../src/logic/updates/service/ARCHITECTURE.md)；构建、签名、验收与发布步骤见 [发布流程](../ainative/skills/cbim-release/SKILL.md)。本文不授权投放，也不记录某一历史版本的验收结果。
