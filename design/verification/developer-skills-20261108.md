## 2026-11-09：稳定系统与架构原则补充

按用户补充，将低变化频率、业务变化隔离和长期复用价值明确为分层／抽象目标；系统、模块和类均要求单一职责与开闭原则，层、模块、文件及类型依赖遵循单向依赖。同步 AGENTS、5 种 Skill 和开发者说明，区分接口与实现的稳定，并要求交付稳定核心、变化点和影响传播的证据。

继续进行指令层面的人工推演，未作为模型行为评测：

| 场景 | 原则要求的判断 |
| --- | --- |
| 一个模块很久没有提交，但无人使用 | 不能据此称为稳定资产；核对真实消费者和使用证据 |
| 一个类同时因计费规则和报表格式变化而修改 | 核对两个独立变化原因，评估职责拆分，而非只减少方法数量 |
| 每增加一种业务都要修改公共核心的分支和字段 | 重新识别变化点；已知变化通过契约扩展，装配点可以注册新实现 |
| 文件依赖无环，但大部分模块都访问一个可变全局对象 | 继续核对职责、状态所有权和过密依赖，不以无环代替解耦 |
| 稳定核心发现真实缺陷 | 正常修复并核对消费者、契约及兼容性，不把开闭原则误作禁止修改 |

本次复核仍使用上述验证入口，核对 15 个入口的格式、5 组副本、相对链接与工作区差异。具体执行时间与结果保存在本机结构化记录中；本次不新增产品测试或架构检查器能力。

## 2026-11-09：按业务变化点与频率划分封装

按用户追加要求，模块或类必须按业务变化点划界，变化频率不同的代码分别封装。已在 5 种 Skill 中分别落实为方案评估、共性提取、源码架构说明、开发验收和认知交接要求，并同步 AGENTS 与开发者说明。评估记录包含变化点、业务驱动、频率及依据、所属封装、稳定接口；不以提交数机械推断边界。

指令层面的场景推演（未执行源码重构或独立模型评测）：

- 低频稳定执行机制与高频业务策略混在一个类：分别封装，经稳定契约组合，检查策略调整是否仍牵动核心字段或分支。
- 批量格式化造成某文件近期提交较多：排除非业务变更，依据真实需求和业务变化判断；证据不足时标明未知，不据此机械拆类。
- 两段代码都频繁变化，但分别由不同业务需求驱动：继续按业务变化点分开，不因频率相同或代码相似而合并。
