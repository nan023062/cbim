# 反馈工具不可用：可复现结论与修复验证

日期：2026-11-09。范围：正式版用户反馈、已确认提示缺陷、源码诊断修复。**当前结论：已确认并修复“工具缺失一律提示重新登录”的错误归因；可复现本机授权回包未保存时工具缺失，以及同一运行不刷新工具的行为。本机保存连接后，继续原会话的新一轮会成对取得反馈工具，未复现有效连接后的新一轮持续缺失。** 本次没有发布安装包或替换 NAN-LI 的 0.1.0。

## 1. 用户报告的环境与复测事实

| 项目 | 用户提供的值 |
| --- | --- |
| 运行设备 | NAN-LI |
| 应用 | CBIM Assistant 0.1.0，Windows x64 |
| 工作区 | `C:\Workspace\project1` |
| workspaceId | `e299b483d83062092ce113e91725ffc72dc4bc5f95334b65e67b82bb0f02e3d6` |
| instanceId | `65893119-fe3c-4be8-b829-f85dca8d90b5` |
| 主 Agent／实例 | `cbim:main`，running，writeEnabled: true |
| 版本检查 | 用户页面显示 2026/11/9 00:29:05 检查后没有更高正式版 |

用户在原 CBIM 会话中观察到：两个内置 Skill 都能返回正文并收集信息；四轮收集后，实际可调用清单始终没有 `cbim_feedback_submit` 和 `cbim_feedback_receipt`。用户补充确认 **GitHub 已授权、writeEnabled 为 true，但两项工具仍不可见**。

可确定写入缺陷报告的结论是：**该会话中，完成 GitHub 授权没有使反馈工具变为可用；不能将“缺少工具”直接诊断成“账号未连接”。** 这不是“所有连接成功的会话都无法注入工具”的结论。

以上是用户在 NAN-LI 的实测记录。本次代码验证在 LINAN-XDT；未取得原设备设置页的本机连接回执、原运行日志或应用文件指纹。用户提供的“版本与更新”页面不能代替“GitHub 反馈”页的连接状态。不能把当前修复机的状态写成原设备状态。

`cbim_knowledge_tool_catalog` 只覆盖知识族，反馈族由运行装配单独加入；知识目录中没有这两个名字，不能单独证明模型的完整工具集缺失。`writeEnabled:true` 也不等于本轮已经获得具体反馈工具或提交许可。

## 2. 已确认的提示缺陷（对应原报告第 5 节）

修复前，两份产品 Skill 在没有提交工具时都要求用户去“设置 → GitHub 反馈连接账号”。源码确认这是无条件降级提示，没有先核实连接事实。该提示会把装配、运行代际或其他异常误报成账号问题，应独立于原设备根因修复。

本次改为先检查实际工具，再按只读诊断区分原因：

| 诊断事实 | 用户下一步 |
| --- | --- |
| 本机没有保存连接／连接过期 | 在设置中连接，之后发送新消息继续 |
| 有效本机授权流程尚待回包 | 返回并保持设置页打开，等本机显示已连接；不重复网页授权 |
| 本机已连接，但本轮未装配操作工具 | 发送新消息开启新一轮，沿用原上下文；仍缺失则查版本与日志 |
| 原绑定发生变化 | 新运行重新捕获当前连接；原未知提交仍只核实，不自动重发 |
| 诊断组件缺失、设置读取或安全存储错误 | 报告真实类别，不指向反复登录 |
| 诊断工具也不可见，或声称就绪但操作工具仍缺失 | 明确工具不可用、原因尚未核实；检查版本、重启与原运行日志 |

只读状态查询不读取提交账本，也不能证明原 Issue 未创建。已有未知提交保持待核实，不能借诊断结果、换正文或新会话重发。成功后仍静默结束，不增加 Issue 链接、结果通知或处理进度。

## 3. 当前可复现结论（对应原报告第 6 节）

| 条件 | 可重复观察到的结果 | 证据层级 |
| --- | --- | --- |
| 空项目中尚未建立本机连接，启动主会话 | submit／receipt 同时缺失；诊断为 `GITHUB_NOT_CONNECTED` | 真实 Application + Pi 的模型 HTTP 工具清单 |
| 已启动 Device Flow，但尚未轮询并保存授权结果 | 两项操作工具仍缺失；诊断为 `GITHUB_AUTH_PENDING`，诊断查询不代替授权轮询 | 真实 Application + Pi；GitHub 为确定性夹具 |
| 运行开始时未装配工具，随后本机连接变为已连接 | 原运行仍没有两项操作工具；诊断为 `FEEDBACK_NEW_TURN_REQUIRED` | 状态工具单元测试及一次性装配源码；不冒称已做活动 Pi 中途登录的端到端验证 |
| 本机已保存有效连接，再发消息继续同一会话 | 两项工具同时进入实际模型请求；BUG／需求均能提交并核实，成功后的额外消息被隐藏 | 真实 Application + Pi；每条测试路径仅一张夹具 Issue |
| 断开本机连接，再继续原会话 | 两项操作工具同时移除，原提交没有重发 | 真实 Application + Pi |

对应可执行证据：[生命周期测试](../../tests/github-feedback-lifecycle-pi.test.ts)、[状态及权限测试](../../tests/github-feedback-status.test.ts)、[本机认证与提交测试](../../tests/github-feedback.test.ts)。修改前的两条真实 Pi 生命周期测试同样能在连接后取得工具，说明本次修复的确定性缺陷是错误归因和缺少诊断；没有证据将“已保存有效连接后新一轮仍持续缺失”定性为通用注入故障。

沿实际代码核实的调用链：

1. `Application` 持有桌面 `GitHubFeedback` 服务，交给 `main/execution.ts`。
2. 每次主 chat 运行通过 `GitHubFeedback.prepare`／`auth.capture` 捕获本机已保存连接；未连接不提供提交端口。
3. `loop-engine.ts` 根据该端口一次性装配成对的 `FeedbackTools`，经 Pi 临时桥注册。
4. 普通原会话的新一轮会重建运行并捕获当前连接；活动运行中途登录不会即时替换原工具和固定目标。
5. 网页授权与本机保存连接不是同一步。当前 Device Flow 由可见的 `GitHubFeedbackSettings` 页面轮询；离开页面会停止轮询，回到页面可继续仍有效的流程。这解释了上表中本机授权尚未落盘时的可复现行为，不将该条件追认为 NAN-LI 当时的实际状态。

账号授权、应用接收并保存连接、运行捕获端口、Pi 实际活动清单是不同阶段。原报告列举的“组件未加载”“白名单未注入”“版本不匹配”“启动异常”在本次原故障排查中均未被证实，不作为当前结论或已修复根因。

本机使用改动前的相关实现，运行真实 Pi 子进程和 Application，在空项目中依次测试未连接、登录后继续原会话、断开后再继续：BUG 与需求两条路径均通过。连接后两项工具都出现在实际模型 HTTP 请求中，断开后同时移除。该结果没有复现 NAN-LI 的故障，也没有否定用户的原设备观察。

另一次 `cbim_ask_user_question` 的 `fetch failed` 仍作为独立现象；尚无证据与反馈工具不可见同源，不据此改写传输或自动重试规则。

## 4. 本次代码交付与维护入口

- `core/connectors/github-feedback.ts`：新增严格的连接检查与运行可用性协议，无凭据、设备码或提交内容。
- `main/resources/github-feedback-auth.ts`：`checkConnection` 读取本机连接及代际，不解密、不联网、不触发 Device Flow 轮询；读取失败保留明确错误类别。
- `scheduler-engine/tools/feedback-status-tool.ts`：独立只读 `cbim_feedback_status`，将实际运行的成对装配事实与当前连接状态合并；未连接仍能查询。
- `main/execution.ts`、`scheduler-engine/execution/loop-engine.ts`：仅主会话注入诊断，成员不继承；不刷新原提交端口。
- `core/policy/tool-policy.ts`：状态工具限精确名称、版本、非原生、单一 read 效果和本工作区。提交／核实继续要求原反馈范围，read 仍不能提交。
- `core/brain/pi/{bridge,engine}.ts`：分别记录宿主 prepared 与 Pi active 工具名称清单及 missing；受保护的 `/tools` 拒绝非法清单，缺项返回并记录 `TOOL_CATALOG_MISMATCH`。`request-budget-bootstrap.ts` 在启用逐请求预算时同样放行原桥的这一固定地址。日志不含参数、反馈正文或凭据。
- 主 Agent 指引及两份产品 Skill：按真实诊断提示，不用知识目录推断全局缺失，沿用已填上下文。GitHub 设置页补充“保持页面打开，等待本机已连接”的说明。

职责按变化点分开：用户提示与诊断规则归反馈工具和 Skill；认证状态归桌面资源服务；通用 Pi 桥只核对名称；原提交账本、幂等与未知结果屏障保持原归属。新增一种提示只修改反馈诊断规则，不需要修改写入账本或更新子系统。这是当前需求的边界判断，未据一次改动宣称长期稳定性已获证明。

同步维护了上述源文件的文件头／关键接口注释，以及九个受影响目录的 CONTRACT 和 ARCHITECTURE：Core connectors、policy、brain/pi，Main、Main/resources，Scheduler tools、conversation、execution，Frontend settings。新工具已加入目录代码清单与类图，现有节点补充实际行为说明。

本次没有实现手动反馈表单、设置页完整组件状态面板、后台自动轮询或开发进度回访；也没有创建新的线上测试 Issue。

## 6. 结论适用范围与复现定位

本报告以第 3 节的可复现场景收口。已修复的是错误提示及诊断缺口；本机连接后新一轮装配正常，NAN-LI 的既有观察仍按用户实测保留，未进行该设备正式包复验。

相同现象再次出现时，可比较同一运行的应用构建、本机连接状态、宿主期望与 Pi 实际清单。新清单事件位于 canonical 日志中的 `engine.status`、`metric:tool-catalog`；prepared 有而 active 没有，仅表示没有活动清单确认。该入口用于定位具体复现条件，不更改本次已验证结论。

只提取必要公开状态、工具名称和错误码，不分享 `connection.json` 全文、加密 token、模型密钥、完整会话或工程。原 0.1.0 没有新增诊断事件，缺少这些日志不能反过来证明组件损坏。源码验证通过不等于已发布或已更新用户设备。
