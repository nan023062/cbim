# Step33：模块负责人进入正式派发与领取

日期：2026-11-08。状态：本片实现、回归修正、源码边界检查、最终构建及三场新版 EXE 验收已完成。全仓与修后定向分别记录，不称单批全绿。对应 [实施计划](../task/module-owner-dispatch.md) 的 R02-C；本报告不能作为整组 R02 或第 1–8 组已完成的依据。

## 已接通的行为

- 主调度按明确模块查询负责岗位，将预期版本写入目标分配和派发；任务保存服务生成的冻结绑定。不同岗位分开执行，同静态 Agent 不代表同一岗位或运行实例。
- 实际领取重新核岗位状态、能力采纳、受控来源、模型及模块责任版本。主聊天模型不能替换岗位模型；没有负责人、未采纳或禁用配置明确拒绝，不自动选择内置执行者。
- 知识快照、模型设置和任务短事务按固定顺序取得；真实引擎在领取后启动。模型更新先发生则拒绝旧配置，领取先发生则保留捕获配置；检查点预约和实际续轮均重新核验原绑定。
- 新存储协议由 Store 生成，通用变更也受不可变绑定规则约束。历史未绑定任务可读，新的领取明确要求重新规划；旧在途按原运行事实收束。旧直接业务 `loop.start` 和续轮入口拒绝，普通聊天与知识治理保留。
- 主对话成员卡、任务详情及目标分配展示原岗位、模型和来源版本。手动“核实当前负责人配置”独立显示当前差异，不改写历史、隐式采纳或重派；迟到响应按任务身份和修订隔离。
- 人工验收及人工接续在任务事务外核实证据，再以知识快照和原周期状态 CAS 提交，避免端口内受控知识提交与任务事务互相等待。决定和接续仍分别保存，不由查询自动启动。

## 过程中发现并处理的问题

- 原 canonical 任务及 Workflow 证据投影漏传 `ownerBinding`，使真实已绑定任务无法通过严格证据核验；补齐投影，未放宽校验器。
- 旧测试使用独立派发账本或无负责岗位直接执行业务。按当前真实协议显式登记岗位、模型及责任，保持原验收目的；没有修改全局 `seedTeam` 自动授予负责人。
- 唯一账本回归中，验收文件端口注入受控知识提交会在原任务事务内等待自己。改为外部取证与最终短事务分离，保留版本检查并补接续竞争用例；实际文件端口仍只读文件，此测试不等于已经证明线上用户发生过该死锁。
- 首轮真实 Pi 夹具错误假设两个写任务并发、把纯文本坏回包当 JSON，以及检查点硬编码进度版本；分别改为实际领取顺序、真实错误格式和读取当前版本。原失败报告保留，不声称首轮全绿。
- 撤销依赖的六节点长对话在上下文估算达到 50,265 / 65,536 时真实触发自动压缩；该固定响应夹具没有摘要分支，四次摘要重试后触发运行超时。只将此用例容量提高为 131,072，继续开启真实压缩，产品默认值和专用压缩测试不变；原诊断报告保留。
