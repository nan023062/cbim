## 一、理论要解决的问题

项目知识、专业方法与具体任务混杂时，换项目需要重写能力，换能力容易影响业务规则，每次任务还要重复推断项目结构。CBIM 用独立的能力与业务模型减少这种耦合，并通过显式任务绑定使二者协作。

CBIM 关注知识如何组织以及任务如何获得必要上下文。它与渐进式架构演进、人工认知保障共同支撑整体 AI Native 体系，但不承担另一个专项理论的完整论述。
## 二、CBIM：能力与业务独立，个人记忆可选

**CBIM = Capability-Business Independence + Memory。**

### 2.1 C：能力是可复用的专业资产

C 描述完成某类操作的方法和专业知识，例如代码分析、依赖识别、测试设计、美术资源处理、策划规则分析与配置审查。技术栈专长可以属于能力，但本项目的路径、模块事实和业务取舍不应硬编码进通用方法。

能力复用不是复用某段聊天历史，而是把方法、输入输出和适用边界明确下来，再绑定不同项目的上下文。

### 2.2 B：业务是项目的长期知识

B 描述具体项目的模块、依赖、契约、流程和架构决策。DNA 是模块知识的表达，包含定位、契约和雷区；契约不仅是方法签名，还包括行为、数据所有权、生命周期和失败语义。

B 同时容纳待收敛知识与正式约束：

- `observed_patterns` 保存已经整理、需要持续观察的模式、证据和决策。
- `established_abstractions` 指向已验证、获批准的抽象，正式定义保存在 DNA。

长期保存不等于强制执行。“确认存在重复，但当前需求不稳定，暂不抽象”也是有价值的长期项目知识。知识是否长期存在，与它是否拥有约束效力，是两个维度。


#### 模块是研发工作单元，不限定为代码模块

B 中的模块是具有明确职责、输入输出、依赖和验收约定的业务或专业工作单元，通过 authors 记录真人作者。工作区责任登记明确模块的负责人成员，任务冻结本次责任与执行范围。它可以是代码模块，也可以是 Quality Assurance（QA，质量保证）测试模块、美术模块、策划模块。模块不是单纯的物理文件夹，也不必按部门机械拆分；同一个玩法可以关联多个专业模块。

| 模块类型 | 可能的产物 | 契约示例 |
|---|---|---|
| 程序模块 | 源码、接口、配置、构建产物 | 行为、数据所有权、调用方式、兼容性 |
| QA 测试模块 | 测试用例、测试数据、自动化脚本、验收记录 | 覆盖范围、环境前提、预期结果、证据要求 |
| 美术模块 | 图片、模型、动画、材质、Prefab、源工程 | 尺寸、格式、命名、绑定关系、性能预算、交付规范 |
| 策划模块 | 需求规则、数值表、配置、文案、关卡方案 | 字段语义、取值约束、玩法规则、与实现方的交接要求 |

这些是概念示例，不是已经建立的项目模块或文件清单。DNA 的定位、契约、雷区适用于所有类型，但契约与验证内容随产物变化，不把每个模块都解释成编程接口。

C 保存“如何设计测试、如何处理资源、如何分析数值”等可复用能力；B 保存“本项目某玩法的测试覆盖、某界面的资源规范、某系统的数值规则”等具体知识。不能把 QA 或美术模块误当成能力节点，也不能把具体业务路径写入通用 Agent 能力定义。能力加入工作区后可以形成长期负责模块的岗位成员，责任关系属于项目适配，允许明确变更。

调度组合的对象是目标、能力和业务模块；文件扩展名只帮助选择工具，不足以判断业务归属。不同产物可以使用不同执行方法和验证方式，但仍遵守相同的责任与授权边界。

### 2.3 组织对偶：Agent + Skill 与 Module + Workflow

C 的承载节点是 **Agent**，节点挂载 **Skill**；B 的承载节点是 **Module**，节点挂载 **Workflow**。team/ 承载能力侧的组织与 Agent，workspace/ 承载业务模块。

| 对偶维度 | C：能力侧 | B：业务侧 |
|---|---|---|
| 节点 | Agent：专业能力定义 | Module：业务职责与契约定义 |
| 挂载内容 | Skill：完成某类操作的方法 | Workflow：本模块操作的步骤、条件与出口 |
| 项目扩展目录 | team/ | workspace/ |
| 主要知识 | 方法、输入输出、工具要求与能力边界 | DNA、业务流程、依赖与物理工作区源 |

对偶描述组织关系，不要求两侧文件数量相同，也不要求 Agent 与 Module 一一对应。一个 Agent 可挂载多个 Skill，一个 Module 可挂载多个 Workflow；共享内容通过引用挂载，不复制正文。DNA 是 Module 的业务知识基础，不等同于 Workflow。

执行 AI 按 core 的共享规则组合 Agent 与 Module，将所选 Workflow 的步骤匹配到适用 Skill。无专属 Workflow 时，AI 成员 根据已明确的任务与模块，使用 CBIM 大脑执行循环，不伪造业务流程；没有专属 Skill 也不阻止在实际能力和工具范围内执行。挂载不代表默认全量加载。

模块目录表达逻辑父子关系，目录路径即模块 id；sources 以目录索引实际物理工作区，scope 说明直接维护边界；同一物理源及其别名只保留一份维护声明，不以不同 scope 重复登记。父子及祖先模块的同向目录包含属于正常组成关系，跨分支包含保留为工程结构存量警告。Agent 和模块的 authors 引用真人花名册，多位作者必须同组。作者所属组可为首次岗位配置提供候选线索，日常派发依靠明确的模块负责人索引；作者不等于负责人成员。Agent 的职业与技术定位通过名称、摘要和能力说明表达，不另设领域标签字段。

Agent 定义不是必须常驻的进程或一次会话；Feature/Refactor 是 Agent 可承担的职责层级，不是替代 Agent 节点的另一套能力体系。能力抽象不绑定具体业务，工作区成员承载岗位适配与长期责任，模块显式标记负责人成员；主 Agent 按模块查询负责人后派发，具体组合及版本写入任务包。更换负责人改变项目分工，不修改通用能力定义。见[工作区成员与模块负责人索引](../design/task/module-owner-index.md)；这是目标设计，不声明相关运行能力已实现。

### 2.4 I：独立演化，通过任务组合

I 表示能力与业务可以分别维护、分别演化，在任务中建立明确绑定。增强分析方法，不应要求重建模块树；业务新增模块，也不应要求重写通用分析方法。

独立并不意味着彼此完全不了解。方法必须接收适用的技术条件和业务契约，但这些信息通过输入、引用和版本绑定进入，而不是散落在不可拆分的提示词中。

### 2.5 M：可选的个人本地短期记忆

M 保存个人临时线索、未整理的调查笔记和短期尝试，不进入团队共享版本管理。它用于辅助当前工作，不承担团队契约、审批和交付证据的保存责任。

C、B 承载团队共享且版本管理的长期知识。本地任务审批、验收和实际变更证据保存于 `<用户主目录>/.cbim/<项目标识>/task-records/`，个人短期线索保存于 `<用户主目录>/.cbim/<项目标识>/memory/`；两者都不默认共享。需要跨设备恢复或人员接管时显式传递任务记录，不能因为属于本地临时目录就丢弃在途任务所需证据。

个人线索经核实和审核，可以成为 C 的方法或 B 的业务知识。这个过程是知识形成，不是自动把个人记忆提升为团队规则。没有 M，团队核心流程仍应能够执行和恢复。

## 三、结构外化与渐进式理解

### 3.1 把需要一致的事实从会话中移出

模块边界、契约、依赖、任务状态与审批依据必须可以被定位和核实。不能要求每个 Agent 从长对话中重新猜测项目共识。

结构外化的价值在于降低重复推断和交接损耗，而非增加文档数量。源码、测试材料、美术资源和策划配置等原始产物承担相应事实，DNA 承担语义约定，索引承担定位，任务记录承担过程证据，各有明确职责。

### 3.2 自然语言入口，技术定位由系统承担

业务发起者知道想改变的体验或交付结果，但未必知道模块和文件结构。统一使用自然语言表达目标，意味着技术定位与范围判断应由系统及负责人承担，而不能藏在“请用户填写模块路径”的模板要求里。

发起资格与执行权限分开。任何角色可以表达需求，但实际修改受到模块、契约和风险边界约束。

### 3.3 最小必要上下文，而非信息越少越好

先定位，再读取相关 DNA、契约和必要原始产物；存在证据缺口时才有依据地扩大范围。关键词命中只产生候选，不能直接证明根因或修改位置。

精简上下文不能牺牲跨模块不变量和必要依赖。目标是使每项输入都有用途，而不是追求没有依据的“理论最小”或让模型一次理解整个项目。

## 四、专业判断与确定性控制各司其职

Agent Skill 属于 C，表达专业方法；业务 Workflow 属于 B，表达业务操作的步骤、条件和出口。两者可以组合，不必相互替代。

需要分析和取舍的部分交给专业能力；已明确的顺序、条件、审批和副作用控制交给可验证流程。确定性控制不表示每次执行得到相同答案，而是执行路径及其变更有规则和证据。

自然语言中的“禁止”和流程文档中的“必须”不自动形成硬约束。权限、执行器、校验器和人工责任应共同落实它们。描述、实施和验证是不同状态，不能因文档写得完整就声称系统已具备能力。

Feature / Refactor 表示 CBIM AI 助理在本次任务中组织的业务交付或架构评估职责，不是由循环固定绑定的 Agent 类型。CBIM AI 助理负责选择流程、拆分与协调；每个执行任务绑定一个 Agent 与一个或多个由该 Agent 维护的模块，执行者在已确定的工作区内完成分配的分析、实现或验证工作。任务内跨模块结论由AI 成员 提供，跨任务结论由 CBIM AI 助理汇总。

Feature Agent 对应业务人员，负责在既有规则、契约和授权范围内交付具体业务任务；Refactor Agent 对应架构师，负责跨任务、跨模块观察结构问题、识别共性、提出抽象、规范统一、职责拆分和演进方案，并在获批后推进落地。

这是一组职责层级，不是代码职业分类。两者均可组合程序、QA、美术、策划等 C 能力，作用于相应 B 模块。例如测试用例补充属于 Feature 职责，跨玩法测试体系的收敛属于 Refactor 职责；资源制作属于 Feature 职责，公共资源组织规范的演进属于 Refactor 职责。

Agent 角色描述承担什么责任，C 描述运用什么专业方法，B 描述处理什么项目对象。角色不会因此获得额外权限；Refactor Agent 的架构分析职责不替代人类负责人对正式架构决策的批准。两者可共享能力，不必成为两套重复知识或永久运行的进程。

## 五、结构层、调度层、执行层与校验层

| 层 | 理论职责 | 边界 |
|---|---|---|
| 结构层 | 外化能力、模块、契约和关系 | 提供可核实的知识，不代替实际实现 |
| 调度层 | 将目标绑定到合适能力和业务范围 | 不能凭路由结果扩大授权 |
| 执行层 | 运用能力处理明确的业务上下文 | 不能将局部目标扩展为任意架构修改 |
| 校验层 | 判断产物是否满足契约、边界与目标 | 不以执行结束替代验证 |

这些是职责分层，不要求一层对应一个 Agent 或进程。CBIM 通过内部大脑与调度引擎承载执行，领域知识与引擎适配分离；更换执行引擎不应要求重建能力与业务知识。文件夹划分和实现工具是执行方案，不能单凭目录结构证明独立性已经成立。

## 六、知识状态、来源与权威

C、B 是团队共享且版本管理的长期知识。B 中的观察模式可以长期存在而不具有强制约束效力；正式抽象经审定后提供明确的复用与使用边界。`observed_patterns` 与 `established_abstractions` 均属于 B，后者正式定义归 DNA，索引只负责定位。

个人刚发现的线索可以保留在 M，核实整理后才进入共享知识。当前由作者（author，linan）本人维护观察模式，是维护责任的安排，不改变它属于 B 的事实。具体权限和审批关系见执行方案。

任务审批、产物验证和交付回执是共享工程证据，不能只留在个人 M。长期知识与任务证据都应具备来源和版本，过期知识不能因曾经被批准就永远正确。

## 七、独立性的判断

| 检验场景 | 应有表现 |
|---|---|
| 更换业务项目 | 通用专业方法保留，重新绑定项目知识与适用条件 |
| 增强某项能力 | 不需要重写业务模块树和项目契约 |
| 新增业务模块 | 现有方法可在获得必要上下文后使用 |
| 更换执行引擎 | 项目知识仍可理解、定位和验证 |
| 个人 M 不可用 | 团队仍能从共享资产继续工作 |

独立性是需要验证的架构目标，不是因为使用 C/B 命名就自动成立。上下文减少、能力复用和维护成本改善需要真实任务证据。
