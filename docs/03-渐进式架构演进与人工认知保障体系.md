# 渐进式架构演进与人工认知保障体系

> 当前适用边界（2026-11-12）：首先服务单人或少数人的本地 AI 团队开发。普通开发、验证与返工应在已授予的范围内自动推进；下文“人工判断”针对需要新授权、业务取舍或正式规则变更的情况，不为每个任务增加逐步审批。完整产品闭环尚需补齐，现状见 [源码审计](../design/verification/local-ai-workflow-audit-20261112.md)。

## 一、两个必须一起解决的问题

业务在探索中变化，无法预先确定所有抽象；AI 提高实现速度后，代码增长又可能快于人的理解。只解决重复代码，可能得到无人理解的框架；只要求人逐行跟进，又可能消耗自动化带来的收益。

本体系将架构收敛和认知积累作为相互约束的过程：结构可以渐进形成，但正式变更必须有证据、决策与理解。目标不是让每次开发都产生抽象，而是让结构变化有依据，让负责人始终具备判断和接管能力。

### 适用于不同专业产物

本文的演进对象也包括测试体系、美术资源组织和策划规则结构。代码抽象是其中一种情况：重复测试可以形成稳定的用例组织或测试数据约定，美术交付可以收敛为经验证的资源规范，策划规则可以形成复用的配置模型。相似产物只是观察信号，不要求统一成基类或代码接口。

收敛是否合理由对应专业负责人判断；只有影响公共契约、稳定层或全局边界时才进入相应架构审批。人工理解也按专业体现：Quality Assurance（QA，质量保证） 需掌握覆盖与盲区，美术需掌握源资源、引用和导入限制，策划需掌握规则、数值依赖和玩家效果。

后文的软件重构与代码示例仅适用于代码任务。非代码产物按自身语义检验行为或效果保持，不把编译、单元测试作为所有任务的通用完成标准。

## 二、渐进式架构：允许探索，保留收敛能力

### 2.1 边界相对先行，抽象随证据生长

在需求持续变化的游戏研发中，必要的责任边界、稳定层和安全约束应先明确；具体抽象可以随着真实功能和变化模式逐步形成。

允许早期独立实现与短期重复，不等于放弃架构。关键在于重复能否被观察、记录和重新判断，而不是写完后永远失去踪迹。

### 2.2 观察状态使“暂不重构”成为显式决策

从看到相似代码到建立公共框架之间，需要观察空间。观察记录表达共同语义、变化维度、证据和当前判断，使“继续观察”“暂缓”“驳回”都有依据。

因此 `observed_patterns` 属于 B 的长期知识，不属于 M 的个人临时记忆。其维护责任由治理安排确定，知识类别不会因为只有一个人维护而改变。

### 2.3 信号触发判断，不代替判断

重复次数、AST 相似度、复杂度与依赖数量可以帮助发现问题，但不能直接证明值得抽象。代码相似可能源于不同业务，语义同源也可能有不同实现。

抽象判断需要同时考虑不变量、变化方向、使用成本、迁移与回归成本，以及维持独立实现的价值。达到阈值可以触发评审，不能自动触发重构。

### 2.4 复用有适用边界，收敛有退出路径

正式抽象提供优先复用的依据，也必须明确不适用的情形。不能为提高复用率强行套用，不能把减少代码行数等同于改善架构。

正式抽象也会过时。废弃、替换和迁移属于正常演化，需要保留使用方与行为的可追溯关系。长期稳定来自可控变化，不来自拒绝变化。

## 三、人工认知保障：理解也是交付的一部分

### 3.1 决策权需要理解支撑

如果负责人只确认功能表现，却无法解释核心数据流、关键不变量和失败路径，形式上的人工审批不足以维持掌控力。

AI 承担调查、生成、验证和方案准备；人保留架构取舍、核心风险判断与责任。人可以借助 AI 理解实现，但不能把最终判断简化为对 AI 自评的认可。

### 3.2 产物、意图、风险共同构成可接管的交付

产物说明改了什么，设计意图说明为什么这样改，风险说明帮助判断失败如何发生及如何排查。三个维度共同降低黑盒程度，不要求每个小任务都生成三份独立文档。

风险说明只表达已知风险和未知范围，不承诺穷尽故障。关键代码阅读、代表性故障推演与实际验证仍不可被文档替代。

### 3.3 共享契约的变化需要相应理解

架构固化和高影响变更应让负责人形成可解释的心智模型：输入从哪里来，状态归谁，失败影响谁，先查哪里，怎样恢复。

认知保障贯穿方案、审查和复盘，不只是交付后补一张“已读”记录。治理成本也需与变更影响匹配，不能让每个局部调整都承受同样重的流程。

## 四、架构演进与人的理解如何协同

| 架构变化 | 需要形成的认知 |
|---|---|
| 独立业务实现 | 知道目标、修改范围与已知风险 |
| 进入模式观察 | 理解相似处、差异处和当前为何不抽象 |
| 提出收敛方案 | 理解不变量、扩展点、替代方案与迁移成本 |
| 固化公共抽象 | 能解释数据流、契约、失败路径与使用限制 |
| 扩展、替换或废弃 | 清楚哪些调用方受影响以及如何迁移、回退 |

Feature / Refactor 表示 CBIM AI 助理在本次任务中组织的业务交付或架构评估职责，不是由循环固定绑定的 Agent 类型。CBIM AI 助理负责选择流程、拆分与协调；每个执行任务绑定一个 Agent 与一个或多个由该 Agent 维护的模块，执行者在已确定的工作区内完成分配的分析、实现或验证工作。任务内跨模块结论由AI 成员 提供，跨任务结论由 CBIM AI 助理汇总。

Feature Agent 对应业务人员：完成具体玩法、测试、美术或策划任务，并提供实际产物、局部问题和模式线索。Refactor Agent 对应架构师：跨任务、跨模块分析共性与差异，评估职责边界，提出公共抽象、资源规范、测试体系或配置模型的演进方案。

Refactor 的职责从观察与方案阶段开始，不限于审批后执行代码重构；获批后可组合相应专业能力推进落地。它不能自行固化正式规则或绕过人类批准。人类负责人仍负责正式架构决策、风险判断和关键理解。

两者按职责分工，不按文件格式或部门分割。Feature 与 Refactor 共享事实、证据与专业能力，不形成互不相通的系统；业务产出为结构判断提供材料，结构演进再指导下一轮业务工作。

## 五、知识一致性连接结构与认知

如果 DNA 与代码不一致，负责人理解的可能只是旧结构。知识维护因此是架构演进的一部分：检查实际职责、语义契约、依赖与风险是否仍符合当前描述。

知识失配与代码问题分别判断。文档遗漏可能只需修正文档；结构缺陷可能需要设计调整；未知情况应保留为未知，不能为了给出等级而假装完成诊断。

观察模式与正式抽象的知识归属遵循 [CBIM 理论](02-CBIM架构设计理论.md)：两者都属于共享 B，个人 M 只是可选线索来源。演进决策不能依赖团队无法获取的个人记忆。

## 六、闭环与判断边界

```text
业务探索 → 模式观察 → 人工判断
                     ├─ 继续观察、暂缓或驳回 → 保留依据，等待新证据
                     └─ 批准收敛 → 实现与回归 → 正式抽象
                                             ↓
                              负责人理解、知识校验与复盘
                                             ↓
                                  指导下一次业务探索
```

上述关系表达理论反馈，不代替执行流程。观察状态、审批人、任务隔离、测试与交付后复盘安排，见 [全流程设计方案](04-AI-Native开发全流程设计方案.md) 第四、第五篇。

重复率下降不必然意味着维护更容易；文档增加不必然意味着理解更深入；一次测试通过也不能证明风险已穷尽。评估应关注行为保持、变更成本、知识一致性、负责人解释能力和实际排障接管表现。

## 七、体系适用的限度

早期原型、普通业务增量与稳定公共框架需要不同强度的治理。允许短期重复不等于无限累积债务，强调认知也不等于要求每个人记住所有实现。

本体系不承诺自动找到最优抽象或消灭黑盒风险。抽象判断、认知复盘和反馈机制的价值需要真实研发验证，自动化应服务这些目标，而非以扫描次数、Agent 数量或审批数量衡量成熟度。
