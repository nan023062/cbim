# 本地 AI Native 团队开发全流程设计方案

> author：linan
> 版本：设计方案 1.3｜日期：2026-11-12
> 定位：单人或少数人使用的本地自动开发目标流程，不作为运行授权，不声明全部流程已经实现。

本方案与 [总纲](01-AI-Native设计思想总纲.md)、[CBIM 架构理论](02-CBIM架构设计理论.md)、[架构演进与认知保障](03-渐进式架构演进与人工认知保障体系.md) 共同构成概念设计。对象模型见 [本地 AI 团队核心模型](../design/team-workspace-network.md)，实现及缺口见 [源码审计](../design/verification/local-ai-workflow-audit-20261112.md)。此前 Unity 玩法组试点是设计背景，不再限定产品范围。

## 第一篇：方案范围与交付对象

用户给出目标、约束与授权范围，Agent 团队在本地工作区组织开发、验证和返工，交付可核实成果及复用知识。优先打通一个真实代码项目的完整闭环，再扩展业务类型和多个本地工作区。

当前不建设 Cindy 承载、跨设备联网协作、大型组织或分布式治理。执行引擎、模型和工具提供执行能力；团队责任、业务目标和交付裁决仍属于 CBIM。模型调用等既有功能可能使用网络，本方案不宣称完全离线可用。

交付包括具体变更、验证结果、遗留问题和必要的知识更新。完成回答、成功调用工具、生成文件或成员报告成功，均不能单独证明用户目标已经完成。

## 第二篇：系统组成与职责

| 对象 | 负责什么 | 关键边界 |
| --- | --- | --- |
| Agent 与 Skill | 专业能力、方法与工具使用 | 通用能力不包含具体项目事实 |
| 工作区与 Module | 项目架构、业务知识、物理来源与契约 | 逻辑模块与物理目录分别表达 |
| 岗位成员与负责人登记 | 在当前工作区承担的职责 | 与作者来源、一次运行身份分开 |
| Workflow | 可复用业务步骤、条件与出口 | 自然语言步骤不等于程序强制执行 |
| 目标、任务与执行记录 | 规划、协作、状态与证据 | 执行终态与目标验收分别裁决 |
| 引擎适配器 | 启动、取消、事件和工具协议 | 引擎结束只报告执行事实 |
| 知识服务 | 有版本的查询、预览与提交 | 核实经验后才更新正式知识 |

C 保存可复用能力，B 保存业务事实，M 可保存个人临时线索。核心流程不依赖个人私有记忆；正式执行与交付证据归持久运行记录。当前 `authors` 仅是作者来源字符串，不要求真人花名册或同组关系；派发使用工作区岗位与负责人登记。

## 第三篇：单任务全流程

1. **建立目标。** 明确成果、验收条件、预算和允许修改范围；只有影响目标或权限的缺失信息才需要人补充。
2. **定位上下文。** 从索引找到相关模块，再读取必要的契约、来源和能力，不为每次任务全量重读仓库。
3. **规划与委托。** 按职责建立任务和前置依赖，绑定岗位、模型、知识版本及工作范围。简单工作可由主 Agent 直接完成。
4. **执行与协调。** 成员报告真实进展、阻塞和产物；主调度依据可信结果继续分工或重规划。求助和派发回执均不等于完成。
5. **自动 review 与验证。** 按变更和消费者选取检查，结果绑定实际产物版本。需要独立 review 时建立明确任务，作者自述不能替代证据。
6. **有界返工。** 将失败原因及原候选身份交给修复任务，再核实新结果。限制轮次、成本和无进展重复，保留旧证据。
7. **交付与沉淀。** 核实验收条件、未决副作用及剩余任务；将有复用价值的方法和项目知识分别归入 C/B。

上述是目标闭环。现有代码具备计划、派发、成员结果自动回流和完成证据核验；通用代码验证、最终验收失败后的自动修复及无人值守恢复仍需补齐，不能把本文当成已经接通的状态机。

## 第四篇：架构观察、评审与重构流程

从真实变更原因、重复规则和边界问题判断是否值得抽象。已授权范围内的局部分析、实现和验证自动推进；需要新业务取舍、扩大权限或改变正式规则时才升级给人。

保护稳定能力，将易变策略限制在明确边界。优先使用既有依赖图、契约和增量 diff；只有职责或契约实际变化时才更新对应视图，不为每次 review 重建全仓说明。具体约束由 [架构规范](../design/project-architecture-standard.md) 和 [治理流程](../design/architecture-governance-process.md) 维护，本文不另建审批表或待办清单。

## 第五篇：质量检查、知识维护与负责人复盘

区分格式正确、执行成功、行为符合预期和业务目标满足。JSON/CSV/PNG 的结构校验不能替代编译、单元测试或业务验收；命令退出成功也不证明检查覆盖了需求。

交付说明改动、依据、真实检查和未验证部分。知识更新关联原变更及证据；冲突时重新查询和预览，不绕过知识事务直接写 `.cbim/`。

用户能随时看见目标、进展、阻塞、成本和介入理由。认知保障是帮助人理解和接管系统，不是要求每个模型回合签字。重复失败、未知副作用或授权不足时，停止依赖该结果的动作并提供恢复入口。

## 第六篇：资产组织与实施顺序

产品加载范围由 [内置知识白名单](../src/backend/core/knowledge/builtins.ts) 决定。`design/runtime/` 正文进入运行上下文，不能因普通 Markdown 引用少就删除。项目开发 Skill 与产品内置 Skill 分别维护。

布局和字段以 [模块规范](../design/business/module-spec.md)、[Agent 规范](../design/capability/agent-spec.md)、[Skill／Workflow 规范](../design/runtime/shared-skills-workflows.md) 为准；任务与恢复以 [任务契约](../src/backend/core/tasks/CONTRACT.md) 及真实存储为准，本文不复制 Schema 或猜测用户数据路径。

现行入口是桌面应用与内部 TypeScript 服务。旧 Python 工具、旧 `design/skills/` 方法副本和模块预览器已退出维护，原文可从 Git 历史查阅。

先围绕单工作区的验证、返工与可靠交付收敛，再扩展复杂的本地协作。具体开发选择来自 [GitHub Issues](https://github.com/nan023062/cbim/issues)，概念文档不保存实时进度。

## 第七篇：一个任务贯穿全流程

以“修复背包容量计算并补齐回归”为例：主 Agent 定位契约和实现，明确边界条件；开发成员修改逻辑，验证步骤检查正常、满容量和异常输入；失败用例、命令结果与源码版本回到修复任务；修复后运行受影响检查。若公共契约变化，再检查真实消费者。

主 Agent 汇总 review 与执行证据。剩余阻塞、过期证据或未知副作用未处理时不能关闭为完成。最终交付差异与验证结论，必要时更新业务知识。这是检验产品的目标场景，不代表已经存在默认背包团队或该场景已通过端到端验收。

## 第八篇：验收标准、待决事项与当前边界

| 判据 | 所需证据 |
| --- | --- |
| 自动完成正常任务 | 真实需求到变更及验证的完整记录，无逐步人工推动 |
| 自动修复失败 | 真实验证失败、定向返工、新候选通过，预算和轮次有界 |
| 处理依赖与并行 | 前置关系、产物版本、冲突处理和整合结果可核实 |
| 可靠恢复 | 中断前后身份及副作用一致，不重放未知写入或补造成功 |
| 可信交付 | 验收条件有对应证据，未运行检查明确标注 |
| 沉淀并复用 | 知识有来源，在后续真实任务中加载并产生可核实用途 |
| 成本可控 | 按需取上下文，复用确定性索引和检查，记录返工与 token 成本 |

端到端验收通过前分别报告已有机制和未接通环节。网络协作、云服务、大型组织和插件平台不作为本阶段完成条件。

## 附录：执行适配与维护约定

许可绑定工作区、运行及具体操作。知识、工具说明、组织身份和模型自述均不能扩大许可。既有 `read/ask/execute`、范围冻结、回执与恢复规则继续有效；本方案不绕过现有约束。

未知副作用先核实；已知可重复的只读检查和满足幂等条件的动作才有条件自动重试。取消与失败不抹掉已发生的写入。应在这些证据边界内增加自动化，不能靠放宽完成判断取得表面闭环。
