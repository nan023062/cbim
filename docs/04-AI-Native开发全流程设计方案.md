## 第一篇：方案范围与交付对象

### 1.1 适用范围

本方案适用于 Unity 游戏渐进式研发，首期在心动小镇客户端玩法组选择模块试点。任务发起者包括策划、程序、美术和 QA；使用者提交自然语言需求，系统完成模块定位、执行任务包生成及执行路由。

本报告解释职责、执行阶段、资产、审批、失败恢复和验收的设计。设计思想的关系见 [总纲](01-AI-Native设计思想总纲.md)，CBIM 与演进认知的完整理论分别由两个专项文档维护，本报告不展开理论论述。

### 1.2 方案覆盖

| 工作面 | 本报告规定的内容 |
|---|---|
| 任务执行 | 受理、模块定位、能力绑定、审批、实现、验证与交付 |
| 知识管理 | 共享知识的存储、更新、失配检查与负责人确认 |
| 架构变更 | 模式观察、评审、重构任务、回归及抽象登记 |
| 人工审查 | 技术 review、业务验收、关键实现复盘 |
| 运行保障 | 权限边界、中断恢复、实际版本与回执核实 |

### 1.3 交付对象与当前状态

实施目标包括可用的索引与 DNA、任务包、执行与校验流程、架构注册记录和共享结果证据。当前只完成方案文档，未部署工作流切换、权限隔离、自动扫描或自动执行器。

游戏代码、原有工作流及项目启动入口均不因本报告而改变。试点范围、负责人、运行环境与具体实现参数按第八篇确认。

## 第二篇：系统组成与职责

### 2.1 资产归属与存储要求

| 组成 | 保存什么 | 不承担什么 |
|---|---|---|
| C：能力（共享长期知识） | 专业方法、Agent Skill、输入输出约定、工具边界、能力版本 | 不硬编码本项目业务路径和决策 |
| B：业务（共享长期知识） | 模块树、DNA、依赖图谱、业务 Workflow、观察中模式、正式抽象及项目架构决策 | 不承担通用能力正文的复制维护；观察状态不等于正式契约 |
| M：个人短期记忆（可选） | 本地临时线索、未整理的调查笔记和短期失败尝试 | 不共享、不进入团队版本管理，不承担正式知识、审批或团队任务状态 |

C、B 纳入团队版本管理。审批、验收、交付回执和能力效果证据保存在共享任务记录中，不归入个人 M，也不因其产生于单次任务而可随意丢弃。没有个人 M 的新成员仍应能依据共享资产接手工作。

模块 DNA 必须包含定位、契约、雷区，并关联负责人和核验依据。契约不仅包括方法签名，还包括适用条件、数据所有权、失败行为、生命周期和兼容性约定。

#### 2.1.1 模块类型与能力派发

`workspace/` 承载全部专业的 B，不只登记代码模块。module.json 保存摘要、authors、sources、直属 children 及知识与流程引用，不保存核验状态字段；核验过程与结果保存在任务记录中。DNA 描述定位、契约和注意事项。模块按逻辑父子关系组织，sources 只索引物理目录；文件通过所在目录及 scope 定位，不直接登记文件级 source，也不复制原始资产到知识目录。

| B 模块示例 | 输入与产物 | 调用的 C 能力示例 | 适用验证 |
|---|---|---|---|
| 玩法代码 | 源码、接口、配置 | 代码分析、实现、调试 | 编译、行为测试、运行与性能检查 |
| 玩法 QA | 需求、测试用例、数据、测试脚本 | 用例设计、覆盖分析、测试执行 | 需求覆盖、预期结果、环境及执行证据 |
| 界面美术 | 图片、模型、材质、Prefab、源工程 | 资源处理、格式转换、视觉检查 | 格式尺寸、引用、导入效果及专业验收 |
| 玩法策划 | 规则文档、数值表、配置、文案 | 规则分析、数值检查、表格处理 | 规则一致性、数据约束及玩家效果 |

表中仅为路由示例，不代表已安装全部能力。Lead 根据任务目标、产物格式、所需操作、工具可用性与权限选择 Agent Skill 和执行者。能力或工具不足时明确缺口并交专业负责人处理，不默认用代码生成替代所有文件操作。

一个自然语言需求可以拆为跨专业子任务，明确产物交接与依赖，分别派给合适能力 Agent。仅派发各子任务必要的知识和资料；不按发起者职位决定全部路由，不把每项任务都变成程序开发任务。

### 2.2 执行分层与横向治理

| 层 | 职责 | 输入 | 输出 |
|---|---|---|---|
| L0 结构层 | 维护可定位、可核实的共享 C/B 资产 | 当前代码、测试材料、资源、配置、人工决策与共享任务证据 | 索引、DNA、图谱、能力定义、注册记录 |
| L1 调度层 | 理解需求，定位模块，组合能力与流程 | 自然语言需求、相关结构资产 | 有版本和边界的执行任务包 |
| L2 执行层 | 在授权范围内实现和验证 | 子任务、必要知识、指定能力 | 实际产物、执行记录、验证证据 |
| L3 校验层 | 核对越界、契约、行为和业务效果 | 实际差异、测试、审批版本 | 审核结论、验收结果、修正要求 |
| 横向治理 | 维护知识、决定架构演化、落实认知复盘 | 各层结果与变化信号 | 已批准的知识、抽象、流程与能力改进 |

CBIM 由内部大脑与调度引擎承载执行，Lead/Worker 表达任务中的协调和执行职责，不对应不同的运行内核。权限、状态迁移与契约检查是否已接通，应逐项核实实际实现；工具存在不等于隔离和门禁已经有效。

### 2.3 Agent Skill 与业务 Workflow

team/ 保存 C 的 Agent 定义、Skill 与真人花名册；workspace/ 保存 B 的 Module 定义、DNA 与 Workflow。Agent 加入具体工作区后形成有岗位适配的长期成员；模块通过工作区责任登记标记负责人成员，主 Agent 按模块索引派发，再按需将 Workflow 步骤匹配到适用 Skill。责任登记不反向耦合通用能力定义，静态模块注册表也不重复保存另一份负责人。core 是共享规则，不是独立运行的调度服务。节点对偶见 [CBIM 设计理论](02-CBIM架构设计理论.md)，待实施协议见[模块负责人索引](module-owner-index.md)。

| 维度 | Agent Skill | 业务 Workflow |
|---|---|---|
| 挂载 | 能力节点 C | 业务节点 B |
| 问题 | 如何完成这类专业操作？ | 这个模块的操作应按什么步骤推进？ |
| 驱动 | 提示词、推理方法与工具调用 | 明确的步骤、条件、分支、审批、出口与恢复 |
| 维护 | 能力负责人 | 模块负责人 |
| 复用 | 跨项目复用，运行时绑定上下文 | 业务绑定需重新核实，通用流程骨架可复用 |

Workflow 可在某一步调用 Skill，也可执行纯工具操作。Skill 可以单独用于简单任务，但不绕过任务的授权与验证要求。Markdown 写有步骤不等于硬流程；只有执行器和校验器落实状态与出口，才能称为机器强制。

### 2.4 职责角色：Feature 对业务人员，Refactor 对架构师

Feature / Refactor 表示 CBIM AI 助理在本次任务中组织的业务交付或架构评估职责，不是由循环固定绑定的 Agent 类型。CBIM AI 助理负责选择流程、拆分与协调；每个执行任务绑定一个 Agent 与一个或多个由该 Agent 维护的模块，执行者在已确定的工作区内完成分配的分析、实现或验证工作。任务内跨模块结论由AI 成员 提供，跨任务结论由 CBIM AI 助理汇总。

Feature Agent 与 Refactor Agent 按职责层级划分，均适用于程序、QA、美术、策划模块。专业能力通过 C 组合，具体工作对象通过 B 定位；不要求两个固定常驻进程，也不建立两套重复能力库。

| 角色 | 对应职责 | 负责事项 | 权限边界 |
|---|---|---|---|
| Feature Agent | 业务人员 | 在既有规则内完成具体需求，检索并使用适用契约或规范，产出、验证并提供问题线索 | 不借局部任务静默修改公共规范、共享契约或模块边界 |
| Refactor Agent | 架构师 | 跨任务、跨模块观察共性与结构问题，提出抽象、规范统一、职责拆分与演进方案；获批后推进实施和验证 | 不自行批准正式架构变更，不自动合并或发布架构级变更 |

| 专业场景 | Feature 职责示例 | Refactor 职责示例 |
|---|---|---|
| 程序 | 完成一个玩法逻辑 | 收敛多个玩法的公共机制 |
| QA | 补充某玩法测试用例 | 整理跨玩法覆盖模型、测试数据和测试规范 |
| 美术 | 制作或调整界面资源 | 统一资源组织、交付约定与复用规范 |
| 策划 | 编写玩法规则、调整数值配置 | 整理共用配置模型、规则边界与交接标准 |

Lead 先判断任务属于具体业务交付还是结构演进，再根据产物类型、工具与权限绑定专业能力。Feature 发现结构问题时提供线索，由 Refactor 分析并形成建议；是否修改共享结构由对应人类负责人批准。两类职责的产出都要接受适用的独立审查和验证。

### 2.5 人类责任

| 角色 | 最终负责的事项 |
|---|---|
| Requester 发起者 | 原始目标、业务取舍、业务效果验收 |
| Module Owner 模块负责人 | 对应专业的 DNA、模块契约、执行方案与产出质量；可由程序、QA、美术或策划负责人担任 |
| Architect 架构守护者 | 全局依赖边界、稳定层、架构收敛与正式抽象决策 |
| Capability Owner 能力负责人 | Skill 方法、权限边界、版本和效果评估 |
| Reviewer 校验者 | 技术或业务验证；按上述职责分工，不以 AI 自评替代 |
| Governor 治理者 | 复盘、知识失配跟踪、决策落实与跨模块协调 |

同一人可以兼任角色，但任务中必须明确每项责任由谁承担。审批绑定具体方案版本和范围，不能用笼统“同意继续”覆盖后续所有变化。

本节涉及的真人 Owner、Reviewer 与审批责任，不能和 AI 模块负责人混为一谈。authors 记录真人作者，maintenance 记录显式真人维护声明；工作区另以 ModuleOwnership 持久记录模块的 AI 主责成员，模块领域视图显示 ownerMemberId。该关系不在 module.json 重复保存，按[负责人索引设计](module-owner-index.md)派生展示并用于调度。作者只提供追溯及岗位配置线索，不自动取得执行或审批权；多位作者仍须引用花名册中同组人员。负责人索引是新设计，实施状态以路线图为准。

## 第三篇：单任务全流程

### 3.1 发起者输入

统一模板只有四项业务信息，可由自然语言自动整理：

```markdown
## 想做什么
目标或遇到的问题。
## 发生在哪里
玩法、界面、操作步骤，以及可提供的截图或资料。
## 期望结果
怎样判断效果正确。
## 不希望改变什么
已知业务限制；不清楚可以留空。
```

CBIM 保留原始表述，区分明确要求、已确认约定、技术假设和待确认问题。缺少业务信息时询问操作和期望，不要求发起者选择模块或填写产物路径。

### 3.2 精准定位与上下文加载

定位链为：**自然语言 → 精简业务索引 → 候选模块 → DNA/契约核实 → 必要原始产物 → 执行范围。**

索引包含模块 ID、专业类型、职责简述、玩法与界面名称、操作和别称、产物类型、DNA 与原始产物位置。业务概念和模块允许多对多对应。

| 步骤 | 读取范围 | 判断依据 |
|---|---|---|
| 关键词与语义检索 | 精简索引 | 找到候选，不认定根因 |
| 模块核实 | 候选的职责与相关契约 | 区分现象位置、依赖位置、修改位置 |
| 抽象匹配 | 相关正式抽象索引及适用条件 | 是否能正确复用，而非名称相似就套用 |
| 必要调查 | 限定源码、测试材料、资源或配置及关联观察记录 | 补足具体行为与影响证据 |

不加载全库 DNA、全部 Skill 或整棵依赖树。每次扩大读取范围说明原因和路径。索引失效或知识冲突时标为待核实，不沿用旧结论；无法定位时请负责人协助，不自动全项目扫描。

治理扫描是独立任务，按登记范围分批进行，不把全库扫描结果塞入日常任务上下文。RAG 是可选检索实现，Roslyn 仅用于适用的 C# 代码分析；表格、图片、模型和测试材料采用相应读取与校验工具。工具选择不能绕过索引与读取边界。

### 3.3 任务包由 CBIM 生成

执行前至少明确以下内容，完整模板见本节下方：

| 类别 | 必须表达 |
|---|---|
| 需求 | 原始需求、子目标、业务验收条件 |
| 定位 | 目标模块、必要依赖、证据、知识与原始产物基线 |
| 能力 | 能力与 Skill 版本，适用 Workflow 及步骤映射 |
| 边界 | 允许读取、允许修改、禁止修改、稳定层影响 |
| 契约 | 应复用的正式抽象、跨模块使用约定、禁止绕过的内部边界 |
| 执行 | 子任务依赖、产物、测试与回归计划 |
| 审批 | 模块负责人、必要的架构审批、获批版本 |
| 收尾 | 实际差异、验证证据、风险、知识变化与验收结果 |

一个任务可涉及多个模块，读取范围与修改范围分别声明。审批前可以只读调查；涉及权限、稳定层或关键契约的未知项不视为“不涉及”。

验证和审批随产物选择：QA 用例任务不要求无关编译，美术资源任务需要资源及效果验收，策划表格任务检查数据约束与业务结果。非代码任务涉及共享契约或稳定层时，仍按实际影响升级审批。

### 3.4 阶段、执行者与出口

| 阶段 | 执行者 | 产出 | 进入下一阶段的条件 |
|---|---|---|---|
| 受理 | 发起者 + Lead | 原始需求与验收目标 | 目标足以定位，缺失信息已明确 |
| 定位 | Lead + 分析能力 | 模块、依赖和事实依据 | 修改位置与关键影响已核实 |
| 方案 | Feature（业务任务）或 Refactor（结构演进任务） | 执行任务包与复用或演进方案 | 范围、契约、验证方式明确 |
| 审批 | Owner；必要时 Architect | 对具体版本的批准 | 获得适用授权 |
| 实现 | 对应职责 Agent 组合所需专业能力 | 代码、测试材料、美术资源、策划资料等产物与差异 | 未越界，产物可验证 |
| 验证 | 对应专业的校验工具与验证角色 | 适用的编译、测试、资源、规则或效果验证证据 | 适用检查通过，缺口明确处置 |
| 审查 | 模块负责人 | 技术、风险与知识审查结论 | 问题关闭，关键认知要求满足 |
| 业务验收 | 发起者及相关 QA | 可观察效果确认 | 满足原始验收目标 |
| 交付 | 获授权的交付执行者 | 版本回执与可追溯结果 | 提交与发布分别核实，不混称完成 |
| 沉淀 | 系统记录 + 负责人确认 | 结果、知识变更和观察记录 | 记录可用于后续任务，无未说明的同步缺口 |

### 3.5 稳定层与跨模块依赖分支

**使用稳定层已有契约，不等于需要修改稳定层。** 按以下分支处理：

- 现有契约满足需求：业务任务直接使用，保留相应验证。
- 契约不足或实现必须改变：生成独立跨模块需求单（A2A），明确目标、缺口、证据和依赖方。
- 对应 Owner 审查方案；涉及稳定层时追加 Architect 批准。
- 获授权的执行通道完成前置变更并验证，原任务核实新基线后继续。
- 前置任务未完成时，仅暂停依赖它的子任务；不擅自绕过契约，也不扩大无关任务范围。

风险按实际影响判定。技能、Buff、UI 等业务名称不自动意味着低风险；若涉及存档、同步、热更或高频性能路径，应纳入相应评估。

### 3.6 失败、中断与恢复

| 情况 | 处理 |
|---|---|
| 定位不确定或 DNA 失配 | 限定调查并请负责人核实，不开始猜测性修改 |
| 审批退回 | 修订任务包，保留决策理由和版本 |
| 测试失败 | 在原授权范围内修复；范围变化重新审批 |
| 环境无法验证 | 记录阻塞与未覆盖项，按约定安排替代验证，不能记为通过 |
| Worker 发现越界需求 | 暂停相关修改，回到边界与审批环节 |
| 执行中断 | 保存实际产物、当前步骤及外部操作回执，恢复时重新核实 |
| 代码或契约基线发生变化 | 判断受影响证据与批准是否仍有效，只重做失效部分 |
| 用户取消 | 停止后续动作，记录已发生的副作用与待处理事项 |

不因网络超时或回执缺失盲目重复提交、通知或发布。恢复从实际文件、版本和外部回执确认状态，而非仅依赖聊天记录。

## 第四篇：架构观察、评审与重构流程

### 4.1 架构知识的记录与定位

架构观察与正式抽象状态按需记录在相关模块 DNA 中。当前模块注册表只保存 id 与 summary，不承担观察状态或评审结论，也不另设架构注册表。以下是知识分类，不要求创建固定目录。

| 区域 | 归属 | 记录内容 | 权威边界 |
|---|---|---|---|
| `observed_patterns` 观察中模式 | B | 同源候选、证据、变化维度、决策历史 | 共享长期知识，尚未要求所有业务复用 |
| `established_abstractions` 正式抽象索引 | B | 已批准抽象的定位、适用范围、DNA/契约引用 | 不复制完整契约正文 |

不是所有类和接口都需要登记。优先记录具有明确复用价值、使用边界和维护责任的抽象。以源码作为签名事实来源，以 DNA 保存语义契约和状态，以模块注册表提供定位入口。

`observed_patterns` 由当前方案发起者（作者（author，linan）本人）单人维护，团队读取并通过版本记录追溯，其他成员不直接修改；AI 可辅助提出候选并按作者（author，linan）指令更新。作者（author，linan）维护观察记录不替代模块负责人或架构守护者对正式变更的批准。个人刚发现、尚未整理的线索可以留在 M，进入持续观察后才由作者（author，linan）整理为 B 的记录。

### 4.2 观察记录与状态

每条观察记录包含：ID、业务语义、实现位置及基线、共同逻辑、变化维度、相似与不同的证据、关联任务、负责人、状态、决策理由和复查触发条件。

| 状态 | 含义 | 后续动作 |
|---|---|---|
| `observing` | 已发现候选，证据或稳定性不足 | 继续收集真实需求与实现变化 |
| `pending_review` | 达到评审触发条件 | 人工判断复用收益、变化方向和迁移成本 |
| `hold` | 暂不适合抽象 | 记录理由及复查条件，避免每次重复提案 |
| `reject` | 当前证据显示不是合适的同源抽象 | 保存适用基线与理由；关键证据变化后可以重开 |

批准重构后关联独立重构任务。只有实现、回归和人工审查完成，才登记为正式抽象，并保留观察记录的演进关系。

### 4.3 检测范围与评审输入

优先查询目标模块的相关抽象与观察记录，必要时用 Roslyn 语法、语义分析辅助检查 C# 实现。AST 相似度、调用关系和重复次数是证据，不能单独证明业务同源或值得抽象。

评审触发可以结合重复实现、重复缺陷、变更同步成本和职责过载。具体阈值由试点建立；达到阈值只进入评审，不自动重构。

评审必须回答：共同的不变量是什么？变化点是否稳定？强行统一会不会增加条件分支和耦合？现有抽象能否扩展？迁移、回归和维护成本是否值得？继续重复是否仍是合理选择？

### 4.4 重构流程

```text
观察记录与业务问题线索
  → Refactor Agent 分析结构与候选方案
  → Owner 与 Architect 评估证据
      ├─ 证据不足：继续观察
      ├─ 时机不合适：暂缓并注明复查条件
      ├─ 非同源或收益不足：驳回并保留理由
      └─ 批准方案：建立独立重构任务
           → Refactor Agent 组合相应专业能力推进实施
           → 行为等价与性能等适用回归
           → 人工终审
           → 授权交付与正式抽象登记
           → 负责人复盘、调用方按计划迁移
```

方案应列出不变量、扩展点、候选替代方案、影响范围、迁移顺序、行为基线、验证计划和回退方式。纯重构不能夹带未批准的业务行为变化；确需行为调整时单列需求和验收。

在本项目中使用独立 P4 CL/shelf 和适用 review 流程隔离重构；若资产位于 Git，则使用相应分支/MR。方案不强行将游戏代码迁到 Git。AI 不自动合并或发布架构级变更。

### 4.5 正式抽象的使用与退出

正式抽象索引包含：ID、意图、适用范围、非适用情形、负责人、契约/DNA 引用、实现与使用方位置、版本和风险引用。

Feature Agent 开始生成前检索适用抽象。适用则优先复用；不适用则写明事实依据，可以提出扩展或保留独立实现，不能为满足复用率强行套用。

正式抽象也可能过时。废弃或替换需识别使用方、给出迁移方案、完成回归并更新索引；不得仅因新方案存在就删除旧契约和实现。

## 第五篇：质量检查、知识维护与负责人复盘

### 5.1 交付材料要求

每次开发交付应包含三个维度，而非强制生成三个独立文件：

| 维度 | 最小内容 | 保存方式 |
|---|---|---|
| 可验证产物 | 实际代码、配置、资源或测试，以及验证证据 | 工程与任务结果关联 |
| 设计意图 | 为什么这样改、职责与数据流如何变化、为何复用或保持独立 | 小任务写结果段落；重大设计形成独立说明并引用 DNA |
| RiskCard 风险说明 | 已知失败模式、触发条件、影响范围、排查入口、恢复方法及未知项 | 任务风险变化记录；长期知识回归 DNA 雷区 |

分析任务不强制产生代码。小改动可以注明未引入新的架构或风险变化及依据，不制造空洞材料。风险卡不能穷尽风险，也不能替代关键代码 review。

### 5.2 周期与增量检查安排

| 机制 | 触发 | 执行者 | 产出与关闭条件 |
|---|---|---|---|
| 知识一致性审查 | 任务交付前及提交后增量检查；按计划分批复查 | Agent 调查、Owner 确认、Governor 跟踪 | 失配清单；修正、证明仍有效或明确隔离后关闭 |
| 稳定层维护 | 涉及稳定层的变更；周期 review | Owner + Architect | 影响分析、前置批准、验证与回执；未审变更不得当作合法完成 |
| 任务包驱动开发 | 每次任务 | 发起者、Lead、Worker、Owner | 受控产物与结果；验收、适用知识更新和证据齐备 |
| 业务架构演化 | 观察信号、较大改动后、周期体检 | Agent 提议，Owner/Architect 决策 | 观察、暂缓、驳回或重构任务；每项有明确责任与去向 |

首期只在试点范围执行，周期扫描逐步扩展。全量体检不等于一次读取全项目。

### 5.3 知识一致性与健康状态

增量检查覆盖变更模块、直接调用它的模块，以及它直接调用的模块；发现连锁影响再沿证据扩展。检查职责、语义契约、实际依赖、雷区和定位路径。命名空间引用或旧代码消失只提供线索，不自动证明依赖或约束消失。

| 状态 | 判断 | 行动 |
|---|---|---|
| 已核实一致 | 在声明基线和检查范围内匹配 | 保留证据，并非永远正确 |
| 局部失配 | 描述或索引遗漏，未发现破坏性影响 | Owner 修正相关知识 |
| 重要失配 | 契约、数据所有权或调用方受到影响 | 停止依赖错误知识的执行，Owner 与 Architect 评估 |
| 严重结构风险 | 已核实违反关键依赖规则或职责边界 | 进入架构评审；是否重构由人决定 |
| 未知 | 缺少证据或未完成检查 | 不伪装成绿色或自动升级为严重问题 |

知识过时与代码腐化分开处理：修正文档不必然需要改代码，发现重复也不必然需要抽象。

### 5.4 稳定层保护

红线模块在本方案中指被明确登记为稳定层保护对象的模块；多处复用、影响广、契约关键或历史风险高是判定依据，最终清单由 Architect 确认。

每个保护对象必须有 Owner。Owner 审查技术变更，Architect 批准稳定层影响；同一人兼任时仍记录两项判断。无论谁发起，都不以身份绕过前置审批。紧急通道需单独明确授权、回退和补审规则，未定义前不默认开放先提交后审核。

普通 Worker 默认不能写稳定层。读取可以按任务授权开放。权限由真实身份与工具通道落实，文件只读属性和提示词不足以证明不可绕过。代码能否调用内部实现需要契约和依赖校验，不能靠写权限解决。

### 5.5 验证与可观测性

验证按影响选择：单元测试、契约测试、集成测试、Unity Editor 或游戏运行验证，以及性能、资源、生命周期、存档兼容、跨端一致性等适用检查。新增行为补充有意义的测试；存量测试缺口要记录和处置，不以“不存在测试”等同于“无需验证”。

重构需先建立行为基线，再核对功能与适用性能表现；测试通过是证据之一，不是行为等价的绝对证明。

优先使用项目现有日志与诊断设施。跨请求链路需要时关联追踪 ID，高频帧逻辑避免无条件加日志。关键故障应能关联任务、变更版本和风险说明；溯源优先保存在版本及任务记录中，不默认向每个源码文件添加 AI 标记。

### 5.6 负责人审查与交付后复盘

新正式抽象或高影响变更在审查中必须覆盖：核心数据流、关键不变量、典型失败路径、回退与排查入口。不能把关键理解全部推迟到上线后。

在交付后安排一次负责人深度复盘：阅读核心实现、推演代表性故障、核对风险说明、补充人工经验。建议以一周内完成作为试点目标，实际排期需负责人确认。

复盘结果应让负责人能够说明“输入从哪里来、状态归谁、失败会影响谁、出了问题先查哪里”。不能仅用“已读”或一张审批记录证明理解。

### 5.7 共享知识治理与可选个人 M

团队治理使用共享 C、B 和工程记录：检查过期知识、重复模式、错误映射和反复失败，由 AI 提炼候选、相应负责人确认后更新能力、DNA 或 Workflow，并保留来源与决策。观察中模式由作者（author，linan）本人维护，不能自动转为团队共同编辑。

个人 M 仅用于辅助当前工作：按需写入和检索本地线索、调查笔记及短期尝试；任务结束或依据变化后，由本人整理、标记失效或删除。不建立团队共享 M，也不提交到团队版本库；本地存储目录为 `<用户主目录>/.cbim/<项目标识>/memory/`，生成时机、格式、按需读取与失效处理遵循 [个人短期记忆规则](../design/memory/memory-spec.md)；宿主规定专用存储渠道时使用宿主渠道。

从 M 提炼出的通用方法经审核进入 C，持续业务观察或规则经审核进入 B。个人记忆不自动成为正式知识；审批与验证证据必须直接进入共享任务记录，不能仅留在本地。M 不可用时，核心流程仍须可执行、可恢复。

本阶段不部署 Dream、后台自动架构变更或常驻治理任务。能力匹配调整使用共享且可追溯的任务证据；个人 M 不作为执行前置条件。

## 第六篇：资产组织与实施顺序

### 6.1 目录与权威来源

core 保存通用设计、Schema、CBIM AI 助理的任务流程与维护脚本；team 保存专业 AI 成员 及真人花名册；workspace 按逻辑模块树保存业务知识。物理产物保持原位置，通过模块 sources 索引，不镜像源文件夹结构。

```text
项目根/
├── Client/、Server/、Tools/、RawAssets/ 等物理工作区
├── proj-workflow/           独立保留的旧资产
├── <用户主目录>/.cbim/<项目标识>/             本地工作数据，根忽略规则统一排除
│   ├── memory/            可选个人短期线索
│   └── task-records/      本地任务记录与恢复证据
└── .cbim/
    ├── design/
    │   ├── README.md       总体设计
    │   ├── docs/          设计理论与方案
    │   ├── capability/    Agent 规范与 Schema
    │   ├── business/      Module 规范与 Schema
    │   └── scripts/       注册表维护与校验
    ├── team/
    │   ├── registry.json  groups → agents 两级索引
    │   ├── people.json    真人 id、name、team
    │   └── <组>/<Agent>/
    │       ├── agent.json
    │       ├── principles.md
    │       └── skills/    按需建立
    └── workspace/
    │   ├── registry.json  模块 id、summary
    │   └── <一级模块>/<逻辑子模块>/
    │       ├── module.json
    │       ├── module.md 完整模块知识
    │       └── workflows/<工作流名>/workflow.md 独立操作流程，按需建立
```

一级模块为 client、server、devops、art-assets、design、qa；一级节点本身也有 module.json 和 module.md。现有模块已按此布局整理；知识与操作步骤分别保留唯一正文。同一模块可索引多个物理源，同一物理源只保留一个维护模块，其他模块通过引用使用；Client_debug 与 clinet-debug 镜像不参与。

agent.json 与 module.json 是能力与业务静态定义的唯一来源，Markdown 保存原则、知识和流程正文。对象目录路径即 id，统一相对项目根解析。Module 在 module.json 显式维护 id 与直属 children，并校验它们与实际目录一致；overview 不重复索引字段，workflow 不重复知识正文。Agent 索引按组组织，Agent 和模块静态索引条目均只含 id、summary，不重复保存源路径、作者或完整契约。项目成员与负责人关系另由工作区登记保存，模块页面关联展示，不混入可复用定义包。

目标执行路径是先按摘要定位模块，读取 sources 确认物理工作范围，再按负责人索引查询工作区成员并解析其能力、模型、Skill 与岗位适配。未分配或关系失效时明确补齐分工，不临时绕过负责人。authors 与 people.json 的组归属可以辅助首次配置和调整岗位；跨专业工作通过明确协作或拆分任务组织。作者不等于自动获授权的执行者或审批人。此路径须随负责人索引协议实施接通，不把本文示例当作当前接口。

注册表脚本同步索引并校验 Schema、引用、摘要、作者人员引用与同组约束；不自动证明业务知识或运行效果。新增、移动和修改定义后按维护说明执行 --write 和 --check。

`<用户主目录>/.cbim/<项目标识>/` 与 `.cbim/` 同级，由根 `.gitignore` 和 `.p4ignore` 统一排除常规版本管理收集。其 `memory/` 保存可选个人短期线索，`task-records/` 保存关联产物版本的本地任务进度、快照、审批与验证证据；后续临时目录也放在此处。它们不默认共享，跨设备恢复或人员接管须显式传递必要记录；清理前保留在途任务所需证据。

| 信息 | 唯一正文来源 | 其他资产如何使用 |
|---|---|---|
| 对象字段及引用 | agent.json / module.json | 注册表同步摘要与定位信息 |
| 真人身份及组归属 | team/people.json | authors 引用人员 id |
| 模块定位、契约与注意事项 | 模块 DNA | 任务按需读取 |
| 观察模式、正式抽象与架构决策 | 相关模块 DNA | 引用证据和决策，不另建重复注册表 |
| 某次修改与验证 | 任务结果及版本回执 | 交接和恢复时核实 |
| 可复用专业方法 | Agent 的 Skill | 按任务需要读取与执行 |
| 临时调查线索 | 可选本地 M | 核实后才进入共享知识 |


### 6.2 切换与旧资产处理

应用打开工作区后加载知识服务，由调度引擎准备当前 Agent 的指引、能力和模块上下文。项目旧资产独立保留，不默认同时加载两套流程；已有任务切换时交接产物、状态与授权，恢复前重新核实版本与已发生操作。

旧知识已发现质量问题，不批量复制为可信 DNA。对试点模块重新核对当前源码、契约和负责人意见，再选择性吸收。旧工作流的停用与删除需核对团队使用者、入口引用和恢复需要；试点不用不等于全项目可删。

版本管理适配既有 P4/Git 边界。代码和知识分属不同系统时记录对应版本，并分别核实提交结果；部分成功要保留恢复状态，不能笼统报告全部同步成功。

### 6.3 分阶段落地

| 阶段 | 建设内容 | 阶段出口 |
|---|---|---|
| 基线准备 | 选择试点模块、Owner、稳定层对象；核实 DNA 与索引 | 能从自然语言正确定位，关键边界明确 |
| 最小交付闭环 | 人工确认任务包，限定执行，验证与业务验收，保存证据 | 完成 2—3 个真实业务任务并复盘 |
| 演化与认知闭环 | 观察记录、正式抽象索引、风险说明、一次架构评审或有依据的暂缓 | 决策可追溯，负责人能解释关键设计 |
| 执行机制固化 | 工具入口接入、按需加载、状态核实、权限与恢复验证 | 恢复和失败场景可验证，无静默越界 |
| 逐步推广 | 增量一致性、分批体检、效果反馈与治理自动化 | 指标改善且人工维护成本可接受 |

原先“半个月、1—2 月、3—6 月”的时间框架可作规划参考，不作为已承诺排期。每阶段以证据达标决定推进，不为赶时间绕过隔离和验证。

## 第七篇：一个任务贯穿全流程

以下为说明流程的假设案例，不代表已核实的项目模块或现有缺陷。

**输入：**“背包满时钓到鱼，希望看到明确提示；不要改变原有奖励结算。”

1. **定位。** Lead 用“钓鱼、容量、奖励提示”等线索检索，核实逻辑、UI 和奖励契约。它不因出现“背包”就认定背包模块有 bug。
2. **复用。** 检索已有提示抽象及使用条件。若有适用机制，直接复用；若没有，允许在已批准范围内做局部实现。
3. **任务包。** 列出应修改与只读依赖范围，固定“不得改变奖励结算”的验收约束，Owner 确认方案。
4. **稳定层分支。** 如果只调用奖励接口，不新建稳定层任务；如果必须改变结算契约，建立前置需求单并追加架构审批。
5. **实现与验证。** 核对容量足够、容量不足、重复操作和依赖失败等适用场景；验证提示及结算行为，而非只确认编译通过。
6. **产物。** 保存实际变更、提示数据流说明、失败风险和排查入口。发起者确认玩家看到的效果。
7. **观察。** 如果后续采集、制造也出现同源提示逻辑，记录一个候选模式；出现第三处不自动抽基类。
8. **架构决策。** Refactor Agent 分析共同语义、差异和收敛方案，Owner 与 Architect 按职责评审；不适合收敛时保留独立实现并记录原因。
9. **独立重构。** 获批后 Refactor Agent 迁移，验证所有使用方行为，人工终审后登记正式抽象。
10. **认知与反馈。** 负责人确认失败路径与扩展边界；下一次开发通过精简索引找到该抽象，无需重读全部历史。

原任务交付后，后续观察与重构使用各自记录和任务包推进，不延长原任务的完成状态。

## 第八篇：验收标准、待决事项与当前边界

### 8.1 如何证明闭环有效

| 维度 | 观察指标 | 验收重点 |
|---|---|---|
| 定位效率 | 定位耗时、误定位、重复搜索、无关读取 | 自然语言能到达正确范围，精简不漏关键约束 |
| 交付质量 | 验收通过、返工、回归缺陷、验证缺口 | 功能完成可被独立证据证明 |
| 边界控制 | 越界尝试与实际越界、审批范围失配 | 未批准写入被阻止，范围变化不能静默推进 |
| 知识健康 | DNA 失配数、处置时间、无依据规则 | 过时知识不会继续作为可信输入 |
| 架构演化 | 重复问题复发、观察去向、迁移和维护成本 | 不以抽象数量或代码去重率代替架构质量 |
| 人工认知 | 关键设计解释、排障演练、review 时间 | 负责人具备理解和接管能力 |
| 恢复能力 | 中断恢复、重复副作用、版本可追溯性 | 恢复基于真实状态，不误报交付完成 |

先记录试点基线，再确定目标值；目前不虚构效率提升比例或合格阈值。指标需区分业务复杂度、实际影响与样本量。

### 8.2 实施前需要确认

- 首个试点模块及 Owner，初始稳定层清单和精确路径。
- 当前内部执行引擎可落实的工具、文件权限和隔离机制。
- 任务记录的保存位置、产物版本与恢复依据；仅在需要确定性自动化时另行设计机器执行格式。
- 观察记录的评审触发条件、复盘周期和负责人排期。
- 适用测试环境、存量缺口及缺口处理方式。
- P4/Git 中各类资产的归属与跨系统回执关联方式。

这些属于实施决策，不转嫁给自然语言任务发起者。

### 8.3 当前交付与完成定义

当前应用通过内部知识服务管理 Agent/Module、注册表、真人花名册、有效 Skill 和 Workflow。主 Agent 负责受控知识治理及任务调度；业务工作由独立执行实例完成。空初始化不预设领域模块或自定义角色，应用提供静态默认执行角色，实际配置以知识查询为准。

主 Agent 是具备工程思维、架构思维和结构化思维的团队与技术管理者：核实现状、目标和约束，维护模块职责、依赖和责任，将任务组织为执行者、模块列表、目标与验收要求，审阅证据并安排后续工作。它直接通过受控知识服务增删改查 `.cbim/`、治理团队和业务架构，按证据渐进演进；业务文件实现、命令和业务验证交给执行 Agent。知识写入仍受 read/ask/execute、版本与事务控制，重要人工决定不由模型伪造。执行者自主探索目标模块、实现并返回证据，不递归派工。默认执行角色补足空团队；周期结束释放执行实例，保留主实例与历史。可恢复求助、正式业务验收及完整治理状态闭环尚未接通，不能以 Schema 通过替代业务验证。

单任务完成时核对以下交付条件：

- 原始需求、获批任务包与实际修改相对应。
- 适用验证和业务验收已完成，未覆盖项有明确处置。
- 相关知识变化已更新或记录待处理状态及影响。
- 审批、版本回执和结果证据可供其他成员接手。
- 需要负责人复盘的任务已记录结论或明确后续安排。

团队是否扩大试点，依据本篇指标和阶段出口决定；方案文档完成不等于运行系统验收通过。

## 附录：执行适配与维护约定

### A. 工作流启动

在 CBIM 设置中配置模型，打开工作区后从主 Agent 对话提出目标。主 Agent 管理团队和业务知识并组织执行任务；内部知识变更经过当前权限、版本和事务，业务实现由执行者完成。缺失能力先核对工具清单，记录缺口并继续可用步骤，知识服务不可用时不裸写正式知识。

### B. Worker 上下文与执行权限

只派发当前子目标所需的知识、契约与原始产物范围，不继承全部调查日志。公共约束在对应执行上下文中加载一次，依赖按证据展开。记录额外读取的原因和路径。

审批稳定层变更不自动赋予普通 Worker 全局写权限；由获授权的执行通道处理。读取与修改分别授权，任务包、Skill 与 Workflow 不能互相扩大权限。

### C. Workflow 与 Skill 的维护

| 对象 | 维护者 | 审核内容 |
|---|---|---|
| Agent Skill | 能力负责人 | 架构守护者核对能力边界，能力负责人验证方法与输出 |
| 业务 Workflow | 模块负责人 | 架构守护者核对流程合理性，模块负责人确认业务契约 |

变更说明使用方和影响范围，并保留版本；运行中任务不静默切换到未经核实的新版本。简单任务可不使用业务 Workflow，在任务包注明原因，适用审批和验证仍保留。

确定性执行器应校验前置条件、分支、步骤出口、审批、失败恢复和副作用重试。仅有 Markdown 定义时标注为流程规范，不宣称硬执行已经实现。

DNA 更新先由 Agent 分析语义变化并起草，负责人审核；写入已批准的精确内容才属于机械操作。通知依赖方前确认收件范围、内容和发送授权，结果不明先核实，不能盲目重发。
