# 工程文件组织与代码阅读设计

## 目的与范围

维护者熟悉 Unity/C#，需要一眼看清封装的状态、实现细节和对外契约。`src/` 的 TypeScript/TSX 保持现有语言和运行机制，采用明确的成员顺序、命名、访问边界和中文注释。公开名称调整须同步真实调用方并维护契约兼容。规则来自维护者对全项目源码整理的要求；本规范不表示全部存量源码已经完成迁移。

## 文件与声明

- 文件头写明作用定位、设计意图与实现形式：实例对象、无状态工具模块、接口/数据契约、React 组件或装配入口。说明所在层、协作边界和必要生命周期约束。
- 无状态工具模块统一使用按能力命名的静态工具类（如 JsonUtils），通过 `XxxUtils.Method()` 调用。TypeScript 没有 C# 的 `static class` 声明，使用普通 class、private constructor 和 static 成员表达禁止实例化的工具封装。禁止把实例状态或业务服务改为全局静态状态。
- 对象使用类封装实例状态；契约使用 interface/type，React 保留组件与 Hook 机制。队列、请求表和缓存即使属于工具目录，只要持有独立生命周期与状态，就仍是实例类。按职责组织文件，不将不同能力堆入万能 Utils。
- 通过声明顺序、访问修饰符和空行表达结构，不使用折叠分区注释。同文件多个类分别组织自己的成员，不混合实例状态。
- 类内按“私有成员 → 受保护成员 → 公开成员”组织，同一访问级别内再按“字段 → 属性 → 构造函数 → 方法”组织。显式标注 private/protected/public；已有 `#private` 保留运行时私有语义。接口成员本身是契约，不添加非法访问修饰符。
- 模块顶层以“内部类型”和“公开类型/入口”表达声明边界，重导出集中到公开入口区。工具算法和辅助函数迁入所属工具类的 private/public static 方法，常量迁入 static readonly 字段。未导出表示模块内部，export 表示可导入；不能给顶层函数加 private/public。React 组件、Hook、宿主要求的入口函数遵循框架调用约定，在文件头说明其形式与原因，不伪装成静态工具方法。
- 字段指存储状态，属性指 get/set 访问器；只读字段仍归字段。接口或数据类型的属性在所属契约内组织，不伪装成运行时实例。
- 每个方法、字段、属性、构造函数与契约成员均有简短中文说明；说明业务含义、用途或不变量，不只翻译标识。参数在存在单位、路径基准、空值或身份歧义时补充说明；普通局部变量无须逐一注释。
- 展开压缩语句与复杂控制流，具体排版与命名遵守下节；纯排版不顺带更名或改变行为，命名迁移同步全部引用。公开接口注明输入输出、前置条件、副作用、失败/取消/重试及资源责任中实际适用的部分。

## 代码格式规范

以下要求统一用于 TypeScript/TSX 源码编写、整理与 review。统一的格式、命名和留白是源码阅读体验的一部分，应保持稳定、一致的视觉节奏。C# 风格指阅读布局，语言和类型语法仍使用 TypeScript；编辑器或格式化工具不得因默认行宽自动拆分要求单行的声明，也不得压缩本规范要求的行间留白。

### 1. 大括号独占一行

- 类、接口、独立类型正文、方法、普通函数、构造函数、访问器及控制流代码块采用 Allman 风格：左大括号放在声明或条件的下一行，右大括号另起一行，与对应声明／控制语句对齐。箭头函数整体按第 8 条保持单行。
- 普通方法和函数的空块、单行正文同样展开，不写成 `{}` 或 `{ return value; }`；箭头函数不受此展开要求约束。
- `else`、`catch`、`finally` 放在上一块右大括号的下一行；各自代码块继续按 Allman 展开。
- 导入列表、解构、对象字面量和 JSX 表达式的大括号按其语法组织，不当作独立代码块。方法签名、类声明头和单行导出表达式中的内联类型保留在声明行。
- 回调或表达式结束所需的 `);`、逗号等可跟在右大括号之后，例如 `});`；不能在其后接写另一条语句。

### 2. 每条语句独占一行

- 每条赋值、调用、声明、返回或抛出语句分别书写，不写成 `update(); save(); return result;`。箭头函数内部按第 8 条作为整体单行的明确例外，外围语句仍分别书写。
- 控制条件与执行语句分行且相邻，中间不加空行；多变量声明的各项逐行列出，同一声明内部不加空行。`for` 头中的初始化、条件和递增是同一语法结构，不按连续执行语句拆开。
- 一行一个语句不等于所有表达式必须单行；复杂正文可按语义换行，下面明确要求单行的声明除外。

### 3. import 集中置顶

- 所有静态 `import`（包括 `import type`）集中在文件头说明之后、全部正文之前，不穿插在类、接口、常量或重导出之间。
- 相邻导入声明之间按第 6 条空一行；导入区与第一条正文声明或其说明注释之间也恰好空一行。shebang、许可证和必须置顶的工具指令仍保留要求的位置。
- 整理时保留静态导入原有顺序；与重导出调整相对位置时，核对实际模块加载次序及副作用。
- 动态 `import()` 和类型中的 `import(...)` 保留原位置，不将延迟加载改成启动加载。置顶要求不表示将所有 `export` 移到导入区，重导出仍按模块公开入口组织。

### 4. import 与 export 声明单行

- 每条 `import`、`import type`、具名重导出、`export type` 重导出及 `export *` 均写在一行，不因导入项多或行长主动拆分。
- 没有独立正文代码块的导出声明整条保持单行，包括常量初始化、对象表达式、类型别名引用及链式调用。`export const pageReadInput = z.object(...).strict();` 不拆成多行链式调用。
- 导出的类、接口、普通函数及具有类型正文的 `type` 保留正文结构：声明头单行，大括号和成员按对应规则展开。导出初始化表达式中的箭头回调保持单行，普通函数回调的代码块按 Allman 展开。
- 原有多行字符串、模板或 JSX 文本不能为了单行而改变内容；说明注释放在声明前或对应代码块内，不用行注释截断单行声明。

导入与导出示例（仅展示布局）：

```ts
/** 作用定位：演示输入契约的导入与导出布局；设计意图：声明整行书写，保持类型与运行时校验对应。 */
import { z } from 'zod';

/** 读取参数的结构与长度边界。 */
export const pageReadInput = z.object({ url: z.string().url().max(2048), maxChars: z.number().int().min(500).max(20000).optional() }).strict();

/** 从校验器推导输入类型，避免重复定义。 */
export type PageReadInput = z.infer<typeof pageReadInput>;

/** 仅演示具名重导出保持单行。 */
export { z } from 'zod';
```

### 5. 方法签名保持单行

- 方法、普通函数、构造函数、访问器及接口方法的声明头保持一行，包含修饰符、名称、泛型参数、全部参数和返回类型；参数多或返回类型长也不按行宽拆开。
- 使用 TypeScript 的 `方法名(参数): 返回类型` 顺序，例如 `public Read(path: string, options: ReadOptions): Promise<string>`，不改成 C# 的返回类型前置语法。
- 参数、返回值中的内联类型与声明头保持同一行；方法正文从下一行的左大括号开始。箭头函数的参数、返回类型、`=>` 及全部正文按第 8 条保持同一行。
- 此处约束方法声明，不将调用处的多参数换行套到声明头；函数调用的参数布局见第 9 条。

### 6. 独立语句、成员与大括号间距

- 相邻独立语句之间恰好空一行，保持舒展的阅读间距，不堆叠多个空行。按语句和成员边界留白，不按物理行数插空；此规则覆盖导入与导出、字段、属性、接口成员、局部声明和执行语句。
- 同一条语句因阅读需要分成多行时，内部连续排列，不插空行。例如调用及构造调用的参数、链式表达式、多变量声明、数组元素和普通对象字面量的属性；其中的函数正文和方法成员仍遵守各自规则。
- 大括号承担块内首尾的间距：声明头紧接左大括号，左大括号紧接第一行代码或其说明，最后一行代码紧接右大括号。连续嵌套的大括号及同一语句内的 `else`／`catch`／`finally` 不额外插空；空代码块的左右大括号相邻。控制块结束后若还有另一条独立语句，仍空一行。
- 相邻独立函数、类、接口以及方法、字段、属性、构造函数、接口成员之间始终空一行，即使上一声明或成员以右大括号结束。成员分隔优先于大括号间距，不能用上一函数的 `}` 抵消两个函数之间的空行；单行箭头或内联类型内部仍遵守既定单行规则。
- 中文说明或 JSDoc 紧贴所属成员，注释内部不按代码行逐行插空。成员之间的空行放在上一成员结束与下一成员的说明之前，不隔开说明与声明；即使上一成员以 `}` 结束也保留这一个空行。
- 单行 import/export、方法签名及第 8 条的单行箭头函数保持完整，不为插入空行而拆开；间距加在独立声明或语句之间。多行字面量、模板与 JSX 文本保持原内容，受换行限制的语法仍遵守下文语义边界。
- 成员顺序与留白共同表达结构，无须添加折叠标记。重载签名与实现保持同组，getter/setter 保持同组，不因排版改变成员顺序或初始化依赖。

### 7. 成员命名

变量名称以小写字母开头，多单词采用小驼峰 `camelCase`；私有和受保护字段在名称前加一个 `_`，形成 `_camelCase`。所有方法使用大驼峰 `PascalCase`，首字母及后续各单词首字母大写；属性继续使用小驼峰。方法与属性均不因访问级别添加字段前缀。

| 成员类别 | 命名格式 | 示例 |
| --- | --- | --- |
| `private` 字段 | `_camelCase` | `_isRunning`、`_requestId` |
| `protected` 字段 | `_camelCase` | `_retryCount`、`_maxRetries` |
| `public` 字段 | `camelCase`，不加 `_` | `isRunning`、`requestId` |
| 方法，不论访问级别，含实例、静态及接口方法 | `PascalCase` | `LoadConfig()`、`GetValue()` |
| 属性，包括 get/set 访问器及接口属性 | `camelCase` | `currentValue`、`displayName` |

- 实例字段、静态字段、`readonly` 字段及构造函数参数属性遵守相同的访问级别命名规则，不因 `static` 或 `readonly` 改用全大写。普通参数与局部变量使用 `camelCase`，不因位于私有方法内而添加 `_`。
- 字段前缀与属性名区分，例如私有存储字段 `_currentValue` 可由 `currentValue` 访问器公开；私有方法写成 `LoadConfig()`，不写成 `_LoadConfig()`。保存函数值的字段或局部变量仍按变量规则命名，方法声明按 `PascalCase` 命名。
- 函数值成员如果实现已有方法契约，名称必须与契约一致，例如实现 `Read(): string` 的对象写成 `{ Read: () => value }`；不能因为实现使用箭头函数就改回 `read`。独立函数变量不因此改为方法命名。
- 已有 JavaScript 运行时私有成员保留 `#` 语义：字段使用 `#_requestId`，方法使用 `#LoadConfig`，访问器使用 `#currentValue`；不得为统一前缀改成普通字段或删除运行时访问限制。
- 类、接口、类型名称不在本条变量／成员命名范围内。`constructor`、Symbol 成员、框架要求的 React 组件名称及外部固定协议键保留各自语法与契约；实现或重写外部固定方法时保留原契约名称，不为命名统一改变序列化字段或外部 API。
- 方法命名必须有可重复的自动校验，覆盖类、接口、类型字面量和对象方法，拒绝无法核实的动态方法名。固定协议例外精确限定到文件、所属声明及方法名，说明原因，失效或重复命中的例外也应报错。更名后同步消费者、类型键、字符串调用和测试替身，并验证外部包协议；命名检查通过不代表运行行为已经验证。

### 8. 箭头函数保持单行

- 箭头函数从参数列表、返回类型、`=>` 到整个函数体保持一行，不因行宽或格式化工具主动换行。表达式形式、`async` 形式和带 `{ ... }` 代码块的形式均适用。
- 带代码块的箭头函数也将大括号与内部语句放在同一行。这是 Allman 大括号和每条语句独占一行的明确例外，不仅要求声明头单行。
- 作为参数传入的箭头回调，以及赋给变量、字段或导出值的箭头函数，遵守相同规则；箭头函数外的其它语句仍各占一行。
- 单行排版不能改写多行字符串、模板或 JSX 文本的内容，也不能让行注释吞掉后续代码。保留这些语义约束，不能机械删除所有换行；不为缩短行长改变函数种类或 `this` 绑定。

```ts
/** 表达式形式直接返回结果。 */
const getValue = () => 42;

/** 多条内部语句也保留在同一个箭头函数行内。 */
const readValue = () => { const value = 42; return value; };

/** 参数和返回类型与表达式正文同在一行。 */
const doubleValue = (value: number): number => value * 2;
```

### 9. 函数调用的多参数换行对齐

- 函数、方法或 `new` 构造调用的参数过多、单行不便阅读时，将参数列表分行；同一级调用的每个参数另起一行，使用相同缩进对齐，不在一行连续排列多个参数。本条不预设固定参数数量阈值。
- 函数名与左圆括号 `(` 保持同一行，第一个参数紧接在下一行，中间不插入空行。参数属于同一条语句，参数行之间不空行；右圆括号 `)` 单独收尾，与最后一个参数之间不插入空行，分号可跟在右圆括号之后。
- 区分调用实参与声明形参：方法声明仍按第 5 条保持单行。第 4 条要求单行的导出声明及第 8 条的完整箭头函数继续保持单行，不因其中包含调用而拆开。
- 每个参数内部的对象、回调或嵌套调用遵守自身规则；字面量、模板、JSX 文本及必要注释换行保持原语义。不为换行改变参数顺序、求值顺序或调用次数。

```ts
SaveDocument(
  documentId,
  content,
  options,
  cancellationToken
);
```

### 10. if 执行体与大括号

- TypeScript 的 `if` 支持代码块。执行体仅有一条且排版后占一行的普通语句时，省略大括号；语句紧接条件下一行并缩进，中间不空行。`else` 的单行执行体同样处理，`else if` 保留连续分支结构。
- 执行体包含多条语句，或单条语句本身需要多行时，使用 Allman 大括号。块内首尾不空行，独立语句之间空一行；同一条语句的参数和表达式续行仍连续排列。只包裹原本属于分支的执行体，不能按缩进把后续独立语句并入分支。
- 省略大括号必须保持作用域、自动分号插入和 `else` 归属。局部声明、空块及无法安全展开的嵌套控制流保留必要大括号；不能为统一外观改变行为。第 8 条要求完整单行的箭头函数仍优先遵守单行规则。

```ts
if (!value)
  return false;

if (platform.engineArtifacts)
{
  this.enginePackages = new EnginePackages(
    artifactPath,
    platform.engineArtifacts
  );

  this.ready = true;
}
```

### TypeScript 语义与格式化边界

格式调整必须保持求值顺序、模块加载、字面量与 JSX 文本的含义不变。空白调整须保持语法树一致；第 10 条允许增加或移除不改变作用域的单语句 `if` 包裹块，验证时仅忽略这些包裹块，其他语法结构、词法内容和注释原文必须一致。尤其不能在 `return`／`throw` 与表达式之间插入换行，也不能破坏 `async` 等受换行限制的语法。对象返回值保持 `return { ... };`，不要机械改为 `return` 后另起一行大括号。

保持语义的空格、缩进和换行调整本身不改变运行逻辑或算法效率；源码位置、文件大小和调试映射可能变化。单行声明、箭头函数单行及代码行间距规则优先于格式化工具的默认行宽与紧凑布局；箭头函数以外的独立正文遵守 Allman。所有排版规则都不能覆盖语言语法或字面量内容的要求。

## 重排的语义边界

声明顺序可能影响字段初始化、计算属性名、装饰器、静态块、模块顶层执行与 React Hook。先核实依赖和副作用，不能为排序改变执行顺序。需要重构初始化时先给出等价安排并验证；尚未安全重排的部分显式说明顺序约束，不能假称已满足全部成员排序要求。重载签名与实现保持连续，getter/setter 成组；保留 shebang、许可证与工具指令位置。不改动序列化字段名或外部协议来迁就 C# 命名。

## 目录是系统封装

每个维护中的源码目录保留一份 `ARCHITECTURE.md`，作为当前模块面向人的架构模型与设计说明。整个工程通过“工程 → 系统 → 模块 → 类”的多层模型逐层解释；每一层只解释本层，沿导航下钻后再理解下层实现。

模块自己的单元测试放在本层 `unittest/` 中，属于内部验证设施，不作为产品架构图里的虚拟业务子模块。测试设施不要求另建 `ARCHITECTURE.md`，不进入产品源码的成员命名、文件头及自动排版扫描；其测试归属、依赖、类型和执行结果仍必须检查。

### 阅读目标与内容边界

1. **设计意图是核心。** 说明模块解决什么问题、承担什么职责、为什么这样划分，以及各部分如何协作完成目标。
2. **描述本层代码。** 写清当前目录内各个类的定位、分工和关系。没有类时按真实函数集合、组件或入口表达，不虚构代码类。
3. **子模块是虚拟类封装。** 每个直接子模块在本层模型中视为一个完整的虚拟类，只展示它的整体职责、协作关系和阅读入口。图中标明“虚拟封装”；内部类、函数、状态和实现细节由子模块自己的文档负责。目录嵌套表示系统组合，不代表语言中的嵌套类或继承。
4. **类图服务于理解设计。** 展示实际继承、实现、依赖与经核实的组合关系。持有引用不自动证明生命周期所有权，导入不自动等于运行时调用；关系方向与含义必须有源码依据。
5. **保持简洁。** 不强制罗列全部文件、类型、字段、方法、参数和返回值。只保留解释设计与协作边界必需的内容，源码链接用于深入阅读。参数级契约、操作步骤、验证记录和生成器说明不作为架构文档主体。
6. **描述当前事实。** 不虚构设计动机，不混入未实现方案。当前职责、关系或设计意图受代码变化影响时同步修正文档；未影响模型时无需制造图差异。
7. **生成器服从阅读目标。** 自动生成只辅助维护结构与导航，不能用机械声明清单替代架构建模，也不能覆盖人工设计说明。生成标记保持不可见，校验统计和工具操作说明留在开发记录或工具说明中。

验收标准：维护者打开这一份文档，就能一览当前模块的设计思想、主要组成及协作关系，并知道需要深入时去哪里阅读。大型工程通过多层虚拟封装保持每层可理解，不在顶层展开全工程的类与依赖。

### 组织方式

正文通常包含“设计意图”和“主要组成”：前者用简短段落交代目标与职责划分，后者说明本层类及必要的无类模块定位，并链接源码。关键协作过程可直接写入设计意图，也可另设简短说明；不要求为接口契约、状态字段或开闭原则分别凑章节。

“架构关系”展示本层实际类、选定的函数／组件模块，以及直接子模块的虚拟封装。子模块只导航到其 `ARCHITECTURE.md`，父层不重复内部类图、文件清单或接口明细。相关的外部协作者只作为理解本层所需的边界出现。

图较大时按协作关系分组，明确跨图对应节点与关系；不要缩小整图或依赖读者记忆识别断开的关系。独立封装之间没有依赖时如实展示，不为连通图形虚构连线。纯资源叶子说明其整体用途即可，不编造代码类。

### 维护与生成约定

本仓库在 `src/` 及其维护中的子目录执行这一约定。仓库根目录、测试、脚本、设计记录、标准文档、第三方依赖、构建产物、缓存和运行数据不属于强制覆盖范围；源码、样式、配置、资源及必要许可证继续保留。

人工维护 `## 设计意图` 和 `## 主要组成`。组成表采用“组成／定位”两列，每项以相对源码链接定位实际类或有共同职责的无类模块；各个本层类都须有清楚定位，不要求收录所有文件或类型。子模块的职责在它自己的设计意图中维护，父层只引用其概括，不另建第二份职责表。

自动工具只替换独占行的 `<!-- architecture:generated:start -->` 与 `<!-- architecture:generated:end -->` 之间的关系图及子模块导航，逐字保留区域外人工正文。文档只保留一对正确标记，代码示例中的标记不作为写入依据。缺少设计说明、组成指向失效、遗漏本层类定位、标记损坏或依赖无法核实时拒绝整批写入，不生成占位设计。人工重写设计说明是显式的文档维护，不属于生成器的自动职责。

旧说明收敛时保留必要的稳定导航或同步迁移引用，核对仍影响模块边界的重要约定；历史明细可通过版本记录追溯。不能以简化模型为由改变产品行为或删除源代码。

## 模块单元测试与增量验证

### 测试随责任模块维护

- 每个单元套件只验证当前模块的功能。单元测试统一放入所属模块的 `unittest/`；模块专用夹具可放在同一目录，共用纯数据与断言保持独立。工程工具的单元测试同样归所属工具目录的 `unittest/`。
- 子模块验证自己的规则、状态和失败行为；父模块验证自身规则以及本层组合。父模块不重复穷举子模块的内部实现。需要真实多模块联合断言时登记为契约测试，需要真实应用、进程或平台生命周期时登记为集成测试。
- 目录位置不替代责任审查。单元不得直接或间接加载完整 Application、导入其他套件或依赖测试顺序；迁移必须保留原有断言、契约及集成覆盖，不能仅改变分类取得通过。
- 测试归属登记同时记录责任模块、实现入口、所属目录和测试类型。新增、移动、删除测试均同步登记、发现规则、CI 分片及直接引用。

### 以成功回执决定增量执行

- 记录模块实现指纹、契约指纹、测试及辅助输入指纹、依赖契约指纹、执行环境指纹，以及实际执行的结果、时间和报告。复用以内容及环境为依据，不仅按 Git 提交号、修改时间或文件是否出现在 diff 中判断。
- 首次验证、没有有效成功记录、模块实现变化、测试或夹具变化、相关契约变化，以及工具链、配置或环境变化时，重新运行对应模块的所选测试。未受影响且有有效成功记录的模块复用原结果，不逐层无差别重跑。
- 独立契约必须明确登记契约文件和行为版本。返回语义、错误、权限、状态、副作用、取消及资源责任改变时同步契约正文或行为版本；类型签名不变不能证明行为不变。未建立独立契约的模块使用实现依赖闭包作保守指纹，不擅自宣布消费者不受影响。
- 模块单元可在经过明确声明的依赖契约边界停止传播；真实组合的契约测试仍追踪实际实现。集成及真实环境验收不复用本地成功缓存。缓存可以手动强制绕过，不代替代码 review、后续完整 CI 或发布验收。
- 执行前使旧成功回执失效；失败、取消、中断、缺少报告、零用例、全跳过、文件选择不一致或运行期间输入变化，均不得记录为可复用成功。同工作区的缓存写入串行化，损坏记录按未验证处理。
- 通过文件读取、运行进程或其他动态方式消费的本地配置、样本及脚本必须登记为额外输入；不能纳入指纹的外部状态应禁止缓存。只读列计划不得启动测试或制造成功记录。

### 测试与 Release 隔离

测试可以与实现同目录管理，但只由测试入口加载。产品源码不得直接或间接引用 `unittest/`、集中测试夹具或测试运行器，包含类型引用。测试可以参与开发类型检查，不属于生产构建入口。

生产构建必须检查真实加载的模块和最终 chunk 依赖，测试被内联也应失败；资源包和安装包的暂存目录发现自有测试文件同样拒绝。不得仅依赖文件后缀过滤或 tree-shaking 声称 Release 没有测试代码，也不能为移除测试而忽略错误的产品依赖。

## 设计资料的保留与删除

`docs/` 独立维护概念设计、标准与准则；`design/` 只保留依据这些标准形成的产品目标、核心取舍、未落地设计和原型。不强制另建工程资料目录：操作流程沿现有工具或项目 Skill 维护，开发和验证事实记录在 Git 提交及关联 Issue／PR，历史资料通过固定版本追溯；发布正文可以由构建显式提供，不能依赖已删除路径。当前实现说明归 `src/`，品牌等独立运行资源归 `assets/`；内置 Skill、提示词、运行规范与 Schema 作为代码常量在所属源码模块维护。`docs/` 不反向依赖项目设计或工程操作文件。具体清理批次、数量、提交和验证结果记录在相应提交及关联 Issue／PR 中，不反向成为通用标准的依据。本节不要求设计目录采用源码目录的单份 `ARCHITECTURE.md` 结构。

### 按实际用途决定保留范围

`assets/` 只放有实际读取、引用或打包用途的资源。品牌图像和资源摘要属于资产；与业务版本绑定的 Skill／提示词／运行规范和校验 Schema 则以字符串或结构化常量放入各自源码模块，通过显式导入使用，不再从资产目录读文件，也不保留两份正文。跨模块目录只组合各模块公开常量，保留内容版本与引用语义；面向维护者的 README、操作说明和开发记录不属于资产，不放入该目录。必要导航与工具使用方式复用根 README、现有项目 Skill 或源码说明，避免随资源包复制维护文档。

| 材料 | 处理原则 |
| --- | --- |
| 产品目标、核心取舍、未落地设计和原型 | 设计目录只保留这四类及原型必需资产／脚本；已经落地的设计可保留选择理由，删除迁移进度与重复实现快照。未落地内容明确标为候选，不自动成为待办 |
| 已完成的功能切片、旧治理基线、已被替代的方案、仅作跳转的旧文档 | 核实已无独立维护用途，保存可追溯版本并迁移引用后可删除 |
| 历史验证报告、一次性架构快照及配套 HTML／截图 | 无当前使用者且原始事实可追溯时可删除；不将其当作当前行为保证 |
| 操作指南与工程记录 | 优先复用工具／Skill、Git 提交及 Issue／PR，不强制新建资料目录；删除目录时同步流程入口，历史原文按固定版本追溯，不把历史“下一步”当成待办 |
| 产品加载的规范、Schema、配置、兼容资料和必要许可证 | 按真实消费者与兼容要求维护，不能因扩展名、年代、目录位置或链接数量删除 |
| 构建／发布读取的版本正文、签名公钥及其必要依据 | 先核实真实消费者。删除资料目录时可将正文改为显式构建输入，历史正文与公钥保留在版本历史及既有发布中；同步读取入口并验证，不改写冻结制品、运行信任根或绕过构建指纹 |
| 独立未提交工作、尚未纳入版本控制的资料 | 保留原状；不能声称 Git 已保存实际上未收录的内容 |

相邻文件不因主文档删除而自动成为可删资产。对预览图、母版、检查脚本及兼容 Schema，分别核实是否仍供设计、工具或产品使用；不为追求删除比例扩大范围。

### 删除前核对用途与历史原文

先明确本次资料清理范围，检查工作区已有改动，再核对 Markdown 导航、源码或脚本读取、构建打包、发布流程与外部约定。仅静态导入为零或 Markdown 链接少，不能证明文件无人使用。涉及产品行为、读取路径或兼容变化时，在已有授权范围内作为相应实施变更并按实际影响验证，不能仅按纯文档清理报告通过。

删除前记录包含完整原文的固定提交与仓库相对路径，并核实内容确实存在且与准备退出的版本对应。共享历史链接应指向协作者可访问的已推送提交，不使用会移动的分支名，也不把尚未推送的本地提交当成线上阅读入口。仅本机追溯时明确给出 `git show <提交>:<仓库相对路径>`；未提交内容需要先得到可靠保留。

无需为退出维护的资料再复制一套本地归档目录。引用当前实现时指向现行规范、设计或源码模型；引用某次历史结论时指向当时的固定版本，不能用现状页面冒充旧版本证据。长记录收敛时保留清楚的历史入口，日期、结果、失败与限制仍按原文解释。

### 删除后的同步与验证

同步目录导航、保留文档、开发入口及必要多宿主副本中的链接和章节锚点。仍被发布正文直接引用的依据，需要保留可用入口；不能为了清理引用擅自改写已冻结的发布正文。无用途的空目录可以一并移除，删除前核实实际路径位于本次清理范围内。

完成时记录删除与保留范围、历史版本入口、引用校验及未运行检查。核对无新增失效引用、无误删仍被读取的资料；对承诺保持不变的源码、运行资产和发布输入可用字节摘要验证。原有失效链接与本次新增问题分开记录，不能将未修复问题报告为已通过。

纯资料清理只验证事实、格式、引用、版本追溯及入口一致性，不运行产品测试、类型检查或构建。删除历史测试报告不减少测试覆盖，不豁免后续合并、安装升级或发布验收。

## 交付与验证

每次源码变更都核对相关注释和本层架构模型。职责、协作关系、设计意图或子模块边界变化时同步说明；仅方法内部实现变化且模型仍准确时，不强制添加成员或改画关系。

验证分别覆盖：模型是否符合实际代码，类定位是否齐全，子模块是否只作为虚拟封装出现，关系与导航是否正确，以及人工说明是否得到保护。还需人工阅读设计意图与协作说明，判断是否能建立当前模块的整体认识；生成无漂移、数量统计或源码解析通过不能代替这项判断。

修正偏差后重新核验受影响范围。纯文档及 Skill 修改只检查事实、格式、引用和多入口一致性；生成器变化运行对应单元及架构检查。只有产品行为或接口实际变化时才选择相关产品验证，不自动运行全量测试、类型检查或构建。

源码整理仍核对真实调用方、初始化与副作用。工具函数迁为静态方法时同步真实消费者并验证函数身份、this 绑定及兼容边界，不以文档更新冒充代码迁移完成。

## 静态工具类示例

下面是组织方式示例，不表示项目已经存在该工具类。

```ts
/**
 * 作用定位：Core 层无状态文本工具，为调用方处理明确给定的文本。
 * 设计意图：将纯文本算法集中到静态工具类，不持有业务状态或外部资源。
 * 实现形式：静态工具类；禁止实例化，公开方法不修改调用方数据。
 */
export class TextUtils
{
  /** 脱敏命中时用于替换原文的固定标记。 */
  private static readonly _replacement: string = "[REDACTED]";

  /** 仅提供静态能力，不允许创建工具对象。 */
  private constructor()
  {
  }

  /** 精确替换全部非重叠命中；空敏感文本保持原文，不解释正则表达式。 */
  public static Redact(text: string, secret: string): string
  {
    if (secret.length === 0)
      return text;

    return text.split(secret).join(TextUtils._replacement);
  }
}
```

## 实例类示例

```ts
/**
 * 作用定位：演示按实例维护计数的对象封装。
 * 设计意图：各实例状态独立，外部只通过公开方法改变状态。
 * 实现形式：实例类；无外部资源，无需销毁。
 */
export class Counter
{
  /** 当前实例累计次数，从零开始。 */
  private _count: number = 0;

  /** 当前累计次数的只读视图，不向外提供赋值入口。 */
  public get value(): number
  {
    return this._count;
  }

  /** 累加一次并返回新值，仅修改当前实例。 */
  public Increment(): number
  {
    this._count += 1;

    return this._count;
  }
}
```
