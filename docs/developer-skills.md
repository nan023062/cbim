# 开发者可持续维护 Skill

这些 Skill 位于当前 Cindy 项目工作区，用于工程开发、维护和桌面发布。当前共四项能力；每项均提供 `.agents/skills/`、`.claude/skills/`、`.codex/skills/` 三个同步副本，包含配套引用资料，不重复计为不同能力。

## 四项能力的分工

| Skill | 回答的问题 | 适用时机 |
| --- | --- | --- |
| [architecture-evolution](../.agents/skills/architecture-evolution/SKILL.md) | 分层与边界怎样演进，哪些共性值得抽象为稳定能力？ | 架构评估、耦合治理、重复实现、共性业务、工具封装、继承与多态 |
| [architecture-maintenance](../.agents/skills/architecture-maintenance/SKILL.md) | 代码和资料是否一致，系统怎样工作、为什么这样设计、下次改哪里？ | 源码变更、注释与类图同步、理解工程、重要变更认知交接 |
| [cbim-development](../.agents/skills/cbim-development/SKILL.md) | 这一步做什么，怎样验证并接续？ | 开发 CBIM、推进已授权步骤 |
| [cbim-release](../.agents/skills/cbim-release/SKILL.md) | 哪个制品可以发布，遇到中断怎样恢复，用户升级是否真的通过？ | 桌面发版、投放更新通道、签名迁移、发布恢复及官网收尾 |

这组配置属于 Cindy 工程开发入口，未加入 CBIM APP 内置 Skill 清单，也没有创建常驻任务或岗位开发自动化。文件已配置不代表已经进行全仓架构评估或实际代码重构。

## 日常怎样使用

可以直接表达目标，也可以指明 Skill：

- “使用 `architecture-evolution`，结合本次需求检查工程全局分层与职责，给出最小可行的演进方案。”
- “使用 `architecture-evolution`，检查已维护源码中的共性实现，解释哪些适合工具函数、领域封装、继承或多态；先给出判断。”
- “使用 `architecture-maintenance`，用一条真实操作链帮助我理解工程，并说明新增一个同类能力要改哪里。”
- “按已确定方案实施这一处抽象提取，同步注释、架构图和认知说明，并验证受影响消费者。”
- “使用 `cbim-release` 发布最新桌面版，沿用已明确的发行模式，通过检查与升级验收后同步官网。”
- “使用 `cbim-release` 继续上次中断的发布，先核实已有草稿和附件，只补齐尚未完成的步骤。”

每次实现先确认改动的全局位置；出现相应证据时才深入评估架构演进或共性沉淀。已授权实施会继续完成必要修改与验证；只要求分析时交付分析，不自动执行重构。一次小修不需要机械运行所有流程，也不会自动发版。

## 发布时怎样使用

`cbim-release` 的 [通用项目](../.agents/skills/cbim-release/SKILL.md)、[Claude Code](../.claude/skills/cbim-release/SKILL.md) 和 [Codex](../.codex/skills/cbim-release/SKILL.md) 入口相同。主文件给出阶段门槛；配套资料分别提供正常发布步骤、按症状查询的故障恢复、证据字段和完成条件。

它复用当前打包、验签、发布和 Actions 实现，明确一体发布命令不会等待候选验收，以及当前验收脚本仍固定 0.1.1／未签名／0.x 的限制。每次新版本先核实并适配真实旧版和模式，不能将旧验证直接当作新签名迁移通过。缺证书时可以按用户明确选择发行未签名版；后续签名用更高版本，不覆盖原公开附件。

安装测试在隔离 runner 进行，公开、真实在线升级、官网部署和双分支同步各有独立回执。此 Skill 不增加后台发布服务，不强制用户升级，也不因为被加载就获得外部写入授权。只修改 Skill 时验证格式、引用、一致性及场景决策，不重新运行生产发布。

## 复利来自稳定语义和明确边界

分层、模块化和抽象共同服务于一个目标：提炼出越来越多变化频率低、可持续复用的稳定系统，使常规业务迭代主要发生在变化点，已有稳定能力继续积累使用价值。接口、核心实现与具体策略的稳定程度分别判断；真实使用和变更历史可以提供证据，长期未使用或没有提交本身不能证明成熟。

所有系统、模块和类的封装遵循以下原则：

1. **单一职责：** 让同一类决策和变化原因聚在一起。一个封装不应因不相关的业务变化而反复修改；单一职责不等于只能有一个方法。
2. **开闭原则：** 面对已经识别的变化，主要通过新增实现、组合、策略或合理继承扩展，在装配点接入，保护既有稳定核心。若每增加一种业务都要改公共分支或字段，就需要重新审视边界；缺陷修复与确有必要的契约演进仍须正常实施和验证。
3. **单向依赖：** 真实的层、模块和文件依赖形成有向无环结构，包含类型引用。易变业务和实现细节依赖稳定契约，稳定核心不反向认识具体消费者；通过契约归属与装配解除反向依赖，而非把耦合藏进动态加载、事件或全局状态。
4. **按业务变化点划界：** 模块或类承载明确的业务变化点，变化频率不同的代码不能放在同一封装里。低频稳定机制与高频业务策略分别封装，通过稳定契约协作；提取共性不能把不同变化节奏重新绑在一起。

评估一个边界时，记录变化点、驱动需求、变化频率及依据、所属模块／类和稳定契约。频率依据实际业务变化或明确需求，排除格式化、批量重命名等噪声；没有证据时标明未知，不按提交次数机械拆分。同样频率的独立业务也不能因此合并。验证时选一项业务变更，说明高频部分怎样独立调整、低频核心为何无需随之修改。

单向依赖让职责和影响范围更容易追踪，是后续循序渐进治理的基础。无环之外仍需检查依赖过密、职责混杂和共享状态；用实际调用、状态归属及测试验证解耦效果。

共用同一规则的代码应有可靠的维护入口；仅外形相似、却因不同业务原因变化的代码，可以保留独立。技术机制与领域规则分别寻找归属，不把所有共性都放入万能工具类。

工具函数适合稳定的无状态操作；领域对象或服务封装业务不变量；接口与策略支持多态替换；组合适合独立变化的能力；浅层继承和模板方法适合真实的类型关系或稳定算法骨架。选择依据是契约、变化方式和真实消费者，而不是强制套用某种模式。

每次有价值的演进都留下可读的证据：当前问题、调整前后的边界、为什么这样选择、实际验证、下一次需求的修改入口。抽象是否成熟由后续真实使用检验，不由减少的代码行数或新增类的数量决定。

审阅时可以直接核对：**哪些能力变得稳定了？为什么只有这一类变化会修改它？新增同类业务怎样扩展？依赖方向与变化传播是否更清晰？** 一次只迁移可验证的切片，持续改善这些答案。

## 本工程的落点

现状从 [源码架构](../src/ARCHITECTURE.md)、[源码布局说明](source-layout.md) 和真实入口核实；例如 updater 独立边界不能为了共用 HTTP 代码就反向依赖业务运行时。具体层级规则由 `architecture-maintenance` 和依赖检查器维护，其余 Skill 引用该规则，不另行复制固定 CBIM 目录表。

架构理由与维护者说明放在现有 `docs/` 相关资料中；代码注释、目录 `ARCHITECTURE.md` 及其生成源按现有规范同步；实施顺序与实际结果进入 [路线图](../design/tool-architecture-roadmap.md) 和 [开发记录](../design/development-log.md)。当前只交付 Skill 和开发规则，未预填未核实的全局认知图或抽象候选。
