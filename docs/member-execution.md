# 成员执行与结果回传

当前接通“主会话工具派发 → 主轮释放执行占用 → 独立成员 Pi 会话 → 结构化交付候选、已核实求助或真实失败 → 原主会话自动续跑”，同时保留可信桌面的显式派发和启动接口。主对话展示成员实时动态，任务视图展示可选中节点的派发流程图。主 Agent 和自定义 Agent 使用同一大脑、工具与权限门禁，区别来自角色配置、Skill 和各模块 Workflow。

自动协作仅推进当前应用进程中、由真实主聊天运行发出的委派，不扫描所有邮箱启动任务，也不提供成员递归派发。下面的 `window.cbim.call` 示例用于可信桌面集成；显式派发同样必须属于已有主调度周期和目标计划，没有无周期业务执行入口或成员启动表单。操作真实项目会调用已配置供应商并产生工具副作用，由用户选择工作区、目标和本轮权限，模型不能自行升级。

## 自动与团队模式

对话输入区的协作模式与执行权限分别选择。新对话默认自动模式；没有保存模式偏好的历史对话沿团队模式。模式在新目标开始时冻结，进行中或等待中的目标不可切换；结束或取消后，可在同一对话改选下一目标。

- **Auto**：主会话默认直接探索、实现和验证，不要求先创建团队、模块、负责人或正式派发计划。内置 `cbim:project` 始终表示项目根范围，真实模块是其子级；查询不落盘或生成维护人。已有知识用于指导工作，按里程碑和真实重复需求渐进整理团队、业务边界及共享方法。明确需要委派时仍走正式计划和派发：已有负责人使用真实岗位与岗位模型；确实无负责人时可用独立内置执行员；只有项目确实无模块时，正式兜底才能使用根范围。
- **Team**：必须明确模块与有效负责岗位；缺失时停止业务派发，等待人工确认。不会以主模型、默认执行员或隐式模块绕过配置。
- **共同约束**：read 禁止写入和命令，ask 等待实际批准，execute 仍检查边界；`.cbim/` 只经知识服务修改，原生命令并非操作系统沙箱。正式委派不得忽略停用、失效或过期岗位，仍核维护关系、本模块 Workflow 和 human 验收。主轮按实际权限领取工作区租约，可能写入的运行保守独占。

兜底的 `fallbackBinding` 由服务生成，保存原因（`no_modules` 或 `unassigned_owner`）、原周期、模块、模型与知识/能力指纹；计划、派发回执、任务和运行日志一致。它与登记岗位的 `ownerBinding` 互斥，不制造 memberId、来源证明、维护人或正式责任登记。领取时重核当前配置，后来登记负责人或知识/模型变化会阻止旧兜底继续领取；历史结算保留原事实。

维护入口：纯契约在 core/team/automatic-execution.ts，存储关联在 core/tasks/automatic-execution-rules.ts，知识范围在 scheduler-engine/context/automatic-context.ts，持锁解析在 OwnerExecutionService。既有权限、预算、运行租约与人工验收机制复用；常规兜底规则变化集中在上述边界，不修改权限核心。

## 主会话自动协作

主 Agent 是具备工程思维、架构思维和结构化思维的团队与技术管理者：核实现状、目标和约束，维护模块职责、依赖和责任，将任务组织为执行者、模块列表、目标与验收要求，审阅证据并安排后续工作。它直接通过受控知识服务增删改查 `.cbim/`、治理团队和业务架构，按证据渐进演进；Team 的业务实现与验证交给执行 Agent；Auto 主会话可以直接完成。知识写入仍受 read/ask/execute、版本与事务控制，重要人工决定不由模型伪造。没有合适自定义角色时，可将内置静态 `cbim:executor` 明确登记为项目岗位并设置模块责任；它继承 Team 根 Skill，由独立任务实例执行，不把默认定义写入 `.cbim/`，登记路径不跳过岗位及模型采纳；Auto 的显式委派兜底采用上节独立绑定。Auto 直接工作和单独知识沉淀不强造团队目标；一旦显式规划或派发，仍须按原完成门禁审阅。未知副作用、未确认输入和不完整日志不能被轻量收尾掩盖。

现有成员状态由可靠事务推进：依赖未就绪为 `waiting`；领取/启动意图为 `communicating`；真实引擎就绪为 `working`；终态或安全检查点释放执行占用后回到 `idle` 或仍有前置待办的 `waiting`。模型正文不能直接改状态。“自身思考”指独立模型上下文中的理解、规划和工具选择，不承诺导出私有思维。当前支持同周期内一次受限文件任务的检查点续执行；长期驻留自治、跨重启恢复和更细粒度通信状态仍需后续实现。

1. 主 Agent 定位模块与真人维护关系，通过 `cbim_module_owner_inspect` 查询负责岗位，将真实查询返回的 `ownerSelection` 保存到目标计划和 `cbim_dispatch_task` 请求。同负责人模块可合并，不同负责人分开派发；服务生成不可变 `ownerBinding`，不能由模型提供证明。`cbim_dispatch_inspect` 只读查询本会话派发图。工作区、主会话、运行和调用身份均来自后端绑定，不接受模型指定权限或发送方。
2. 派发工具只可靠入队，不在工具调用中等待成员。主轮安全完成、引擎关闭且工作区占用释放后，`AutoCollaboration` 启动可执行成员；已有占用释放时再推进，不以长时间等待占据主执行槽。
3. 已登记成员使用项目岗位独立采纳的模型、Skill 和项目适配；Auto 兜底使用原周期模型、内置角色和 Team 根 Skill，实际领取复核责任及配置版本；主会话的模型选择不能覆盖成员模型。权限模式仍来自本轮用户授权，“本次任务全部通过”不传给成员；ask 成员仍单独审批，前置候选未验收且不扩大权限。
4. 成员完成并释放占用后，调度读取候选、证据与限制，或者失败、受阻、仍待前置等真实状态。结果以带批次来源的 Pi custom 消息进入同一个主原生会话，明确是任务数据而非用户新指令或授权；主 Agent 再处理原目标。失败且没有结果信封的批次也可以回报。
5. 回注来源先保存在主运行日志，按 `continuationId` 和结果消息 ID 防止重复启动，再确认结果收件。前端显示系统回传提示，不生成虚假的用户消息。已有用户消息保留在原可编辑队列，协作期间暂缓，主续跑安全完成后再处理。

停止主任务会先阻止后续自动启动，再请求停止关联成员并暂停用户队列；迟到批准不能重新启动。应用关闭或重新打开工作区不会自动恢复协作批次。派发和运行事实、结果信封及回注来源仍持久保存，未知副作用需要核实。

主轮和成员轮共同受应用级并发上限约束，默认 4，可在设置中修改。已受理成员和结果回注保留稳定等待票据，不先领取任务、不创建运行或占工作区锁；释放后由原协调器重新核实。会话显示等待原因，纯等待不增长工作时长。新聊天容量不足明确未受理并保留草稿；原普通队列暂停而不丢消息。停止、关闭或重启不会把旧票据自动转为执行。详见[全局运行准入](global-runtime-management.md#全局并发准入)。

每个新主 session 默认拥有自己的主 Agent 实例，普通对话与图根引用同一个 `agentInstanceId`。用户一轮任务开始时创建调度周期 `scopeId`，跨越主模型调用、成员执行和结果回注，最终答复或停止后关闭。执行实例随该周期的任务创建，关闭时释放；主实例及会话、任务图、证据和用量记录保留。普通问答也有周期，但不伪造业务任务；模型一次返回不等于整个调度周期结束。

主对话使用主实例的 `conversation` 通道，正式任务使用各自执行实例的 `task` 通道；执行者和主调度不共享实例或原生上下文。同一静态执行角色在新任务中创建新的周期实例，已释放实例不能再次执行。旧图保留既有引用，不重写旧日志；只有显式续聊的新轮保存绑定。知识结构异常不阻断内置主会话身份登记，正式派发仍须通过结构、模块和维护关系检查。

## 成员求助与主调度补做

执行者遇到缺信息、依赖、权限、能力或范围问题时，可调用成员专属 `cbim_task_help`。输入只有 `kind / reason / question / attemptedToolCallIds`，接收方和完整运行身份由系统绑定；不能选择其它收件人，也不产生新的执行授权。

工具先返回 `staged`，随后成员必须结束本轮。只有正常关闭、canonical 日志完整、回执和顺序核实通过，才在原任务上保存不可变 `help`，将任务记为 `blocked`、成员释放占用回到空闲，并生成独立求助信封。停止、失败或未知结果不会伪装成安全交接；主对话、任务节点和详情只展示这份已结算事实，不根据模型正文判断。

主调度收到问题后核实图谱和原目标，以新任务、新实例安排补做；成功候选可按既有规则替代旧受阻任务。确需用户补充时可申请安全等待，但有尚未执行的依赖任务仍会被门禁拒绝，应按下节明确撤销或继续完成它们。这个流程没有恢复旧成员运行，也未实现对等聊天、长期驻留或任意活动任务子树取消。求助理由为权限不足不等于用户同意提权。

## 主调度撤销尚未启动的待办

主调度使用 `cbim_dispatch_inspect` 查看当前图，再用 `cbim_dispatch_cancel` 提交明确列表、版本和原因。模型输入为 `{expectedGraphCursor:{streamId,seq},targets:[{taskId,expectedRevision}],reason}`；主会话、周期和运行由系统绑定，不能夹带权限或自动扩大范围的参数。

只能撤销当前周期从未领取、没有运行或候选的任务，必须一并明确列出必要的未启动依赖后继。遗漏时整批拒绝并返回相关任务 ID；图或版本变化也需重新核实。已领取/运行任务继续使用停止流程，该工具不会发送 abort，也不生成假的取消运行。

成功后节点和连线保留，记录 `cancelledBeforeStart` 的原因、时间及主运行，原派发信封标为已处理，执行实例清理待办回到空闲；实例仍在周期关闭时释放。界面显示“已撤销（未启动）”，普通停止不使用该标签。重复同命令返回原回执，重开不启动旧任务。

撤销后旧审阅失效。主 Agent 必须按新图重新审阅才可申请 waiting；用户明确补充后，仍以新任务/实例补做，完整成功候选替代旧受阻和撤销任务，不能靠撤销凑成完成。若主 Agent 在同一轮派发后又全部撤销，本轮按真实审阅直接收口，不额外回注一次没有执行结果的模型轮次；周期历史不删除。

## 主调度为未启动任务追加前置

主 Agent 可以先创建 B、依赖 B 的 C，后来再创建 A，并用 `cbim_dispatch_add_dependency` 给 B 追加 A 的结果前置。输入包含当前图游标、目标版本、source/target 的任务与计划版本、原因；主会话、周期、主运行与命令身份由系统固定。任务创建顺序不等于执行顺序。

两端及它们全部启用依赖后继必须尚未领取，属于同一活动周期和当前目标计划，原知识与 Workflow 仍有效。已经执行、产生候选或检查点的任务不能借此重新排队；自身、重复、循环、旧版本、未确认输入或待重规划目标均拒绝。选择闭包与提交使用同一调度事务；知识在提交前复核，不宣称知识存储与调度存储具有跨存储原子锁。

成功只增加一条固定 A 计划版本的边，将原 B 置为等待并追加 `dependencyAdditions` 审计。B 的节点版本加一，原 task、计划、实例、逻辑会话和指派信封保持；新边不伪造结果 ID。主轮结束后仍按原权限、预算和并发准入领取，A 产生真实候选后 B 才能启动，领取事务将实际结果固定到前置。两端及后继均被重新纳入当前周期跟踪。

主对话显示最新依赖调整，B 的详情保留全部追加/替换记录。追加显示当时的任务、计划、原因与主运行，不把它称为执行完成。重复同命令只返回原回执，变参冲突；回包丢失先查询真实图审计，不以新调用重复加边。停止或重启不会自动启动尚未执行的任务。每任务最多 32 次追加，每次核实的两端及后继并集不超过 500 个；其它依赖修订能力另行推进。

## 主调度替换未启动任务的前置

当 A 已安全求助或明确失败，而 B、C 仍从未领取时，主 Agent 可先派发独立补做任务 A2，再用 `cbim_dispatch_replace_dependency` 将 B 的单条前置从 A 替换为 A2。替换前须重新读取当前图和目标版本，明确旧边、新候选的任务/计划/run/result 身份与原因；不能任意删除依赖，也不能用模型正文冒充候选。

服务复用 canonical 交付证据核验，检查 A 没有未决工具、A2 完整且属于当前知识版本、覆盖原模块，并核对 B 及全部待办后继仍未启动、原角色和模块安排仍有效。版本、知识、候选或领取状态变化则整体拒绝，不能顺便升级旧任务的配置。

成功后一个事务退役旧边、保存固定 A2 候选的新边、追加 B 的不可变审计并同步等待状态。B 的节点版本递增，原计划、目标、模块、角色实例、会话和 assignment 保留；C 同样保持原身份。协调器将 B/C 明确加入当前主轮的待办跟踪，待主轮结束后按全部前置、原权限、软限额和全局准入推进，回执本身不代表已开始执行。

任务图只绘制启用连线，A 的失败或求助节点仍保留。主对话显示最近依赖调整摘要，点击 B 查看全部追加/替换原因、前后来源、候选轮次和记录时间；读取不启动任务。旧审计及退役边不能改写或复活。最终完成仍须主 Agent 审阅真实候选，并明确 A → A2 的替代关系；换边不是业务验收或人工决定。

该路径不恢复 A 的旧 Pi，也不改变已启动任务、跨周期依赖或未知副作用。重启只读取持久事实，不自动重建旧协调批次或启动 B/C。

## 成员检查点与同周期续执行

成员可用 `cbim_task_checkpoint` 提交当前进度版本、已确认文件基线 ID 和原因。工具成功仅代表请求暂存，并封闭本轮后续工具；调度器在引擎正常结束并真正关闭后，核实完整 canonical 日志、调用回执、文件、知识与原生历史，才保存不可变检查点。节点显示 `checkpointed`，释放模型名额和业务占用，保留原任务、角色实例及会话。

主 Agent 读取新图后用 `cbim_dispatch_resume` 明确预约原任务：提交图游标、目标与节点版本、检查点 ID 和原因。预约保存独立 assignment，并不立即启动模型。主轮结束后协调器将原任务及尚未启动的依赖后继重新纳入批次，核对权限、前置候选、知识、模型、文件、原生历史、额度及全局准入；真正领取时原子消费一次预约，创建新 run 和递增租约。原 task、实例及原生会话不变，旧 canonical 日志不改写，新轮保留步骤结构但清空旧证据与候选，完成必须提交本轮新证据。

第一版每个任务只允许一次检查点和一次续执行，且必须处于同一活动周期。全部实际 read/write/edit 文件须由已确认的最新基线覆盖，运行中仅允许这些文件操作和指定的 plan/step/inspect/artifact_capture 维护工具。启动时冻结的图谱知识可使用；额外运行时知识查询、bash、动态搜索/目录集合、插件、失败或未知副作用尚不能证明恢复范围，会拒绝检查点。不能为了满足限制省略业务所需的验证；不符合条件时继续正常执行，或通过求助让主调度安排新任务。

检查点和未消费预约都属于未完工作，不能据此完成目标或进入等待用户。停止/关闭会封存待办，历史仍可查看；重启将旧活动周期记为中断，不自动调用模型或恢复预约。续执行启动核实失败不消费检查点；已领取后失败保留真实新 run，不能把失败伪装成未执行。既有求助、失败、取消、关闭及已释放实例不因新增协议复活。当前没有通用跨重启恢复，也不把检查点当作交付、人工验收或下一轮提权授权。

主对话、任务图与节点详情只显示已持久化事实：保存检查点、等待续执行、新轮已登记、已封存或已为交接放弃。选择旧轮继续显示旧检查点与原因，不借用新轮候选；界面读取不触发恢复。详见[检查点实施约束](../design/task/member-checkpoint.md)。

## 负责人变更后的存量交接

更换模块负责人不会把旧任务移给新人。主 Agent 在原活动周期检查旧待办：从未领取的任务使用原有完整依赖闭包撤销；已正常保存、尚未恢复的检查点使用 `cbim_dispatch_abandon_checkpoint` 明确放弃。已登记恢复预约但未领取也可处置，正在执行或已消费检查点的任务不能走这条路径。

放弃工具要求图、目标、节点及计划版本、检查点、预期预约和明确原因；主运行与命令身份由可信工具闭包确定。服务先查原命令，再核原 canonical、TaskSpec、终态及冻结证明，最后短事务裁决。当前负责人、模型、知识、业务文件或 native 文件已经变化，不要求先恢复旧配置才能终止待办；缺失或损坏的历史 canonical 仍然拒绝。处置不产生新运行，不刷新证明，也不回滚已发生的文件操作。

原任务进入 `cancelled` 并保存 `checkpointAbandonment`；原检查点、预约、运行、负责人、模型和证据均保留。只有原未领取恢复信封被处理，检查点结果信封可独立完成迟到确认。领取与放弃只能有一方先提交；已落盘后停止或回包损坏不撤销事实，后续核实原命令，不重新操作原会话。

主 Agent 继续明确撤销未启动后继闭包，按当前负责人创建新计划及任务图。目标完成必须引用新成员的真实候选，在 `superseded` 中逐项替代旧任务，并满足原验收及人工要求。责任变更、取消和交接回执都不是业务成果。旧依赖边保留，不因放弃而自动解锁后继。

界面展示“已为交接放弃”、原因、主运行、命令、版本、租约和时间；普通停止不会显示此标签。目标卡可点原任务和新成果查看各自详情，不修改任务图连线或旧归属。已关闭、中断周期只读保留，重开不会自动放弃或启动。该有界交接不等于通用异常恢复、跨重启续执行或自动搬迁人员。实施范围见[存量交接计划](../design/task/module-owner-handoff.md)。

## 启动前具备的内容

- 工作区已在 CBIM 打开，知识结构有效；主聊天有可用模型，执行岗位已独立采纳可用模型和能力配置。
- 使用真实叶子 Agent ID，或内置默认执行角色 `cbim:executor`；`cbim:main` 不能成为执行者。目标模块已登记并具备显式维护关系与真人维护人，默认角色不绕过这些检查。
- 在团队架构“项目岗位”登记稳定成员，并在业务模块设置唯一负责人；默认执行角色也须明确登记及绑定，不能用缺省角色或主模型补齐失效配置。
- 每个模块使用自己的 Workflow；没有专属 Workflow 时明确采用通用执行流程，不继承父模块或兄弟模块的流程。
- 主会话使用固定 `rootSessionId`，必须等于所属主对话的 `taskId`（由 `loop.chat` 返回），不是页面页签 ID 或成员任务 ID。独立逻辑主会话不会自动创建聊天页面，也不会混入其他聊天的图。

模块、角色或维护关系缺失时，应先通过授权知识服务补齐。不能伪造注册表、直接修改 `.cbim/` 或把任务派发当作知识治理授权。

## 1. 通过主会话规划与派发

在已完成岗位及责任配置的可信桌面调试环境中发起主任务。正式派发由主 Agent 查询负责人、保存目标计划后调用工具；普通问答不伪造业务节点。下面的查询可能发生在模型尚未派发时，图中暂时没有成员任务是正常状态。

```js
const call = (action, args = {}) => window.cbim.call(action, args);
const workspaceId = '从 list 返回值选择的工作区 ID';
const main = await call('loop.chat', {
  id: workspaceId,
  message: '核实资源加载模块并给出真实验证证据',
  options: {permission: 'read'},
});
const rootSessionId = main.taskId;
const identity = {workspaceId, rootSessionId};
let graph = await call('dispatch.graphSnapshot', {identity});
const root = graph.root;
```

派发回执只证明任务、信封和图增量可靠入队，没有启动模型。集成方若使用 `dispatch.task`，必须提供实际活动 `scopeId`、匹配既有目标分配的完整模块集合和最新 `ownerSelection`，不能靠 `dispatch.open/memberCreate` 绕过计划。`commandId` 在工作区内标识一次操作，未知回包先查询原命令，不用新命令重复派发。旧 `loop.start` 及旧业务续轮明确返回 `OWNER_DISPATCH_REQUIRED`；历史仍可读取。

任务详情显示派发时的岗位、模型和来源；“核实当前负责人配置”调用 `dispatch.ownerInspect` 只读比较当前配置。修改负责人、岗位或模型不会改写旧任务，A→B→A 也不恢复旧绑定。旧无绑定排队任务不能新领取；已有运行按原事实收束。显式交接按上节处理旧待办再创建新任务，不自动转交旧运行。

## 2. 显式启动与观察

通常由自动协调器领取。以下启动接口仅供控制该活动周期的可信集成方使用；已领取、版本变化或责任失效时会拒绝，不能与自动协调器争抢后强制重试。

```js
graph = await call('dispatch.graphSnapshot', {identity});
const taskId = '从本会话图中明确选择的任务 ID';
const node = graph.tasks.find(task => task.taskId === taskId);
if (!node) throw new Error('任务不存在，请重新查询派发图');
const taskIdentity = {...identity, taskId: node.taskId};
const startCommand = {
  ...taskIdentity, commandId: crypto.randomUUID(),
  expectedRevision: node.revision,
  options: {permission: 'read'},
};
const started = await call('dispatch.executionStart', startCommand);
// started 仅表示已可靠保存启动意图；不表示模型已执行完毕。
const execution = await call('dispatch.executionInspect', taskIdentity);
const delta = await call('dispatch.graphDelta', {
  identity, cursor: started.cursor,
});
const monitor = await call('runtime.snapshot');
```

`options` 支持 `permission` 和 `turnTimeoutMs`（1000～3600000 毫秒），未选权限时为 read。成员模型从原岗位绑定取得；若兼容调用还传 `profileId/model`，必须与绑定完全一致，否则 `OWNER_MODEL_MISMATCH`。缺失、过期或禁用配置不会回退全局默认。权限含义：

| 权限 | 当前效果 |
| --- | --- |
| read | 可读业务文件、查询知识、规划和记录证据；拒绝业务/知识写入及命令 |
| ask | 写入及命令等待本轮人工确认；必须有人处理审批接口 |
| execute | 本轮允许执行，但仍经过知识边界、版本、平台检查和回执持久化 |

显式启动使用调用方选择的权限；自动协作冻结派发主轮的用户选定模式。维护关系、其他会话或上轮“本次全部通过”均不授予权限。主会话对业务文件只持有读取占用，其知识写入经过独立串行事务及版本校验；执行成员的 ask/execute 因可能写业务而独占工作区。只读运行可并行，同一动态实例不能双跑。

| 观察值 | 含义 |
| --- | --- |
| run.starting | 领取意图已落盘，尚不代表进程正在执行 |
| task.running / run.running | 实际引擎就绪并提交启动事实后，允许工具执行 |
| task.result_ready | 有与派发目标一致的有效结构化交付候选，尚未验收 |
| task.blocked | 引擎结束但尚无有效候选；有 `help` 时表示已安全交接的求助，否则查看真实限制或基线问题 |
| failed / cancelled / interrupted | 失败、停止或恢复中断；需要核实实际产物 |

执行前冻结完整角色和有效 Skill、多个模块正文及 Workflow、内置规范、前置候选、公开模型参数和本轮权限；密钥只在启动闭包中提供。工作区知识及内置规范在准备、启动和候选提交时复核，变化会阻止旧基线继续交付。

## 3. 审批、问题与停止

成员审批与普通对话分开。在任务图点击正在执行的成员节点，可以看到该成员的待确认操作、选项问题和停止按钮。选择 ask 后需要操作者明确决定；打开详情不会自动批准。以下接口也供集成方使用：

```js
const approvals = await call('dispatch.approvals', taskIdentity);
// 展示选定请求的 name/input，操作者作出本次决定后再调用：
await call('dispatch.approve', {
  ...taskIdentity, approvalId: approvals[0].id,
  allow: true, allowAll: false,
});
const questions = await call('dispatch.questions', taskIdentity);
// 按 questions[0].questions 逐题展示选项与其它补充输入，收集所有回答后：
await call('dispatch.answerQuestion', {
  ...taskIdentity, questionId: questions[0].id,
  answers: [{option: 0, other: ''}], // 示例只有一题；每题必须有一个回答
});
// 主动停止，待引擎和事务收尾后再查询终态：
await call('dispatch.executionStop', taskIdentity);
```

列表可能为空，应由调用方在选定请求存在时操作。`allowAll:true` 仅表示本次成员运行全部通过；运行结束或停止即失效。选项回答不授予工具权限。停止请求不回滚已经产生的副作用，也不立即伪造 cancelled；迟到批准不能重启已停止的工作。

## 4. 读取候选并确认收件

成员必须用 `cbim_task_plan` 原样保存派发目标和验收文本/顺序，使用 `cbim_task_inspect` 的真实回执、`cbim_task_step` 记录步骤，最终经 `cbim_delivery_prepare` 形成有效候选。步骤允许修订；目标、模块范围或验收需要改变时，应报告限制并重新派发。普通最终回复不替代候选。

```js
const view = await call('dispatch.executionInspect', taskIdentity);
if (view.task.status === 'result_ready') {
  console.log(view.task.result); // summary、evidenceRefs、limitations；acceptance=not_evaluated
  const recipient = {...identity, agentSessionId: root.agent.agentSessionId};
  const inbox = await call('dispatch.messages', recipient);
  const message = inbox.find(item => item.kind === 'result' && item.taskId === node.taskId);
  if (message) {
    await call('dispatch.acknowledge', {
      ...recipient, messageId: message.messageId, commandId: crypto.randomUUID(),
    });
  }
}
```

结果信封指向 `task.result`；独立的 `help` 信封指向同图 `task.help`。`dispatch.acknowledge` 本身只把该收件人的 result/help 信封改为 processed，不领取新任务、不恢复旧成员，也不判定业务验收或用户授权。主会话自动协作另由协调器完成回注与续跑，可靠记录来源后再确认；手工 IPC 派发不自动加入该协调器的批次。

前置任务通过派发输入 `prerequisites: [{taskId, expectedPlanRevision}]` 声明。只有同图对应版本的 result_ready 才满足启动条件；启动事务固定 `resultId` 及候选完整内容，接收成员会看到摘要、证据与限制。前置结果仍未验收，不扩大权限。当前自动批次中的任务可在前置满足后推进；批次外的手工任务仍需显式启动。无法满足的前置会如实回报主会话，不无限占用等待槽。

## 显式文件基线与外部变化复核

正式执行成员可调用 `cbim_task_artifact_capture({expectedTaskProgressVersion, sourceToolCallIds})`：先用任务计划工具获得当前进度版本，引用本轮已经成功结束的 read/write/edit 单文件调用。文件位置从真实参数提取，哈希由平台读取实际字节计算，模型不能自报路径、哈希或完整覆盖。工具只保存证据，不改变业务文件；主调度不拥有这项业务采集能力。

一次最多选择 16 个来源、16 个普通业务文件；单文件 8 MiB、合计 32 MiB，每轮最多保存 8 份成功基线。路径越界、知识库、设备、备用数据流、符号链接/目录联接、硬链接及读取中变化被拒绝，不用截断内容生成有效指纹。采集期间拒绝其它工具和在途审批，前后复核知识与进度，停止取消采集；外部并发修改只能尽力检测，不承诺系统级原子快照。

采集事件写入原运行日志 `artifact.baseline_captured`。只有事件、来源授权链、固定成员身份及本次成功工具回执一致，才会在 `cbim_task_inspect` 返回 `artifacts` 引用。采集工具自身不能作为步骤完成证据；它只证明采集时字节，不能追认此前测试使用了这些字节。

在任务节点中选择明确执行轮次，点击“加载基线列表”，选择一份记录，再点击“复核所选文件”。列表不读取业务文件，不默认选择最新记录，也不轮询磁盘。逐文件显示内容一致、已变化、缺失或不可核实；重新复核只读取，不修改历史、不启动模型。该面板与执行回执报告、核实周期的依据分别维护。

```js
const identity = {workspaceId, rootSessionId, taskId, runId};
const list = await call('dispatch.artifactReport', identity); // 仅列可信记录
const observed = await call('dispatch.artifactReport', {
  ...identity, baselineId: '用户明确选择的基线 ID',
});
```

所列文件一致不代表整个工作区未变。任何命令、未覆盖写入、未知结果和采集后的操作仍需单独核实；知识变化不会被字节一致抵消。旧日志不补造基线，旧求助/失败/停止/中断任务也不会因此恢复。这只是后续检查点与验收的证据基础，未实现人工验收或原成员恢复。开发与验证进度见[实施计划](../design/task/artifact-baseline.md)。

## 恢复、监控与数据位置

自动派发的执行通道随任务隔离，不在后续周期复用。兼容的无周期成员通道仅在上轮正常 completed、无未决工具且原生身份一致时可续接；failed/cancelled/interrupted 通道暂拒续接。当前没有异常通道修复或重试按钮，不能删除日志绕开。应用重启先将未完成运行收口为 interrupted，再关闭遗留周期并释放执行实例，不自动调用模型或重放工具。

工作区用户数据中的 `dispatch/dispatch.jsonl` 保存成员、信封、任务、冻结运行及图事务；`dispatch/runs/tasks/<taskId>/<runId>/events.jsonl` 保存运行事件，原生会话位于 `dispatch/runs/pi/sessions/`。完整执行知识和原生路径只用于后端，不进入图和全局监控 DTO。

团队架构的 Agent 节点已接入只读「执行历史」，按静态角色、独立 Session、运行轮次查看公开过程；主 Agent 和默认执行角色也可查询。删除定义后从「历史角色」进入，实例释放不删除履历。索引保存在应用用户目录，原运行日志保持原位；历史页手动刷新，不启动、恢复或审批任务。操作与数据边界见 [Agent 的 Session 执行历史](agent-session-history.md)。

监管从已持久化事件更新。成员轮次通过 memberBinding 归属派发任务，不重复生成 source=loop 任务；token/cost 保留实际报告值，未知费用不算免费。pendingOutbox 只计 pending 信封，claimed/processed 保留审计但退出待消费压力。

## 当前验证与限制

测试覆盖上下文冻结、同版本复核、独立身份、真实 Pi 子进程、可靠领取与结果提交、取消、关闭恢复和用量去重。真实 Pi 测试使用本机确定性模型响应，不使用用户供应商密钥，不等同于真实模型的自主业务判断或团队协作质量。

`tests/application-collaboration-pi.test.ts` 使用真实 Application、派发持久化和 Pi 子进程，配合本机可控模型响应，验证主工具派发、真实文件读取、候选回注，以及 ask 独立审批、写入验证、用户队列顺序、停止和重新打开后不重放。`tests/member-continuation-pi.test.ts` 验证原生历史中回注为 custom 数据、普通用户续聊仍是 user。打包界面另由下述 `test:collaboration` 验证；两类证据都不宣称真实供应商自主协作质量。

尚未实现：成员启动表单、从组织节点主动发起成员聊天、原执行者的可恢复检查点/等待、异常通道人工修复、重启后自动协作恢复及逐请求硬预算。可靠求助、全局 FIFO 并发准入和可选周期软限额已经接通，运行间限额不等于每次请求的硬账单上限。组织节点已能只读查看 Session 历史，不提供上述主动操作。新增分工只由主调度决定，主调度不直接执行业务任务。文件基线仅覆盖明确采集的有界文件，不是完整工作区影响检测；证据有效性不代替验收语义判断。

## 主对话与任务流程图

主对话正文现在直接显示主 Agent 的执行进展：目标计划与分工、成员派发、当前运行与前置候选接收、交付摘要及证据数量、审阅与等待原因。最近六个关键节点默认可见，早期节点和长说明折叠；这是已保存目标与图的当前事实投影，完整历史仍在原工具记录。成员卡同时显示公开执行计划的当前步骤和候选限制；“已报告”“交付待审阅”“完成申请待复核”均不代表目标完成，只有原可靠关闭规则满足才显示完成。历史目标明确标记，重开从相同持久记录还原，不生成新的时间戳或后台工作。

- 主对话保留原有主 Agent 流式正文，在独立署名的成员卡片显示最近三项任务；查看详情可定位对应图节点。其他任务从“查看全部任务”进入图。
- 任务视图默认展示主 Agent 根节点与正式派发的任务节点，实线箭头表示派发，虚线箭头表示前置依赖。主会话的普通执行轮次不会被伪造为成员任务。
- 点击根节点查看主会话实例、通道及调度记录；点击任务节点查看独立执行成员的公开流式正文、工具状态、计划/证据和交付候选，也可查看历史轮次。实例释放不删除这些证据；候选始终标为“尚未验收”。
- 图与成员日志分别按游标增量刷新，空响应保留引用，后台页签降低频率；页面切换和刷新不停止成员执行。图同步失败保留上次可信图，并提供重试。
- 旧 `test:members` / `test:collaboration` 的无绑定样例对应其历史构建，不能作为当前协议的启动示例。当前岗位派发桌面验证使用 `pnpm exec tsx scripts/owner-execution-ui-smoke.mts`，加 `--stale` 验证责任变化；按 `CBIM_TEST_EXE` 或最新构建选择实际程序。真实 Pi 配合 localhost 固定响应，不证明在线自主分工质量，见[本步报告](../design/verification/module-owner-dispatch-20261108.md)。

## 成员执行事件公开接口

主对话卡片和节点详情通过 `dispatch.executionEvents` 读取同一份公开流：

```js
const page = await call('dispatch.executionEvents', {
  workspaceId, rootSessionId, taskId, runId,
  cursor: previousCursor, // 首次省略；后续使用上次响应 cursor
  limit: 200, // 1～500
});
```

首次读取和游标超前返回 reset；delta 只带新事件；noop 没有 events，仍含当前 run 快照。run 状态以派发事务为准，图中的 result_ready 对应运行 completed，二者均不表示验收通过。分页 cursor 只到本页末尾；hasMore 为 true 时继续取下一页。游标不能跨 run 使用，工作区、主会话、task、run 任何一项不匹配都会拒绝读取。

每个 run 首次恢复一次日志，期间收到的实时事件按 seq 合并去重；后续查询读取内存增量，不每秒重读完整日志。序号保留为连续前缀，Session 连接等受限事件转换为公开状态占位。新运行尚未创建第一条日志时可以返回空前缀，随后正常收到增量；历史日志损坏不能被当成空运行。

后端按事件和字段白名单筛选，不返回冻结角色/模块正文、原生 Session 路径等内部字段，也不转发原生私有推理事件。工具卡保留工具名称、调用标识、状态、本轮回执及工作区内非 `.cbim` 的业务路径；原始工具输入输出、写入正文、命令参数和知识工具完整正文不会发送到前端，内部错误替换为通用文案。结果摘要会明确显示“详细正文未公开”，不能当作完整工具输出或额外验收证据。公开对话、目标/验收要求与结构化计划仍保留业务文本，未自动检测其中的密钥或个人信息；前端只排版公开投影。查看详情不会修改执行权限。
