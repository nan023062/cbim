# CBIM 产品说明：面向 AI 原生团队的生产与治理体系

## 核心定位

**CBIM 是面向 AI 原生团队的生产与治理体系。** 它推动团队重新划分职责，让任何职业的人都能借助 AI 直接参与实现，同时保证项目和生产流程长期可持续。

CBIM Assistant 是承载这一体系的桌面产品入口。工作流、知识管理、架构可视化、工具连接与确定性校验共同支撑生产和治理。

**开放实现能力，守住系统底线，是 CBIM 必须同时完成的目标。**

## 团队按能力与责任组织

CBIM 管理的是一个复合、多工种的大型团队。团队由两类责任构成，划分依据是能力与承担的责任，而非传统工种；同一个人可以在不同任务中承担不同责任。

| 责任 | 参与者与工作 | 最终负责的对象 |
|---|---|---|
| 核心治理者 | 少量具备架构与系统思维的程序、策划、美术等，负责核心框架、专业规则、工作流程和治理机制；AI 放大其系统设计与工程管理能力 | 生产体系的健康与可持续性 |
| 创作与执行者 | 来自美术、策划、QA、程序等职业，借助 AI 辅助或全自动执行，将创造力、想象力转化为可验证的实际成果 | 本次成果是否符合目标 |

AI 扩大双方的能力，但最终责任仍须落实到人。程序也参与这两类责任，其定位不再由“谁能写代码”决定。

## 虚拟团队的调度与执行

虚拟 Agent 是角色定义，AgentInstance 是具有独立状态和上下文的运行成员。主 Agent 与自定义 Agent 共用同一大脑和执行内核；其个性、专业方法和默认工作方式由配置、工作原则及 Skill 决定。

主 Agent 的定位是具备工程思维、架构思维和结构化思维的团队与技术管理者。它以事实核实当前工程，以模块边界、责任和依赖组织工作，以明确目标与验收驱动交付；根据执行证据渐进治理知识与架构，避免脱离现状的整体重做。重大方向、职责调整和高影响决定保留给人，治理过程应让人能够理解、审查和接续。

每个主会话默认拥有自己的主 Agent 实例，由它承担调度员和团队业务知识管理者两类职责：理解总体目标、管理 Team 与业务架构知识、分派任务、组织依赖、核实结果，并在获得新事实后追加后续任务。主 Agent 可在授权范围内通过 CBIM 知识服务增删改查 `.cbim/`，无需为知识治理另造业务任务；未配置自定义负责岗位时，业务文件、命令和构建验证由主 Agent 按本轮权限直接完成；已配置自定义岗位才交给对应执行 Agent。内置默认执行 Agent 已退役。

其他成员都是执行 Agent。它们独立分析目标、按需查询 Team 环境和专业知识、在分配的模块范围内探索、实现和验证。需要帮助或发现额外工作时返回主 Agent，由主 Agent 决定是否新建任务；执行 Agent 不递归派工、不自行扩展总体计划。独立推理和上下文不等于展示私有思维，界面只展示公开回复、工作状态、工具过程与交付证据。

主 Agent 的核心是建立在业务图谱和团队图谱之上的[目标调度循环](main-agent-orchestration-loop.md)：借助 LLM 持续分析需求、匹配模块与能力、派发任务、等待结果、审阅证据；目标未满足时进入下一轮拆解、补证或返工，完成条件满足后才成功结束。具体实现和运行验证由执行 Agent 的内层循环承担。主模型一次回复结束、没有继续派工或成员返回候选，都不能独立证明总体目标完成。这是外层循环的目标约束，当前尚缺程序化完成门禁与持久评估状态。

团队架构和业务架构是工作区唯一的静态定义；任务图按主会话独立存在，根指向该主实例，任务节点记录“执行实例 + 目标模块 + 任务目标”。所有派发边从根出发，任务之间可有真实依赖；结果返回不画反向边。具体约定见 [任务派发图契约](agent-dispatch-contract.md)。

一轮用户任务开启一个调度周期，可以经历多次主模型回合、成员执行和结果回传。每个正式 Task 都创建新的执行实例；整轮完成、失败或停止后释放执行实例，保留主会话、主实例、任务图和证据。静态人才配置可复用，动态执行实例不跨任务共享。

每个静态 Agent 拥有自己的 Session 历史入口，包括主 Agent 和自定义角色。已退役的默认执行 Agent 只保留历史查询。主角色可关联多个彼此独立的主会话，执行角色可关联不同任务的独立执行通道；履历按当前工作区中的角色归集，不合并模型上下文。团队节点可以查看该角色的会话、任务目标、公开执行过程与结果。释放运行实例或删除角色定义后，历史仍保留在本机应用运行数据中；人才市场只复用静态配置，不携带私有会话。历史查看是只读行为，不唤醒成员，也不展示私有思维或原生工具正文。

## 对未来团队工作方式的假设

### 1. 职业边界变宽，任务围绕目标组织

策划可以实现玩法代码，美术可以实现表现逻辑，QA 可以直接修复问题。一个人能承担的工作，由业务理解、判断能力以及可调用的 AI 能力共同决定，不再严格受限于原有工种。

### 2. 懂业务的人直接完成实现闭环

创作者从表达目标出发，借助 AI 完成方案、实现、验证和迭代，减少跨工种排队和意图传递损耗。人的责任随之扩大：不仅提出想法，还要判断实际结果是否符合目标。

### 3. AI 承担执行，人集中于创造与判断

实现方式可以从 AI 辅助逐步走向自动执行。人提供目标、创意、审美、专业判断与必要决策；AI 承担具体实现、工具操作、验证和知识整理。自动化程度取决于任务是否明确、约束是否充分、结果是否可验证。

### 4. 少量核心治理者支撑更大规模的创作

核心团队将专业经验沉淀为框架、契约、规则、工具和验证机制，使其进入每一次日常执行。核心团队重点处理系统性问题、规则覆盖不到的例外，以及高影响的演进决定。

关键假设是：治理能力能够通过 AI 和机制扩大覆盖范围，无须随每项执行工作同比增加人工审核。这是需要通过真实任务验证的假设。

### 5. 自由创作与持续治理同时发生

执行者在明确边界内自主探索；系统持续识别质量问题、重复实现、职责冲突与依赖恶化，并将需要判断的问题交给核心治理者。治理成果再进入后续任务：

**创作与实现 → 验证与反馈 → 发现系统问题 → 核心治理 → 更新框架与规则 → 支撑下一轮创作。**

### 6. 专业要求分化，责任始终明确

广泛参与者获得更宽的实现能力；核心治理者承担更高的系统设计与长期维护要求。每个任务应明确成果负责人，框架与规则的演进也应有明确的治理负责人。

## 产品结构如何承载这一定位

| 产品部分 | 承载的工作 |
|---|---|
| 工作区 | 组织具体项目的生产与治理；自动化作为工作区内部子功能，不建立跨工作区自动化 |
| 对话与任务流程 | 表达目标，明确约束和责任，组织方案、实现、验证与反馈；自动执行能力按任务条件逐步建设 |
| 团队组织架构图 | 预览团队能力架构，呈现成员与可调用能力，支持按责任和能力组织任务 |
| 团队知识图 | 预览项目业务架构，为理解模块、契约与依赖以及后续治理提供依据 |
| 链接器 | 提供可定制的外部工具连接桥梁 |
| 人才市场 | 提供跨业务项目复用的完整团队、专项 Agent 与单个 Skill 静态定义 |
| 业务模板 | 整套复用业务架构及其模块与 Workflow；不能单独应用其中的模块或流程 |

资源仓库由登录状态决定：未登录用户使用手动指定的本地目录；登录后自动连接账号所属的服务器仓库，三个资源入口统一切换，不再手动填写服务器地址或令牌。CBIM 当前没有自有中心服务器，账号登录尚未接入；首版交付本地模式，服务器仓库显示占位。资源存储与连接不等于资源已经具备自动执行能力。

## 成功标准与交付边界

**更多人能够自主创造，更多成果能够持续交付，而项目复杂度和治理成本仍然可控。** 评估时应同时关注自主完成任务的能力、成果验证与持续交付情况，以及返工、依赖恶化、维护负担和人工治理成本。

本文描述产品定位与演进目标，不是已实现功能清单。当前已有工作区、内部知识治理、规则校验、资源仓库、主 Agent 调度对话与独立成员执行；本进程的主轮派发可在释放占用后自动执行，并把候选送回同一主会话，任务图显示对应节点与公开过程。主会话与图根统一身份，正式执行使用独立周期实例；周期关闭保留历史并释放执行对象。完整业务验收状态机、执行者求助/答复协议、自动异常重试恢复，以及持续发现系统性问题的完整治理闭环仍未完成；不能把候选返回或图谱展示当作业务已验收。

实际交付与验证范围以 [验证结果与限制](acceptance.md) 为准；实现结构见 [桌面实现架构](assistant-architecture.md)，界面与交互见 [工作区界面](workspace-ui.md)。
