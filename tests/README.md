# 按模块维护测试

`modules.json` 是测试归属与执行选择器，不是开发待办。每个已维护测试文件只登记一次：责任模块、源码入口和测试类型。模块按业务变化原因划分，不要求一个类一个模块，也不要求把所有历史文件搬目录。新增模块单元优先放在 `tests/unit/<模块>/`。

| 类型 | 验证责任 | 夹具边界 |
| --- | --- | --- |
| `unit` | 一个模块的规则、状态和失败语义 | 直接构造模块；依赖使用窄端口或受控适配；不加载 Application，不依赖其它测试执行 |
| `contract` | 明确的模块间协议、生产者/消费者约束及架构规则 | 保留必要真实协作，说明两端和断言目标；不能把不相关单元塞入此类以绕过检查 |
| `integration` | 应用装配、真实进程/平台、端到端生命周期 | 拥有独立目录、进程与清理；保留恢复、未知结果和真实协作证据 |

纯断言使用 `support/assertions.ts`，临时目录使用 `support/temp-directory.ts`，领域数据构造器放在对应辅助模块。`helpers.ts` 专门提供 Application 夹具，不再混放纯断言。辅助文件不能 import `.test` 文件；测试之间不能传递状态、执行顺序、端口或目录。每个测试清理自己的资源并恢复 mock，禁止依赖前一个测试的产物。

## 日常执行

```sh
pnpm test:module --list
pnpm test:module --module foundations/files
pnpm test:module --module backend/main/settings
pnpm test:module --module backend/main/web --kind contract --list
pnpm check:test-modules
```

默认仅执行所选模块的 `unit`。需要消费者验证时根据 diff 显式选择 `--kind contract`、`--kind integration`、`--kind all`，或用 `pnpm exec vitest run <明确文件> [-t <用例>]` 选取更小范围。不存在的模块、空选择和错误参数退出失败，不退回全仓执行。模块选择不是影响分析器：公共契约变化仍须查消费者，不只运行基础库自身测试。

## 自动检查与 review

`scripts/test-modules.mjs` 和 PR 验证共同执行以下规则：

- 所有 Git 已跟踪测试及显式登记的新测试有唯一归属；缺文件、漏登记、重复归属和未知类型均失败。未提交、未登记的个人草稿暂不接管；新增测试一旦加入 Git 就必须登记。
- 单元沿测试辅助文件查真实运行时导入，限制在所属模块及明示的基础数据/契约支持范围。目录根只包含该目录直接文件；需要子模块须明确列出根，不能用 `src/` 隐藏全仓依赖。
- 所有导入（含类型）都参与完整应用可达性判断；单元不能间接到达 `Application` 或完整应用夹具。所有测试类型都禁止导入其它测试套件。
- 基础库只能经公开入口使用，其业务反向依赖和循环由现有依赖检查负责。测试目录归属不改变源码分层。

静态检查不能证明断言只有一个业务责任，也不能发现所有动态共享状态或 mock 与真实端口不一致。Review 仍须检查变更原因、夹具生命周期、断言归属和失败语义。既有真实跨模块/应用测试按事实登记并保留；不能把它们一律宣称为已解耦单元，也不能删除断言换取通过。当前归属是可审阅基线，随实际修改继续精化，不是已对全部历史测试逐条完成语义审阅的保证。

本次实际拆分覆盖：网页基础读取/服务/工具、网页设置/IPC、核心读模型/注册表/分层规则、会话内容/布局、消息队列/界面状态、候选审阅工具/展示。原有场景和断言保留。完整四片回归仍由面向 master 的 PR 验证执行；日常模块通过不等于全量、桌面安装或发布通过。
