# 上下文最小化：CBIM V2 架构设计原则

## 一、免责声明

在进入正文之前，先把话说清楚。

CBIM V2 目前仍然是 spec（设计规范），尚没有运行时数据反过来验证它。V1 已经实装跑过一轮 A/B 基准方法论验证，部分基础结论可以用过去式陈述；但 V2 在 V1 之上做了若干结构性改动，这些改动本身没有被实际负载检验过。

更具体地说，以下几件事至今没有得到验证：Dream 自维护机制的长期效果（包括它是否真的能压住知识熵增）、跨项目能力复用的实际成本（脑区抽离出来到底有多少能直接搬走）、多 agent 协同的稳定性（团队层叠加之后的失败模式还没踩过）。

所以本文不是一份“经过验证的最佳实践指南”。本文记录的是设计原则的演化，不是已被证实的最佳实践。

## 二、引子：一次提示词重写的代价

驱使 V2 重新整理设计原则的，不是某次系统崩溃，而是一次再普通不过的迁移。

V1 时代，我们写了一个面向 Web 项目的“前端 agent”。这个 agent 的提示词里写着它的角色、技能、工作流程、协作方式、输出格式——一切都打包在一份文档里。当项目从 Web 转向 Mobile 时，预期是替换技术栈相关的章节就够了。实际发生的是：整段角色提示词需要重写。因为“我是谁”和“我处理什么业务”在文档里早已焊死，技术栈一变，连“我擅长什么加工方式”这种本该稳定的部分都被业务术语污染了，无法独立拎出来。

跨项目时情况更糟。两个项目都需要“代码评审能力”，但因为这套能力在 A 项目里是写进“A 项目评审 agent”的，在 B 项目里又是写进“B 项目评审 agent”的，两份提示词彼此抄袭、各自漂移，最后谁也不知道哪份才是当前应该参照的版本。

这件事的本质不是“提示词太长”，而是不该装在一起的东西被装在了一起。能力（怎么思考、怎么加工）和业务（要处理哪个领域的什么对象）这两件本可独立演化的事情，被强行揉成了一份文本。结果是任何一侧的变化都要付出双倍的代价。

不是上下文太长，是上下文里掺了不该掺的东西。

## 三、核心命题：上下文最小化是唯一总目标

CBIM V2 的全部设计取舍，最后都回到同一个总目标：**上下文最小化**。

但“最小化”在这里有一个容易被误解的含义。它不是“把提示词写短”，也不是“少装一点东西就够了”。它指的是：每一次推理所装进上下文的内容，都应该按维度严格筛选，只装与当前这次推理直接相关的那一种东西，其他维度的东西不要混进来。

上下文最小化不是少装，是按维度装。

按维度装意味着先要承认这个世界有维度。一个工作单元里至少有两个相互正交的维度：能力维度（这次推理用的是什么思维加工方式）和业务维度（这次推理处理的是项目里哪个具体领域的对象）。如果这两个维度被压扁到同一份文档里，那么任意一边的变化都会污染另一边，“最小化”就无从谈起——因为根本没法只换其中一边。

所以总目标只有一个，但它的实现必须靠两条独立的拆解线把两个维度分开建模，再靠两个支撑机制把这套结构稳定地维持下去。下文的第四到第八章，正是按这个顺序展开。

## 四、为什么是脑：两层独立的拆解

在进入两条拆解线之前，必须先把一个根本性的立场说清楚，否则后面任何一个细节都会被读偏。

CBIM 把单个 agent 类比为“一个会思考的个体（一个人）”。一个人有完整的大脑，大脑由若干功能不同的脑区组成。这件事跟这个人此刻是独自在家工作，还是在一家公司的团队里工作，没有关系——无论独自一人还是身处团队，他的大脑结构都是完整的、不会因为加入团队就把脑区拆出去分给同事，也不会因为独自工作就把脑区合并成一团。

agent 同理。**脑是 agent 的固有结构**，是对这个 agent 思维能力的拆解与建模，它本来就该有，不是任何东西的退化、坍缩、被迫或单机妥协形态。

在这个立场之上，CBIM 区分两层**完全独立、互不干扰、各自演化**的结构：

- **思维层**——讨论的是一个 agent 内部的事。把一个人的思维能力按加工模式拆成多个脑区（下文会展开为前额叶、顶叶、海马体、运动皮层）。这一层始终存在，不随部署形态变化：单机也好，跨网络也好，每一个 agent 永远是一个结构完整的“多脑组织”。
- **团队层**——讨论的是多个 agent 之间的事。一台机器上跑一个 agent，多台机器上跑多个 agent，它们之间靠协议协作，构成一个团队。这一层只有在跨机器的时候才需要展开，是叠加在 agent 之上的第二层结构，不是把单个 agent 的脑区摊开变成 team。

业务维度按同样的分层方式与之对应：本地侧对应一个**领域工作区**——也就是当前 agent 正在处理的某一个领域，比如代码工作区、美术工作区、策划工程工作区；跨网络侧对应一个**项目**——由若干个领域工作区合起来才构成的完整项目。

把两层结构列在一张表里：

| 层级 | 基本单元 | 拆解方式 | 业务侧对应 |
|------|----------|----------|------------|
| 思维层（始终存在） | 一个 agent（一个人） | 思维能力 → 多脑区 | 本地一个领域工作区 |
| 团队层（跨机器才展开） | 一台机器 = 一个 agent | 多 agent 协作 | 跨网络一个项目（多领域工作区） |

为什么用“脑”来建模而不是用别的隐喻？因为 agent 的本质类比就是“一个会思考的个体”，而对个体思维能力最自然、最稳定的拆解方式，就是按脑区——也就是按加工模式——来拆。脑区的边界是思维能力的边界，这个边界不依赖部署形态：单机和跨网络用的是同一套思维拆解，团队层只是在它之上再加一层组织结构而已。两层各自独立演化，互不干扰。

这个立场也给出了 CBIM 前向兼容性的正确表述：同一套思维拆解在单机和跨网络两种部署下都适用——单机时只有思维层这一层在工作，跨网络时在思维层之上再叠加一层团队层，思维层结构不变。所以本地版本身就是完整自足的一层，不是简化版、不是阉割形态、也不会在未来某天“展开”成别的东西。

把这件事跟上下文最小化对齐：思维层按脑区拆，意味着单 agent 每次推理只调用与当前任务相关的那个脑区，上下文最小；业务层按工作区拆，意味着每次任务只进入相关的领域工作区，上下文最小。两层各自最小化，并不是因为单机部署被迫做出妥协，而是“按思维维度建模 + 按业务维度建模”这件事本身，就是让任意规模的系统都保持上下文最小的正道。

## 五、拆解线一·能力维度→脑区

把脑作为 agent 的固有结构之后，第一刀要砍的是：**把能力从业务里彻底剥离**。

这一刀对应一个具体的硬动作：删除 ModuleDescription 上的 Owners 字段。在 V1 里，这个字段记录的是“哪个能力对象拥有这个业务模块”——它正是能力与业务焊死的物证。V2 主张能力对象不再记业务归属，业务模块是谁的、由谁处理，应该由调度时根据当下任务和脑区职责动态决定，而不是写死在能力描述里。

剥离之后，能力侧按**加工方式**拆成四个脑区：

- **前额叶**——sealed（封闭、不接受外部直接调用），是整个 agent 内部唯一的调度入口。所有外部任务先到前额叶，由它判断该调用谁。
- **顶叶**——负责确定性的工程转换和架构推理。它处理那些有标准解、可以被严格论证的问题。
- **海马体**——负责记忆的存取与蒸馏。短期记忆的写入、长期记忆的查询、记忆向知识的提炼都从这里走。
- **运动皮层**——负责一切对外动作，包括文件读写、命令执行、API 调用。

外部 AI 服务（比如调用别家的大模型 API）在这套结构里只能作为 ExternalMotorCortex（外部运动皮层）接入——它是肌肉，不是大脑，只负责执行被指派的动作，不参与决策。这个定位明确了系统的责任边界：决策权永远在本地的前额叶手里。

为什么按加工方式而非任务领域来切？因为任务会漂。

反例：如果按“前端 agent / 后端 agent”这种任务领域的切法去分，那么技术栈一旦变化——React 换成 Flutter，REST 换成 GraphQL——这套划分就彻底报废，需要重新拉一套。但是“做确定性的工程转换”这件事，在 React 时代和 Flutter 时代是同一件事；“做记忆存取”在 Web 时代和 Mobile 时代也是同一件事。加工方式是稳定的，任务领域是漂移的。

按任务分跟业务漂，按加工模式分才能跨项目活下来。

这一刀的最小化收益是：每次推理只装相关脑区的那一片提示词，不再把“我会做的所有事”全塞进去。一个查记忆的请求，进的是海马体，不会顺带把前端框架知识也带进上下文。

脑区这一刀切下去，顺手解开了一个现在做 agent 绕不过去的死结：工具挂太多就废。一个 agent 接上十几个 MCP（一种给 agent 接外部工具/服务的标准接口）之后，光是工具说明本身就把上下文吃掉一大块，调用时还频繁选错——选错的那一刻你就知道，它其实没看清自己手上到底有什么。skill 同理，挂得越全，单 agent 越笨重越易错。能力越全反而越蠢，于是现实里只能少连；少连又不够用。这是死结。

脑区天然就是工具的分装单位。编程脑区只连编程类的 MCP 和编程相关的 skill，海马体只连记忆相关的工具，依此类推。任意一次推理挂载的不是全集，只是当前那一片该有的那一摊。某个脑区将来用得多了、自己也会膨胀，那就交给后面 Dream 一章会讲的自裂变，把过载的脑区裂成更专的子脑区，工具负载重新摊回合理体量。“工具不能连太多”这条天花板，被“按脑区分装 + 过载就裂”两步拆掉了。主脑（前额叶）的位置因此也清楚了：它挂的是项目层面的工具，比如 Jira、飞书这类项目管理 MCP；更要紧的是，跨机器协作时，一个 agent 的主脑直接对接另一个 agent 的主脑——前面说的“agent 之间靠主脑协作”，落点就在这里，主脑就是团队层的对接口。一个 agent 连不了一百个工具，但一百个脑区各连一摊就行。

## 六、拆解线二·业务维度→模块树

能力侧切完，业务侧也要切。

业务侧的组织载体是 **workspace 模块树**。每个模块都是一个目录，目录下有一个 `.dna/` 子目录——`.dna/` 是 CBIM 约定的模块知识目录，存放“这个模块是什么、依赖什么、对外提供什么”这三类核心信息，是模块的“身份档案”。

模块树可以无限分叉、递归往下拆，直到拆成一个个体量合理的小工作区。这棵树要受两条硬约束：**单向依赖**（不允许循环依赖）和**单一职责**（每个模块只负责一件事）。这两条等价地说就是：这棵树必须是真正的树（无环），并且每个节点只回答一个问题（不混业务）。

但模块树的价值不止于把业务“拆小”。每一层模块还要做第二件事：**用类图来建模这一层的结构**。类图，就是描述一组对象及其关系的结构图——这一层里有哪些关键对象、它们彼此是什么关系。配上单向依赖，模块树就成了一个可以逐层缩放的理解结构：

- 宏观层（项目/根模块全景）：看顶层有哪些子系统、彼此怎么依赖。
- 中层（子系统模块）：看这个子系统内部由哪些模块组成、各自的职责与依赖。
- 微观层（叶子模块）：看这个模块里的具体类与它们的关系，类图在叶子模块落到代码级。

这里要立一个赌注，也是本章的核心假设：**只要每一层的信息量都被控制在“LLM 一次能看明白、并能判断这一层合不合理”的范围内，且层与层之间靠单向依赖严格衔接（无环、不回头），那么逐层组合起来，全局结构就是合理的。** 不奢求 LLM 一次看懂整个项目——那超出任何上下文窗口；而是让它每次只看懂一层、判断一层。类图是每一层“局部合理”的载体，单向依赖是层与层之间衔接的保证。局部合理，就推得出全局合理。

**这套结构不是为 LLM 量身定做的工程花招，它本来就是大型组织的运转方式。** 任何一个庞大组织都分很多层，每一层的负责人只盯自己的直接下属是否合理；下属的下属，交给下属自己去管。原因很朴素：人的关注圈有限，管理学里管这个叫“管理幅度”。两边一一对得上——管理幅度对应上下文窗口，只管直接下属对应一层只看直接子模块，汇报线只向上一级不跨级对应单向依赖无环，管理者眼里“我这摊由哪些部门组成”对应这一层的类图。约束是同一个：个体注意力有限。结构也就只能是同一个：分层、有界管辖、单向汇报的一棵树。LLM 不过是又一种注意力有限的工人，那就用管人的老办法去管它。

反过来说，真正的草台班子就是一言堂——一个顶层试图直接拍板所有层级的所有决定，不分层、不放权。它并不掌握每个叶子的局部上下文，却越级替它做决定，这是教科书式的外行管理内行。结果必然两头落空：有决策权的人没有决策所需的上下文，有上下文的人没有决策权，系统就这么散了。分层模块树做的恰好相反——把每一层的决策权交还给真正持有那一层知识（类图加上下文）的那一层，内行管内行。这也是为什么大公司必须分层、CEO 不能直接拧到每颗螺丝钉：不是不想管，是管不过来、也不懂细节，硬管就成了外行指挥内行。LLM 处理大型项目的现状是另一种散——每次工作的关注范围是飘的、不固定的，没有稳定的大局观，于是两头吃亏：缺全局视野，也缺系统性覆盖，有些地方被反复看，有些地方从没被认真设计。分层模块树把“层级”固定下来，每一层都有自己的知识载体（这一层的 `.dna/` 描述加类图），关注不再随机，而是被结构路由——从全局到微观每一层都被显式关注到、设计到，不漏层，不偏食。最关键的一点：大局观不再依赖 LLM 自己记住（它记不住），而是被外化进树的结构里。LLM 不需要自己拥有大局观，树替它持有大局观，它只要每次站对一层、用那一层的知识工作。这和图工程把控制流从提示词外化进行为树，是同一个手法：**凡是 LLM 装不下的，就别让它硬记——搬进结构里：控制流外化成行为树，大局观外化成模块树。**

这其实和上下文最小化是同一件事，只是换到了“理解/审查”这一面：每一层的类图加上单向依赖，恰好把“理解这一层所需的上下文”压到 LLM 视角之内。它也是架构脑（顶叶）能工作的前提——架构脑每次只处理模块树的一个节点、这个节点的类图、以及它直接依赖的对外契约，不需要把全局展开摊在桌上。

能力维度的拆解和业务维度的拆解放在一起，会产生一个乘积效应：每次推理用的是一个专业脑区，进入的是一个专业工作区，二者都最小，乘起来就是上下文最小化在结构上能拿到的最好结果。

反例一：monolithic 不拆。如果业务侧不切，整个项目就是一坨，无论检索系统多强大、嵌入做得多精细，每次任务都是在全项目这个大池子里游泳。RAG 召回越准只能说明它在大池里捞得快，掩盖不了上下文池本身过大的事实。业务侧也得拆，否则脑区再小，进的工作区一片汪洋照样溢出。

反例二：层内塌方。如果某一层的类图臃肿到 LLM 一次看不全，或者出现循环依赖让这一层根本无法独立理解，“局部合理”这一层就断了——它断在哪一层，全局合理的假设就从哪一层崩塌。这正是单一职责和单向依赖要守住的底线：不是为了好看，是为了让“每一层都能被一次看懂”这件事在工程上成立。

一句话收住这一刀：**不要求 LLM 一眼看懂整个项目，只要求它每次看懂一层——层层合理，全局自洽。**

工作区不只圈业务知识，还圈业务工具和流程，从业务这一侧也解同一个死结。每个工作区除了 `.dna/` 里的知识，还带两样东西：这一类业务的标准做法，也就是这个工作区专属的 workflow；以及这个工作区专属的 MCP 工具。agent 进入一个工作区时按业务动态加载这套专属工具和 skill，离开就卸掉，不是一直全挂着——进入“程序工程”工作区就接上 Unity 的 MCP 和这个工作区的 workflow 然后开工，切到别的领域工作区就换成那一摊。和能力侧合起来看，结论很干净：任意时刻一个 agent 真正挂载的工具，是当前脑区的工具和当前工作区的工具的交集，永远是最小可用集，不是全集。“工具不能太多”这个死结，能力维度和业务维度从两头一起把它解开了——你根本不需要把所有工具同时挂在一个 agent 上。工具不是一次性全挂上，是走到哪一层、进哪个工作区，才接上那一层该用的那几件。

这一刀的最小化收益落在另一句话：每次任务只装当前节点本身，加上它直接依赖的对外契约，仅此而已。不装兄弟节点、不装祖父节点的内部实现、不装跨子树的细节。

## 七、支撑机制一·图工程

两条拆解线讲完了，下面是两个支撑机制，第一个是图工程。

两条拆解之后还残留着一个隐形污染源：**协作流程藏在提示词里**。

一段“先调用 A，A 失败就转 B，B 成功后把结果交给 C”的工作流程，过去通常以自然语言写在系统提示词或者 agent 角色描述里。这种写法有三个问题：第一，模型每次都要重新解析这段流程文本，把本来是确定性的控制流当成不确定的语言问题反复推理；第二，要改动流程就得改提示词，提示词的版本化、diff、审计都不如代码方便；第三，跨 agent 的流程靠提示词硬编码出来，agent 之间的耦合很重，改一处带动多处。

解法是：**把控制流从提示词里赎出来，落进显式的行为树**。

行为树是用代码描述“先做什么，再做什么，失败怎么办”的可执行树形结构，每个节点是一个明确的动作或控制逻辑（顺序、选择、并行、重试）。它是一种把流程从语言态搬进结构态的方式。

CBIM 主张的图工程分两个阶段：

- **编译期**——主脑（前额叶 + 顶叶协作）根据当下任务规划出一棵行为树，输出成一份不可变的中间表示，称为 NeuralCircuit IR（神经回路中间表示）。这一步对应“想清楚怎么做”，产物是一份可序列化、可审计、可版本化的数据结构。
- **运行期**——一个确定性的引擎按照这棵树执行，LLM 只在节点内部做局部的智能判断，不负责整体流程的编排。智能和确定性各司其职：流程编排是确定性问题，交给引擎；某个具体节点要不要重试、要不要回退、判断结果对不对，这是智能问题，交给 LLM。

Prompt 工程的下一阶段是图工程——把控制流从提示词里赎出来。

这一机制的最小化收益是：流程描述根本就不再进入任何一次推理的上下文，每个叶子节点只看自己这一步需要的最小上下文。前面所有节点的细节、后面所有节点的预案，对当前节点来说都是噪音，都不必装进来。

## 八、支撑机制二·Dream：睡觉、复盘、成长

第二个支撑机制处理的是另一类被请求-响应式系统普遍忽视的问题：**系统不会自我维护**。

只在被调用时才动作的系统，长期来看会出现三类劣化：

- **记忆膨胀**——短期记忆持续写入但从不蒸馏成结构化的长期知识，最后变成一锅烂粥，召回质量持续下降。
- **知识漂移**——模块树为了应付一次次具体需求被打补丁，长着长着长歪了，脑区职责也悄悄扩散，没人去重新校准。
- **能力陈旧**——同一类失败反复发生，但系统没有任何识别机制去发现“这件事我已经失败了第七次”。

但只把 Dream 说成“维护”，是看低了它。Dream 模拟的是人类思维进入沉思、学习、复盘的那段过程。人睡觉不是停机，是在沉思和复盘里把白天的经历沉淀成长期的自己——第二天醒来的那个人，比昨天多了一点东西。Dream 就是 agent 的这个过程。它不只是把劣化的部分修回去，它是让这个 agent 真的成长。维护是被动的下限，成长才是 Dream 真正的位置。

系统也需要睡觉——不是为了停下来，是为了第二天更聪明。

CBIM 设想的解法是 **Dream 回路**——Dream 是 CBIM 给系统闲时后台自维护时段起的名字，每 20 小时的时间窗触发一次（避免与正常任务争抢算力，也避免维护过于频繁）。每次 Dream，沉思、学习、复盘的全过程会产出四样东西：

- **沉淀记忆**——把白天零散的短期经历固化成可检索的长期记忆，归到海马体里。
- **提升技能**——复盘做过的活，把反复用到的那几手打磨成更利落的 skill，挂回对应的脑区上。
- **沉淀知识**——把散落的理解收敛进模块的 `.dna/`，留在该留的工作区里。
- **总结工作流**——把重复出现的任务路径总结成可复用的 workflow，落回对应工作区的专属流程里。

这四样东西不是凑数的并列，它正好是整套系统赖以运转的四类资产：记忆、技能、知识、工作流。前面说“脑区挂的 skill 从哪来”、“工作区的专属 workflow 怎么越用越好”，答案就在这里——都是 Dream 一次次沉淀出来的。

Dream 内部最关键也最克制的高阶动作叫**自裂变**。判断标准只有一句话：容器装不下就分家。

具体来说：当某个脑区在某一类任务上反复失败，且失败模式可以归因到“它管的事太多了”，就裂出一个子脑区专门处理这类事；当某个业务模块下沉淀出新的主题聚簇，并且这个聚簇已经稳定、可以独立成一节，就裂出一个子模块。

裂变是结构性变更，必须严格设护栏，否则系统会越裂越乱：

- **一轮最多 2 个裂变提议**——克制是基本原则，宁可下次再裂，不允许一次性把系统抖动得无法回头。
- **三块脑区永不可裂变**——前额叶（主脑）、架构脑（顶叶里负责架构推理的部分）、海马体。前两者是整个系统的脊椎，最后一者是裂变机制自身的基础设施（裂变本身依赖记忆来识别“我反复失败”）。这三块一旦被裂开，系统就丢失了定位“该谁处理这件事”的能力。

系统不会自己保持简单——必须有专门时段做维护。

Dream 对应的最小化收益是：长期判断（这个脑区是不是过载了、这个模块是不是该分家了、这条记忆是不是该提升为知识了）在 Dream 时段里被固化成结果，下次推理直接读取结果即可，不必在每一次正常上下文里重新推算。结构性的判断不进日常推理，这是另一种形式的上下文最小化。

## 九、Agent 的工作流：定位即工作

前面拆的、立的，最终都要兑现成一件事：一个 agent 拿到需求之后，到底怎么干活。

这条工作流不是另外设计出来的，是前面那套结构（分层模块树、单向依赖、每层的类图、外化的大局观）自然导出来的。一个 agent 接到需求，做四步：

1. 分析拆解需求——把需求切成可定位的子问题。
2. 匹配知识图谱——拿子问题去模块树和 `.dna/` 知识里检索匹配。
3. 定位模块——落到具体的那个（或那几个）模块，往往是叶子。
4. 局部工作——只在定位到的模块范围内理解与修改。

四步看起来平淡，关键在第四步给出的承诺：每次工作不必全局扫描，也不必全局修正。原因要讲清楚。改动只要落在叶子模块内部、且不动它的对外契约，单向依赖就保证上层的类图不受影响——上层根本不需要被重新审视，因为它对这个叶子的认知只到契约这一层，契约没变，它的局部合理性就没变。只有当改动要动到某一层的对外契约、要改这一层的类图时，关注才上移一层；而且也只上移到直接相关的那一层，不是全局。换句话说，“改一处就得通读全项目”那种恐惧，在这套结构下被消掉了——不是靠 LLM 记性变好，是靠定位精准加局部封闭：工作范围被结构本身锁死在一小块里。这一章里的“上下文最小化”就落在这件事上——工作范围被定位收窄到一个模块，看的、想的、改的，都只在这一小块里发生。

再往回看一眼：这条工作流其实就是前额叶/主脑在编译期做的事——它规划行为树，把任务路由到正确的叶子模块，靠的就是这棵模块树。于是前面两条拆解线（脑区／模块树）和两个支撑机制（图工程／Dream），在“agent 怎么干一次活”这件事上汇成一条线。设计合不合理，最终就看这一条：干活的时候，能不能只盯一小块，就把事办对。能，就是合理的；不能，前面所有结构都是空话。

**定位即工作——找对了那一层，活儿就已经做了一半。**

## 十、收尾

把全文压成一句话：

一个总目标——**上下文最小化**；两条拆解线——**能力切脑区、业务切模块树**；两个支撑机制——**图工程外化控制流、Dream 做长期治理**。

CBIM 的两层结构是这一切的底层立场：思维层始终是一个结构完整的多脑 agent，无论部署在哪都是这个样子；团队层只在跨机器时才叠加展开，把多个 agent 组织成一个跨网络的项目。本地版从来不是简化版——它就是完整自足的一层，团队层是另一层。这两层结构合起来还有一个隐藏好处——每一层都小到 LLM 能一次看懂、一次判断，层层合理，全局就自洽，不必指望谁能一眼看穿整个项目。

正交性、单向依赖、单一职责，这些都不是目的，它们是手段——是让上下文最小化在结构层面能够被稳定持有的手段。把它们当成目的去追求，就会陷入“为了优雅而优雅”的形式主义陷阱；把它们当成手段去用，才能在每一次具体的取舍里回到那个唯一的总目标。

任何系统都会熵增、都会变乱，CBIM 也不会例外。区别只在于有没有一个专门机制让它有机会变回简单——Dream 就是这个机制。

一个总目标，两条拆解线，两个支撑机制——其余都是细节。
